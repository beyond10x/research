## Question

What does native dynamic concurrency (the main agent decides during the run whether, when and how to
spawn sub-agents) do to task success, resource use and failure modes of three frontier coding agents on
long-horizon coding tasks, compared with the same agent with concurrency disabled (§1, §3.1)?

## Findings

### F1 · practice · sub-agent-delegation · E4
- practice: enable each agent's native dynamic concurrency (Codex multi_agent_v2, Claude Code Dynamic Workflow through `ultracode`, Kimi Code AgentSwarm) against the same agent and model with sub-agents disabled; same model, prompt, environment and time budget, highest reasoning effort (§3.2, §3.4).
- claim: concurrency "does not consistently improve end-to-end task success rates"; gains on long-horizon benchmarks, "especially LoopsBench", none on bounded SWE-bench Verified (§1, §4.1).
- evidence: Table 2, task pass in percent, concurrent against sequential. SWE-Verified (n = 100): Codex 71.0 against 71.0, Claude Code 59.0 against 83.0, Kimi 59.0 against 77.0. LoopsBench (n = 28): Codex 25.0 against 21.4, Claude Code 21.4 against 7.1, Kimi 25.0 against 25.0. NL2Repo (n = 26): Codex 57.7 against 34.6, Claude Code 65.4 against 57.7, Kimi 46.2 against 57.7. RepoZero (n = 150): Codex 40.7 against 40.0, Claude Code 26.7 against 42.7, Kimi 38.7 against 37.3. ProgramBench: 0.0 for all agents in both modes. Exact McNemar tests with Holm correction, both task groups pooled: Claude Code decline p = 5.08348 × 10^-7, Kimi decline p = 0.0132176, Codex improvement p = 0.229481 (§4.1). The text gives resolution effects from an 11.9 point decrease to a 2.3 point increase (§1).
- effect: mixed
- reader: the on and off contrast on equal tasks with model, prompt and budget held fixed, so E4, though each task ran once per cell and no randomisation of runs is described. Cells are small: on LoopsBench 14.3 points is 4 of 28 tasks (reader's arithmetic), so single tasks move a cell. The off mode removes the Workflow, Task and Agent tools for Claude Code (§3.4), so the contrast is the whole delegation tool set, not one parameter. Independent: the authors evaluate vendors' products, not their own; one author co-wrote LoopsBench (reference 30).

### F2 · practice · sub-agent-delegation · E4
- practice: as F1; the measurement is tokens, shell calls and tokens per solved task.
- claim: concurrency "incurs substantially higher computational cost"; "these additional resources do not translate proportionally into successful outcomes" (§4.2).
- evidence: token use 1.41 to 3.31 times the sequential level across agents (§4.2, abstract). Table 2, tokens in millions, concurrent against sequential: LoopsBench Codex 51.65 against 11.45, Kimi 41.49 against 11.29, Claude Code 21.73 against 15.52; ProgramBench Codex 27.05 against 9.19; SWE-Verified Codex 3.37 against 1.34. Shell calls on LoopsBench: Codex 505.6 against 144.6, Claude Code 791.6 against 107.4, Kimi 618.0 against 120.8. Tokens per solved task, Codex: 24.12 million against 7.69 million; per solved task the figure rises for all three agents (§4.2). 11.2 billion recorded tokens in all, $20,780.02 at standard API rates (§1).
- effect: hurts
- reader: same E4 contrast as F1. Tokens are provider-recorded; the text gives the range per agent and the 1.41 to 3.31 cannot be reproduced from Table 2 cell by cell (see Discrepancies). Cost here is tokens, not dollars per agent.

### F3 · practice · sub-agent-delegation · E4
- practice: as F1; the measurement is wall-clock time.
- claim: "despite parallel execution, dynamic concurrency does not generally reduce end-to-end runtime" (§4.2).
- evidence: mean runtime is higher under concurrency for all three agents overall and in 14 of the 15 agent-benchmark cells of Table 2. Claude Code on SWE-Verified 27.8 minutes against 17.5. Claude Code on LoopsBench 91.5 against 74.8. Of 366 tasks solved in both modes, concurrency is faster in 102 (27.9%) and at least 20% faster in 46 (12.6%) (§4.2).
- effect: hurts
- reader: the average is worse and a minority of paired solved tasks is faster, so "hurts" is the direction of the mean. The paper's time budgets bind in some benchmarks (a 40-minute run in the seqtk example, §2), so time and success are not independent. The speedup subset is selected on both modes solving the task.

### F4 · observation · concurrency-gain-by-task-horizon · E3
- practice: none applied; the concurrent against sequential difference in test pass rate is read across the benchmarks ordered by mean reference implementation size (§4.1, Figure 3).
- claim: "larger expected implementation sizes are associated with a greater average test pass advantage from dynamic concurrency" (§4.1, Finding 1).
- evidence: averaged equally over the three agents, the test pass difference is -8.29 points on RepoZero, -0.04 on NL2Repo, +1.24 on ProgramBench and +4.31 on LoopsBench (§4.1). Mean reference size on LoopsBench is 26.8K lines (§3.3). Claude Code task pass: -24.0 points on SWE-bench Verified, +14.3 on LoopsBench (§4.1).
- effect: helps
- reader: four benchmark points, not a fitted trend, no test; benchmarks differ in task type, language and time budget, and the sizes and the benchmarks are confounded. The effect is a direction for the largest tasks only: on the three smaller benchmarks the difference is negative or near zero. The sample is 28 tasks on LoopsBench.

### F5 · observation · concurrent-writes-to-shared-files · E2
- practice: none applied; in 1,062 concurrent trajectories two annotators each labelled concurrency failures from a codebook (Cohen's kappa = 0.77). Shared state and merge problems are the largest category (§6.1, §6.2).
- claim: concurrent agents "modify shared files, artifacts, or environments without proper coordination, resembling data races" (§6.2, D).
- evidence: Table 3. Category D 267 of 804 pattern instances (33.2%). Concurrent Writes 213 (26.5% of instances; 62.9% of those for Codex): Deliverable Overwrite 120 (14.9%), Same-File Collision 42 (5.2%), Source Overwrite 14 (1.7%). Shared Environment Contamination 54 (6.7%), for example two sub-agents recreating /tmp/t1 and one replacing the shared system Git executable (§6.2). The 804 instances occur in 650 trajectories.
- effect: hurts
- reader: a count of labelled episodes in the concurrent runs only; the sequential runs were read for comparison but have no counts. A pattern is not tied to a lost task: several cited cases still pass all official tests (the Codex Clipper case). Labels are manual annotation by three annotators, each case by two, with a reported kappa.

### F6 · observation · fan-out-exhausts-time-budget · E2
- practice: none applied; failure patterns where the main agent launches more or longer sub-agent work than the run's time or token budget allows (§6.2, A3 and B1).
- claim: load imbalance occurs "when the main agent launches too many sub-agents or assigns too much work to individual sub-agents"; sub-agents are terminated at the deadline before results return (§6.2).
- evidence: Table 3. Load Imbalance 166 instances (20.6%), of which Fan-out Budget Exhaustion 154 (19.2%); 39.8% of the instances for Claude Code. Wrong Start, Join or Result Timing 166 (20.6%), of which Early Sub-Agent Termination 128 (15.9%). Case: Kimi Code seqtk, 20 sub-agents launched in one batch at 17.5 minutes of a 40-minute run with an assumed 2-hour sub-agent timeout; 18 aborted at the deadline, the program passes 92 of 440 tests (§2, §6.2).
- effect: hurts
- reader: counts over instances in concurrent runs without a matching count in sequential runs, so the share of runs lost to this is not given. The 40-minute budget is stated for the seqtk run only; the finding applies to time-boxed runs.

### F7 · observation · no-failure-takeover-by-main-agent · E2
- practice: none applied; failure patterns where the main agent does not recover or monitor sub-agent work after delegation (§6.2, B2 and B3).
- claim: a failed sub-agent's work is left unrecovered, or the main agent "keeps waiting even when the task is already complete" (§6.2).
- evidence: Table 3. No Failure Takeover 42 (5.2%); No Active Main Agent Monitoring 25 (3.1%), of which Unused Completed Result 13 (1.6%) and Blind Timeout Wait 12 (1.5%). Cases: a rate-limited verification sub-agent not restarted, artifact passes 147 of 148 tests; a 10-minute blocking wait near the deadline for an unfinished sub-agent while the finished artifact (39 of 39 tests) is never finalised (§6.2).
- effect: hurts
- reader: small shares and two cases; the paper gives no count of how many of these runs lost a task.

### F8 · observation · incomplete-sub-agent-brief · E2
- practice: none applied; failure patterns of context handed to sub-agents: incomplete task requirements, no shared interface contract, an overloaded brief, a global completion declared without check, and a retry that repeats earlier work (§6.2, category C).
- claim: agents in separate contexts "do not receive or preserve the context needed to connect their work" (§6.2, C).
- evidence: Table 3. Category C 75 of 804 instances (9.3%): Incomplete Sub-Agent Brief 23 (2.9%), Unverified Global Completion 18 (2.2%), Checkpoint-Free Retry 25 (3.1%), Missing Cross-Agent Contract 5 (0.6%), Bulk Handoff Overload 3 (0.4%), Lossy Handoff 1 (0.1%). Cases: python-fsutil sub-agents with separate file assignments and no shared API contract give nine failures at the first integrated test run; an 80K-character brief built from up to 60 findings per probe, after which the receiving sub-agent repeats its investigation; a stalled design assignment relaunched four times with the same brief, leaving only Cargo.toml (§6.2).
- effect: hurts
- reader: the smallest category; the one for which prior work (written contracts) gives a remedy. No count of lost tasks.

### F9 · observation · serial-critical-path-under-parallel-sub-agents · E2
- practice: none applied; failure patterns where sub-agents run in parallel but the work that decides completion stays sequential, or required work has no owner (§6.2, A1 and A2).
- claim: "the concurrency does not accelerate the critical implementation work" (§6.2, A2).
- evidence: Table 3. Pseudo-Concurrency 47 (5.8%), of which Serial Investigation 40 (5.0%) and Preflight-Gated Work 7 (0.9%); Missing Owner 16 (2.0%), of which No Implementation Owner 14 (1.7%). Cases: Kimi Code ProgramBench tailspin, 17 investigators and none assigned to implementation, 0 of 785 tests; Kimi Code NL2Repo verifiers, no owner for the core module, none of the official tests pass (§6.2). First sub-agent starts at a median 4.0% of the trace for Codex, 22.1% for Claude Code, 26.0% for Kimi Code; 24.3% of Codex executions create sub-agents that never overlap, against 1.7% for Claude Code and 2.8% for Kimi Code (§5.2).
- effect: hurts
- reader: the timing numbers describe delegation behaviour and are not tied to outcomes in the text. Small shares.

### F10 · observation · complementary-parallel-work · E1
- practice: none applied; in a selected set of 131 concurrent and sequential pairs the concurrent run did better, sub-agents completed separable parts while the main agent worked on the core and then integrated them (§7).
- claim: concurrency helps "when sub-agents work on different and complementary parts of the entire task in parallel while the main agent successfully integrates their results" (§7).
- evidence: Kimi Code NL2Repo justext: 8 sub-agents on delivery files and checks, the main agent on the core algorithm; both modes pass all tests, wall time 467.997 seconds against 734.116 (§7). One case.
- effect: helps
- reader: the 131 pairs were chosen because the concurrent run did better (higher test pass, a solve, or at least 60 seconds and 20% faster), so no rate follows. One case shown in the text; others are in the released artifact.

### F11 · observation · parallel-alternative-solutions · E1
- practice: none applied; two agents build competing solutions to one problem and the main agent selects or combines them (§7).
- claim: concurrency "can also be helpful when multiple agents develop different solutions to the same problem in parallel" (§7).
- evidence: Codex ProgramBench Halite: main agent and one sub-agent each build the game environment; the combined result passes 292 of 391 tests, sequential mode fails to build and passes 0 of 391. NL2Repo unidecode: sub-agents implement versions 1.3.8 and 1.4.0 of the tables and the main agent adopts 1.4.0 (§7). Two cases.
- effect: helps
- reader: same selection as F10. Not compared with a single agent given the same extra compute (for example two sequential attempts).

### F12 · observation · independent-validation-sub-agent · E1
- practice: none applied; a sub-agent checks an assumption or the implementation of the main agent and returns corrective evidence early (§7).
- claim: concurrency "is beneficial when sub-agents independently validate assumptions or implementations" (§7).
- evidence: Codex LoopsBench security labs: a crypto sub-agent identifies the P-256 curve-order requirement, the concurrent artifact passes all checks and the sequential one fails. NL2Repo trimming: a nested sub-agent's upstream probe gives the CSV header naming rules, the concurrent artifact passes all tests and the sequential one does not (§7). Two cases.
- effect: helps
- reader: same selection as F10. The slug is separate from `task-specific-validation-subagents`: here the validator is spawned by the main agent during the run, not built for a stage.

## Limits stated by the authors

- Findings are scoped to the three tested agents and five benchmarks (§8.2).
- Agent runs are stochastic and the cost of long-horizon runs limits repeated runs; the authors argue the trends hold because Codex's sequential LoopsBench pass rates are close to the originally reported ones and the original study reports stable trends over repeated attempts (§8.2).
- Manual annotation may be subjective; mitigated by a 50-trajectory pilot codebook, double annotation, discussion and adjudication by a senior author (§8.2).
- Sampled 25% of each long-horizon benchmark and 20% of SWE-bench Verified because a full LoopsBench run costs $11,354 (§3.3).

## Reader's notes

- One run per agent, task and mode (2,124 cells = 354 × 3 × 2, §3.3). Differences of one or two tasks on 26 and 28 task benchmarks are within what a rerun could change; the paper's argument against run noise is a comparison with a previously reported Codex number on one benchmark.
- The "off" mode is not the same ablation across agents: Codex disables multi_agent options, Claude Code disables Workflow, Task and Agent tools, Kimi sets swarm_mode=false (§3.4). Each agent uses a different mechanism with a different join policy (batch wait, workflow script, message passing, Figure 1), so F1 to F3 are per agent, not about concurrency in general.
- Claude Code falls 24.0 points on SWE-bench Verified; the paper does not say whether that is delegation overhead on small tasks or Workflow's script generation and review stages.
- The failure taxonomy counts only concurrent runs. Finding 5 says the patterns go "beyond those in sequential agent execution", but no sequential counts are given. 650 of 1,062 concurrent trajectories carry at least one pattern (61.2%, reader's arithmetic); the link of each pattern to a lost task is shown by cases, not counted.
- The delegation-scale results of §5.1 (sub-agents created rise from 6.69 on easy tasks to 15.84 on hard ones) and the delegation timing of §5.2 describe behaviour with no outcome direction and are not findings here. Only F9 uses the timing numbers.
- Sampling within a benchmark is stratified by the benchmark's own difficulty groups; the sampled tasks are not checked for contamination in the parts read.
- Codex (GPT-5.4), Claude Code (Opus 5) and Kimi Code (K3) are different models; a difference between agents mixes model and scaffold (§3.2 gives the reason for fixing the pairs).

## Discrepancies

- Token ratio: the abstract and §4.2 give 1.41 to 3.31 times the sequential level "across agents"; Table 2 cells range from 0.97 (Claude Code on ProgramBench, 6.02 against 6.18 million, reader's arithmetic) to 4.51 (Codex on LoopsBench). §4.2 says token consumption "similarly increases" after saying shell calls increase for every agent and benchmark; tokens do not in one cell.
- Finding 5 says the patterns are "distinct" from those in sequential execution; the counts are for concurrent runs only (§6.2).
