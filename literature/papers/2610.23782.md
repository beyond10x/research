## Question

Do coding agents already reason about program behaviour in issue resolution, does it go with
resolution (§2), and does a scaffold that forces that reasoning at each stage resolve more
issues (§3, §5)?

## Findings

### F1 · observation · code-reasoning-in-agent-trajectories · E3
- practice: in 7,955 trajectories, an LLM (Claude Fable 5) labelled each step whose reasoning mentions a code element for 12 forms of code reasoning (variable state, call dependency, loop, conditional, return). Trajectories were then split into with and without code reasoning (§2.1, §2.2).
- claim: "Agents involving code reasoning in their trajectories achieve higher resolution rates" (abstract); the association is significant (§2.2.2).
- evidence: code reasoning appears in 66.95% of trajectories on average over 14 configurations (§2.2.1). Resolution is 69.84% with it and 50.81% without (§2.2.2). Chi-square per scaffold, Table 1: mini-SWE-Agent 183.0 (p = 1e-41), iCAT-Agent 5.31 (p = 0.021), OpenHands 4.27 (p = 0.039), Claude Code 3.91 (p = 0.048). Sonar Foundation Agent and ExpeRepair are left out for too few trajectories without code reasoning. Share with code reasoning by difficulty, averaged over 14 configurations: 63.9% easy, 67.6% medium, 70.5% difficult (§2.2.3). Label audit on 120 trajectories: 59 of 60 labelled "with" and 53 of 60 labelled "without" confirmed by three humans (§2.1.1).
- effect: helps
- reader: E3, a split of existing trajectories with no intervention. The trajectories are not on the same tasks across scaffolds, and harder tasks both get more reasoning and fail more (§2.2.3), which works against the claimed direction; an agent that has to reason its way through a long trajectory may also differ in other ways from one that does not. Trajectory length also bounds how many steps can be labelled, and the paper does not say it controls for length. The labeller is an LLM; the 7 of 60 "without" labels not confirmed means the "without" group contains some reasoning (§2.1.1).

### F2 · practice · enforced-code-reasoning-stages · E4
- practice: DeskCheck, a five-stage scaffold of sub-agents (Explore, Localize, Repair & Refine, Audit, Validation) that makes the model simulate execution in its own text at four of the stages, instead of running tests. Built by prompt changes on mini-SWE-Agent and, for Claude Code, on a "localize, repair, validate" scaffold that the authors built because no official SWE-bench-Pro harness exists (§3.1, §3.2). Same instances as the baselines, high reasoning effort, network off, git history stripped.
- claim: DeskCheck "improves the resolution rate" over mini-SWE-Agent and Claude Code "agnostic to the studied backbone models" (§1, §3.3.1).
- evidence: Table 2 on 731 SWE-bench-Pro instances. MiniMax-M3: 65.25% against 54.72% (+10.53 points). GPT-5.6-Luna: 59.37% against 53.08% (+6.29). Claude Haiku-4.5 with Claude Code: 51.16% against 42.82% (+8.34). Unique fixes: 97 and 49 against mini-SWE-Agent, 74 against Claude Code (Figure 11, §3.3.1). Exact McNemar test p = 2.6e-13, 1.0e-11 and 1.6e-11 (§3.3.4). Gain over mini-SWE-Agent by difficulty: +9.4, +8.7, +8.0 points for easy, medium, difficult; over Claude Code +11.4, +8.0, +7.8 (§3.3.2). Gains by language are in Figure 13 only. Rerunning the baselines twice on the 97, 49 and 74 instances that only DeskCheck resolved, they resolve 16, 7 and 14 of them in at least one retry; the paper reads this as "83.18% of these gains likely stem from DeskCheck itself" (§3.3.4).
- effect: helps
- reader: an A/B on the same 731 instances, so E4, with one run per instance for the main table. The treatment is a bundle: new prompts, five sub-agents, a call-graph tool, extra test execution and the reasoning steps, so the table does not say which part helps (F4 to F9 separate them for MiniMax-M3 only). The authors wrote DeskCheck and also wrote the Claude Code baseline scaffold (independent: false). The rerun covers only instances DeskCheck won and the baselines lost, and does not rerun DeskCheck, so it cannot separate DeskCheck's luck from the baselines' misses (regression to the mean). The "+10.53%" labels are percentage points (reader's arithmetic: 10.53 / 54.72 = 19.2% relative).

### F3 · practice · enforced-code-reasoning-stages · E4
- practice: as F2; the measurement is tokens and dollars per instance.
- claim: DeskCheck "incurs only $0.02-$0.28 (average = $0.14) additional cost per instance" and "increasing token usage by 7.6% on average" (abstract, §1).
- evidence: Table 2, tokens and cost per instance, DeskCheck against baseline. MiniMax-M3: 5.61M and $0.52 against 5.27M and $0.41. GPT-5.6-Luna: 1.42M and $0.10 against 1.65M and $0.08. Claude Haiku-4.5: 6.75M and $1.59 against 5.89M and $1.31. "At most 14.6% more with Claude Haiku-4.5" (§3.3.1). 5.61 + 1.42 + 6.75 = 13.78 against 5.27 + 1.65 + 5.89 = 12.81 is +7.6% (reader's arithmetic).
- effect: hurts
- reader: cost goes up in all three settings, by 27%, 25% and 21% (reader's arithmetic from Table 2), which the paper calls "negligible" or "marginal" against the absolute dollar amounts. The 7.6% is a ratio of summed tokens and is dominated by the two expensive settings. For GPT-5.6-Luna DeskCheck uses fewer tokens and still costs more; the table does not say why (it may be the input and output mix). Cost is a list-price figure and the paper does not say how it was computed in the parts read. The Claude Code baseline is the authors' own scaffold.

### F4 · practice · execution-path-simulation-localization · E4
- practice: the Localize sub-agent builds the repository call graph, predicts anchor locations from the issue, picks the paths that cover the anchors plus the top-1 most visited path plus an LLM-predicted bug path, then simulates each path on a predicted input and flags edit sites, with no reproduction test written or run (§3.1.2).
- claim: "simulating execution paths" finds the root cause where the baselines stop at surface symptoms (abstract, §3.1.2); "simulating execution paths ... identifies more bug-relevant locations" (§5).
- evidence: ablation with MiniMax-M3 on 100 instances, Table 6: turning code reasoning on in localization only (V0 to V1) moves resolution from 53% to 56% and method-level recall from 0.59 to 0.65. This is the only ablation row where recall moves by more than 0.01 (Table 6).
- effect: helps
- reader: a real ablation (E4) but one model, one run, 100 instances, so 3 points is 3 instances and no test is given. V0 still keeps the call-graph tool and the other stage prompts, so only the explicit simulation step is removed.

### F5 · practice · reasoning-instead-of-reproduction-tests · E3
- practice: locate the bug by reasoning about execution paths and run no reproduction test before patching, against agents and a diagnosis system that write and run reproduction tests first (§3.4.1).
- claim: DeskCheck's reasoning-only localization "consistently achieves the highest method-level recall", and avoids the cost and the environment setup of running tests (§3.4.1).
- evidence: Table 3, 107 Python SWE-bench-Pro instances (the only ones SWE-Doctor supports), the three models. Method-level recall averaged over the models as stated in §1: DeskCheck 0.66, mini-SWE-Agent 0.46 (final patch only), Claude Code 0.38, SWE-Doctor 0.23. DeskCheck has the highest resolution with every model; the first block of Table 3 (model labels garbled in the extracted text) shows 73.83% for DeskCheck against 57.94% for mini-SWE-Agent and 60.75% for SWE-Doctor. DeskCheck has lower file-level precision than some baselines (§3.4.1). Reproduction tests run before patching per instance (Figure 15 text): mini-SWE-Agent 1.84 and 2.27 for MiniMax-M3 and GPT-5.6-Luna, Claude Code 8.51, SWE-Doctor 12.6 and 43.4.
- effect: helps
- reader: E3, systems compared on the same instances without a control that changes only the localization method. Ground truth is "the methods modified in the golden patch", which the paper itself says may include edits beyond the issue and misses other valid fixes (footnote 10). SWE-Doctor-P recalls far more than SWE-Doctor-L and resolves more than mini-SWE-Agent, and the authors read that as its patch generator benefitting from runtime symptoms rather than its localization (§3.4.1); so recall of the localization step alone does not predict resolution across systems. 107 Python instances only.

### F6 · practice · patch-simulation-refinement · E4
- practice: after the first patch, the model predicts input and expected-output pairs from the issue, simulates the patch on each in text, and on a mismatch rewrites the patch from the stated discrepancy (§3.1.3).
- claim: the simulation "rescues" near-hit patches (abstract, §3.4.2).
- evidence: ablation, Table 6 (MiniMax-M3, 100 instances): adding code reasoning in repair (V1 to V2) moves resolution from 56% to 58% and recall from 0.65 to 0.66. Full benchmark, §3.4.2: refinement fires on 72, 264 and 80 instances, of which 58 (80.6%), 130 (49.2%) and 35 (43.8%) are resolved. Among the 331, 343 and 418 instances that the baselines fail, refinement fires on 30, 161 and 65 and rescues 17, 30 and 21 (57%, 19%, 32%) against 27%, 10% and 15% without refinement. Chi-square, Table 4: 11.92 (p = 0.001), 4.68 (p = 0.030), 11.27 (p = 0.001).
- effect: helps
- reader: the ablation step is +2 points on 100 instances, within noise. The rescue rates are an association over self-selected groups: refinement only fires when the simulation finds a violation, so it selects patches that were near-hits, and untouched patches include those with no defect and those hopeless. It is a mechanism trace (E3 grade for that part), not a control.

### F7 · practice · requirements-audit-of-patch · E4
- practice: in a clean context, extract the requirements from the issue text, predict an input and expected output for each, simulate the patch on it, and send violations to a lightweight repair that may also refute the violation (§3.1.4).
- claim: auditing against the requirements "completes the patch" when the agent overlooked a requirement of a long issue (§1, §4.3).
- evidence: ablation, Table 6: audit on (V2 to V3) moves resolution from 58% to 61% and recall from 0.66 to 0.67. Full benchmark, §3.4.3: violations flagged on 294, 287 and 223 instances; lightweight repair changes 240, 161 and 141 patches, of which 160, 91 and 76 are resolved; of 262 violations dismissed as false alarms, 126 are still resolved. Among baseline failures, changed patches are rescued more often than untouched ones: 37% against 25%, 24% against 11%, 30% against 14%. Chi-square, Table 4: 4.84 (p = 0.028), 9.89 (p = 0.002), 11.90 (p = 0.001). One case: a patch meeting 6 of 8 requirements goes from 0/1 to 1/1 fail-to-pass tests (§4.3).
- effect: helps
- reader: same limits as F6: +3 points on 100 instances for the ablation, and a correlation for the rescue rates. The false-alarm line shows the audit raises a violation that is wrong in 262 cases; the audit pays for those with extra repair work, and the paper does not count it separately.

### F8 · practice · io-pair-reasoning-before-tests · E4
- practice: before writing validation tests, the model reasons about corner-case inputs and their expected outputs, then turns the pairs into executable tests that run together with the repository's regression tests, and loops on failures (§3.1.5).
- claim: tests "built from reasoned input-expected output pairs ... cover more diverse scenarios and edge cases" (§3.4.4); validation is "particularly effective" (§5).
- evidence: ablation, Table 6: validation on (V3 to full) moves resolution from 61% to 68%, "the largest gain". Full benchmark, §3.4.4: patches revised after generated tests fail on 109, 235 and 93 instances, of which 78, 117 and 51 are resolved. Among baseline failures, edited patches are rescued more often than unedited ones: 47% against 26%, 19% against 11%, 31% against 16%. Chi-square, Table 4: 10.10 (p = 0.002), 3.85 (p = 0.047), 7.73 (p = 0.005). One case: DeskCheck covers a case-insensitive and a multi-word input that the baseline's tests missed (§4.4, Table 5).
- effect: helps
- reader: the largest step in the ablation, 7 points on 100 instances, one model, one run. This step also adds executed tests, so it mixes the reasoning step with the generation and running of tests; the ablation keeps test generation and execution on in all variants (§5), which isolates the reasoning step. This is the finding closest to a practice a team could copy: ask for input and expected-output pairs before writing tests.

### F9 · practice · stage-isolated-sub-agents · E3
- practice: run each stage as its own sub-agent with its own context "to manage its context ... alleviating possible context pollution" (§3.1); the Audit stage opens a clean context (§3.1.4).
- claim: DeskCheck's gain is "from code reasoning across multiple phases rather than from isolating contexts into sub-agents" (§5).
- evidence: Table 6: V0, the staged scaffold with code reasoning switched off everywhere, resolves 53% with recall 0.59; mini-SWE-Agent resolves 53% with recall 0.57. Same MiniMax-M3, same 100 instances.
- effect: none
- reader: E3 because V0 is not mini-SWE-Agent with sub-agents added alone: it also keeps requirement extraction, test generation and refinement operations, so the comparison does not isolate context separation. One model, 100 instances, one run.

### F10 · observation · benchmark-tests-reject-correct-patches · E2
- practice: three human evaluators checked, against the issue text, the patches that both DeskCheck and mini-SWE-Agent (MiniMax-M3) failed on SWE-bench-Pro (§3.3.5).
- claim: "resolution rates on SWE-bench-Pro underestimate actual capability, calling for caution when comparing approaches by small margins" (§3.3.5).
- evidence: of 234 instances that both fail, the evaluators judged 94 DeskCheck patches and 96 mini-SWE-Agent patches correct (Krippendorff's alpha = 0.70), 190 false negatives in all, of which 32 Python, 125 Go, 31 JavaScript and 2 TypeScript. Causes: hidden tests contradict the issue, cover conditions it never states, call function or symbol names that appear only in the golden patch, or rely on fixtures present only at grading. One Go case: the issue names one new function, the hidden test calls five private helpers by their golden-patch names, and the patch fails to compile so 0 of 33 tests run (Figure 14).
- effect: hurts
- reader: a count with nothing to compare against, so E2; the paper does not say whether the three evaluators knew which system wrote each patch. The effect is on the validity of the resolution metric the paper uses for every finding above, and hurts it for both systems about equally (94 and 96), so the gap between them is less affected than the absolute rates. Only MiniMax-M3 was checked.

## Limits stated by the authors

- Scaffolds and models may not transfer to other scaffolds or more recent LLMs; the SWE-bench family only (§7, external validity).
- LLM non-determinism: addressed by McNemar and by rerunning the baselines twice on the instances only DeskCheck resolved (§7, internal validity).
- SWE-bench-Pro's hidden tests may reject correct patches; the authors checked the failures of DeskCheck and mini-SWE-Agent by hand (§7, construct validity).
- The localization ground truth is the golden patch's methods, which may include edits beyond the issue and miss other valid fixes (footnote 10, §3.4.1).
- Future work: extend beyond bug fixing, and check that the simulated execution in the model's text is correct ("certify the faithfulness of code reasoning") (§8).

## Reader's notes

- The authors evaluate their own system against baselines they configured; the Claude Code baseline is a scaffold the authors built (§3.2).- The trajectory study (F1) and the DeskCheck evaluation (F2 to F9) are two different studies. The first says reasoning goes with resolution; the second changes the scaffold. The second does not show that the simulated execution is correct, only that the pipeline resolves more. The paper says it plans to check faithfulness (§8).
- The trajectory labels come from an LLM. The audit (alpha 0.87 against the human majority) supports the labels on 120 trajectories, with 7 of 60 "without" labels not confirmed (§2.1.1).
- Rising code-reasoning share with difficulty (63.9%, 67.6%, 70.5%, §2.2.3) is described in the paper as agents reasoning more when problems are harder, but no outcome is attached to it; not graded as a finding.
- The ablation in Table 6 uses MiniMax-M3, 100 instances and one run; each step is 2 to 7 points. The paper gives no test for the ablation.
- Resolution here is the benchmark's hidden tests passing; F10 shows the tests reject correct patches in a fraction of cases, mostly in Go.
- Model names (GPT-5.6-Luna, MiniMax-M3, Claude Fable 5) are as written in the paper and could not be checked by the reader.
- The paper header reads "Anonymous et al." and the ACM metadata is the template default; the venue is not stated.

## Discrepancies

- The abstract, §1, §3.3.1 and §8 write the gains as "6.29% to 10.53%" and "up to a 10.53% performance gain"; Table 2 shows percentage points of resolution rate (reader's arithmetic: relative gains are 19.2%, 11.8% and 19.5%).
- §3.3.5 says the 234 instances that both fail were checked and "94 ... and 96 ... of them" were judged correct, then gives "190 false negatives"; 190 counts patches (94 + 96), not instances.
