## Question

Can a coding agent, while implementing a scoped task, avoid a defect that a later real pull request
had to fix and that the task text never mentions, and do prompts or review commands close the gap
(§1, §4)?

## Findings

### F1 · observation · unstated-defect-foresight · E2
- practice: the agent gets the repository at PR1 and a generated task description, with no information about PR2; the patch is scored on PR1's tests (resolve rate) and on held-out PR2 fail-to-pass tests (foresight resolve rate, FRR: all PR1 tests and all PR2 tests pass) (§4.1).
- claim: agents "resolve the stated task far more often than they anticipate the later defect" (§4.2).
- evidence: across 11 models average resolve rate 60.68% and average FRR 14.84%; average anticipation score 26.39% (Table 1). FRR ranges from 6.13% (Qwen3.5-27B) to 24.53% (Claude Opus 5); highest resolve rate is 91.98% (Qwen3.8 Flash Next) with FRR 20.75% (Table 1). Mean time between PR1 and PR2 is 158 days, median 88 (§3.2). One instance, a generator consumed twice after reordering, was failed by all eleven models (§4.2).
- effect: hurts
- reader: numbers that describe agent output on one benchmark with nothing varied, so E2. One run per model is implied and not stated; no variance is reported. Closed models ran on their own harnesses with their own budgets and open models on mini-swe-agent (Table C.1, C.2), so differences between models mix model and harness. The resolve rate and FRR are different tests of the same patch, not a control.

### F2 · practice · explicit-defect-specification · E3
- practice: give the agent PR2's task description, which states the defect, starting from PR2's base commit, and score it on the PR2 tests; compare with the foresight setting where only PR1's task is given (§4.3).
- claim: "the primary bottleneck is identifying the latent defect rather than implementing its repair once identified" (§4.3).
- evidence: 5 models. Defect specified: average resolve rate 91.23% (Qwen3.8 Flash 97.64, DeepSeekV4 Flash 85.85, GPT-5.6 Sol 94.81, Claude Sonnet 5 86.32, Claude Opus 5 91.51). Defect unspecified: average FRR 19.91% and anticipation score 27.59% (Table 2, §4.3).
- effect: helps
- reader: the two settings differ in start commit, task text and metric (resolve on PR2 tests against FRR over PR1 and PR2 tests), so the 91.23 against 19.91 is not a like-for-like gap; FRR also needs PR1 to pass. The models were the top two open-weight by FRR plus three frontier models, chosen after the main run (§4.3). Table 2 names a model "Qwen3.8 Flash" where Table 1 has "Qwen3.8 Flash Next" with the same figures.

### F3 · practice · proactive-edge-case-prompt · E4
- practice: append a prompt to the task that asks the agent to forecast edge cases its implementation may miss or introduce, to work them out from the codebase before, during and before submitting, to stay inside the requested behaviour and to verify with its own scratch script (§4.4, Appendix C.1).
- claim: "both interventions can recover part of the foresight gap, but often at the cost of task completion" (§4.4).
- evidence: Table 3, resolve rate / FRR, baseline to proactive. GPT-5.6 Sol 84.43 / 18.40 to 82.55 / 31.60. Claude Opus 5 77.83 / 24.53 to 75.47 / 32.55. Claude Sonnet 5 59.91 / 16.98 to 44.81 / 13.68. Text gives FRR +13.20 and +8.02 and resolve rate −1.88 and −2.36 for Sol and Opus (§4.4). The Sonnet change, FRR −3.30 and resolve rate −15.10, is the reader's arithmetic from Table 3 and is not discussed in the text. Best result, Opus 5 with FRR 35.85%, is below its 91.51% resolve rate with the defect specified (§4.4).
- effect: mixed
- reader: an ablation on equal tasks, so E4, but on 3 of 11 models with one run each and no test of significance; a 1.9 point FRR change is 4 instances of 212 (reader's arithmetic). The prompt is the authors' own and the benchmark counts handled defects without penalising unneeded defensive edits (§5). §1 says FRR rises 11.32 points for Opus 5 under proactive prompting; Table 3 gives 8.02 (see Discrepancies).

### F4 · practice · self-review-prompts · E4
- practice: after the agent submits its patch, call the harness's native review command (`/self-review` for Claude Code, `/review` for Codex) on the same agent and let it repair what it finds (§4.4).
- claim: "native review mechanisms in Claude Code and Codex increase FRR for all three models but reduce resolve rate in every case" (§4.4).
- evidence: Table 3, resolve rate / FRR, baseline to self-review. GPT-5.6 Sol 84.43 / 18.40 to 69.81 / 24.06 (resolve −14.62 in the text). Claude Opus 5 77.83 / 24.53 to 68.40 / 35.85. Claude Sonnet 5 59.91 / 16.98 to 57.08 / 18.40. One aiohttp case: baseline Opus reproduces PR1's approach and misses the defect; with proactive prompting it anticipates the PR2 fix and breaks PR1 tests through extra cleanup (§4.4).
- effect: mixed
- reader: E4 by design (same tasks, same agent, with and without the step), three models, one run each, no test. The Sonnet FRR gain of 1.42 points is 3 instances (reader's arithmetic). The reviewer is the agent that wrote the patch with the same context, so this is a self-review, not an independent review. §1 says "popular code review skills are not able to increase FRR", which §4.4 contradicts.

### F5 · practice · proactive-prompt-with-self-review · E4
- practice: apply the proactive prompt during implementation and the native review command after the patch (§4.4).
- claim: the combination raises FRR for two models and lowers resolve rate further (Table 3 caption: "the resolve rate drops steadily across different techniques").
- evidence: Table 3, resolve rate / FRR, baseline to combined. GPT-5.6 Sol 84.43 / 18.40 to 70.28 / 32.55. Claude Opus 5 77.83 / 24.53 to 64.62 / 35.85. Claude Sonnet 5 59.91 / 16.98 to 42.45 / 14.15. Anticipation score rises for all three, for example Opus 30.57 to 52.97 (Table 3).
- effect: mixed
- reader: E4 by design, same limits as F3 and F4. The combined setting does not beat self-review alone on FRR for Opus (35.85 in both) and costs 3.8 more points of resolve rate (reader's arithmetic from Table 3). The text does not discuss this arm.

### F6 · observation · foresight-by-defect-difficulty · E3
- practice: none applied; the 212 instances are binned by the difficulty an LLM judge assigned to the PR2 fix (easy under 15 minutes, medium 15 minutes to 1 hour, hard over 1 hour) and by PR1 difficulty (§3.2, §4.2).
- claim: "Foresight degrades with difficulty and severity"; resolve rate "does not decrease monotonically" across PR2 difficulty while FRR does (§4.2).
- evidence: FRR falls from 18.3% to 2.1% from easy to hard PR2 defects; every model scores lower on hard than on easy; GPT-5.6 Sol scores 0 on hard (§4.2). Hard PR2 has n=35, easy n=125 (Table D.1). Across PR1 difficulty (n=47, 77, 88) both resolve rate and FRR fall (Figure 4, §4.2). 59% of PR2 tasks are easy and FRR is still low (§4.2).
- effect: hurts
- reader: difficulty labels come from an LLM judge following SWE-ReBench V2 (§3.2); no check of the labels against human ratings is given in the parts read. Per-model FRR in the hard bin rests on 35 instances, where one instance is 2.9 points (Table D.1). The 18.3% and 2.1% are averages over models; the text does not say how they are weighted.

### F7 · observation · silent-defects-harder-to-anticipate · E3
- practice: none applied; instances are labelled silent (the code returns a wrong answer without an error trace) or loud (it raises), and by severity (critical, major, minor), by an LLM judge (§3.2, §4.2).
- claim: "defects without an explicit failure signal are substantially harder to anticipate" (§4.2).
- evidence: FRR 18.5% on loud against 12.5% on silent defects; FRR 5.0 points lower for major than for minor defects, nine of eleven models better on minor, resolve rate unchanged (§4.2, Figure 4). 129 of 212 PR2 tests fail on an assertion, so are silent; severity is 124 major, 83 minor and 5 critical (§3.2). Table D.2 groups major with n=129, which matches 124 + 5 (reader's arithmetic); loud n=83, silent n=129.
- effect: hurts
- reader: a split of existing results, not assigned. Silent, major and hard defects probably overlap, and the paper does not separate them. Opus 5 shows the largest severity gap (FRR 33.7 minor against 18.6 major) and Qwen3.5-27B reverses the loud against silent split (4.8 against 7.0, Table D.2).

### F8 · observation · uneven-language-and-file-support · E3
- practice: none applied; FRR is split by repository language (Figure D.1).
- claim: Python is highest for every model and JavaScript lowest or tied-lowest for ten of eleven (Figure D.1 caption).
- evidence: pooled FRR 19.1% Python, 13.4% Go, 11.0% TypeScript, 7.6% JavaScript; Go has 21 instances and TypeScript 28, so one instance moves those bars by 4.8 and 3.6 points; JavaScript instances come largely from one repository (Figure D.1 caption). Python n is not given in the text.
- effect: mixed
- reader: the authors flag the small strata and the single JavaScript repository themselves; language, repository and defect type are confounded. The main text reports only that foresight varies by language (§4.2).

### F9 · practice · llm-judge-filter-of-szz-attribution · E3
- practice: when the earlier PR is inferred by SZZ (blame of the lines the fix changed), filter the pairs with two LLM judges, DeepSeek V4 Flash and GLM 5.3 Flash, that decide whether the inferred PR introduced the defect (§3.1, A.4).
- claim: the judge panel lowers wrongly attributed PR1s while keeping most correct ones (A.4).
- evidence: on 376 chains with a maintainer-stated PR1, SZZ abstains on 114 and proposes a PR1 for 262, of which 172 match and 90 do not: 34.4% contamination. The panel rejects 77 of 90 wrong (85.6%) and 18 of 172 correct (10.5%); contamination falls to 7.8% (95% CI 4.6 to 12.9) at yield 89.5% (A.4). A separate estimate is 7.3% (CI 4.2 to 12.4) on 252 SZZ candidates, of which 28 survive the pipeline (A.4). A co-author who did not build the pipeline checked a 10% sample of instances and found a valid PR2 for 90.9% (A.4).
- effect: helps
- reader: before and after on one set, with no second judge setup to compare, so E3. The 376 chains are the ones where a maintainer names the cause, which may be easier than the other 90% of the corpus that uses SZZ (A.4). The 90.9% audit has no n for the sample (10% of an unstated base) and the auditor is a co-author.

## Limits stated by the authors

- Only defects that maintainers found, fixed and that reproduce under execution are included; undiscovered defects are excluded (§5).
- FRR does not penalise unneeded defensive changes, so an agent that handles many cases may write overly general code (§5).
- The benchmark covers four languages and a limited set of defect types (§5).
- SZZ can attribute a defect to the wrong PR; the authors estimate 7.3% contamination as an upper bound (A.4).
- Go and TypeScript strata are small and JavaScript comes largely from one repository (Figure D.1).

## Reader's notes

- Benchmark, prompt and ablations are all by the authors; the evaluated models and harnesses are third-party. `independent` is false because the prompt interventions in F3 to F5 are the authors' own and the held-out tests are chosen by their pipeline.
- Runs per instance, seeds and any variance are not stated in the parts read. With 212 instances, one instance is 0.47 points of FRR (reader's arithmetic); several of the Table 3 differences are a few instances.
- Models were run on different harnesses with different limits: 250 steps or turns and a $3 or $5 cost limit for mini-swe-agent and Claude Code, and only a 90 minute timeout for Codex (Table C.2). The resolve rates of three open models (18.40% to 25.47%, Table 1) against the 91.98% of Qwen3.8 Flash Next on the same harness suggest a budget or format effect, which the paper does not analyse.
- The PR2 tests are the anticipation oracle. A PR2 test can reward a specific fix shape (naming, signatures) that the task text does not give. The pair validity judge screens for this (A.1.1 codes B2 and B6), but no rate of screened-out cases is given in the parts read.
- The funnel is 11,609 candidates, 2,262 after judges, 815 after execution validation, 492 after problem-statement checks, 212 drawn (§3.1); how the 212 were stratified is not stated in the parts read.
- All findings measure a benchmark score. None measures whether the extra defensive changes from F3 to F5 are wanted by maintainers.
- The paper's footnote argues contamination is not an issue because the best FRR is 24.53% (§4.2 footnote 2); this is an argument, not a test.

## Discrepancies

- §1 says "FRR increases by 11.32 percentage points for Claude Opus 5" under proactive prompting. Table 3 gives 24.53 to 32.55 (+8.02) for the proactive prompt, as §4.4 also says; 11.32 is the self-review change (24.53 to 35.85).
- §1 says "popular code review skills are not able to increase FRR". §4.4 and Table 3 report that the native review commands raise FRR for all three models (Sol 18.40 to 24.06, Opus 24.53 to 35.85, Sonnet 16.98 to 18.40).
- §1 says 492 instances remain after construction and validation; §3.1 gives 815 after step 3 and 492 after step 4, which is consistent, but A.4 describes a dataset of "376 instances across 46 repositories" for maintainer-attributed chains, against 35 repositories in the benchmark (a different set, not explained in the parts read).
- Table 2 labels a model "Qwen3.8 Flash"; Table 1 and §4.2 call it "Qwen3.8 Flash Next".
- A.4 says contamination among retained chains is 7.8% (CI 4.6 to 12.9) and, in the same section, 7.3% (CI 4.2 to 12.4); the two come from different sets (376 chains and 252 candidates).
