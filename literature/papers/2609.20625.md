## Question

Can a recorded agent incident be turned into a regression test that runs in continuous integration
and checks a code change against the recorded run, while everything else is held fixed (Abstract, §1)?

## Findings

### F1 · practice · cut-point-replay-of-recorded-incident · E4
- practice: record an incident at the agent's model, tool and routing boundaries, then replay it with the first model call served from the record and the tool and the second model call run live with the new code, asserting that the guard fired (§3.2, §3.3, Table 2 caption); compared with a baseline that stubs every boundary from the record and uses the same assertion (§4).
- claim: a "stub-every-boundary baseline" never re-enters the tool, so its verdict "cannot depend on the tool's code"; cut-point tests separate unguarded code from the guarded fix and benign edits (§4, Abstract).
- evidence: Table 2, 6 incidents. Fails the unguarded code: 6/6 cut-point, 6/6 full-stub. Passes the guarded fix and the benign edit: 6/6 cut-point, 0/6 full-stub. Mutants killed: 51/192 cut-point, 0/192 full-stub (§5). Trade incident: the unguarded tool sells 1,000 shares (about $190k) for a request of about $1k and the gated tool blocks it (§4).
- effect: helps
- reader: E4 as an A/B on the same 6 incidents and the same assertion. The baseline fails by construction, since a stubbed tool returns the recorded unsafe result whatever the code does, and the authors say so. The authors wrote the incidents, the guards and the assertions together and say the outcomes "validate the mechanism on curated incidents rather than measure fault detection in general" (§4). `independent: false`.

### F2 · practice · cut-point-replay-of-recorded-incident · E4
- practice: as F1; the measurement is how many mutants of each guarded tool a test kills (§5).
- claim: cut-point tests "catch every mutant that lets the recorded unsafe action through", while the full-stub baseline catches none (Abstract, §5).
- evidence: 192 first-order mutants (relational, logical and constant operators), killed when the verdict differs from the verdict on the unmutated fix: 51 killed by cut-point tests, 0 by full-stub (§5). Of the 141 survivors, 110 change code the recorded input never reaches or leave the decision on that input unchanged, and 31 change output fields the assertion ignores while the action stays blocked (§5). Among mutants that change behaviour on the recorded input, 51 of 82 (62%) are killed (§5).
- effect: helps
- reader: the same A/B as F1, with the same by-construction zero for the baseline. The 62% is over the 82 mutants that change behaviour on the recorded input; over all 192 it is 51 (26.6%, reader's arithmetic). The claim that no survivor lets the unsafe action through is the authors' reading of the 141 survivors, not a separate test.

### F3 · practice · cut-point-replay-of-recorded-incident · E2
- practice: change the agent code in ways that leave the safety invariant unchanged (rewordings) and run the cut-point test on them (§4, Table 2).
- claim: cut-point tests "tolerate 30 unrelated rewordings that leave the safety invariant unchanged" (§4).
- evidence: 30/30 rewordings tolerated; the full-stub column has no entry (Table 2). The number of rewordings per incident and what they changed are not given in the text.
- effect: helps
- reader: a count with no comparison arm and no description of the edits, so E2. Together with the 6 benign edits of F1 it is the only evidence on false alarms.

### F4 · practice · full-replay-of-recorded-run · E2
- practice: replay a recorded run with every boundary served from its recorded envelope, so no model call is made, and run the suite on every commit (§3.2, §5 Workflow).
- claim: full replay "is bit-stable" and costs nothing in provider calls, so recorded incidents run on every commit "at no model cost" (§5).
- evidence: 0 divergences and 0 live boundary crossings over 20 repetitions of the 6-incident suite; 0 of the 12 agent model-boundary crossings issued, so 1,000 full-suite replays cost $0.00; one full-stub pass takes 3.5 ms and one cut-point pass, with the tool and the final model crossing live, 3.6 ms (§5, Table 2).
- effect: helps
- reader: numbers that describe the practice with nothing to compare against, so E2. The model boundaries are deterministic stubs, so the zero divergences hold by construction; the authors say it "validates the replay mechanism rather than reproduction under a nondeterministic provider" (§5, Limitations). No rerun of the same incidents with a live model is reported.

### F5 · practice · recording-agent-boundaries-for-replay · E4
- practice: mark boundaries with a one-line annotation so that each crossing is saved as an immutable envelope (input, output, model version, sampling parameters) with secrets redacted, at record time (§3.1); the overhead is timed with recording on against off, in interleaved pairs in random order, over 50 calls per arm to a local Qwen3.5 4B model (§5).
- claim: recording is "not a detectable source of latency" (§5).
- evidence: in-memory recording adds a median 23 µs per crossing, 0.008% of an assumed 300 ms model call; the store grows by at most 1.44 KB per crossing (Table 2). Mean latency against Qwen3.5 4B: 3,136 ms (s.d. 379 ms) with recording and 3,045 ms (s.d. 387 ms) without; difference +91 ms, 95% CI −59 to +241 ms (§5).
- effect: none
- reader: randomised order on the same model and calls, so E4, but one small model on a laptop CPU, 50 calls per arm. The CI is about 300 ms wide (reader's arithmetic) against a 91 ms difference, and the 0.008% is against an assumed 300 ms call, not a measured one. A run-to-run s.d. of about 380 ms hides any cost smaller than that, which the authors use as their argument. Tool boundaries and large payloads are not timed.

### F6 · practice · per-name-count-check-on-stubbed-boundaries · E0
- practice: serve the kth crossing of a stubbed boundary its kth recorded envelope, and raise when a stubbed boundary is crossed more or fewer times than recorded (§3.2).
- claim: a changed boundary contract "flags the fixture for re-recording rather than passing silently, which keeps the committed test honest as the agent evolves" (§5 Workflow).
- evidence: no data is given. The authors state that the check misses a reordering that preserves each name's count and that an order-sensitive digest is not in the evaluated release (§3.2, Limitations).
- effect: helps
- reader: asserted, E0: no experiment varies a boundary count or an order. The benchmark agents have no loops or retries (Limitations), so the case the check is built for does not occur in the evaluation.

### F7 · observation · single-recording-mutant-survival · E2
- practice: none applied; the survivors of the mutation study of F2 are classified by why a test built from one recording cannot kill them (§5).
- claim: the unkillable mutants "reflect a coverage limit of single-incident fixtures: each recording exercises one input" (§5).
- evidence: 141 of 192 mutants survive a cut-point test: 110 not killable by any test built from these recordings and 31 that change output fields the assertion ignores (§5).
- effect: mixed
- reader: a description of the study's own survivors with no comparison, so E2. `mixed` is the nearest value: the paper reports a count of what the method misses next to a count of what it kills, with no direction claimed for either.

## Limits stated by the authors

- No streaming responses (recorded in assembled form) and no concurrent parallel tool calls (Limitations).
- Replay does not re-raise an exception recorded at a stubbed boundary (Limitations).
- A live cut-point on a destructive tool should target a sandbox, because an envelope captures the interface and not the side effects (Limitations).
- Determinism is "partly by construction" because the released agents replace the model with a deterministic stub; reproduction on a live nondeterministic provider is not measured (Limitations).
- The benchmark is small and self-constructed: six three-step incidents with no loops, retries or multi-agent routing (Limitations).
- Count-preserving reorderings escape the per-name check, and an unmarked nondeterministic call runs live and escapes it; coverage of such call sites is the user's responsibility (§3.2, Limitations).
- A boundary that reads hidden state, such as a clock or a database, breaks the faithfulness of replay (§3.1).
- The LLM-as-judge for non-structural properties is implemented and not evaluated (§3.3, Limitations).
- No reproduction rate is claimed for traces outside the 6 incidents (§4).
- Recordings may hold secrets or personal data; redaction happens at record time (Ethics Statement).

## Reader's notes

- Nothing in the evaluation is a coding agent. The 6 incidents are refunds, invoices, trades, email, payouts and file deletion by small simulated agents; the one coding-adjacent case is a file deletion gate. The method transfers to coding agents only as an idea (record a failed run, test the fix against it).
- Both F1 and F2 compare a method with a baseline that cannot detect the fault by design, so the 6/6 against 0/6 and 51 against 0 say that a test which executes the code beats a test which does not, not how much better cut-point replay is than other regression tests. No comparison with a hand-written test of the guard, a rerun on a live model, or another replay tool is given.
- The 6 incidents map to the task-verification category of the multi-agent failure taxonomy of Cemri et al. (2025), chosen by the authors (§4). The mapping is not checked.
- The 6/6 detection depends on the assertion naming the guard output (`blocked`, Figure 1). The paper does not say how a team picks that assertion for an incident whose fix is not a guard.
- The affiliation is given as Microsoft; the author email addresses are of two other institutions.
- The abstract says cut-point tests "catch every mutant that lets the recorded unsafe action through". That is true of the 192 mutants only through the authors' classification of survivors (F2).
