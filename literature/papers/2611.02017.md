## Question

When a coding agent works on several unfinished tasks of one repository in one continuous session,
how much less often does it resolve the task it returns to, and does a context manager that routes
history and keeps per-task state close that gap (Abstract, §1)?

## Findings

### F1 · practice · interleaved-unfinished-tasks-in-session · E4
- practice: deliver a focus task's requests in one continuous agent conversation with four other unfinished tasks of the same repository interleaved between them, each task in its own persistent checkout; compared with the same focus requests alone, same base revision, held-out tests and budgets. Only the final focus patch is scored (§3.1, §3.4).
- claim: interleaved unfinished work "yields an average focus-task resolution gap of 11.5 percentage points", ranging from 6.0 to 15.0, "despite identical focus requirements, executable verifiers, and task-specific workspaces" (§1, §4.1).
- evidence: Table 1, resolution without and with switching, 200 tasks per cell, one run each: DeepSeek-V4.1-Flash 46.5 and 31.5, GLM-5.3 49.0 and 43.0, Kimi K3 48.0 and 34.5, GPT-5.6 Terra 41.0 and 28.0, GPT-5.6 Sol 52.5 and 38.0, Claude Opus 5 53.5 and 41.5, Gemini 3.7 Flash 29.5 and 23.0. All 7 gaps positive. DeepSeek's drop is a 32.3% relative reduction (§4.1). No statistical test is given.
- effect: hurts
- reader: a paired design on equal tasks, so E4, though the conditions are fixed schedules and not randomised, and each cell is one run with no interval; a gap of 6 points on 200 tasks is within what one run per cell can produce by chance (reader's judgement). Both conditions keep five persistent checkouts, so the paper does not test whether persistence of code helps; its conclusion that "code persistence alone does not ensure reliable resumption" (§6) rests on the gap that remains. Runs without a final submission count as unresolved (§4), so submission failures enter the gap.

### F2 · practice · interleaved-unfinished-tasks-in-session · E3
- practice: as F1; the measurement is tokens, model calls and tool calls per run.
- claim: "Switching increases session-level computation"; resumed focus stages "retain the cost of interruption history" (§4.3).
- evidence: Table 2, tokens in millions, uninterrupted against full switched session: DeepSeek 8.594 and 101.953, GLM 4.904 and 14.970, Kimi 4.739 and 24.335, Terra 1.511 and 9.741, Sol 2.294 and 16.921, Opus 3.145 and 18.237, Gemini 8.880 and 46.058. Resumed focus stages alone use 1.41 to 2.95 times the tokens of a full uninterrupted session, with model calls not uniformly higher (§4.3). Figure 1(a) labels cost increases from +40.9% to +195.3%; which label belongs to which model is not legible in the text.
- effect: hurts
- reader: E3 because the switched session does the interruption tasks' work too, so the comparison is between different workloads and the authors say the ratios "describe the combined workload ... rather than the isolated cost of resumption" (§4.3). The focus-only figure still includes the interruption history in context and "aggregate usage cannot separate this effect from differences in outputs and native context management" (§4.3). The token ratios in the text do not match Table 2 (see Discrepancies).

### F3 · observation · interruption-source-locality · E3
- practice: none applied; the 200 focus tasks are split by whether the four interruption tasks modify distinct files in a shared immediate source directory (near) or share no immediate directory (far); 100 focus tasks each (§3.3).
- claim: "The far group consistently exhibits larger gaps"; the pattern "indicates an association between source locality and resumption performance rather than an isolated causal effect" (§4.2).
- evidence: Table 1, gap in points, near against far: DeepSeek 11.0 and 19.0, GLM 1.0 and 11.0, Kimi 12.0 and 15.0, Terra 10.0 and 16.0, Sol 13.0 and 16.0, Opus 8.0 and 16.0, Gemini 2.0 and 11.0. Average 8.1 against 14.9; within-configuration differences 3.0 to 10.0 (§4.2). Switched resolution is higher in the near group for all 7; for 5 the uninterrupted ordering is the reverse (§4.2).
- effect: helps
- reader: `helps` means near interruptions leave a smaller gap than far ones. The groups hold different focus tasks, which the authors say. The 100 near and 100 far focus tasks were chosen "using task metadata and earlier execution outcomes for a fixed diagnostic cohort" (§3.3), so selection could correlate with difficulty. Locality is measured by directory, not by what the tasks are about. The mechanism ("more reusable context") is stated as consistent with the data, not shown (§4.2).

### F4 · practice · task-history-routing · E4
- practice: an auxiliary model assigns each request to an existing or new task from a task catalogue and earlier user messages, and the model sees only that task's interaction groups plus shared instructions and unassigned interactions; below routing confidence 0.8 the full history is kept; the native compactor is told to preserve each task's requirements, progress and pending work. Compared with native OpenCode on the same tasks (§5.2, Appendix F.1 and F.3).
- claim: task-aware routing and compaction are "useful interventions under switching" (§5.3).
- evidence: Table 3, switched resolution, native against +Router: DeepSeek-V4.1-Flash 31.5 and 42.5 (+11.0), GLM-5.3 43.0 and 46.5 (+3.5). Uninterrupted resolution 46.5 and 45.5, 49.0 and 49.5. For GLM the gain "occurs entirely in the far group", 40.0 to 47.0 (§5.3). The auxiliary calls count toward the budget (§5.3); their cost is not reported in the parts read.
- effect: helps
- reader: an ablation on equal tasks, so E4; two models, one harness, one run per cell, no interval. The +Router condition bundles routing and the changed compaction instruction, so the gain is not attributable to routing alone. The authors built the module and the benchmark it is scored on, and chose it after trajectory inspection of the same tasks (§5.1), so overfit to the benchmark is a risk.

### F5 · practice · per-task-state-memory · E4
- practice: an auxiliary model incrementally keeps a record per task (goal, constraints, progress, pending work, relevant files, uncertainties) from completed interactions, separating user requirements, tool observations and assistant claims, and injects it on resumption in place of older assistant and tool exchanges it covers; added on top of the router (§5.2, Appendix F.2).
- claim: "State memory adds gains beyond routing" (§5.3).
- evidence: Table 3, switched resolution, +Router against +RCM: DeepSeek-V4.1-Flash 42.5 and 47.0 (+4.5), GLM-5.3 46.5 and 48.5 (+2.0). Uninterrupted resolution 45.5 and 46.0, 49.5 and 49.5.
- effect: helps
- reader: the contrast is one component added to a fixed base on equal tasks, so E4. The +2.0 for GLM is 4 tasks of 200 in one run. Same confounds as F4: own module, own benchmark, 2 models. Memory cost in tokens or calls is not reported in the parts read.

### F6 · practice · task-aware-context-management · E4
- practice: router plus task-state memory together (RCM) as an OpenCode plug-in, against native OpenCode, under uninterrupted and switched execution (§5.2, §5.3).
- claim: switched resolution improves by 5.5 to 15.5 points "while maintaining comparable uninterrupted performance" (§6); the gaps narrow to −1.0 and 1.0 (§5.3).
- evidence: Table 3 overall, native then +RCM: DeepSeek-V4.1-Flash switched 31.5 and 47.0, uninterrupted 46.5 and 46.0, gap 15.0 and −1.0; GLM-5.3 switched 43.0 and 48.5, uninterrupted 49.0 and 49.5, gap 6.0 and 1.0. Gains are larger in the far group than in the near group for both models (§5.3). The paper does not give the RCM runs on the other 5 configurations.
- effect: helps
- reader: E4 as an A/B on equal tasks. The RCM switched score of DeepSeek (47.0) is above its own uninterrupted native score (46.5); the authors say this does not establish "a benefit from switching itself" (§5.3). Evaluated by the system's authors on 2 of 7 configurations, one run each, with auxiliary calls defaulting to the coding model (§5.2).

### F7 · observation · cross-task-interference-and-state-loss · E1
- practice: none applied; the authors read saved switched traces for two signatures. Requirement-state loss: a returned focus edit or plan violates an earlier focus requirement or forgets a prior decision. Cross-task interference: work tied to another checkout enters the focus task's reasoning, edits or submission scope (§E.1, Table 8).
- claim: "cross-task requirement confusion and loss of task state" are recurrent resumption behaviours (Abstract).
- evidence: three cases (§E.2 to E.4). Click, DeepSeek-V4.1-Flash: uninterrupted artifact passes all required tests, switched passes 3 of 7 fail-to-pass tests and all 732 pass-to-pass; the callable-default extension was added without the earlier Boolean guard. Moto, GPT-5.6 Sol: the switched agent returned to the right checkout, then ran `git diff` over all five workspaces at finalization and produced no applicable focus patch, while the uninterrupted run passed all 5 fail-to-pass and 8 pass-to-pass tests. NetworkX, DeepSeek: both conditions pass all 25 fail-to-pass and 41 pass-to-pass tests; the switched agent preserved earlier invariants across returns. No frequencies are given in the parts read.
- effect: hurts
- reader: E1 because the claim of recurrence rests on three selected cases and one of them is a success. Signatures are assigned only when visible in the trace (§E.1), by the authors; the AI use statement says no AI was used for qualitative trajectory classification. Figure 1(b) splits failures into implementation, submission and incomplete execution, with values in the figure only, so the share of failures due to either signature is not in the text.

## Limits stated by the authors

- The locality comparison is an association, since the near and far groups contain different focus tasks (§4.2).
- Token ratios describe the combined focus and interruption workload, not the isolated cost of resumption (§4.3).
- Aggregate token usage cannot separate repeated processing of history from differences in output and native context management (§4.3).
- Gains of the context manager do not establish a benefit from switching itself (§5.3).
- Interruption tasks use their own checkouts, so the benchmark isolates conversation-level recovery from on-disk conflicts (§1, Appendix C.4).

## Reader's notes

- Each cell is one run of 200 tasks; no confidence interval or test is given anywhere in the parts read. Table 1 gaps of 6.0 and 6.5 points are 12 and 13 tasks.
- Interruption tasks are other tasks of the same repository with disjoint source files and their own checkouts (§3.3, Appendix C.4), and their requests are cleaned review-history text; real sessions with shared files and an operator who relabels tasks are not covered.
- The controller names the active checkout path in every request and withholds any recovery summary (Appendix B.3). A human operator or a harness that summarises on return would give the agent more than this setup does.
- Later stages are built from pre-merge review rounds, with "benchmark-authored extensions" added "where additional behavioral coverage is needed" (§3.2, Appendix C.3). The share of such stages is not stated in the parts read.
- The evaluated models and harness versions (Table 5) are as named in the paper; the same harness differs across models (OpenCode with two models), so model and harness effects are not separated in Table 1.
- Uninterrupted resolution does not predict switched resolution: Kimi K3 and GLM-5.3 differ by 1.0 point uninterrupted and 8.5 switched, and Claude Opus 5 leads uninterrupted (53.5) while GLM-5.3 leads switched (43.0) (§4.1). This is not a finding here because no practice or condition with a direction applies.
- The context manager's added cost (auxiliary routing and memory calls at the coding model's price) is said to count toward budget but is not quantified in the parts read.

## Discrepancies

- §4.3 says full switched sessions use "4.5-11.1 times as many tokens" as uninterrupted ones. Table 2 gives 3.05 (GLM-5.3) to 11.86 (DeepSeek-V4.1-Flash) (reader's arithmetic).
- §4.3 says "2.4-4.3 times as many model calls". Table 2 gives 1.73 (GLM-5.3) to 4.25 (Gemini 3.7 Flash) (reader's arithmetic).
- §4 says each agent invocation has a 900-second budget "with at most three timeout continuations across the entire session"; Appendix B.2 gives a 900-second budget "per attempt and for 3 times retry" for every scheduled request. The per-request and per-session reading differ.
- The Abstract and §1 say gains of "5.5 to 15.5 percentage points"; the Conclusion writes "5.5–15.5%". The numbers match Table 3.
