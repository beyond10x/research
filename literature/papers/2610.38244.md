## Question

When several implementations satisfy the same functional requirements, do coding agents follow their own
default, the precedent in the repository, or an explicit instruction in the task, and how does the
location and form of the precedent or instruction change that (Abstract, §1)?

## Findings

### F1 · practice · existing-code-precedent-over-defaults · E4
- practice: extend a repository whose six existing endpoints all use the implementation opposite to the agent's default, with a task description that asks the agent to follow the conventions of the existing code without naming the choice; compared with the same task in a repository with the endpoint files removed (§3.2, §3.3, §4.2).
- claim: "repository precedent overrides these defaults"; implementation preferences measured without precedent "do not necessarily predict agents' choices when extending existing code" (§4.2).
- evidence: with no precedent, 359 of 360 runs choose the default (Table 3). With every endpoint opposite the default, 359 of 360 follow the repository: 299/300 in the five pairs whose default is the baseline and 60/60 in dispatch (§4.2, Figure 5). Dictionary dispatch is chosen in 59 of 60 zero-precedent runs and in none of 60 runs once every endpoint uses an if/elif chain (§4.2).
- effect: helps
- reader: an intervention on equal tasks, E4. `helps` is on following the repository's convention. §5 says the zero-precedent and precedent conditions "were collected under different execution settings", which weakens the contrast. One Flask API task family, 15 runs per cell.

### F2 · observation · agent-default-implementation-choices · E2
- practice: observed: the choice each agent makes on six implementation pairs when the repository holds no relevant endpoint example (§3.2, §4.2).
- claim: the defaults "are nearly deterministic and agent-independent"; all four agents share the same default in each pair, so differences among agents later do not come from different starting preferences (§4.2).
- evidence: 359 of 360 runs choose the default and 23 of the 24 pair-agent cells are unanimous; the one deviation is a Sonnet run on dispatch (14/15) (Table 3, §4.2). All 360 runs pass the hidden tests (§4.2). The defaults are integer IDs, snake_case, flat response, unprefixed Boolean name, direct error response, dictionary dispatch (Table 3).
- effect: none
- reader: no condition was applied and nothing is compared with it, so E2. The paper reports a distribution with no direction; `none` here means no difference among agents. The authors' reading is that each default is "the most direct expression of the required behavior in Python and Flask" (§4.2); that reading is not tested.

### F3 · practice · local-precedent-support-level · E4
- practice: vary how many of the three existing files of the resource being extended (local files) use the alternative, 0/3 to 3/3, with the sibling-resource files held at the baseline (§3.3).
- claim: "Local precedent strongly influences implementation choices"; adoption rises with local support and never decreases (§4.3).
- evidence: pooled over 6 pairs and 4 agents, adoption of the alternative is 0% (0/360) at 0/3, 21% (74/359) at 1/3, 49% (175/360) at 2/3 and 96% (347/360) at 3/3 (§4.3, Figure 5). No decrease in any of the 24 pair-agent combinations; Cochran-Armitage trend p ≤ 5.6 × 10−5 for Sonnet and p ≤ 1.3 × 10−5 for Opus on all six pairs (§4.3). Thresholds differ: Sonnet adopts string IDs in 10/15 runs with one local file, whereas Boolean naming stays at or below 1/15 for every agent through 2/3 (§4.3). Response envelope never reaches full adoption for the Claude agents at 3/3: Sonnet 8/15, Opus 9/15 (§4.3).
- effect: helps
- reader: the support level is the manipulated variable on equal tasks, E4. `helps` is on adoption of the supported pattern. Support level and file identity change together (§5); F4 addresses that.

### F4 · practice · example-file-placement · E4
- practice: hold the number of supporting local examples fixed (1/3 or 2/3) and move which local file carries the alternative: tasks_create, tasks_update or tasks_list (§3.3).
- claim: "changing file placement can shift adoption from 0% to 100%", and where examples appear can matter as much as, or more than, how many appear (§4.3).
- evidence: ID serialization with Sonnet, exploratory: 1/15 to 10/15 by placement at 1/3 support, p = 9.6 × 10−4 (Figure 6). Replications: gpt-6-sol on ID serialization at 2/3, 0/15 to 15/15, Holm p ≤ 6 × 10−5; Sonnet on field casing at 1/3, 0/15 to 11/15, p ≤ 6 × 10−5; Opus on ID serialization, no detectable placement effect, p = 0.148 (§4.3). For field casing with Sonnet, one example in tasks_list gives 11/15 adoptions and two examples in the other local files give none (§4.3). Detectable in 3 of 4 settings (§4.3). 75 and 270 trials, 345 in total (reader's arithmetic), including an import-order control (Table 2).
- effect: helps
- reader: placement is the manipulated variable, with Holm-corrected randomisation tests, so E4. `helps` is on adoption, and the finding is that adoption depends on placement; which file matters is not explained, and the authors say so (§5). The most influential placements include tasks_list; 3 settings with 2 agents and 2 pairs, so the size of the effect elsewhere is untested.

### F5 · practice · local-vs-sibling-precedent · E4
- practice: put the alternative in 1 to 3 sibling-resource files (the project endpoints) while all local files (the task endpoints) use the baseline, so that the two groups conflict (§3.3, §4.4).
- claim: "Sibling-resource precedent rarely overrides local code"; "Repository conventions do not necessarily propagate across resource boundaries through examples alone" (§4.4).
- evidence: across 1,079 classifiable sibling-only trials the sibling-supported alternative is adopted 13 times (1.2%): Sonnet 6/269, gpt-6-sol 5/270, gpt-5.6-sol 2/270, Opus 0/270. In four pairs each agent records 0/180. All 13 occur at full sibling support. With three supporting files: 13/360 for sibling against 347/360 for local (§4.4). In all 45 Sonnet ID-serialization trials with sibling support the project files were in context and 22 transcripts discuss the conflicting format, yet the agents follow the local files (§4.4).
- effect: none
- reader: the contrast is controlled, E4. `none` is the effect of the sibling precedent on adoption. §5 says the local-versus-sibling comparison varies task relatedness and file location together, so it cannot say which one matters.

### F6 · practice · local-vs-sibling-precedent · E4
- practice: make the sibling-resource files agree with the local files, against local files alone (§3.3, §4.4).
- claim: "sibling-resource code agrees with local code, it reinforces the local pattern" (§4.4).
- evidence: response envelope, Sonnet adopts the alternative in 8/15 runs with local support only and 15/15 when both groups use it (Fisher p = 0.0063); Opus rises from 9/15 to 15/15 (§4.4). In the other pairs local support alone already gives full or near-full adoption (§4.4).
- effect: helps
- reader: one pair, two agents, 15 runs per cell; the Opus change has no test stated. The effect is only visible where local support alone is incomplete.

### F7 · practice · stated-priority-rule-over-conflicting-code · E4
- practice: add to the task description a written rule that names the target implementation and says it takes precedence over the existing code, with no code (condition C1); against no guidance (C0) and against the rule plus a code example (C3). All six existing endpoints use the opposite implementation (§3.4, §4.5).
- claim: "written priority rules override conflicting precedent more reliably than code examples alone (98% vs. 63%)" (§1).
- evidence: joint success (hidden tests pass and the target is adopted), 2 pairs by 2 agents by 15 randomised blocks, Figure 7. Pooled of 60: C0 0, C1 59, C3 60. C1 against C0: Holm p ≤ 0.00159. C3 against C1: Holm p = 1, so the example adds nothing to the rule. 238 of 240 runs pass the hidden tests (§4.5).
- effect: helps
- reader: randomised blocks on equal tasks, E4. The rule is a single sentence per pair, and its wording says "takes precedence", which is the property being tested. Two pairs (ID serialization, response envelope) and two agents (Sonnet-4-6, gpt-6-sol). The tests accept either implementation, so only the choice between the two is measured.

### F8 · practice · code-example-of-target-over-conflicting-code · E4
- practice: put in the task description a code snippet that shows the target implementation, without stating its priority (condition C2); against no guidance (C0) and against the written rule (C1) (§3.4, §4.5).
- claim: "An example thus acts as one more precedent that competes with the repository, whereas a stated priority resolves the conflict"; an example alone is "unreliable" (§4.5).
- evidence: joint success pooled of 60: C2 38, C1 59, C0 0 (Figure 7). By agent: gpt-6-sol 15/15 on both pairs; Sonnet 8/15 on response envelope and 0/15 on string IDs, the pair on which Sonnet followed local examples most readily in RQ2 (§4.5).
- effect: mixed
- reader: E4 by the same design as F7. `mixed` because the example works fully for one agent and fails for the other, so the pooled 38/60 hides a split by agent. Only two agents and two pairs.

### F9 · practice · rule-in-native-instruction-file · E4
- practice: put the written priority rule in the harness's native instruction file (CLAUDE.md for Claude Code, AGENTS.md for Codex) with the task description unchanged; against no rule (§3.4, §4.5).
- claim: "A rule delivered through the native instruction file is followed as reliably as a rule in the task description" (§4.5).
- evidence: joint success of 60 per condition across 2 pairs and 2 agents: no rule 0/60, native-file rule 60/60 (15/15 in every setting); risk difference 1.00, Holm p = 0.000244 (Figure 7, §4.5).
- effect: helps
- reader: randomised blocks, E4. Every cell is at the ceiling or at zero. The rule is the same single priority sentence as in F7, and the authors say the experiments evaluate "rules loaded by the harness, not autonomous discovery" (§5). A longer instruction file with other content is not tested here.

### F10 · practice · rule-delivery-channel · E4
- practice: deliver the same written rule in the task description or in the native instruction file (§3.4, §4.5).
- claim: "The two channels do not differ detectably", though the data "cannot show equivalence" (§4.5).
- evidence: task-description rule 60/60 and native-file rule 60/60 joint successes; the 60/60 against 60/60 comparison "is compatible with a difference of up to about 6 percentage points in either direction" (Newcombe interval) (§4.5, Figure 7).
- effect: none
- reader: E4 by design; the result is a null at the ceiling, which the authors state. For the practitioner it says only that neither channel failed on one rule sentence on 2 pairs and 2 agents.

### F11 · practice · local-vs-sibling-precedent · E4
- practice: in four open-source REST API repositories, rewrite the handlers of the resource being extended (local) and of an analogous resource (sibling) independently to one of two patterns, for error handling (propagate to a central handler or construct the response directly) and response envelope (flat or under a `data` key); the agent adds a new endpoint with no guidance about the choice (§3.6, §4.6).
- claim: "Agents follow the local pattern without exception" for error handling; for response envelope local precedent "again dominates, though less uniformly"; sibling patterns have no detectable effect on either (§4.6).
- evidence: error handling, 960 trials: 948 pass the hidden tests and all 945 classifiable successes follow the local pattern (Wilson 95% CI 99.6 to 100%); changing only the sibling pattern has no effect (16 Fisher tests, all p = 1.0) (§4.6, Table 4). Response envelope, 420 trials: 0/207 adopt the envelope with flat local handlers and 148/210 (70%) with enveloped local handlers; the local contrast is significant in 7 of 8 strata, none of the 12 sibling contrasts is (§4.6, Table 6). Overall 355 of 417 (85%) successful envelope implementations follow local precedent (§1).
- effect: none
- reader: the manipulated handlers are rewritten by the authors to an assigned pattern, so E4. `none` is the effect of the sibling pattern; the local pattern has a large effect. Two choices only, and handler count and identity are fixed by each repository, so it does not test support level or placement (§3.6, §5).

### F12 · practice · rule-in-native-instruction-file · E4
- practice: in the four open-source repositories, with every local handler returning a flat payload, put a rule in CLAUDE.md (Sonnet-4-6) or AGENTS.md (gpt-6-sol) to wrap the payload under a `data` key; against a contemporaneous no-guidance control (§3.6, §4.6).
- claim: "A rule in the native instruction file redirects agents in real repositories" (§4.6).
- evidence: runs that both pass the hidden tests and adopt the envelope: 0/120 without the rule, 117/120 (97.5%) with it, 80 to 100 percentage points better in every repository-agent stratum (all eight Holm p = 4.9 × 10−4, the floor of the exact test with 15 blocks). gpt-6-sol 60/60, Sonnet 57/60; the 3 failures are all Sonnet on FastAPI RealWorld (two keep a flat response, one fails a functional test) (Table 5, §4.6).
- effect: helps
- reader: E4 with a concurrent control, though the control is not described as randomised. One implementation choice and one rule sentence; the harness loads the file, so discovery by the agent is not tested (§5).
### F13 · observation · precedent-adherence-varies-by-choice-and-agent · E3
- practice: observed: how completely local precedent determines the choice, by implementation pair, repository and agent (§4.3, §4.6).
- claim: adherence to local precedent "varies across implementation choices, repositories, and agents"; response envelope is the choice that local precedent determines least completely (§4.6).
- evidence: controlled repository, response envelope at 3/3 local support: Sonnet 8/15 and Opus 9/15 against 15/15 for both GPT agents (Figure 5). Open-source repositories, enveloped local handlers: Sonnet 15/15 in ExpressJS API and FastAPI Clean, 0 of 30 in Go REST, 3/15 and 6/15 in FastAPI RealWorld; gpt-6-sol 11 to 15 of 15 in every repository (Table 6, §4.6). Sonnet adopts string IDs at 1/3 support in 10/15 runs against 1/15 for gpt-6-sol (Fisher p = 0.0017), and dictionary dispatch the other way, 4/15 against 12/15 (p = 0.0092) (§4.3).
- effect: mixed
- reader: the comparison is between agents and repositories that nobody assigned, with no control, so E3. Each agent is a model plus a harness, so a difference cannot be put on the model alone (§5). `mixed` because the same precedent gives full adherence in one cell and none in another.

## Limits stated by the authors

- The local-versus-sibling comparison varies task relatedness and repository location together (§5).
- The experiments control which precedents are available, not which ones the agent attends to (§5).
- The zero-precedent condition measures task-specific choices without endpoint examples, not context-free model preferences (§5).
- The native-file experiments test rules loaded by the harness, not discovery by the agent (§5).
- The classifiers capture selected implementation patterns, not maintainability or code quality (§5).
- Example count and file assignment vary together in the support-level experiments; the placement analysis shows sensitivity to file identity but does not explain it (§5).
- The zero-precedent and precedent conditions were collected under different execution settings; retries and interruptions disrupted scheduling in RQ4; an Opus placement run was excluded and rerun; open-source classifications were revised and incomplete patches recaptured (§5).
- Differences between agents cannot be attributed to models alone (§5).
- 15 repetitions per cell, one Flask API task family, two open-source choices with explicit guidance on one; support-level and placement effects are untested beyond the controlled repository; two providers (§5).

## Reader's notes

- Both implementations of every pair pass the same hidden tests, so the study measures style choices (naming, wrappers, error style), not correctness. Whether following precedent is good for the repository is not measured; the authors' recommendation of design-decision traceability is not tested.
- The rules in F7, F9 and F12 are written to be matched by a classifier of one construct each, and the target construct is named in the rule. The result says that agents follow a stated, concrete priority; it does not say how they fare with a vague convention, a long rule file or several rules in conflict.
- The task description in Stage 2 told the agent to follow existing conventions (§3.3). F1, F3 to F6 and F11 are therefore results under that instruction; with no such sentence the agents may behave differently, and that is not tested.
- All agents are recent models run through their own harnesses with default settings; the settings and the harness versions are not stated in the parts read.
- Authors built the pairs, the repositories, the classifiers and the rules; no independent set of pairs is used. The open-source rewrites of handlers are synthetic: the repositories were edited to hold an assigned pattern.
- Several results rest on cells at 0/15 or 15/15, where the p-values reach the floor of the exact test (§4.6).
