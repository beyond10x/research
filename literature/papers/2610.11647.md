## Question

When an installed agent skill is co-installed with a similar skill that does the same job, does the
agent lose the installed skill's core behaviours while the task still passes, what decides which skill
runs, and can a guard stop the loss (§1, RQ1 to RQ3)?

## Findings

### F1 · practice · co-installed-similar-skills · E4
- practice: observed under a manipulated condition. Each of 312 pairs (installed skill A, similar skill B) is run with only A, only B, A and B, and A with an unrelated skill C, same request and starting repository, on 3 models. Fidelity is the share of A's first three applicable core functions (requirements quoted from its text, fixed before any run) that a run fulfils (§2.2, §3.8, §3.9).
- claim: "a similar skill takes one in five runs away from the installed skill" and lowers its fidelity, most on the core functions only A asks for (§1, §4.2).
- evidence: paired change from only-A to A+B, with 95% CI over pairs (§4.2). Use of A falls 19.9 pp [−23.1, −16.7]. Fidelity falls 2.6 pp [−4.4, −0.8]; on A's exclusive core functions 5.6 pp [−7.3, −3.8]; on shared ones +0.1 pp [−2.8, +2.9]. The unrelated skill C lowers use of A by 5.9 pp [−8.5, −3.3] and fidelity by 0.2 pp. Fidelity of A alone is 57.3% against 46.3% for B alone (§4.2). Within-project pairs: use of A falls 18.3 pp (§4.2). On Codex, 193 pairs: use of A falls 18.2 pp and fidelity on exclusive core functions 3.4 pp, against 20.1 and 4.6 pp on Claude Code for the same pairs (§3.1). How common the condition is: for 63.7% [61.3, 66.0] of installed skills (about 26,100 families) the most similar skill by another author does the same job, and for 23.5% [21.2, 25.7] (about 10,100) the most similar skill in the same installation list does (§4.1). In the 489 projects that copy a whole collection, 37% of judged skills have a same-job skill in the list, against 19% in other lists (§4.1).
- effect: hurts
- reader: E4 because configurations differ in one factor on identical cases and C separates "a similar skill" from "one more skill". The pairs are not randomised draws of real co-installations: cross-project pairs are constructed, only skills that run offline and have at least three core functions were eligible (768 of 1,604, 48%, §3.7), and the fidelity checks are partly scored by an LLM judge (GPT-6 Astra, 594 of 921 primary checks, §3.9). One run per combination. The prevalence numbers are E2, rest on the same LLM judge, and cover public repositories only. The fidelity effect is small in absolute terms; the use-of-A effect is the larger one.

### F2 · practice · task-completion-masks-skill-loss · E4
- practice: observed under the same A+B and only-A configurations; the outcome is whether the task is completed, scored by an LLM judge that does not see the configuration (§3.7, §3.9).
- claim: the conflict "hides behind success": task completion does not fall while use and fidelity of A do, so a benchmark that checks only whether the task passes "would call co-installation harmless" (§1, §4.2, §5.1).
- evidence: task completion changes +1.9 pp [−1.0, +4.9] from only-A to A+B (§4.2). Completion is 57.2% with only A and 58.1% with only B, while fidelity differs by 11.0 pp [−13.5, −8.6] (§4.2). Figure 1 and Figure 3: single runs where the task is completed and the core functions are not (Haiku 4.5, Opus 5).
- effect: none
- reader: "none" means the confidence interval spans zero, not that no loss exists; the paper's point is that this outcome cannot see it. The mechanism is partly by design: the cases were written so that any competent way of doing the work counts as complete (§3.7), and the paper itself notes capability skills can lower completion when substituted (§2.3) and the per-type completion change is shown only in Figure 4c, not in the text.

### F3 · observation · skill-non-use-under-conflict · E3
- practice: observed in A+B runs; each run is classified by which skill it used, where use means a Skill-tool call or reading or running files in the skill's directory (§3.9).
- claim: "Most of the loss occurs in runs that do not use A at all"; B adds "mainly substitution" beyond one more skill (§4.2).
- evidence: with B co-installed 12.1% of runs use only B and 38.0% use neither skill, against 30.3% that do not use A with only A installed (§4.2, Figure 5). A substituted run loses 8.0 pp of fidelity. Substituted runs carry 36% of the fidelity loss, runs that use neither skill 45%, runs that use A 20% (§4.2, Figure 4b). With C, 36.0% of runs use neither skill and 0.1% only C (§4.2).
- effect: hurts
- reader: a decomposition of the F1 loss, not a control on its own. The 20% attributed to interference is small, so the evidence that B's instructions alter A's behaviour once both are read is thin. The gap between 36.0% (with C) and 38.0% (with B) neither-skill runs is 2 points (reader's arithmetic), so the 38.0% is mostly the effect of adding any second skill.

### F4 · practice · skill-scope-precedence · E4
- practice: observed under manipulated placement. For the 81 same-name pairs, B is placed in the personal directory (which overrides the project skill A and removes it from the listing) or in a plugin (both listed, namespaced), against B in the project (§3.8).
- claim: "Where a skill is installed decides which one runs"; a personal B overrides A in every listing, yet models still read A's files in many runs (§4.3, Finding 4).
- evidence: personal scope, 243 runs: A is in none of the listings; use of A falls 35.0 pp [−43.0, −26.9]; B is used in 46.5% of runs; in 29.2% the model still reads A's files; fidelity of A is 3.9 pp lower [−7.5, −0.3] (§4.3). Plugin scope: A used in 58.0% of runs and B in 2.9%; use of A falls 6.2 pp, against 16.9 pp when B is in the project for the same pairs (§4.3, Figure 5).
- effect: hurts
- reader: E4 as a manipulation on identical pairs, with only 81 pairs and one run each. The result follows the platform's documented precedence rule, so the finding for a practitioner is that a same-name skill in the personal directory silently disables a team's project skill, and that this is tested on Claude Code 2.1.283 only. The authors note that Gemini CLI and Copilot CLI prefer the project skill and Codex lists both (§2.1), which was not tested.

### F5 · practice · skill-listing-order · E4
- practice: observed under manipulation. The swapped configuration reverses the listing order of A and B by prefixing B's directory name with one character (§3.8).
- claim: "Listing order barely affects which skill is used", in contrast to position bias reported for tool selection (§4.3).
- evidence: order changes use of A by +0.6 pp [−2.0, +3.3]; the renaming itself adds +4.4 pp (§4.3, Figure 5).
- effect: none
- reader: E4 by design, but the order cannot be changed without renaming B, so the order effect is separated from the rename effect only by contrasting pairs that listed A first with the others (§4.3). The test spans zero with an interval half-width of about 2.7 pp (reader's arithmetic); it excludes large effects, not small ones.

### F6 · observation · undisclosed-skill-substitution · E2
- practice: observed in A+B runs; disclosure means the final reply says that more than one suitable skill exists, says which skill was used, or asks the user to choose, judged by the LLM output judge (§3.9).
- claim: "A substitution is almost never disclosed" (§4.3).
- evidence: in the 113 runs where B replaced A, the final reply says more than one suitable skill exists in 0%, names the skill used in 0.9%, and asks the user to choose in 0%. Over all A+B runs the reply names the skill in 7.7% and says more than one exists in 3.2%, mostly Opus 5 (21.0% and 9.4%); it never asks (§4.3).
- effect: hurts
- reader: numbers with nothing to compare against (no condition in which disclosure was requested), so E2. "Hurts" is the reader's reading of the paper's claim that undisclosed substitution is a defect; the paper measures only that disclosure is rare. Disclosure is not measured against any instruction that asks the agent to name the skill used.

### F7 · observation · model-differences-in-skill-choice · E3
- practice: observed; the same configurations are compared across Sonnet 4.6, Haiku 4.5 and Opus 5 (§4.3, Figure 5).
- claim: "The models differ sharply in every configuration" (§4.3).
- evidence: in A+B, Opus 5 uses both skills in 36.8% of runs and neither in 15.5%, Haiku 4.5 uses neither in 56.4%. Opus 5 reads A's files in 53.1% of personal-scope runs, where A is not listed (§4.3). Opening B first costs exclusive core functions 22.1 pp with Haiku 4.5, 12.1 pp with Sonnet 4.6 (not significant after correction) and nothing with Opus 5, which often reads both skills (§4.4).
- effect: mixed
- reader: a between-model comparison on the same pairs, without control for what else differs between models. One run per cell. The listing cap was set to 20,000 characters for all three models (§3.8), so the cap does not explain the gap.

### F8 · observation · first-read-decides-skill-conflict · E3
- practice: observed in the A+B and swapped runs. The first read of a skill is the first tool call that invokes it through the Skill tool or reads or runs a file in its directory. Where the two configurations open different skills first, B-first is compared with A-first within the same pair and model (§3.9).
- claim: "A conflict is decided at the first read of a skill", which in most runs comes before any file is changed; what is lost is what only A asks for (§4.4, Finding 5).
- evidence: 79 pair-model combinations (63 pairs); runs look alike up to that read (median 6 against 6 tool calls). B-first fulfils 9.4 pp fewer exclusive core functions [−15.0, −4.0], Holm-adjusted p = 0.004, and 7.5 pp fewer applicable ones. 97% of runs that open B first change no file before the first read (§4.4, Figure 6a). Of the core functions fulfilled with only A, 37% of the exclusive ones are lost against 8% of the shared ones; each exclusive core function adds 1.9 pp of loss [0.9, 2.9] (§4.4).
- effect: hurts
- reader: E3 because which skill a run opens first is observed, not assigned (§6 says so). The 79 combinations are the ones where the two configurations happened to flip, a selected subset of the 312 pairs times 3 models.

### F9 · practice · first-read-guard-hook · E4
- practice: a pre-tool hook that denies the first read of B while A is unread, tells the model to use A without naming any core function, and denies B once A is in use. Tested on the 187 pair-model combinations (119 pairs) where the model opened B first in the main run, each run once with and once without the hook in random order (§3.9, Table 3: 670 runs).
- claim: the hook "brought fidelity on the exclusive core functions back to the level of runs that open A first, with a significant gain for every model" (§4.4, Finding 5, abstract).
- evidence: after a denied first reach for B the model switched to A in 96% of 179 cases (Sonnet 4.6 94%, Haiku 4.5 96%, Opus 5 99%). Over all runs the hook raised fidelity on exclusive core functions by 9.1 pp [+6.0, +12.1] and on all applicable ones by 6.6 pp [+3.9, +9.2]. Where both runs of a combination reached for B first the gain was 17.8 pp [+12.8, +22.8]; per model 17.4, 20.7 and 12.8 pp. Redirected runs against no-hook runs that opened A first: 0.0 pp [−10.2, +10.3]. Task completion changed +4.1 pp [−1.3, +9.6] (§4.4).
- effect: helps
- reader: E4: the hook is randomised per combination on equal cases, and it is the only intervention in the paper. The authors designed and evaluated their own guard, and the test population was chosen from runs where B had been opened first, so the effect is conditional on that. The hook names A in its message, so it works only where a platform or user already knows which skill must win; the paper does not test a hook for a pair where no preferred skill is declared. Claude Code only.

### F10 · practice · distinctive-skill-names-and-descriptions · E0
- practice: skill authors give a skill a distinctive name and a description that states its specific tasks (§5.3).
- claim: a distinctive name "avoids overrides by the platform" and a specific description "reduces the chance that a request meant for another skill is routed to it" (§5.3).
- evidence: no test of this advice. Related evidence only: the platform's override rule applies to same-name skills (§4.3, Table 1), and below a description similarity of 0.9 only 10% to 37% of cross-project pairs in each band are confirmed as the same job, so similar wording does not imply the same job (§3.4).
- effect: helps
- reader: the claim is the authors' recommendation; no run varies name or description specificity, apart from the one-character rename of B in F5, which moved use of A by +4.4 pp.

### F11 · practice · prune-duplicate-skills · E0
- practice: a user audits the personal skills directory for skills that override project skills, and a project that copies a whole skill collection removes skills that duplicate ones it already installs (§5.3).
- claim: this reduces the pairs that can conflict, since copied collections "bring many pairs" (§5.3).
- evidence: no test of the removal. The prevalence numbers in F1 describe how many such pairs exist (37% against 19% in copy-collection projects, §4.1).
- effect: helps
- reader: advice derived from F1 and F4, never applied in a run. Whether pruning keeps the skills a user wants is not examined.

## Limits stated by the authors

- Each combination of model, configuration and pair ran once, a single-sample pass@1; 512 combinations rerun two or three times agree on use of A in 88.9% of comparisons (intraclass correlation 0.78) and on core-function fulfilment with an intraclass correlation of 0.84 (§3.8, §6).
- Which skill a run opens first is observed rather than assigned (§6).
- The full design runs on Claude Code only, because it costs about $5,550 on one platform; a Codex check on 193 pairs shows effects of similar size (§3.1, §6).
- Cross-project pairs are constructed; within-project pairs show the same drop (§6).
- Prevalence estimates are conservative: public repositories rarely show personal skills and plugins, and the pair judge sees only the most similar candidate (§1, §4.1).

## Reader's notes

- LLM judges do most of the work: GPT-6 Astra types repositories, judges pairs, labels skill types, extracts and labels core functions, drafts the cases and checks, and judges 594 of the 921 primary core-function checks and almost all task-completion checks (§3.2 to §3.9). The two human raters, who are authors, agree with the LLM at Krippendorff's α of 0.71 to 0.84 on 30 to 100 samples per step (§3.10). Judge and raters check the same extracted core functions, so a systematic extractor bias would pass through both.
- The scripts alone give a larger loss than the judge (4.2 pp against 1.2 pp, §4.2). The judge-decided part of the effect is small.
- Fidelity counts only the first three applicable core functions, ranked by the wording of the skill. The loss grows when more are counted: 1.7 pp with one, 2.6 pp with three, 4.1 pp with all applicable (§4.2). The headline 2.6 pp is a design choice made before runs, not a ceiling.
- Skills are one request each, run offline in a fresh container with at most 80 turns and 25 minutes; 113 of 5,162 runs timed out (§3.8). Real sessions carry a longer context and a user who can notice a substituted skill.
- The cases never name a skill and carry no agent-addressed instructions in the repository (§3.7), so the agent chooses from descriptions alone. A user who names the skill in the request is not covered.
- The listing cap was raised to 20,000 characters (measured defaults: 8,000 for Sonnet 4.6 and Haiku 4.5, 6,000 for Opus 5) because 95.8% of Opus 5 listings under the default would lose at least one of the two descriptions (§3.8). In a default install some conflicts may instead be a missing description, which the study removes.
- The paper's subject is skills, not instruction files or hooks in general. Its one repeatable method for a team is F9, a hook on a skill's first read.
