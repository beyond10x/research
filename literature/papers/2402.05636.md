## Question

Do ANZ engineers feel positive about GitHub Copilot, and does it make them faster and the code better
and more secure, measured in a six-week experiment before a wider rollout (§3)?

## Findings

### F1 · practice · ai-tools-allowed · E4
- practice: enable the Copilot extension in Visual Studio Code for half of the participants and disable it for the other half, then swap the halves between week 3 and week 4; both arms solve the same algorithmic Python problems, 6 per week and 12 in total, and the control arm may search the internet and use Stack Overflow (§3). Time per problem is self-reported in minutes.
- claim: Copilot users were "42.36% faster" than the control group, "statistically significant" (§5.2); "Copilot improves the productivity of ANZ engineers by 42.36% on an average" (§4.9.1).
- evidence: Table 1, mean time 30.98 minutes control against 17.86 Copilot, median 20 against 10, 1st quartile 15 against 5, 3rd quartile 35 against 20, max 150 for both. Wilcoxon signed rank, one-sided, alpha 0.05: sample size 22, W = 26, p = 0.001 (Table 2). The 42.34% is (30.98 − 17.86) / 30.98 (§4.9.1). 172 of 200 data points analysed; 6 duplicates and 22 unsolved problems removed (§4.7).
- effect: helps
- reader: random halves with a swap is a control on equal tasks, so E4. Time is self-reported and participants were not monitored (§3); the arm is known to the person reporting. The 22 unsolved problems were dropped, and their split by arm is not given. The test sample size of 22 is not explained against 172 data points. The 42% is a ratio of mean times, not a mean of per-person changes. The tasks are short algorithmic problems with an inline completion tool, not agent work on a repository.

### F2 · practice · ai-tools-allowed · E4
- practice: as F1; the measurement is the unit test success ratio of the submitted solutions, graded by the experiment team (§3, §4.4).
- claim: Copilot group code had "12.86% more success ratio ... However, this result is not statistically significant" (§4.9.2).
- evidence: Table 2: sample size 17, W = 98, p = 0.060, decision column reads "H1 rejected". The text gives 12.86% and no group means.
- effect: none
- reader: E4 by the same design. At alpha 0.05 the p-value of 0.060 is no detected difference, which the text states in §4.9.2. The abstract and §5.2 nevertheless say "notable boost in productivity and code quality". With 17 pairs and one-sided testing, a null here is weak evidence of no effect. Whether graders knew the arm is not stated.

### F3 · practice · static-analysis-defects-with-ai-tool · E4
- practice: as F1; the measurement is the count of bugs and code smells that SonarQube reports on the submitted solutions (§4.3).
- claim: "The code produced by Copilot participants contained fewer code smells and bugs on average, meaning it would be more maintainable and less likely to break in production"; "statistically significant" (§5.2).
- evidence: Table 2, Bugs: sample size 17, W = 0, p = 0.033. Code smells: sample size 17, W = 10, p = 0.007. The counts per arm are not in the text.
- effect: helps
- reader: E4 by design, graded on the claim that Copilot code had fewer SonarQube findings. The authors state the tasks were atomic and short, "there was little room for bugs and vulnerabilities to exist" (§5.1), so the counts are small; with no counts given the size of the difference is unknown. "Less likely to break in production" is the authors' inference from static findings, not measured.

### F4 · practice · ai-assisted-code-vulnerability-scan · E2
- practice: scan solutions with SonarQube for vulnerabilities; one security question per week of the A/B phase, a PBKDF2 password hash with a random salt and a FastAPI endpoint that must check a command parameter against injection (§4.9.3).
- claim: no conclusion on security is possible, but "the data suggest that Copilot did not introduce any major security issues into the code" (§5.2).
- evidence: "The SonarQube code review generated only 1 non-zero data point against Vulnerabilities. There is not enough data available to test this metric." (Table 2). Abstract: "its impact on code security remained inconclusive".
- effect: none
- reader: E2 because there is one non-zero data point and nothing to compare against. The reassurance in §5.2 is not supported by a test; the paper itself calls the result inconclusive. The authors say participants found the password question hard and attempted it less (§5.1).

### F5 · observation · seniority-and-ai-speedup · E3
- practice: none applied; the time comparison of F1 is split by self-reported Python proficiency, with Novice merged into Beginner and Expert into Advanced because they have few participants (§4.9.1, Table 3).
- claim: Copilot "was beneficial to participants for all skill levels"; Beginners gained the most (Table 3, §4.9.2).
- evidence: Table 3, mean minutes per problem control against Copilot, improvement: Beginner 20.07 against 9.58, 52.27%; Intermediate 28.60 against 16.70, 41.6%; Advanced 39.82 against 23.70, 40.48%. Proficiency counts in Table 1: Beginner 10 and 9, Novice 4 and 3, Intermediate 40 and 51, Advanced 22 and 22, Expert 6 and 5 (control and Copilot). No test per subgroup.
- effect: helps
- reader: E3, subgroup comparison inside the randomised data with no test and no interaction term. Proficiency is self-reported. Mean time rises with proficiency in both arms, which may reflect harder problems chosen by stronger people or reporting differences. The text of §4.9.1 says the gain was largest for "Expert" programmers, which Table 3 does not show (see Discrepancies).

### F6 · observation · task-complexity-and-time-saved · E3
- practice: none applied; the time comparison is split by the participants' rating of the problem as Very Easy, Easy, Medium or Hard (§4.9.1, Figure 4).
- claim: "For all code challenge levels from 'Very Easy' to 'Hard', the Copilot group spent less time on average than Control group"; the largest improvement was on Hard tasks (§4.9.1).
- evidence: the values are in Figure 4 only. Counts per level, control and Copilot (Table 1): Very Easy 11 and 11, Easy 52 and 59, Medium 15 and 14, Hard 4 and 6.
- effect: helps
- reader: E3 with no statistic. The Hard cells hold 4 and 6 data points, so "largest improvement on Hard" rests on 10 observations. Difficulty is rated by the participant, who knows the arm.

### F7 · practice · ai-tool-introduction-attitude · E2
- practice: let participants use Copilot on the proposed use cases for weeks 1 and 2 and survey them every second day (§3, §4.2).
- claim: "Across all areas, participants responded positively"; the sentiments were "uniformly positive in valence" but "all moderate" (§4.9.4, §5.2).
- evidence: Table 4, median responses: debugging time "A bit less time", time without Copilot "A bit more time", alignment with project coding standards "Well", suggestion quality "Somewhat helpful", effect on reviewing and understanding code, creating unit tests and creating documentation "Positive effect". No number of respondents or responses is given.
- effect: helps
- reader: E2, medians with nothing to compare against; the baseline survey is not reported against the later ones. The authors say volunteers were probably enthusiastic about the tool (§5.1). The sentiment is perception, not measured time.

### F8 · practice · org-wide-rollout-after-trial · E0
- practice: after the experiment, recommend and roll out Copilot to the engineering organisation; about 1,000 engineers use it (§5.2).
- claim: "Early data from 1000 engineers also indicated a significant increase in productivity and job satisfaction" (Abstract).
- evidence: none in the text. §5.2 says "a detailed investigation into the productivity improvements attributable to GitHub Copilot is underway".
- effect: helps
- reader: E0, the claim only. The abstract and contributions list the post-rollout validation (§1) but the body holds no data for it.

## Limits stated by the authors

- Participation fluctuated across tasks, and the roughly 100 engineers are a fraction of about 5,000 (§5.1).
- Some questions, such as the password question, were hard and received fewer attempts (§5.1).
- The tasks were short and atomic, so static analysis could not measure bugs and vulnerabilities reliably; a project-style task would suit better (§5.1).
- Self-reported proficiency may be biased (Dunning-Kruger) and time may be under-reported; the authors assume the same bias in both groups (§5.1).
- Sentiment may be inflated because volunteers were interested in the tool (§5.1).
- Participants were not monitored; time is self-reported (§3).

## Reader's notes

- The authors work for the adopting organisation and the paper ends with a recommendation to productionise (§5.2). They are not the tool's vendor. Both the experiment team and the authors have a stake in the result.
- The crossover swaps the halves between weeks, and each week has different problems. The paper does not say which half used Copilot first, nor test for a week effect.
- The control arm could search the web, which is the normal baseline, but the paper does not report whether the Copilot arm also did.
- Solutions the participants could not solve were removed (22 of 200, §4.7). If Copilot changed which problems were abandoned, that selection biases the time result. The split by arm is not given.
- Table 2's sample sizes (22 and 17) are smaller than the 172 data points; the pairing and the unit of analysis are not described.
- The model behind Copilot, the Copilot version and the date of the data pull are not stated. The paper is about inline completion, not an agent that runs tasks unattended.
- The security design (two questions, static analysis only) could not produce a finding. No security conclusion should be taken from this paper.
- The Wilcoxon signed rank test was chosen over Mann-Whitney because the same people appear in both arms (§4.8); how the pairs were formed per person is not stated.

## Discrepancies

- The overall improvement is 42.34% in the formula (§4.9.1) and 42.36% in the sentence after it and in §5.2.
- §4.9.1 says Copilot was "most helpful for those who were 'Expert' python programmers"; Table 3 has no Expert row (merged into Advanced) and shows Advanced with the smallest improvement, 40.48%, and Beginner with the largest, 52.27%. §4.9.2 says Beginners received the highest benefit.
- The abstract says results "showed a notable boost in productivity and code quality"; §4.9.2 says the unit test success difference "is not statistically significant", and Table 2 gives p = 0.060 with "H1 rejected".
- §4.7 says the 172 data points were "used for all the statistical analysis"; Table 2 reports tests on 22 and 17.
- §4.6 describes Table 1's observations as "significantly less" for Copilot on mean, median and quartiles, with no test attached to those statements; Table 1 gives the same maximum, 150, for both arms, while §4.7 says the Copilot range is "much smaller".
- §3 says participants were "divided randomly in half"; §5.1 says the groups had "the same composition using a random selection process within each experience level".
- The abstract and §1 offer "initial findings" and "initial validation" from about 1,000 engineers; §5.2 says the investigation of those productivity gains is still underway, and no data is shown.
