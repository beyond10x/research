## Question

How should agents be organised so that scientists can verify and understand the code they write: which orchestration pattern, which way of enforcing limits, and which model give the lowest cost per translated file under human specification, a numerical oracle and human approval gates (§1, §3)?

## Findings

### F1 · practice · author-reviewer-loop-instead-of-parallel-subagents · E3
- practice: run one author agent and one reviewer agent in a loop of at most 5 cycles (CodeScribe, runs R4 to R6 and R9 to R11), instead of a Claude Code multi-agent workflow with parallel author subagents and one serial integrator (R1 to R3), on the same task, spec, plan and tools (§2.4, §3.2).
- claim: "a simple author–reviewer loop with enforced limits completed a comparable number of files to a multi-agent workflow at about one-third of the cost per file" (abstract); "The loop was cheaper than the multi-agent workflow overall" (§4.2).
- evidence: Table 2, cost per file settled in USD: workflow 2.58, 2.91, 1.98 (files 13, 15, 16); CodeScribe with Opus 5 1.05, 0.95, 1.07 (files 15, 14, 12); CodeScribe with GPT 5.6-Sol 1.60, 1.07, 1.01 (files 4, 9, 10). Minutes per file: workflow 6.4, 4.6, 5.5; Opus 5 loop 2.9, 3.0, 3.1. The two Sonnet 5 loop runs cost 1.94 and 2.09 per file for 3 files each.
- effect: helps
- reader: E3 because the two arms differ in orchestrator, base agent and execution policy together, as the authors say (§3.2: "cannot isolate the effect of either factor"). The authors built both arms and the workflow was written "with minimal supervision" (§2.4). 3 runs per arm, with different models inside the loop arm. Costs are list prices (§4.1). The ratio from Table 2 for Opus 5 runs is about 0.4 (reader's arithmetic), so "one-third" holds only at the best pairing; see Discrepancies.

### F2 · practice · author-reviewer-loop-instead-of-parallel-subagents · E4
- practice: the same author-reviewer loop run in Claude Code with Opus 5 (ccloop, R12 and R13), against the multi-agent workflow in Claude Code with Opus 5 (R2); agent and model held fixed, only the pattern varies (§3.2).
- claim: "The loop cost about 40% as much for the same deliverable, in about the same time per file" (§4.2); both runs "settled on the same files".
- evidence: Table 2, R12 against R2: files 15 and 15, total cost 17.76 and 43.68 USD, cost per file 1.18 and 2.91, minutes per file 4.6 and 4.6, tool calls per file 23.5 and 45.9. R13: 13 files, 24.50 USD, 1.88 per file, 6.3 minutes per file, 39.7 tool calls. Table 3 lists the same modules for R2 and R12.
- effect: helps
- reader: a one-factor contrast on equal tasks, so E4, but R2 is a single run and the text compares it with R12, the cheaper of the two ccloop runs. R12 was helped by Claude Code's memory from an earlier run (F9) and R13, run without it, cost 1.88 per file (0.65 of R2, reader's arithmetic). The loop arm was written with detailed supervision and the workflow arm with minimal (§2.4).

### F3 · practice · orchestrator-enforced-limits-over-prompted-limits · E3
- practice: enforce iteration caps, tool-call caps, repeated-failure rejection, a shell allowlist and read-only protection of human files in the orchestrator between model calls (CodeScribe), against the same limits stated only in the prompt of an unrestricted Claude Code loop (§2.4, §4.3).
- claim: "Agents bounded and checked by the surrounding system were more efficient and stayed within the execution policy, while agents governed only by prompt instructions did not. Reproducible, auditable, and predictably terminating runs therefore require enforced structure rather than prompted constraints" (§4.3).
- evidence: ccloop author phases "frequently ran past the bound, one reaching 67 iterations (limit 30)"; "csloop saw no phase exceed the bound or deviate from policy" (§4.3). Table 2, Opus 5 runs, cost per file: CodeScribe 1.05, 0.95, 1.07; Claude Code loop 1.18, 1.88. Tool calls per file: 29.9, 25.3, 27.5 against 23.5, 39.7. No count of phases that exceeded the bound is given beyond the one case.
- effect: helps
- reader: E3. The arms differ in base agent as well as in enforcement (§3.2), and the authors wrote the CodeScribe orchestrator. Cost per file of R12 is 0.16 USD above the CodeScribe Opus 5 mean of 1.02 (reader's arithmetic) and tool calls per file were lower in R12, so the efficiency part of the claim rests mostly on R13. Enforcement had a cost: a blocked command costs an iteration, and the agent replaced a blocked `awk` with a Python one-liner (§4).

### F4 · practice · model-choice-in-author-reviewer-loop · E4
- practice: run the same CodeScribe loop with Sonnet 5, the cheaper-billed tier, instead of Opus 5 (§3.2, §4.4).
- claim: "The cheapest-billed model was therefore the least efficient per file settled" (§4.4).
- evidence: Table 2, Sonnet 5 runs R7 and R8: 3 files each, cost per file 1.94 and 2.09, minutes per file 11.6 and 11.5, tool calls per file 130.3 and 148.0. Opus 5 runs R4 to R6: 12 to 15 files, 0.95 to 1.07 per file, 25.3 to 30 tool calls per file. Sonnet 5 "spent much of their budget on retries, as their bash calls failed more often" (§4.1). R14 (Claude Code loop, Sonnet 5): 3 files, 1.12 per file, 1 of 5 cycles.
- effect: hurts
- reader: one factor varied on equal tasks, 2 runs of the cheaper model, so E4. R8 is marked incomplete with no agent log archived (Table 1), and the total cost is lower for Sonnet 5 (5.83 and 6.27 against 12.87 to 15.69), because the runs ended after 3 files. Per file cost is the paper's metric; the verified share of the 3 files is not given.

### F5 · practice · model-choice-in-author-reviewer-loop · E4
- practice: run the same CodeScribe loop with GPT 5.6-Sol through an OpenAI-compatible endpoint instead of Opus 5 (§3.2, §4.4).
- claim: "R10–R11 performed similarly per file to the Opus 5 runs at a similar token cost, though GPT 5.6-Sol used more tool calls"; "the results carry over to a different provider" (§4.4).
- evidence: Table 2, GPT 5.6-Sol runs R9, R10, R11: files 4, 9, 10; cost per file 1.60, 1.07, 1.01; tool calls per file 76.5, 42.3, 48.8; cache share 79, 82, 83% against 91 to 92% for Opus 5. R9 is the exception, with 4 files and 1.60 per file.
- effect: mixed
- reader: E4 by the same one-factor design, 3 runs. Files per run (4, 9, 10) are fewer than for Opus 5 (12 to 15), so "similar per file" hides lower output. GPT 5.6-Sol was billed at "discounted-period rates" (§4.1), which makes its cost comparison time-dependent.

### F6 · observation · parallel-fanout-repeats-context-reading · E0
- practice: nothing applied; the authors explain why the parallel multi-agent workflow cost more per file (§4.2).
- claim: "When many agents write files in parallel, each one gets its own copy of the same background material, so the text processed grows with the number of files attempted, while the number finished depends only on what survives the single integration step"; "Multiple parallel agents pay off only when the work and its context are independent" (§4.2, §5).
- evidence: no measurement of duplicated reading is given in the text. Input tokens per file are plotted in Figure 7e (values in the figure only). The authors state that "the reasons are specific to this task".
- effect: hurts
- reader: a mechanism proposed after the cost comparison of F1 and F2, with no test. The statement that the files "do not depend on each other" and are "small next to the material an agent has to read" is the authors' description of the task.

### F7 · practice · approval-gate-limits-work-ahead-of-review · E0
- practice: a gate script blocks opening a new group of files while 3 completed groups wait for human approval or while a waiting group has a failed file; only a human writes `approvals.toml`, and the agents can read it but not modify it (§2.2, §3.2).
- claim: "Hallucinated progress is contained by checks that the workflow must confirm before a file counts as verified"; "only a human can record the approval that lets the next stage proceed" (§1, §5).
- evidence: none; no run reports how often the gate blocked work, how many approvals were recorded or how long review took.
- effect: helps
- reader: described as a design principle (P1, P2), and the 14 runs ran through it, but nothing compares runs with and without it, and it is the only human step in the study. The multi-agent workflow "terminates only at the approval gate" (§2.4), so the gate also sets that arm's length.

### F8 · practice · independent-oracle-verification · E1
- practice: accept a translated file only when two checks pass: a coverage probe that perturbs the file and confirms the benchmark result changes, and agreement of the unperturbed file with the reference benchmark value within a tolerance; files no benchmark exercises are tagged translated but not verified (§3.1).
- claim: correctness is "measured directly" against the existing code, so progress the agent only reports does not count (§1, §3.2, §5).
- evidence: one case, §4.4 and §5. For the file `Mods/types_mod.f`, two incompatible translations of the kind constants (real types in two Opus 5 runs, plain integers in the other runs) "passed every test", because the converted code "used the type keywords directly wherever a kind was needed". The authors count such a file as settled. The agent's own checklist in `agent_log.md` is not used for counts because it "included files edited only to update the build system" (§4.1, no number).
- effect: mixed
- reader: the oracle is the study's measure, so its misses cannot show in the results. The case shows a correct-by-oracle translation that the authors call a gap in the specification. The settled counts in Table 2 include "units whose Fortran original was left in place" and do not separate verified from translated; no verified-only count is given.

### F9 · observation · cross-run-agent-memory-carries-decisions · E1
- practice: not applied; Claude Code's default memory directory outside the lab notebook was left on for R1 to R3 and R12 and purged before R13 and R14 (§4.3, §4.5).
- claim: the memory of R1 "helped R12 skip the Mods/ directory", so R12 "finished faster and at lower cost"; one note "influenced agent decision-making in three later runs without leaving a trace in our records"; "a mechanism that can introduce a correct assumption across runs can introduce an incorrect one the same way" (§4.3, §5).
- evidence: R1 flagged `types_mod.f` for human review and wrote a no-op for it in memory; "every later Claude Code run skipped the file and the Mods/ directory entirely"; R13 and R14, after the purge, processed Mods/ and the file (§4.5, Figure 8). Table 2: R12 1.18 USD per file and 4.6 minutes per file, R13 1.88 and 6.3. All CodeScribe runs started fresh and translated the file (§4.5).
- effect: mixed
- reader: nobody assigned the memory condition, so this is an observation from the order of runs. The earlier run's flag was a correct human-review call and the later skipping lowered cost, but the same mechanism left 3 files per run unprocessed in Mods/ and is untraceable in the logs. Table 3 shows R1 settled 3 files in Mods; R2, R3 and R12 settled none.

### F10 · observation · spec-gap-diverges-across-runs · E1
- practice: not applied; the specification said nothing on how to represent the Fortran kind parameters `sp`, `dp`, `ex`, `qp` in C++ (§4.4, §5).
- claim: "A gap in the shared specification ... left the C++ representation ... unresolved, and two incompatible answers ... were produced by the models"; "a mistake in that layer affects the outcome of every run" (§5).
- evidence: two of three Opus 5 runs wrote real C++ types (`float`, `double`, `long double`, `__float128`); the third Opus 5 run and all three GPT 5.6-Sol runs wrote plain integers (4, 8, 10, 16); one GPT run copied the precision arguments 6, 15, 18, 33 as values. All passed every benchmark test (§4.4).
- effect: hurts
- reader: one file in one codebase. The result says that oracle-passing code can still differ between runs on an unspecified decision; the paper does not say which answer a domain expert would accept. The first Claude Code run was the only one that caught the gap, by flagging it (F9).

### F11 · observation · file-selection-agreement-across-models · E2
- practice: not applied; deterministic tools under `dev/tools` score each file by dependencies, parser blindness and fan-in from a Doxygen call graph, and the agent picks among ready files (§4.5).
- claim: "all fourteen runs picking files in nearly the same order and settling on largely the same files, regardless of which model or orchestrator ran them"; "The models had little impact on which files were picked" (§4.4, §4.5).
- evidence: Figure 8 (times in the figure only) and Table 3, files per module BDK, Mods, W2jet: R4 0, 4, 11; R7 0, 3, 0; R9 0, 0, 4; R12 5, 0, 10; R13 0, 3, 10. All runs drew on the same 3 modules. At the start only a handful of ready files had fan-in above one, so convergence is "expected" (§4.5).
- effect: none
- reader: no run without the ranking tool, so the tool's share cannot be separated from the small candidate pool, which the authors say explains it. Table 3 shows module mixes that differ between runs; no file-level overlap number is given. The text names the first Claude Code run as the one whose note changed 3 later runs (F9), which weakens "regardless of orchestrator".

### F12 · practice · human-owned-spec-and-plan-read-only-for-agent · E1
- practice: keep a human-written specification (`desired_spec.md`), plan (`current_plan.md`), approvals and loop configuration in a versioned directory tree outside any orchestrator, with the agent allowed to write only `agent_log.md`; the plan repeats seven fixed topics per round (what to do each round, the log format, approval checks, tools, selecting units, verification, when to stop) (§2.2).
- claim: the shared state "is what lets the same task be rerun under a different orchestrator", and a transformation "can be paused, resumed, or handed to a different orchestrator or a teammate" (§1, §2.2).
- evidence: one case. The 14 runs of §3.2 used the same inputs under 3 configurations. The plan is described as "similar to a skill, but it applies only to a specific transformation" (§2.2). No run compares this layout with another.
- effect: helps
- reader: the claim is shown by the study having run, not by an outcome measure. The same layer also carried the spec gap of F10 into every run (§5).

## Limits stated by the authors

- The study compares variants on a single task, the translation of MCFM (§5).
- A single observation per condition cannot separate an orchestrator or model effect from run-to-run variance; R2 and R14 were run once (§3.2).
- The ccworkflow and csloop arms differ in pattern and base agent, so they cannot isolate either factor (§3.2).
- Costs are list prices; the runs used different billing (§4.1).
- A memory note from an earlier run influenced three later runs and left no trace in the records: "The oversight was ours" (§5).
- Open problems named: the format of the model API, agent execution policy, and exposure of reasoning traces (§5).

## Reader's notes

- The authors built the orchestrator (CodeScribe), the lab notebook, the tools and both workflow scripts, so every comparison is of a system against a baseline the same authors wrote. The loop arm had detailed supervision and the workflow arm minimal supervision (§2.4).
- "Files settled" counts files landed on the branch, including units whose Fortran original was left in place. How many of them pass the two-part oracle is not given (Table 2).
- Cost per file divides by files settled, so a run that settled 3 files (R7, R8, R14) has a noisy denominator.
- Cache share and per-token prices differ by provider and by orchestrator; CodeScribe sets cache breakpoints, Claude Code does not (§2.4, §4.4).
- Human review time, approvals and the review the gate waits for are not measured, although the title and abstract centre on human review.
- The Figure 6 transcript carries the run id `20260724-020711-dd1c55`, a date earlier than all run directories in Table 1; the text says it is an excerpt of a CodeScribe run.

## Discrepancies

- The abstract and §5 say about one third of the cost per file. §4.2 says "about 40%" for R12 against R2. From Table 2 the Opus 5 loop runs cost 0.95 to 1.07 per file against 1.98 to 2.91 for the workflow, ratios from 0.33 (0.95 against 2.91) to 0.54 (1.07 against 1.98); the mean per file is 1.02 against 2.49, 0.41 (reader's arithmetic).
- The abstract says the loop "completed a comparable number of files". Table 2 shows 12 to 15 files for the Opus 5 loop and 13 to 16 for the workflow, but 3, 3 and 4 files for the two Sonnet 5 runs and R9.
- §4.5 groups R1 with R2, R3 and R12 as Claude Code runs that skipped Mods/ files, while Table 3 shows R1 settled 3 files in Mods and §4.5 says the first Claude Code run only flagged the precision-kinds file.
