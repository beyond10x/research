## Question

Which property of a spec-first agent framework keeps agent-written code clean, correct and
maintainable: how it states the specification, or how it enforces engineering discipline on the agent
once the specification exists (§I, §III)? The paper argues for the second and introduces Consort as
the framework that enforces through controls the agent cannot edit.

## Findings

### F1 · practice · deterministic-orchestrator-routing · E0
- practice: sequence the work with a state machine written as code instead of an LLM control loop. It cuts a database branch per unit of work, drives red, green and refactor, enforces the order of the human gates, and writes no spec, code or tests. The scrum-master role is this code (§IV-B, §IV-C).
- claim: routing as code "cannot be lost across context compaction" and cannot "drift or be argued out of a step", which an LLM control loop can; all four comparators had an LLM control loop at the time of drafting, and BMAD has since added a code-driven one (§IV-B, §V-A, Table I).
- evidence: none; the claim is argued, and Table I classifies each framework's orchestration as deterministic or LLM with no run or count behind it.
- effect: helps
- reader: E0, because no run of any framework is reported. The author builds one of the frameworks compared. The failure it names (a control loop lost across compaction) is attributed to superpowers in §II.D without a case or a citation.

### F2 · practice · protected-test-files · E0
- practice: lock the approved test list within a unit of work so that an in-cycle attempt to delete or weaken a test is caught and flagged. One bounded exception: when a later story supersedes an earlier test, a designated step refactors only the flagged tests under an explicit rule and re-verifies. A failing ordinary test is repaired in code, never in the test (§IV-D, Figure 2).
- claim: "immutability answers the test-deletion failure mode"; only Consort holds tests immutable, so elsewhere "a green result certifies nothing" (§IV-D, §V-A).
- evidence: none for the effect. The failure it answers is cited from others: agents disable or delete tests to turn a suite green (§II.C, citing Beck's newsletter, ref [2]). Table I marks the comparators No or n/a on test immutability.
- effect: helps
- reader: E0. The check that catches a weakened test is not described beyond "caught and flagged", so what it detects (deletion, assertion edits, skips) is not stated. The supersession exception re-opens the edit path it closes.

### F3 · practice · green-recorded-by-test-runner · E0
- practice: record success only when a test runner actually passes against a real branch, not when the agent reports it. Failed verify routes to a bounded code repair or, for a superseded test, to the rule-bound exception; unresolved cases go to the human (§IV-D, Figure 2).
- claim: "honest-green" answers inaccurate self-reporting, because "the record of success is the runner's, not the agent's" (§IV-D).
- evidence: none for the effect. The misreporting it answers is cited: agents "report inaccurately what they actually did" in a substantial share of episodes across 20,574 real-world sessions (§I, §II.C, ref [20], title).
- effect: helps
- reader: E0. It stops a false report, but a runner that passes weak tests still stamps green; the paper relies on immutability (F2) and real data (F4) to cover that and shows neither working.

### F4 · practice · tests-against-live-database-branch · E0
- practice: run the whole test-driven cycle, including the fast inner loop, against a copy-on-write branch of a production-shaped database, cut fresh for each verify and discarded afterwards, instead of mocks or synthetic seeds (§IV-A, §IV-E).
- claim: green then requires code that works against real data under the database's constraints and governance, and the agent cannot substitute "a compliant mock for real behavior"; this is "the structural counter to the over-mocking that agents otherwise exhibit" (§IV-E).
- evidence: none in this paper. The mechanism, cost and defect-catching evidence are in an unpublished paper under anonymous review taken "as given" (§I, §IV-A, ref [11]). The over-mocking it answers is cited from a commit-history study (§I, ref [12]).
- effect: helps
- reader: E0 here; the evidence is said to exist elsewhere and is not available to check. Needs a database that supports copy-on-write branching, which the paper lists as a cost (§VII). No comparator has a database in the loop, so Table I cannot show a contrast.

### F5 · practice · role-specialised-agents · E0
- practice: persistent named role agents with a bounded function and no shared memory, passing work through on-disk artifacts: product owner, spec author, architect reviewer, DBA, test strategist, navigator (test-facing steps), driver (code-facing steps), and a UX designer for user-facing work. The agent that writes the code is never the one that judges it (§IV-C, Figure 2, Table I "Eight named roles").
- claim: separation guards integrity ("an agent that both writes code and judges it has every incentive to grade generously") and is "where maintainability comes from"; "the mechanism is role specialization, not enforcement alone" (§IV-C).
- evidence: none. The maintainability claim is stated as the pre-registered hypothesis of §VI, with no result. The comparison with a single generalist rests on an analogy to human teams (§IV-C).
- effect: helps
- reader: E0. The paper separates the integrity claim from the maintainability claim and calls only the second one a hypothesis. The paper's own hypothesis (§VI) bundles four properties, so a future result would not isolate role separation.

### F6 · practice · spec-and-test-list-frozen-per-increment · E0
- practice: freeze the specification and the test list at a hashed human gate for the length of an increment, check them for drift, and evolve them only across increments under a human re-plan (§IV-F, §V-A). The orchestrator also stamps each experiment with a fingerprint of its design and recuts a stale one (§IV-B).
- claim: "editable and able-to-launder-a-failure are the same property" for a non-deterministic author, so a living spec lets the agent drift the spec to match what it built; a frozen one cannot (§V-A).
- evidence: none. Table I marks the spec as editable, model-editable or living in all four comparators and hashed in Consort.
- effect: helps
- reader: E0. A frozen spec trades off against changing requirements during an increment; the paper offers a re-plan across increments and gives no cost. The claim that agents drift specs is not backed with a case or citation.

### F7 · practice · stage-gated-spec-workflow · E0
- practice: gate every decision on a human approval before the work advances: intake, plan, backlog selection, spec and test list, per-story acceptance, deploy, promote (Figure 1, §IV, §V-A). The product owner can mark a story as requiring an end-to-end test that the design lane cannot downgrade (§IV-D).
- claim: "a gate is a control only if it can refuse"; advisory gates (prose, waivable pass-concerns-fail files, convention) "request compliance and can be passed by the agent or waived by the team" (§V-A).
- evidence: none. Table I classifies gates as required (Consort), code-enforced post-hoc (BMAD) or advisory (the other three).
- effect: helps
- reader: E0. A human gate at every decision is also the cost the paper concedes in §V-D and §VII (weight, not worth it for a throwaway prototype). No measure of approval load or latency is given.

### F8 · practice · fresh-turn-when-window-fraction-low · E0
- practice: the orchestrator tracks each session's token use against the model's window and starts the next turn fresh, reloaded from disk artifacts, when a warm resume would leave less than a configurable fraction free (40 percent by default); it keeps warm resumption otherwise to reuse the prompt cache (§IV-G).
- claim: context rot is bounded by code rather than by the agent staying disciplined; the comparators do it by convention (fresh-context subagents, sharded stories) (§IV-G, §V-A).
- evidence: none; the 40 percent default is stated with no tuning or result (§IV-G).
- effect: helps
- reader: E0. The paper names context degradation as the motive and gives no measurement of quality before or after the reset.

### F9 · practice · scoped-context-package-per-turn · E0
- practice: hand each agent turn a package with the exact tests it must pass, the relevant requirements and where those tests live, instead of the whole codebase (§IV-G).
- claim: it "lowers cost and removes the unscoped wandering that otherwise lets an agent drift" (§IV-G).
- evidence: none; no cost figure and no case.
- effect: helps
- reader: E0, one sentence in the paper. A narrow package can also hide the code the change needs; the paper does not address that.

### F10 · practice · cross-story-contract-check-before-code · E0
- practice: in the design lane, check cross-story field contracts before any code is written. When one story mandates a required field and the story that owns the user-submit path has no acceptance criterion supplying it, the lane flags the gap (§IV-D).
- claim: the gap is caught before the build, rather than letting "the feature reach a build that ships a form the database will reject" (§IV-D).
- evidence: one hypothetical example in the text; no real case and no count.
- effect: helps
- reader: E0, bordering on E1 but the example is illustrative and not reported from a run.

### F11 · practice · parallel-experiments-per-story-keep-best · E0
- practice: run several experiments for one story in parallel, each on its own database branch and git worktree, and keep the one that best satisfies the tests (§IV, end of §IV-A).
- claim: "an exploration only cheap branching makes affordable" (§IV-A).
- evidence: none; no number of experiments, no pass rate and no cost.
- effect: helps
- reader: E0. The selection rule is the tests, which are fixed by F2, so the practice picks among implementations that all pass; whether the winner is better in any other way is not claimed.

### F12 · practice · prose-rules-as-control · E0
- practice: put the discipline in instructions to the model (rules, red flags, prohibitions in prose, a "strong but unenforced" test-first rule) and leave orchestration, gates and the test suite editable by the model. The paper's exemplar is superpowers; Spec Kit's advisory constitution and optional ungated TDD sit in the front-loaded structure mode (§III, §II.D, §V-B).
- claim: persuasion "raises the floor on agent behavior, sometimes substantially" but "cannot make a violation impossible"; front-loaded structure is strong at intent and "the agent outruns" it once building starts; "a control that the worker can choose to ignore is not a control" (§III, §VIII).
- evidence: none. Qualitative descriptions of four frameworks from their documentation; the paper cites a hands-on review that finds the discipline "tends to evaporate once the agent begins writing code" (§II.B, ref [4]).
- effect: mixed
- reader: E0, a taxonomy and not a test. The author's own framework is the contrast, and the comparators' descriptions are the author's reading of their documentation, accessed July 2026 (refs [3], [10], [22]). The paper concedes BMAD changed during revision.

## Limits stated by the authors

- The output-quality claim is a hypothesis, not a result; §VI frames the controlled evaluation as pre-registered future work (abstract, §VI).
- The author builds one of the frameworks under test; the dual role "must be declared and mitigated" with framework-neutral tasks, independent reviewers and an invitation to replicate (§VI).
- The frameworks differ in harness portability, so the agent must be held constant to compare enforcement and not tooling; maintainability is a contestable construct to be fixed in advance (§VI).
- The scoring instrument (an LLM judge) ships with Consort and is part of the system under test, so using it unmodified would not be independent; five safeguards are proposed (§VI-A).
- The cited maintainability findings are "correlational and partly industry-sourced" (§I). Spec-driven development is "barely a year old" and a minority practice with open questions about delivery (§I).
- The database layer is the contribution of an unpublished paper under anonymous review and is taken as given (§I).
- Consort trades portability and lightness for verifiability, needs a database dependency and enforcement machinery, and is not worth carrying for a throwaway prototype; at the time of writing it was developed on Claude and is planned to become multi-harness (§V-D, §VII).

## Reader's notes

- No run of any framework is reported, so no finding reaches E1. Every finding is the author's argument, graded E0.
- Table I's cells are the author's reading of the comparators' documentation; the author is a party to the comparison. The "uncontested axis" (a database in the loop) is a property only Consort has by construction.
- The motivating failure modes (test deletion, over-mocking, misreporting, duplication, defects, delivery stability) are cited from other sources; none is a finding of this paper and none is graded here. 2602.00409 and 2605.29442 carry the over-mocking and misreporting data.
- The pre-registered hypothesis bundles four properties (immutable tests, deterministic gates, real-data verification, role agents), so even a positive result would not separate them. The paper itself says the mechanism is role specialisation "not enforcement alone".
- The proposed measures include silent-regression rate, test-gaming counted as tests deleted, weakened or adjusted, duplication and spec-to-code drift, real-behaviour coverage and tokens per shipped feature (§VI); no target magnitudes are asserted.
- The framework's source is public per the arXiv comment field, so the claims about code-level enforcement can in principle be checked in the repository; this was not done.

## Discrepancies

- §V opens by saying "Consort is the only one whose controls are enforced rather than requested"; §V-A (revision note after Table I) says that with BMAD's bmad-loop, "deterministic orchestration and code-enforced gating are no longer unique to Consort". The paper narrows the claim to in-cycle, immutable-test, real-data verification, but the opening sentence was not changed.
