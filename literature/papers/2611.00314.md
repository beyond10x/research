## Question

When two coding agents work in one repository on separate, independently written requirements and
do not see each other, how much joint correctness do they lose against one agent given both
requirements, and which of peer awareness, a message channel, hand-offs or post-hoc merging recovers
it, at what token cost (§1, §2)?

## Findings

### F1 · practice · parallel-agents-without-peer-visibility · E4
- practice: two agents each get one requirement and work at the same time from the same base, each told nothing about the other ("parallel unaware"); changes are merged afterwards and scored on both requirements' tests. Compared on the same instances with one agent given both requirements (oracle) (§3.2, Listings 1 and 2).
- claim: "performance drops dramatically in parallel settings", most sharply on contradictory tasks, where merged code "typically satisfies only one specification" (§4.1, abstract).
- evidence: Claude Opus 4.8 joint pass, oracle against parallel unaware: 62% against 16% on contradictory instances (p < 0.001, n = 50), 86% against 57% on complementary (p = 0.021, n = 35) (Table 1, Table 20). Six open-weight configurations, mean: 60% against 19% (6/6 significant) and 72% against 53% (4/6) (Table 2, Table 21). Parallel unaware costs 1.17 and 1.14 times the oracle (Table 1). In isolation, Opus agent A's patch passes 68% and agent B's 92% while the merged patch passes 16% (Table 10).
- effect: hurts
- reader: E4: same instances, same configuration. The oracle also differs in information (both requirements), so the contrast bundles missing information with missing coordination. Instances were filtered so that no naive merge of the two reference solutions passes (§3.1), which fixes a low floor for unaware agents by construction; the authors state the benchmark is diagnostic and not a prevalence estimate (Limitations). Opus parallel unaware passes 0% of the contradictory seed instances (n = 12) and 21% of the generated ones (Table 5).

### F2 · practice · sequential-handoff-between-agents · E4
- practice: the two agents edit one workspace in turn, A then B, each starting from the previous result and told "another agent has already worked in this repository before you ... Continue from that state" (§3.2, Listing 6).
- claim: "a single hand-off recovers much of the observed performance gap at comparable token cost" (§4.1); the authors add that turn-taking "becomes completely infeasible" with hundreds of agents (§4.1).
- evidence: Opus joint pass, A→B against parallel unaware: contradictory 54% against 16% (p < 0.001), complementary 77% against 57% (p = 0.065); cost 1.18 against 1.17 and 1.12 against 1.14 times the oracle (Table 1, Table 20). Six open-weight mean: 60% against 19% and 71% against 53%, 6/6 in both families, cost 1.06 and 0.96; contradictory A→B equals the oracle's 60% (Table 2, Table 21). Order B→A, open-weight: 46% against 60% (p < 0.001 pooled, 4/6); Opus 50% against 54% (p = 0.754) (Table 21, Table 20).
- effect: helps
- reader: E4 on equal instances. Requirement A is a SWE-Bench Pro task and B is written by the authors or a model, so A→B and B→A are not symmetric, which the open-weight order effect reflects. Two agents only; the authors give no result for more.

### F3 · practice · reentrant-second-turns · E4
- practice: four alternating turns (ABAB or BABA) instead of one hand-off (§3.2).
- claim: "reentrance costs significantly more and provides no discernible performance gains" (§4.1).
- evidence: Opus ABAB against A→B: 50% against 54% on contradictory (p = 0.727), 80% against 77% on complementary (p = 1.000); cost ratio 1.59 (p < 0.001) and 1.33 (p < 0.001) (Table 20). Open-weight mean: 52% against 60% (p < 0.001 pooled, 1/6) and 70% against 71% (p = 0.583); cost 1.84 and 1.79 (6/6 each) (Table 21).
- effect: hurts
- reader: E4. Cost rises and the pass rate does not; pooled significance on the open-weight contradictory drop comes from 1 of 6 configurations on its own.

### F4 · practice · peer-awareness-notice · E4
- practice: add one overlay sentence to the prompt: another agent is working in the same repository at the same time on a related requirement and its changes will not be visible (Listing 4, "aware").
- claim: "simply telling an agent that a peer exists does not help significantly" (abstract); awareness "marginally" improves performance (§4.1).
- evidence: Opus aware against unaware: contradictory 26% against 16% (p = 0.180), complementary 60% against 57% (p = 1.000), cost 0.97 and 1.06 times (Table 20). Open-weight mean: contradictory 19% against 19% (p = 0.890, 0/6), complementary 58% against 53% (p = 0.020 pooled, 2/6) (Table 21).
- effect: none
- reader: E4. The one place a test is below 0.05 is open-weight complementary; the text still reads it as no help. A different wording of the notice was not tried.

### F5 · practice · message-channel-between-parallel-agents · E4
- practice: give the parallel agents `./send-msg` and `./recv-msg`, framed either as free-form messaging (check at least before interface decisions and before finishing) or as sync points (send plan, read peer's, send after each change, confirm before finishing); the channel is an append-only file or a Redis inbox (§3.2, Listing 4).
- claim: communication "improves joint success at a higher token cost, but leaves a substantial gap" to the communication oracle on contradictory tasks (§4.1).
- evidence: Opus against aware: message 20% against 26% on contradictory (p = 0.453), sync 22% against 26% (p = 0.688); complementary 63% and 71% against 60% (p = 1.000, p = 0.344); cost ratios 1.25 and 1.43 on contradictory (p < 0.001) (Table 20). Opus Redis sync against unaware: 32% against 16% (p = 0.039), cost 1.90 (p < 0.001); Redis sync against file sync 32% against 22% (p = 0.125) (Table 20). Open-weight mean, message and sync against aware: contradictory 24% and 27% against 19% (p = 0.002 and p < 0.001; 1/6 and 2/6), complementary 66% and 64% against 58%; cost 1.32 and 1.55 (6/6 each); Redis sync against file sync 28% against 27% (p = 1.000) (Table 21). Sync against message: Opus 22% against 20% (p = 1.000); open-weight 27% against 24% (p = 0.111) (Tables 20, 21).
- effect: mixed
- reader: E4 on equal instances. Better on pooled open-weight pass rate, never significantly better for Opus except the Redis sync variant, and always significantly more tokens. Message and sync differ only in the prompt text, so the framing effect is not separable from how often each run reads the channel (F12).

### F6 · practice · reveal-peer-requirement-with-channel · E4
- practice: "communication oracle": as parallel messaging, but each agent also gets its partner's requirement verbatim and is told to solve both together, with a `--wait` option on receive (§3.2, Listing 5).
- claim: revealing the partner's task exceeds a channel alone, yet it remains below the single-agent oracle on contradictory tasks (§4.1); it works through ownership of the contested code (§4.2).
- evidence: Opus comm oracle against Redis sync: 56% against 32% on contradictory (p = 0.002), 83% against 77% on complementary (p = 0.727); against oracle 56% against 62% (p = 0.508); cost 2.74 times the oracle (Table 1, Table 20). Open-weight mean 48% against 28% (p < 0.001, 5/6), against oracle 48% against 60% (3/6) (Table 21). Opus contradictory oracle conversations: 85% assign an owner to the contested code, merge conflicts fall from 65% to 15% of runs, runs with an owner pass 61% against 29% without; in 15% one agent implements both and the other withdraws (App. M; §4.2 gives 67% to 18%).
- effect: helps
- reader: E4 for the first comparison. It no longer tests a decentralised setting, since agents see both requirements; the authors say so. The owner-versus-no-owner pass rates are an association inside one scenario, not assigned.

### F7 · practice · post-hoc-merge-reconciler · E4
- practice: after parallel work, resolve conflicts with a merge-resolver model (Qwen2.5-Coder 0.5B Merge Resolver from CooperBench) instead of concatenation or plain git merge; a scenario counts as passed if any of the three yields passing code (§3.3, App. N).
- claim: "changing the combination rule recovers some failures, but does not resolve the coordination failures" (§4.1).
- evidence: Opus parallel unaware, contradictory pass by concat, git merge, reconciler: 10%, 14%, 16%; complementary 51%, 54%, 54%; Redis sync 22% to 32% and 69% to 77%; no reconciler-over-merge difference significant (p from 0.062 to 1.000, n = 50) (Table 13, Table 14). Open-weight mean, contradictory unaware: concat 7%, git merge 9%, reconciler 19% (significant in 4/6); Redis sync 14% to 28% (6/6) (Table 15). Best open-weight parallel scenario with reconciler 28% against 60% for one hand-off; Opus parallel stays below 54% (§4.1).
- effect: helps
- reader: E4: three merge rules applied to the same agent runs. The reported pass rate is the best of three rules, so it bounds what a merge step could do, not what one deployed rule does. The effect is significant for open-weight configurations and not for Opus.

### F8 · practice · per-agent-test-access-in-parallel-runs · E4
- practice: each parallel agent gets the gold tests of its own requirement and a `./run-tests` command, and is told to make them pass (§3.2, Listing 7). Contradictory instances only.
- claim: "access to gold tests alone does not recover the oracle's joint success in the parallel setting" (§4.1).
- evidence: Opus joint pass, parallel with gold tests 38% against oracle with gold tests 98% (p < 0.001); parallel unaware 16% (Table 1, Table 20; no test stated for 38% against 16%). Each Opus side passes alone 98% and 98% while both merged pass 38% (Table 10). Open-weight mean 32% against 96% (6/6); parallel unaware 19% (Table 2, Table 21).
- effect: helps
- reader: E4 by the scenario design; the gain over unaware agents is read from Tables 1 and 2 and carries no test in the parts read. The practice raises the pass rate and is far from the ceiling, which is the paper's point.

### F9 · practice · sub-agent-delegation · E4
- practice: one agent gets both requirements and must delegate each to a separate sub-agent and do no implementation itself (§3.2, Listing 3).
- claim: not stated as a headline; it is a reference scenario in Tables 1 and 2.
- evidence: Opus against oracle: 58% against 62% on contradictory (p = 0.688), 77% against 86% on complementary (p = 0.375); cost 1.58 (p < 0.001) and 1.18 (p = 0.023) times (Table 20). Open-weight mean: 46% against 60% (p < 0.001 pooled, 4/6) and 59% against 72% (3/6); cost 0.66 and 0.55 times (6/6 and 5/6) (Table 21).
- effect: mixed
- reader: E4 on equal instances. Opus shows no pass-rate change and higher cost; open-weight configurations show lower pass rate and lower cost. The parts read do not say whether sub-agent tokens enter the cost (Claude Code's sub-agent tokens may not be in the harness total), so the lower open-weight cost may be an accounting effect.

### F10 · practice · edit-history-for-next-agent · E4
- practice: in sequential and reentrant runs, tell the acting agent that the earlier agent's edit history is available in `git log` and `git diff` (§3.2, Listing 6, "hist"), against the current file state only.
- claim: expected that history would discourage reversals; "surprisingly, history actually increases overwriting and redos" (§4.2, App. E).
- evidence: Opus A→B history against repo: contradictory 50% against 54% (p = 0.727), complementary 77% against 77% (p = 1.000) (Table 20). Open-weight mean 53% against 60% (p < 0.001 pooled, 2/6) (Table 21). With history, overwrites rise from 15% to 30% of handoffs and redos from 15% to 39% of reentrant runs (both p < 0.001); git checkout or revert in 31% of redos with history against 7% without (§4.2; configurations covered not stated there).
- effect: hurts
- reader: E4 for the pass-rate comparison; the overwrite and redo rates are textual-persistence metrics, not semantic ("textual persistence rather than semantic preservation", App. E). Opus differences are not significant; the drop is open-weight only.

### F11 · observation · integration-failures-dominate-parallel-runs · E2
- practice: observed: the authors hand-annotated every failing Claude Opus 4.8 run in the oracle and parallel scenarios with open coding, and split contradictory failures into competence (a patch fails its own tests) and integration (both pass alone, no combination passes) (§4.2).
- claim: "single-agent failures can be traced to capability shortcomings while multi-agent settings are bottlenecked by coordination failures" (§1).
- evidence: 92% of oracle failures are an implementation that diverges from the test requirements; 58% of contradictory parallel failures are integration failures, 98% of those with a git merge conflict; 53% of complementary parallel failures merge cleanly and diverge on a name, signature or data shape (§4.2). Counts of failures not given in the text.
- effect: hurts
- reader: E2: shares with no comparison group inside the finding. One annotator group, no agreement figure, Opus only. The competence versus integration split is by test result, so it is objective only for contradictory instances.

### F12 · observation · messages-read-after-first-edit · E2
- practice: observed: in the Opus message and sync runs (file and Redis) and the communication oracle, when messages are read relative to the recipient's first edit, and what the conversation contains, labelled by Claude Sonnet 5 (App. M).
- claim: agents "send early but read late"; "the main cause for coordination failure is ill-timing rather than unwillingness to reply" (§4.2, App. M).
- evidence: communication two-way in 94% of runs; first message before editing in 79% (contradictory) and 88% (complementary); 67% and 68% of messages ever read, 21% and 23% read before the recipient's first edit, 29% and 27% arrive after the recipient finished (App. M). 88% and 76% of conversations discuss the shared artifact, 59% and 74% reach a concrete agreement (App. M, §4.2). 61% of contradictory runs with a concrete agreement still produce a merge conflict and pass at 19% (App. M). Judge against author labels on 30 conversations: 90% agreement, Cohen's κ = 0.67 (App. M).
- effect: hurts
- reader: E2: shares and timings with no comparison. The causal reading ("ill-timing") is the authors' from transcripts. The prompt told agents to check the channel only "periodically, at least before you make interface decisions and before you finish", so late reads follow partly from the instruction (Listing 4).

### F13 · observation · sequential-overwrite-of-predecessor-work · E3
- practice: observed: in sequential runs, whether the second agent removes at least half of the lines the first agent added (an overwrite), and the pass rates with and without one (§4.2, App. E).
- claim: "sequential agents often overwrite their predecessor's work" (§4.2).
- evidence: first agent's added lines survive in 79% of contradictory and 95% of complementary runs; overwrites in 23% and 5% of handoffs. With an overwrite, the first agent's requirement passes in 37% of runs against 73% without; joint success 26% against 55% (§4.2).
- effect: hurts
- reader: E3: a comparison between runs grouped by an outcome-adjacent variable, not assigned; overwrites likely occur where the task is hard or the two requirements conflict. Which configurations the numbers cover is not stated in §4.2.

## Limits stated by the authors

- Two agents and a small dataset; no evidence on larger teams or longer workflows (Limitations).
- ParallACT is diagnostic, not a prevalence estimate: instances were selected to require coordination (Limitations).
- Coding only, because executable tests can check joint correctness; collaborative writing and open research are open (Limitations).
- Future work: n-agent scenarios and training agents to negotiate interfaces and edit ownership (Future work).

## Reader's notes

- 128 of 155 instances, including the second requirement B, its tests and its reconciliation solution, were written by GPT 5.6 Sol in Codex, checked by an audit pass of the same model and then by hand (App. B). The independence of the two tickets is a model judgement.
- The cost metric weights output at 5 and cache reads at 0.1, approximating Opus 4.8 rates, and is relative to each configuration's own oracle; costs are not comparable across configurations (§3.3). Cache-write tokens are dropped for the cross-configuration tables, so Opus costs differ slightly between Tables 1 and 8 (App. G, N).
- Claude Opus 4.8 ran only on the v1 instances (50 contradictory, 35 complementary), so its n is small: a 4-point gap is 2 instances of 50. The v2 instances are harder: open-weight contradictory oracle 72% on v1 and 43% on v2 (Table 4).
- Open-weight configurations run through vLLM with Claude Code reporting no cache reads and different harness token accounting (App. N); harness and model effects are not separated by the design.
- The merge-policy pass rate is the best of three rules (§3.3), so every parallel number in the tables is the most favourable merge outcome.
- Per-instance repeats are not stated in the parts read; the McNemar and Wilcoxon tests assume one outcome per instance and scenario.
- Seed instances (hand-built, n = 12 contradictory) are the hardest: Opus parallel unaware, aware and sync pass 0% on them (Table 5).
- The harness prompts are short and untuned (Listings 1 to 7); the paper does not test other wordings of the awareness or channel instructions.

## Discrepancies

- §4.2 reports that in the communication oracle conflicts "fall from 67% to 18% of runs"; Appendix M reports "from 65% to 15%".
- §4.1 concludes that open-weight awareness "alone does not help" (19% against 19%, 58% against 53%), while Table 21 gives p = 0.020 for the complementary difference pooled over configurations (2/6 on their own).
- §4.2 says communication is two-way "in at least 94% of runs"; Appendix M says "in 94% of runs".
- Table 1's caption says "85 instances", Table 2's family header says "n = 85" for contradictory instances only, and Tables 20 and 8 give n = 50 and 35 for Opus; the sets differ by configuration, as §3.3 says.
