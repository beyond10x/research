## Question

Can an interface that shows an agent's execution as a trace, lets the user fork from an earlier step,
and distils the fork's feedback into skills improve users' understanding of agent runs and the agent's
later success and cost (§1)?

## Findings

### F1 · practice · trace-and-correction-skill-distillation · E4
- practice: after each task, an LLM estimates whether the run and the user's feedback hold reusable knowledge, distils it into a patch of a skill pool (create, revise, merge or remove), and the pool is frozen and loaded on held-out tasks. The condition is Trace-fb, against Base with no skills, same agent, harness and tasks (§4.3, §5.1).
- claim: skills distilled from traces and feedback "reduce input tokens by 23.0% and cost by 15.5%" (abstract); the method "improves both quality and efficiency" (§5.1).
- evidence: Table 1, held-out SWE-bench Verified, 20 tasks, 5 runs, mean ± population SD. Base against Trace-fb: input tokens 1459.60 ± 467.94 against 1123.33 ± 137.32 (thousands); cost 12.88 ± 1.89 against 10.88 ± 0.94 (10^-3 $); time 268.25 ± 15.76 against 229.32 ± 16.00 s; tool calls 38.26 ± 3.91 against 34.47 ± 2.64; output tokens 17.62 ± 0.97 against 15.56 ± 1.34. Text: input tokens −23.0%, cost −15.5%, time −14.5% (§5.1). Absolute cost is about one cent per task. No significance test is stated.
- effect: helps
- reader: an equal-task comparison, so E4. The feedback is simulated from the benchmark verifier, not given by a person (F4). The 30 distillation tasks come from the same repositories and subsystems as the 20 test tasks (§5.1), so this measures transfer inside a repository. One model, one seed (42), one task split. The authors built the system and chose the utility and the thresholds.

### F2 · practice · trace-and-correction-skill-distillation · E4
- practice: as F1; the measurement is pass rate on the held-out tasks.
- claim: "our approach increases the pass rate from 65.0% to 68.0%" (§5.1).
- evidence: Table 1: Base 65.00 ± 3.16, Trace-fb 68.00 ± 2.45, Trace-only 65.00 ± 4.47 (SD over 5 runs of 20 tasks). The 3 points are 0.6 of one task out of 20 (reader's arithmetic). No test is stated.
- effect: helps
- reader: graded E4 for the design. The difference is smaller than one run-to-run SD of the Base arm and no test is given, so the success gain is not established; the cost gain in F1 is the larger effect. It is not stated whether the skill distillation was repeated across the 5 runs or only the held-out evaluation.

### F3 · practice · skill-distillation-from-traces-alone · E4
- practice: distil skills after each task from the execution trace only, with no user feedback, in the same framework (Trace-only); compared with Base (§5.1).
- claim: Trace-only "only focuses on improving efficiency" (§5.1).
- evidence: Table 1, Base against Trace-only: pass 65.00 against 65.00; input tokens 1459.60 against 1303.26 (−10.7%, reader's arithmetic); cost 12.88 against 12.04 (−6.5%, reader's arithmetic); time 268.25 against 257.05 s. The SDs of Trace-only are 4.47 (pass) and 284.74 (input tokens).
- effect: none
- reader: no pass-rate change; the cost and token reductions are within one SD of Base (reader's reading of Table 1). Graded E4 for the design; effect recorded as none because the paper reports no success change and no test.

### F4 · practice · corrections-as-skill-distillation-input · E4
- practice: add feedback to the distillation input. Redirect: when the verifier marks a run unresolved, fork it with the fixed hint "Locate the root cause more carefully and make a minimal, correct fix; avoid unrelated, broad changes."; if the fork is resolved, the two branches become a pairwise example. Outcome Correction: a fixed "I've reviewed the result; the requested behavior is resolved." is appended to an accepted trace and the correction to a rejected one. Trace-fb against Trace-only (§5.1).
- claim: feedback "not only enhances quality by utilizing human corrections as signals but also supports more targeted skill-pool updates for better efficiency" (§5.1).
- evidence: Table 1, Trace-only against Trace-fb: pass 65.00 against 68.00; input tokens 1303.26 against 1123.33 (−13.8%, reader's arithmetic); cost 12.04 against 10.88 (−9.6%, reader's arithmetic); time 257.05 against 229.32 s; J(Ω) 0.26 against 0.28.
- effect: helps
- reader: an ablation of the feedback on equal tasks. The "human" feedback is the benchmark's pass or fail label plus one fixed sentence, so it carries ground truth that a real user may not have, and it says nothing about what a person's correction adds. Comment was not evaluated (§5.1).

### F5 · practice · execution-trace-visualization · E4
- practice: show an agent run as a hierarchical node graph with failed actions in red and per-node time and token cost, instead of OpenCode's native terminal output; each of 10 real traces was paired with one multiple-choice question on comprehension, error localization or root cause (§5.2).
- claim: the visualization "can more effectively and efficiently support users in understanding agent execution traces, localizing errors, and analyzing root causes" (§5.2).
- evidence: 20 participants, counterbalanced questionnaires, 5 questions per format each. Accuracy 95.0% (SD 11.4) against 76.0% (SD 17.9), Wilcoxon signed-rank |Z| = 3.09, p < 0.01. Response time 44.0 s (SD 20.6) against 99.7 s (SD 45.2), |Z| = 3.92, p < 0.001 (§5.2, Fig. 6).
- effect: helps
- reader: randomised and counterbalanced on the same traces, so E4, but it measures reading a recorded trace in an online questionnaire, not steering a live run. The authors wrote the questions, and the participants had a brief introduction to the VibeTrace interface only (§5.2). Participants averaged 24.1 years of age (§5.2). Whether the users in the baseline had the same time to learn their format is not stated.

### F6 · practice · fork-and-redirect-from-earlier-step · E1
- practice: when the agent departs from what the user wants, fork the run from an earlier step and continue with new feedback, keeping the work before the fork, instead of aborting and re-prompting (§4.2.2, §5.4.2).
- claim: the case is said to show "improving the efficiency of the collaboration"; formative participants said "restarting discarded validated progress" and "continuing execution risked propagating errors" (§5.4.2, §3.1 F4).
- evidence: one case, P2 building a meal-suggestion web app. The agent had chosen a visual style without asking; the user forked before the development node and told the agent to settle design first; the agent then asked design questions with its question tool (§5.4.2, Fig. 9). No time or cost number is given. The formative statement comes from 12 interviews with no counts (§3.1).
- effect: helps
- reader: one participant's case reported by the authors; no comparison with a restart. Redirect is also the intervention simulated in F4, where it is a fixed hint.

### F7 · practice · execution-trace-visualization · E2
- practice: expert users use VibeTrace on two assigned vibe-coding tasks (a film-ROI data report and a debug-heavy bead-art web app) and then in their own work (§5.3).
- claim: participants gave "positive feedback regarding VibeTrace's observability, explainability, and controllability" (§5.3).
- evidence: 8 experts. Mean SUS 85.9 (SD 9.4); Usability subscale 89.4, Learnability subscale 71.9. Six of 8 spent most of their interaction time on the Trace panel; P1 and P6 spent more than 50% on the Dialog panel (§5.3, Fig. 7). Several said setup, not the interface, was the main barrier.
- effect: helps
- reader: numbers with nothing to compare against, so E2. 8 participants who were shown a demo by the authors, no baseline condition, and the interview quotes are selected by the authors.

### F8 · practice · trace-and-correction-skill-distillation · E1
- practice: after a user forked a run and accepted the result, the system compared the traces before and after the fork and wrote a skill, `front-end-design-alignment-before-build`, that tells the agent to confirm design style with the user before building a front end whose visual direction is not fixed (§5.4.3, Fig. 10).
- claim: the case "demonstrate[s] how VibeTrace learn from human intervention and distill a reusable skill that can be applied to future tasks" (§5.4.3).
- evidence: one case: in a later similar front-end project the agent matched the skill and asked about design before building (§5.4.3, Fig. 10). No number.
- effect: helps
- reader: one case from the authors' study, no run without the skill. It shows the mechanism producing and reusing a skill once.

### F9 · practice · gated-skill-patch-admission · E0
- practice: before a candidate skill patch enters the pool, an estimator scores the trace and feedback on reusability, informativeness and safety, and a scorer admits the patch only if quality passes a threshold and it predicts savings in tokens, time and tool calls; at most the top 3 patches are applied per task (§4.3, §5.1).
- claim: "the quality gate ensures that efficiency gains cannot compensate for unreliable knowledge" and learning from task-specific or misleading interactions "may negatively affect future executions" (§4.3).
- evidence: none. The thresholds are given (estimator 0.34, 0.50, 0.60; patch 0.50 reusability and correctness; aggregate at least 0.10) but no run without the gate, and no count of rejected or admitted patches, is reported (§5.1).
- effect: helps
- reader: asserted by design; F1 to F4 measure the whole pipeline, not the gate.

### F10 · observation · uncaptured-corrections-repeat · E1
- practice: what was observed: in 12 interviews, users met recurring workflows, preferences and debugging strategies but "rarely retained them across tasks", which forced users "to repeat similar corrections" (§3.1 F5).
- claim: manual maintenance leaves valuable knowledge in transient interactions, which motivates turning interventions into skills (§3.1 F5).
- evidence: qualitative themes from 12 semi-structured 40-minute interviews with thematic analysis; no counts per theme are given (§3.1). The agent's repeated mistakes after a demonstrated fix are stated in §4.3 without data.
- effect: hurts
- reader: interviews with the same group the authors later used to design the system, no counts. The finding is the condition the system's skill loop is built on. It bears on which human turns repeat.

### F11 · observation · unverifiable-agent-summaries · E1
- practice: what was observed: formative participants "questioned the reliability of agent-generated summaries" and found that traces "describe claimed actions without verifiable evidence" (§3.1 F2).
- claim: users prefer representations grounded in observable actions and states over agent narratives (§3.1 F2, DG1).
- evidence: the same 12 interviews, no counts (§3.1). The case in §5.4.1 shows a user finding three tool errors in a node graph, which the final reply alone would not have named.
- effect: hurts
- reader: interview statements and one case. No rate of false completion claims is measured here.

## Limits stated by the authors

- The paper has no limitations section. Stated in the text: Comment feedback is not evaluated in the benchmark (§5.1); the benchmark feedback is simulated with the verifier (§5.1); setup was the main barrier to first use, addressed in a later release (§5.3).

## Reader's notes

- The system, the metrics, the utility J(Ω), the thresholds and the user-study questions all come from the authors; no outside group evaluated it.
- The benchmark arm uses one cheap model (DeepSeek-V4-Flash) for the agent and for all three distillation stages; whether a gain holds for a stronger agent is not tested.
- The skill pool is built once from 30 tasks; whether the pool was rebuilt for each of the 5 repeated runs is not stated. Pass rates of 65.00 and 68.00 on 20 tasks are 13 and 13.6 tasks on average (reader's arithmetic).
- The human-in-the-loop claim in the title and abstract rests on the user studies (F5, F7) and on cases (F6, F8). The benchmark result (F1 to F4) uses no person.
- For this repository's question, the simulated hints (F4) are a fixed sentence and a verifier label; the paper does not measure which real human turns carry the information that the distillation uses.
- The three skill-pool budgets by "three retained difficulty levels" (§5.1) are not otherwise explained in the parts read.

## Discrepancies

- §5.1 reports a "14.0% enhancement in J(Ω)"; Table 1 gives J(Ω) 0.25 for Base and 0.28 for Trace-fb, which is 12.0% on the rounded values (reader's arithmetic). The paper may compute it from unrounded values.
- The abstract says the "user studies" show improved accuracy and efficiency over log-based interaction; only the §5.2 study has a log-based baseline.
