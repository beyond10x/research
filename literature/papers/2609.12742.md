## Question

Can a repository-specific SKILL file, optimized against tasks mined from the repository's own merged
pull requests, make a coding agent do better on later tasks than the same agent with no SKILL, and
can a gain of that size be told apart from the agent's run-to-run variance (§1, §4)?

## Findings

### F1 · practice · repository-skill-optimization-on-mined-tasks · E4
- practice: optimize one SKILL.md for a repository with GEPA (200 scored attempts per repository) against tasks mined from its merged pull requests; run Claude Code with Sonnet 4.6 on held-out tasks with the SKILL and compare each rollout with the stored rollout of the empty seed on the same task (§3.2, §4.1).
- claim: GEPA's documents raise the mean score by 4.9pp, but the gain "cannot be separated from the agent's run-to-run variance" (abstract).
- evidence: paired score against the seed's 0.5: kotest 0.554, ktor 0.567, koog 0.525 (§4.2, Table 1). Resolved held-out tasks: 13 to 16 of 20, 16 to 20 of 26, 14 to 15 of 23 (§4.2). Sign test over disagreeing tasks: no run clears p = 0.05, best p = 0.29 (§4.2). At 20 to 26 tasks the test rejects only when the document wins four of every five disagreements, and two of three when pooled over 69 tasks (§4.2).
- effect: none
- reader: an A/B on equal tasks with the no-skill agent as control, so E4. The direction is positive in every repository but no result is significant, so the effect is recorded as none, as 2602.11988 F1 does. The seed side is one stored rollout per task and the candidate side one rollout, so the single-sample noise the authors describe sits in both. Authors evaluate their own pipeline and metric.

### F2 · practice · repository-skill-optimization-on-mined-tasks · E4
- practice: as F1, with SkillOpt (three epochs, bounded edits, a candidate accepted only if a held-out selection score strictly improves) as the proposer instead of GEPA (§2, §4.1).
- claim: the documents SkillOpt finds "leave it where it started, 0.1pp above the seed" (abstract).
- evidence: paired score koog 0.546, kotest 0.519, ktor 0.437 (§4.2). Resolved-task change on the test split: +2, +1, −2 (Table 1). "SkillOpt's loss on ktor cancels its gains elsewhere" (§4.2). Spend per run $401.44, $263.56, $484.81; wall clock 8.14 h, 13.3 h, 25.2 h (Table 1). Mean of the three paired scores is 0.5007 (reader's arithmetic).
- effect: none
- reader: same design and same confound as F1. SkillOpt cost more than GEPA on all three repositories (Table 1), so the cost-for-gain comparison favours GEPA, but a 4.8pp difference between two optimizers is itself inside the noise the paper describes.

### F3 · practice · repository-skill-on-open-issues · E3
- practice: give the agent each of two issues that were open in koog (#1275 and #1354) with no SKILL, with the GEPA SKILL and with the SkillOpt SKILL; one run per cell (§4.3, Table 2).
- claim: "With either document the agent finishes faster and cheaper on both" issues (§4.3).
- evidence: Table 2. #1275: no SKILL $6.06 and 14 m 59 s wall, GEPA $2.48 and 5 m 32 s, SkillOpt $2.44 and 5 m 30 s. #1354: no SKILL $4.85 and 20 m 29 s, GEPA $3.10 and 7 m 38 s, SkillOpt $4.20 and 8 m 24 s. Model-call time 8 m 21 s without against 3 m 35 s and 3 m 43 s with, on #1275; 7 m 21 s against 4 m 52 s and 5 m 33 s on #1354. The maintainer, blind to the setup, found all three patches for each issue similar in quality, the GEPA ones tidier (§4.3).
- effect: helps
- reader: 2 issues, 1 run per cell, no repetition, so a comparison and not a control. The no-SKILL agent may have varied by chance by this much; the paper's own F1 argument about run-to-run variance applies. The cost fall of 59% to 60% on #1275 and 14% to 36% on #1354 is the reader's arithmetic. Quality was judged on 6 patches by one person.

### F4 · practice · maintainer-review-of-generated-skill · E1
- practice: a koog maintainer reads the GEPA and the SkillOpt documents section by section, marks what is worth keeping and what is missing, and says whether they would merge it (§4.3).
- claim: the GEPA document holds "knowledge one only gets by working in the project"; the SkillOpt document is mostly "very general best practices" the agent "should know by itself" (§1, §4.3).
- evidence: one maintainer, one repository. For GEPA: the multiplatform source-set rules are "all correct, good that it is included" and the module-dependency direction is "very important"; the document misses the `@Tool` annotation and the pattern the team uses to avoid duplicating expect/actual code. For SkillOpt: one item "great and important" (registering a new module is a three-file change), the rest general advice. Verdict: take the GEPA one "as a draft and polish it"; the SkillOpt one "needs more polishing" (§4.3).
- effect: mixed
- reader: E1 because it is a single opinion. The maintainer is thanked in the acknowledgments and the authors work at the company that owns koog (JetBrains), so independence is not established. The paper says "what we collected is an opinion of what the two documents contain" (§4.3).

### F5 · practice · frozen-base-commit-for-skill-tasks · E1
- practice: mine each task by reverting the merged implementation at one frozen base commit shared by all tasks, instead of checking out the pull request's own parent commit as SWE-bench does (§3.1).
- claim: the forward setup made the optimizer write claims "that were false at the version the SKILL would ship against: module paths, build invocations, APIs that had since moved"; reverse mining at a single base "removes this by construction" (§1).
- evidence: one quoted case, a first-configuration document whose opening lines tell the agent to identify which of "two distinct repository shapes" it is working in (§3.1, §I, quoted in §3.1 and the Responsible use statement). No count of false claims and no run of both setups side by side in the parts read.
- effect: helps
- reader: a case from a discarded first configuration, with no comparison of task scores between the two mining directions. The cost is yield: a change is usable only while its code survives at the base, and only 25 of koog's 119 graded tasks, 56 of 100 on kotest and 65 of 131 on ktor reverse-apply without the LLM tier (§3.1).

### F6 · practice · paired-seed-comparison-objective · E3
- practice: score a candidate SKILL by pairing each of its rollouts with the empty seed's rollout on the same task (a rollout that edits tests or reports a success its tests contradict loses; then all FAIL_TO_PASS tests passing; then a bounded tie-break blend), instead of an absolute score (§3.2).
- claim: absolute scores answer other questions than whether the agent does better with the document; pairing makes 0.5 the number to beat and a single-task regression visible (§3.2, App. D).
- evidence: preliminary sweep on JetBrains/tracy with a generic checklist as seed, not the paired protocol of §4 (Table 3). Held-out change: file facts +0.308, file policy +0.087, skill-blind judge +0.029, skill-reading ensemble +0.010, gold match 0 (no file) and −0.053 (clean-diff pool), work mix −0.027, token price 0, binary resolve 0, partial credit 0; pairing 0.500 to 0.500, which shipped the seed. Rescored on six tasks under a 14-turn cap (Table 4): the file-policy document ranks 6.5 of 8 with mean 0.230; the file-facts and tool-call documents produced no patch.
- effect: helps
- reader: the sweep is on one repository with 24 and 29 held-out tasks and no repeats, so the comparison between objectives is E3. "Helps" is the authors' claim that pairing measures the agent's change and not the file's look; on that pool pairing found no gain, so it shows what pairing refuses to reward and not that it finds a document that works. Authors chose the objective that is theirs.

### F7 · practice · document-quality-as-optimization-objective · E3
- practice: optimize the SKILL against a score of the markdown itself: the count of verifiable repository facts (gmu, "file facts"), or completeness and operational tone ("ideal", "file policy") (App. D, Table 3).
- claim: "The score is a property of the file, not of the agent. Grounding can rise on held-out tasks while the agent does not improve" (App. D).
- evidence: Table 3 held-out empty to best: file facts 0.178 to 0.486 (+0.308), file policy 0.300 to 0.387 (+0.087). Table 4, six tasks, 14-turn cap: the file-facts document has binary resolve 0.333 and rank 4.8; the file-policy document has binary resolve 0.167, rank 6.5, "the worst of the set on every metric that looked at behaviour". The gmu document "emitted no patch" on the shared pool (App. D).
- effect: hurts
- reader: the outcome is agent behaviour and the finding says the document score moved without it. Six tasks, ten scorings each, one repository; ranks differ by small amounts. The documents do look like "something a maintainer might ship" (App. D), so the harm is in the objective, not in a visible defect.

### F8 · practice · solved-task-count-objective · E3
- practice: use binary resolve (every hidden FAIL_TO_PASS test passes) as the optimization score (App. D, App. C).
- claim: "the number ranks how easy the split is, and when it moves it overfits the harness" (App. D).
- evidence: about 92% of rollouts scored 0, so the optimizer shipped the seed (App. D); Table 3 binary resolve held-out 0.222 to 0.222, change 0. When a solved-task score did write a document, it wrote the training pull requests back as prose (App. D, §D.2). On http4k, four hand-collected tasks, the empty SKILL already scored 1.0 and every rewrite was rejected (App. C).
- effect: hurts
- reader: preliminary sweep on tracy and an aborted http4k run, 39 solvable tasks and 4 tasks; the cases show the failure modes at the ceiling and the floor, not a rate.

### F9 · practice · static-check-of-reverted-tasks · E2
- practice: run a static check once per mined pool, before any rollout, for defects the LLM reverter leaves in a task: an import dropped that surviving code needs (unimported symbol) and a private function kept after its only call is deleted (stranded fix, which leaves the answer in the repository) (§3.1, App. A).
- claim: the dynamic validation gate cannot see these defects, and the static check catches them (§3.1, App. A).
- evidence: an intermediate koog pool of 280 tasks: 56 rejected, 36 unimported-symbol, 26 stranded-fix, 6 both; 36 of the 56 had already passed the dynamic validation gate (App. A).
- effect: helps
- reader: counts from one intermediate pool, with nothing to compare against. 36 + 26 − 6 = 56 (reader's arithmetic). The paper does not say whether the final pools were checked the same way or what the rejected tasks would have done to the score.

### F10 · observation · mined-task-yield-from-merged-prs · E2
- practice: the share of a repository's merged pull requests that become graded tasks after reverse-application and validation (§4.1, §6, App. C).
- claim: about one merged pull request in five survives, no single filter can be relaxed to enlarge the pool, and two repositories never reached the 100-task floor (§4.1, §6).
- evidence: koog 119 of 660, ktor 131 of 452, kotest 100 (cut by a seeded sample); tracy 5 of 203 (a package rename left none of 213 production files unchanged over three months); http4k 150 of 700 reverse-applied (35 by git apply, 82 by the LLM reverter, 33 without a test hunk) and fewer than 100 graded (§4.1, §6, App. C). Held-out splits of 20 to 26 tasks follow from the floor (§6). One agent rollout costs $0.84 on average and a 200-attempt run costs hundreds of dollars; Table 1 totals $2,013.98 and 69.2 h for six runs (§1, Table 1).
- effect: hurts
- reader: the effect is on the possibility of evaluating a skill, not on agent success. Counts come from a stop rule (the most recent pull requests, stopped once 100 tasks remained), so the paper says they are not a rate for new repositories (§4.1 fn 5, App. C). ktor's 131 of 452 is 29% (reader's arithmetic).

### F11 · observation · synthetic-task-saturation · E3
- practice: compared the tasks of a defect-injection benchmark (SWE-smith, as used by gskill) with the tasks mined from merged pull requests, and the no-skill resolve rate on each (§1, §4.1, §5).
- claim: the injected-defect tasks are small and a capable agent saturates them with no SKILL, so a pass rate has no room to show a gain; mined tasks leave headroom (§1, §4.1).
- evidence: median change of 4 and 7 lines in the released data for the two repositories gskill uses, single-file in 98% to 100%; ours a median of 54 lines over 3 files (koog), 27 over 2 (ktor), 16 over 1 (kotest), with 23%, 50% and 73% single-file (§4.1). No-skill resolve rate 40% koog, 51% kotest, 66% ktor, 53% pooled (§4.1). gskill with mini-swe-agent and gpt-5-mini goes 55% to 82% and 24% to 93%; with Claude Code and Sonnet 4.5 it is 100% with no skill on the first repository and 94.8% to 100% on the second (§1). In the released SWE-smith data, none of 351 Go instances and 1 of 957 Python ones are PR-mirrored; every Go patch is single-file; 37.6% of the Go instances have no problem statement (§5).
- effect: hurts
- reader: the saturation figures are quoted from gskill's report and the released data, not rerun (§5); the authors use Sonnet 4.6 and gskill's transfer run used 4.5 (§1 fn 2). The repositories differ, which the authors state: "the contrast is between ways of building tasks, not between projects" (§4.1). Effect is on the headroom of the measurement.

### F12 · observation · scaffold-recovered-into-skill · E2
- practice: what the skill slot of an optimizer's agent template contains compared with the agent template around it, in gskill's released configuration (§5).
- claim: part of what the optimizer recovers into the skill is scaffolding a production agent does not need, so gains on a thin harness overstate what a skill adds to a stronger one (§5).
- evidence: gskill's instance prompt is 34 characters, the stock mini-swe-agent template shipped beside it is 2,369 characters with workflow, file-editing recipes and submission command; the published skill excerpt reads as generic hygiene ("run tests early", "avoid scratch main.go files in repo root") (§5).
- effect: hurts
- reader: a reading of a released configuration and one published excerpt; "we make no claim about their reported rates" and did not rerun it (§5). The related maintainer remark on SkillOpt's output, general practices that belong "in a global skill", points the same way (F4).

## Limits stated by the authors

- Both proposers need three disjoint splits, so a repository needs at least 100 graded tasks; the floor gives held-out splits of 20 to 26 tasks, and at that size a few-point gain cannot be separated from the agent's variance (§6).
- The pipeline does not apply when historical diffs no longer apply at the frozen base or when reverting a change breaks no isolated test (§6, App. C).
- One maintainer of one repository reviewed the documents; a developer study with many reviewers is open (§4.3, §7).
- A synthesized SKILL can read as authoritative while stale or over-general; the paired score measures a change in one agent's behaviour on one mined dataset and "does not certify that the document is accurate" (Responsible use).
- The tracy sweep is preliminary and not the paired result (App. D).
- Kotlin repositories only, chosen from the authors' interest in JVM tooling (§1).

## Reader's notes

- The seed is one stored rollout per task; the paper does not say the seed rollout was repeated, though its whole argument is that one rollout is noisy. The paired score 0.5 is therefore a noisy reference too.
- The test-split baseline is high compared with the whole-pool baseline: seeds resolve 13 of 20, 16 of 26 and 14 of 23 (§4.2), 62% pooled (reader's arithmetic), against 53% pooled over all tasks (§4.1).
- The paired score blends tests, honesty of the final claim, diff size and tool calls (§3.2). A score of 0.554 is not a resolve rate; the resolved counts are given separately.
- The issue text of many tasks is a synthetic rewrite of the pull request description by one LLM call, leak-checked against the gold patch (§3.1). Whether this changes the effect of a skill is not tested.
- Skills were optimized and judged with Sonnet 4.6 as the agent; no other agent or model, and no human-written SKILL, is compared. The comparison most useful to a practitioner, a hand-written repository SKILL against these, is absent.
- Authors are at JetBrains Research and koog is a JetBrains repository; the maintainer review and the live issues are on that one repository.
- Reading skills across the 3 repositories, optimizer cost was $182.48 to $484.81 per run (Table 1), so even a positive result would cost hundreds of dollars per repository.

## Discrepancies

- §4.1 says "Roughly one merged pull request in five survives"; its own counts give 18% for koog (119 of 660) and 29% for ktor (131 of 452) (reader's arithmetic); kotest's 100 is capped by a sample.
- Table 3 has a gold-match row on two pools (no file, 120 pull requests: held-out change 0; clean-diff pool of 29 tasks: −0.053); App. D says "On that protocol the held-out score fell", which holds for the second only.
- The Table 4 caption says the file-facts and tool-call documents "produced no patch on this pool", yet their rows give binary resolve 0.333 and partial credit 0.467, the same as the rows of documents that did produce patches. Not explained in the parts read.
