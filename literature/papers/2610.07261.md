## Question

Does coordinating parallel coding agents by scheduling, with disjoint declared scopes and a producer-first merge order fixed before the agents start, give clean integration where no coordination and reactive conflict warnings do not (§1)?

## Findings

### F1 · practice · upfront-scope-partition-and-merge-order · E3
- practice: before the agents start, compute a partition of the work items into batches with pairwise-disjoint declared file scopes and a topological merge order from producer to consumer (greedy colouring, Kahn's algorithm, deterministic); deliver each agent its scope and merge slot at register and sync (§4, Algorithm 1). Tier A: 9 scripted scenarios, the agents' edits are scripted, scored by a real git merge (§5).
- claim: clean-integration success rises from 1/9 to 9/9 scenarios and merge conflicts fall from 13 to 0 (Abstract, §6.1).
- evidence: Table 2, experiment 1, no coordination against reactive detection against planner: CTSR 1/9, 4/9, 9/9; merge conflicts 13, 12, 0; wasted LOC 54, 49, 0. On the control scenario with unrelated tasks all three arms succeed and the plane raises no warnings (§6.1).
- effect: helps
- reader: three arms on equal scenarios, but an agent takes its coordinated edit exactly when the arm's rule says so (§5), so the result follows from the simulation's rule and is not a measure of agent behaviour; the author says it "validates mechanism and routing precision, not agent behavior" (§9). Scopes are hand-declared, not inferred. The author evaluates their own system.

### F2 · practice · upfront-scope-partition-and-merge-order · E3
- practice: as F1; N agents rewrite one hot file at once, N from 2 to 32 (§6.1, Figure 2).
- claim: "the advantage of planning is monotone in N" (§6.1).
- evidence: conflicts grow as n-1 and wasted LOC as about 4(n-1) for no coordination and for reactive detection; the planner stays at 0 for N in {2, 4, 8, 16, 32} (§6.1). At N = 8, wasted LOC is 28, 28 and 0 (Table 2, experiment 2).
- effect: helps
- reader: scripted agents again, so the n-1 growth is a property of the scenario's construction. It shows the mechanism scales, not that live agents behave this way.

### F3 · practice · upfront-scope-partition-and-merge-order · E4
- practice: give a live agent, before it starts, an assignment with an allowed and forbidden scope or, for a contract consumer, the exact contract migration and an instruction to code against the new shape after the producer merges; plus the merge order. Scenario: a producer renames an invoice money field (`amount` in dollars to `amountCents`); a consumer works from the old contract in its own worktree (§5, §6.2).
- claim: the planner "rescues an outcome that both baselines miss on every seed" (Abstract); the effect "holds across the tested capability tiers and two vendors" (Table 3 caption).
- evidence: Table 3, CTSR for no coordination, reactive detection, planner: Opus 4.8 (K = 15) 0.00, 0.00, 1.00, CI [0.80, 1.00], 15/15 against 0/15, Fisher's exact p < 10^-4; Haiku 4.5 (K = 5) 0.00, 0.00, 0.60, CI [0.23, 0.88]; GPT-5-Codex (K = 5) 0.00, 0.00, 1.00, CI [0.57, 1.00]. The misses of Haiku (0.40 of runs, reader's arithmetic) trace to "a stray edit, an incomplete migration" (§8).
- effect: helps
- reader: an A/B on equal scenarios with live agents, hence E4. The paper itself says the live comparison "does not isolate timing from information specificity" (§6.2): the planner arm supplies the exact new field name, the other arms do not, so the result mostly shows that an agent given the missing fact uses it. One hand-built scenario, one model per vendor, 5 seeds for two of three models. The author evaluates their own system.

### F4 · practice · upfront-scope-partition-and-merge-order · E4
- practice: as F3, with one producer migrating the contract and N consumers each in their own file (§6.2).
- claim: the planner adapts every consumer where the baselines adapt none (§6.2).
- evidence: adaptation rate 0.00 under both baselines and 1.00 under the planner at N in {2, 4, 8}, frontier model, K = 3 (§6.2, Table 2 experiment 4).
- effect: helps
- reader: a replication of F3's scenario with the same floor and ceiling and 3 seeds per N; it adds scale in N, not independent evidence. A pilot by the author's own description (§5).

### F5 · practice · forbidden-file-scope-in-assignment · E2
- practice: tell the agent in its assignment which file it owns and which files it must not edit (shared-file scenario, frontier model, K = 5) (§6.2).
- claim: "real agents honor" the disjoint-scope partition (§6.2).
- evidence: scope-leakage 0.00: every planner agent put its new work in a separate file and left the owned file untouched, several noting they did so "as coordinated" (§6.2, Table 2 experiment 5). No baseline value is given ("—" in Table 2).
- effect: helps
- reader: no comparison arm, one simple scenario, and an advisory scope that nothing enforces. The author says leakage "could be higher on subtler scopes" (§9). The abstract's "none of 5 strayed" is this cell.

### F6 · practice · reactive-peer-change-warning · E4
- practice: when the daemon senses a teammate's change to a file the agent cares about, send the agent a vague warning ("a teammate may be editing X") with no scope, no contract detail and no merge order (§5).
- claim: "a vague reactive warning is worth about as much as nothing to a live agent" (§1).
- evidence: live contract migration CTSR with reactive detection equals no coordination at 0.00 on all three models (Opus K = 15, Haiku K = 5, Codex K = 5, Table 3). The raw replies show the consumer "knew 'something may change' and still coded to the stale field" (§6.2).
- effect: none
- reader: both arms sit at the floor, so the comparison cannot rank them. The warning was written vague on purpose; a detailed but late warning is not tested and is called future work (§6.2, §9). It is a statement about this warning text, not about reactive detection in general.

### F7 · practice · reactive-peer-change-warning · E3
- practice: as F6, in the scripted Tier A scenarios, where an agent takes its coordinated edit exactly when the warning arrives in time (§5).
- claim: the detector matches the planner on sequential dependencies and "collapses to the C0 baseline" on concurrent scenarios because the warning arrives after the edit (§6.1).
- evidence: CTSR 1/9 against 4/9, conflicts 13 against 12, wasted LOC 54 against 49 (Table 2, experiment 1); at N = 8 wasted LOC 28 against 28 (experiment 2). No per-scenario table is given in the text.
- effect: mixed
- reader: whether a warning is "in time" is set by the scenario script, so the sequential-against-concurrent split is built in. Better on sequential scenarios, equal to nothing on concurrent ones.

### F8 · practice · decision-store-read-and-written-per-session · E4
- practice: record a team decision in a cross-agent memory in session 1; in a fresh session 2, ask the agent which of two symmetric authentication backends to import. The sanctioned choice appears nowhere in the code (§6.3).
- claim: a decision recorded in one session stops an agent in a later session from repeating the mistake, "an information effect no amount of model strength substitutes for" (Abstract).
- evidence: repeated-mistake rate 1.00 without memory and 0.00 with memory, on the frontier model and on Haiku, K = 5 each (§6.3, Table 2 experiment 6). Without memory the agents call the two backends "a genuine tie" and guess.
- effect: helps
- reader: with against without memory on the same task, hence E4. The task is built so that the answer exists only in memory, so the result shows memory carries a fact, not how often real decisions matter or are retrieved. One scenario, K = 5. An earlier version of this test gave a spurious 70% against 100% effect (F12).

### F9 · practice · routing-relevant-fact-instead-of-full-context · E3
- practice: route only the one relevant fact (about 155 tokens) to the agent, against putting 10k to 280k tokens of codebase into its prompt, where the agent must pick the current payments contract among four hard-negative money shapes buried at about 50% depth (§7).
- claim: routing does not rescue accuracy over long contexts at window-fitting scales; the authors retract the hypothesis of an "attention rescue" (§7).
- evidence: both the frontier model and the small model picked the current contract over the decoys at 10k, 50k and 100k tokens (the frontier model also up to about 280k); a three-fact join with named traps gave the same, no accuracy gap even for the small model. At smaller scales the frontier model recalled a buried fact at any position with 100% adherence (§7). No counts or number of runs are given.
- effect: none
- reader: a negative result reported by the author against their own hypothesis, which counts in its favour. No n or per-cell accuracy is printed, so it is graded below E4; the routed arm and the dumped arm are the same task with different context.

### F10 · practice · routing-relevant-fact-instead-of-full-context · E3
- practice: as F9; the outcome measured is prompt size and whether the prompt fits the window (§7).
- claim: the value of routing is "cost and capacity", "not attention" (Abstract, §7).
- evidence: about 155 tokens against 10k to 280k, "68x to 1296x less context per task"; the single-agent prompt of about 280k tokens overflows the small model's 200k window in 5/5 runs, while the per-agent routed prompt always fits (§7).
- effect: helps
- reader: the ratio is arithmetic on prompt sizes the author chose to build (10k to 280k), and the overflow is a property of the window size, so the finding is close to a definition. No dollar cost or latency is measured.

### F11 · practice · service-graph-routing-of-contract-changes · E2
- practice: route a changed API contract through a service graph to the agents in other repositories that consume it, and not to unrelated agents (§3, §6.1).
- claim: "Cross-repo routing is exact" (§6.1).
- evidence: on the fan-out scenario the two real consumers are warned and the unrelated service is not: 100% routing hit, 0% false positives (§6.1).
- effect: helps
- reader: one scripted Tier A scenario with two consumers and one distractor, so a tiny n and a graph the author declared. It measures routing precision, not whether the receiving agent acts on the message (see F6).

### F12 · observation · prose-regex-scorer-artifact · E1
- practice: an earlier run of the decision-adherence test scored replies with a regular expression that negated on a substring, and false-flagged correct replies (§7).
- claim: the 70% against 100% effect it reported on a frontier model was "a scorer artifact"; the author retracts it (§7).
- evidence: one case. Structured-output scoring plus raw-reply logging "erased the effect" (§7); the positive results in §6 are scored on parsed artifacts (the import line, the merged field).
- effect: hurts
- reader: a disclosed measurement error in the author's own harness, with no numbers beyond the retracted 70% and 100%. It shows prose pattern matching can create or erase an effect in an agent evaluation.

## Limits stated by the authors

- Scopes are hand-seeded in the harness, not inferred from natural-language tasks; "the planner's guarantee is only as good as those scopes", and inference is "unbuilt work" (§9).
- Tier A scripts the agent edits and so validates mechanism and routing precision, not agent behaviour (§9).
- Live cells other than the contract cell on Opus 4.8 are K = 5 (or 3) pilots with wide intervals; scenarios are hand-built (§9).
- Scope-leakage was measured on the simple shared-file case only (§9).
- The reactive warning is deliberately vague; a detailed but late warning is not tested, and the live setting does not separate timing from information specificity (§5, §6.2, §9).
- Open: automatic scope inference, re-planning as work changes, enforced instead of advisory scopes (§10).

## Reader's notes

- One author evaluates their own open-source system on a benchmark they built. The planner arm is given information (exact contract, forbidden files) the other arms are not, so the three-arm gaps measure delivery of declared facts more than scheduling. This is the paper's own caveat, but the title and abstract speak of "scheduling".
- The 0.00 floors of both baselines and the 1.00 ceiling of the planner leave little room to see a difference between arms or models; the Haiku 0.60 (3 of 5, reader's arithmetic) is the only intermediate cell. The claim that the benefit "did not shrink as models got stronger" rests on one contract scenario and K = 5 for two of three models.
- Success is clean merge plus a post-integration acceptance check built by the author for the scenario; the text does not describe the check.
- CTSR for Opus 4.8 is K = 15 for planner, no coordination and detection (Table 3); the text does not say whether the same seeds are reused across arms.
- The memory test uses a keyword memory by default (§3); which memory mode was used in §6.3 is not stated.
- Cost, latency and tokens of the live agents per arm are not reported.

## Discrepancies

- §6.2 reads the live result as "the combined planner intervention (up-front timing together with the exact scope and contract)", while the abstract and §1 attribute it to scheduling ("how work is allocated"). §8 itself says the live evidence "supports the combined proactive intervention rather than scheduling alone".
- Table 3's caption says "the two frontier models 1.00", while §5 calls only Opus 4.8 a frontier model and Haiku 4.5 the small one; GPT-5-Codex is not placed in a tier in the text.
