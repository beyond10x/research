## Question

Can a stronger builder model, running inside a coding-agent harness, write an inference-time scaffold
that makes a weaker, fixed target model solve Theory-of-Mind tasks more reliably, with no parameter
updates, and which design choices (builder, reasoning effort, platform, validation use, techniques)
explain the result (§1, §4)?

## Findings

### F1 · practice · strong-builder-scaffold-for-weak-target · E4
- practice: give a coding agent (builder) a workspace with a rule file, a demo of how to call the target, and 5% labelled validation items; it writes and refines scaffold code over about 5 validation runs and submits one entry point; the scaffold is then run on the hidden items with the weaker target and compared with the same target called with a naive prompt (§3, §4, Algorithm 1).
- claim: strong-to-weak scaffolding "is highly effective, nearly doubling average target-model performance from 0.49 to 0.91" (Abstract); "every builder configuration yields positive net uplift" (§1).
- evidence: target GPT-5.4-mini, macro-average accuracy, vanilla 0.488, mean over 57 scaffolded runs 0.763 (+0.275), 100% of runs above baseline, best run 0.912 (+0.423) (Table 1, §5.1). Paired McNemar over 3900 items for the best run: 1717 baseline errors fixed, 105 correct items broken, chi2 1424.4, p < 10^-4 (Figure 10a, §5.8). Top 8 scaffolds repair 83% of baseline-wrong items and break 7% of baseline-correct (§5.10). Raw GPT-5.4 scores 0.619 and many scaffolded GPT-5.4-mini runs exceed it (Table 1, §5.1). Target Gemini-3.5-flash: vanilla 0.761, best run 0.939, 772 fixed and 63 broken (§4, Figure 10a).
- effect: helps
- reader: same items with and without the scaffold, so E4. The baseline is a naive prompt, not a hand-tuned one. The authors say BigToM answers "can be fully exploited through structured reasoning" (§1), so part of the gain is benchmark-specific rules. The builders were told to maximise exactly this score. Authors evaluate their own setup, hence `independent: false`. No cost of builder or scaffold execution is given in the parts read.

### F2 · practice · automated-scaffold-vs-human-designed-harness · E3
- practice: compare the agent-built scaffolds with UserHarness, a human-designed ToM harness for the same target (§4).
- claim: the best automated scaffold "approach[es] the human-inspired harness reference on the same backbone (0.939), despite using no human ToM-specific engineering"; on the harder benchmarks "careful human harness engineering continues to provide an advantage" (§6, §5.1).
- evidence: GPT-5.4-mini, human harness 0.939 against best automated run 0.912 and mean over scaffolded runs 0.763 (Table 1, §4). Per benchmark, best scaffold against human harness: BigToM 1.00 against 0.95, Hi-ToM 0.80 against 0.87, MMToM-QA 0.84 against 0.98, MuMA-ToM 0.88 against 0.96 (§5.1). Gemini-3.5-flash target: human harness 0.941 (§4).
- effect: mixed
- reader: the human harness comes from a cited earlier work by the same first author (Qian et al., 2026); its design effort is not reported, so there is no like-for-like cost comparison. One reference run, no spread given for it.

### F3 · practice · external-harness-proposer · E4
- practice: let a stronger model build the scaffold instead of the target building it for itself; holds platform and target fixed (§5.8 iii, Figure 10b).
- claim: "A stronger builder is not necessary for uplift, but it is necessary for the highest gains" (§5.8).
- evidence: GPT-5.4-mini building for itself gains +0.17 to +0.22 (§5.8). On Cursor, self 3 runs 0.706 (+0.217) against 30 runs of other builders 0.754 (+0.266); on GPT Codex, self 3 runs 0.656 (+0.168) against 6 runs of other builders 0.802 (+0.314) (Figure 10b). Builder means over runs range from GPT-5.5 0.875 (+0.387) to Grok-0.1 0.563 (+0.075), with Codex-5.3 at 0.675 (+0.187) and GPT-5.4-mini at 0.681 (+0.193) (Figure 3a).
- effect: helps
- reader: builder identity is an assigned factor on equal items, so E4. "Other builders" is a pooled group that includes Grok-0.1 and Codex-5.3, which gain no more than self-building; the gain comes from the strong builders in it. 3 runs per self cell, no test stated.

### F4 · practice · reasoning-effort-scaling · E4
- practice: vary only the reasoning effort of the builder, Opus-4.7 at low, medium, high and extra-high, on Cursor and on Claude Code, with target GPT-5.4-mini (§5.7).
- claim: "Greater builder reasoning effort consistently improves scaffold quality"; "the useful compute is therefore not more probing, but deeper hypothesis formation" (§5.7).
- evidence: pooled macro accuracy 0.711, 0.793, 0.807, 0.856 for low to extra-high, Spearman 0.77; extra-high against high p = 0.013 and against low p = 0.002, permutation tests (§5.7). Cursor 0.728, 0.770, 0.788, 0.840; Claude Code 0.694, 0.816, 0.826, 0.872, 3 runs per cell (Table 3). Scaffold size about 510 to 650 Python lines at low and 1000 to 1300 at extra-high (§5.7).
- effect: helps
- reader: an assigned sweep on equal items, so E4. One builder family, 3 runs per cell; the low-to-medium step carries most of the gain and the medium-to-high step is small against the run spread (Cursor medium sd 0.078).

### F5 · practice · alternative-harness-same-model · E4
- practice: run the same builder model on its vendor's native coding-agent platform and on Cursor, with target and task fixed (§5.5).
- claim: platform is "a second-order factor, and its effect is conditional rather than universal"; "builder identity dominates platform identity" (§5.5).
- evidence: native against Cursor over 8 matched configurations: +0.013 on average, native better in 5 of 8, paired permutation p = 0.484; GPT family +0.020, Claude family +0.008 (§5.5). Opus-4.7, Claude Code minus Cursor: low -0.034, medium +0.045, high +0.038, extra-high +0.032 (§5.5, Figure 7b). Pooled platform means 0.799 (Claude Code), 0.754 (GPT Codex), 0.750 (Cursor), confounded by roster (§5.5).
- effect: none
- reader: matched pairs with an assigned platform, so E4. Pairs of 3 repeats each, spread of 0.02 to 0.08 per cell, so differences of a few points are within noise; the platform-by-effort pattern has no test. Only 3 platforms.

### F6 · observation · harness-refinement-budget-scaling · E3
- practice: none applied; builders chose how many validation evaluations to run. Mean 4.9 (median 5, range 2 to 15); the task scored validation use as a secondary criterion (§5.3).
- claim: "builder quality matters much more than how often the builder probes the validation set" (§5.3).
- evidence: number of validation iterations against final full-set accuracy, Pearson r = 0.17, n = 57 runs (Figure 5b, §5.3). Mean validation accuracy rises by 0.216 from first to best logged iteration within runs (§5.3).
- effect: none
- reader: a correlation over runs where the count was the builder's own choice, so E3; strong builders may stop early because they are already good. Not an experiment on validation budget.

### F7 · observation · small-validation-slice-as-proxy · E3
- practice: none applied beyond the fixed design; the builder sees a 5% validation sample (195 items) and the best validation score is compared with the final full-set score (§5.3).
- claim: "a frugal 5% validation slice provides a faithful proxy for the hidden set, guiding refinement without substantial overfitting" (§5.3).
- evidence: best validation accuracy against final full-set accuracy, Pearson r = 0.96, n = 57; mean optimism gap 0.021 (§5.3, Table 2). Per-builder gap from -0.021 to 0.048 (Table 2).
- effect: none
- reader: no overfitting found, so `none`. The 195 validation items are 5% of the 3900 items, so the full-set score may include them; the text of §3 says the test split is the remainder and §4 gives 3900 as the test set (reader's inference, see Discrepancies). If they are included, up to 5% of the score is on seen items.

### F8 · practice · best-of-few-builds-by-validation · E0
- practice: build 2 or 3 scaffolds independently and keep the one with the best validation score, or ensemble them (§5.2, §6).
- claim: "building two or three scaffolds and selecting the best validation performer offers a low-cost way to capture the upper bound of a setting's performance range" (§5.2); "build several independent scaffolds and select or ensemble them" (§6).
- evidence: no selection or ensemble was run. Supporting numbers: repeat standard deviation 0.036 on average and widest repeat range 0.201 (§5.2); validation-to-full r = 0.96 (§5.3); the union of items fixed by the top scaffolds covers 97% of baseline errors, more than any single scaffold (§5.8 iv).
- effect: helps
- reader: E0 because the recipe itself was not tested; the numbers show that builds vary and that validation ranks them, not what selection yields. The 97% is a union of fixes, not an ensemble's accuracy.

### F9 · observation · deterministic-offload-of-task-logic · E3
- practice: none applied as a treatment; builders were told to reduce the target's cognitive load, and each run was tagged by the share of the 3900 items answered by code or rules alone (§5.9).
- claim: "Deterministic offloading is strongly associated with scaffold quality"; the "mechanistic core" is cognitive-load reduction (§5.9).
- evidence: determinism fraction against final accuracy, Pearson r = 0.72, n = 18 runs with tags (Figure 11a, Table 4). Mean determinism fraction by benchmark: BigToM 0.94, Hi-ToM 0.51, MMToM-QA 0.44, MuMA-ToM 0.36 (Figure 11b). Scaffold code size against accuracy r about 0.22 (§5.9). Runs with a deterministic solver 31 of 57 (§5.4).
- effect: helps
- reader: n = 18 and the share differs mostly by builder and by benchmark; BigToM is almost fully rule-solvable, which the authors describe as exploiting the benchmark. A deterministic rule with a logic error also caused the largest run-to-run spreads (§5.2), so the same practice raises the mean and the variance.

### F10 · observation · task-structure-techniques-in-scaffold · E3
- practice: none applied; the authors coded each of the 57 GPT-5.4-mini-target scaffolds for 12 techniques from code and log, and compared runs with a technique against runs without it (§5.4, §5.8).
- claim: the strongest associations "come from techniques that compile task structure into the scaffold"; the comparisons are "associational rather than strictly causal" (§5.8).
- evidence: mean accuracy with against without, runs with / without: polarity or negation logic 45/12, 0.782 against 0.693 (+0.090); structured extraction 29/28, 0.790 against 0.736 (+0.055); hybrid fallback 34/23, +0.040; deterministic solver 31/26, 0.775 against 0.750 (+0.026); forced chain-of-thought 45/12, 0.765 against 0.758 (+0.007) (Figure 9a). Few-shot examples 12/45, +0.042 (Figure 9a). Against this, a verification or arbiter pass 7/50, 0.679 against 0.775 (-0.097), and token-budget tuning 43/14, 0.752 against 0.799 (-0.047); the text does not interpret these two (Figure 9a).
- effect: helps
- reader: observational, techniques co-occur and track builder strength, and the taxonomy was written by the authors after seeing the runs ("based on our observation", §5.4). No uncertainty is given. The negative verification contrast has 7 runs and may reflect which builders add such passes. The benchmark-specific techniques (polarity, MOST-vs-LEAST framing) are not portable to other tasks.

### F11 · observation · answer-format-enforcement-in-harness · E2
- practice: strict parsing of the answer option, temperature 0 and routing by benchmark; used by nearly every builder without being assigned (§5.4).
- claim: they "serve as inexpensive reliability controls" that prevent "malformed outputs, format confusion, or sampling variance" and "make higher performance possible" (§5.4, §5.8).
- evidence: prevalence over 57 runs: format enforcement 57/57, greedy or temperature control 56/57, benchmark routing 54/57, forced chain-of-thought 45/57 (Figure 6a). No contrast group exists for format enforcement (Figure 9a).
- effect: helps
- reader: the effect is asserted from universal use, with no run lacking format enforcement and none scored with and without it. The numbers describe adoption, not effect.

### F12 · observation · harness-gain-shrinks-on-strong-models · E3
- practice: run the same builders and scaffolds for a stronger target, Gemini-3.5-flash (vanilla 0.761), and for the weaker GPT-5.4-mini (vanilla 0.488), on Cursor, 5 builders, 3 repeats each (§5.6).
- claim: "scaffolding is therefore most valuable for weak targets; for already strong targets, it should be applied selectively at the sub-task level and gated by measured headroom" (§5.6).
- evidence: mean uplift +0.262 for GPT-5.4-mini (0.488 to 0.750) against +0.110 for Gemini-3.5-flash (0.761 to 0.871), same direction for all 5 builders (§5.6, Figure 8a). Uplift against headroom (1 minus baseline) per builder-benchmark run, Pearson r = 0.75 (§5.6). For GPT-5.4-mini 0 of 20 builder-benchmark cases fall below baseline; for Gemini-3.5-flash 9 of 20, with Hi-ToM -0.04 and MuMA-ToM -0.02 on average (§5.6). Model-only share on MuMA-ToM rises from 40% to 73% when the target is Gemini (§5.6, Figure 8d). 96% of Gemini's macro uplift (0.42) is on BigToM (§5.6).
- effect: mixed
- reader: the target differs in vendor as well as strength, so the comparison is between two models, not a controlled strength change; E3. The headroom correlation pools runs from 2 targets and 4 benchmarks, so benchmark identity is mixed in.

## Limits stated by the authors

- Theory-of-Mind benchmarks are "a representative testbed rather than the only setting"; broader benchmark families are future work (§7).
- Technique-level comparisons are associational, not causal; contrasts with fewer than 5 runs are marked unreliable (§5.8, Figure 9).
- Pooled platform averages conflate platform with builder roster and are descriptive only (§5.5).
- The build process is "still not fully deterministic" (§5.2).
- Gap to the human harness remains on Hi-ToM, MMToM-QA and MuMA-ToM (§5.1).

## Reader's notes

- No coding task is scored. The coding agents act as builders that write scaffold code; the evidence on harness design carries over to coding agents only by analogy.
- The result is an optimisation against a score the builder can see on 195 items, then reported on the other items. BigToM reaches 1.00 through rules that exploit its question structure (§1, §5.1); the authors state they "do not view such exploitable structure as 'cheating'" (§7).
- The instruction file told builders the grading criteria (average accuracy first, validation evaluations second), forbade hard-coding validation answers, and asked them to reduce the target's cognitive load (Appendix A). The reduction-of-load framing in §5.9 was therefore requested, not found.
- Samples per item for the baselines and the token cost of scaffolded against vanilla calls are not stated in the parts read.
- Each setting has 3 repeats and one baseline score per target; per-cell spreads are 0.004 to 0.078 (Table 3, Table 6).

## Discrepancies

- Validation sample size: §3 and §4 say 5% (195 items); the instruction file in Appendix A says "a random 2% sample of the full benchmark".
- Whether validation items are in the evaluated set: §3 says the hidden test split is the remainder after the 5% validation split; §4 says the hidden test set has 3900 items, which is the sum of the four benchmark sizes, and the validation sample has 195 items, which is 5% of 3900.
- §5.8 says the "apparent negative associations" are for greedy decoding and benchmark routing; Figure 9a gives benchmark routing +0.033 (54 with, 3 without).
- §5.4 says deterministic solvers appear "only in a minority of scaffolds"; the same section's table gives 31 of 57 (54%).
- Figure 3b's "best scaffold" is not defined in the text. Its values BigToM 1.00, Hi-ToM 0.80, MMToM-QA 0.84 match the GPT-5.5 builder means in Figure 3a, but its MuMA-ToM value 0.88 does not (0.857 there), and none match the best run in Table 6 (0.843, 0.888, 0.916).
