## Question

What defects does a coding agent introduce when it implements a specified multi-component system,
how were they caught, and what does one specified retrieval trade-off (filtering candidates to a
graph-identified entity set against unfiltered similarity search) do on a public benchmark (§1)?

## Findings

### F1 · observation · defects-in-spec-directed-agent-implementation · E1
- practice: one agent built the system end to end from a detailed design document that fixed technologies, schema, entity-resolution algorithm and retrieval-filtering strategy; every defect with an attributable diff and symptom was logged from the session artefacts, with no protocol set in advance (§2).
- claim: the agent introduced five systems-level defects of its own, across four constraints, and later fixed them (§1, §3).
- evidence: Table 1, five defects. Reliability: config path depended on the launch directory, broke for one non-default entrypoint. Correctness: storage upsert keyed on random IDs violated the idempotency requirement on re-execution. Consistency: traversal returned edges in both directions but fetched endpoint nodes in one. Efficiency: sequential per-stage network calls. Correctness (rendering): label size computed with a floor that broke scale cancellation. No count of defects that were not logged, no rate.
- effect: hurts
- reader: five cases from one session, so E1. No count of changes or lines is given, so no rate can be read from it. The paper says it does not claim that defect frequencies generalise (§5).

### F2 · observation · defects-without-static-signature-caught-by-execution · E1
- practice: none applied; the paper classifies how each of the five defects was detected (§1, Table 1).
- claim: several defects "had no static or type-level signature, caught only by empirical probing", which argues for "execution-based, not just static, evaluation of agentic systems work" (§6).
- evidence: Table 1 detection column: runtime exception on one entrypoint; a repeated-execution test "added after the fact"; a client-side runtime crash in the rendering library; user-observed latency; an automated screenshot comparison with no static signature. The paper states the rendering defect "was caught only by an automated screenshot comparison during otherwise unrelated interaction testing" (§3).
- effect: helps
- reader: `helps` is the effect of execution-based probing on detecting these defects. One session, no comparison with a static check or with a second reviewer; that no static check could catch them is asserted in §3 and not tested. Authors are the operators of the session.

### F3 · observation · untested-joint-invariant-recurs-at-second-call-site · E1
- practice: none applied; the test suite asserted on returned edges and not on the joint node and edge consistency invariant (§3).
- claim: the invariant violation was "invisible to the type system and to the existing test suite", surfaced only as a crash in an unrelated client, and "was independently reintroduced at a second call site" before the invariant was made explicit and tested directly (§3).
- evidence: one defect, two call sites (graph traversal and an HTTP endpoint exposing the same operation); no counts beyond that.
- effect: hurts
- reader: one case. The agent also generalised the fix after the second occurrence (see F7), so the recurrence cost one extra round and the paper gives no measure of it.

### F4 · observation · fix-not-remeasured-on-motivating-input · E1
- practice: none applied; the concurrency fix was validated on a smaller document than the one that motivated it (§5).
- claim: the agent reported the fix effective without re-measuring latency on the same input, "conflating 'architecturally sound' with 'verified on the regression it targets'"; the development loop "had no mechanism to catch" it (abstract, §5).
- evidence: motivating case was a 242-second latency on an 18-chunk document; after parallelising the stage the agent checked only a smaller document (§5). No post-fix latency for either document is given.
- effect: hurts
- reader: one case, no measurement of the fix at all, so the claim is about the process and not about the speedup. The paper does not say whether the fix would have passed the re-measurement.

### F5 · practice · entity-set-prefilter-of-retrieval-candidates · E4
- practice: restrict vector-retrieval candidates to the paragraphs whose title is in the question's gold supporting-fact title set, then rank by cosine similarity inside that set; against ranking the whole 2,994-paragraph pool. The gold titles stand in for an entity-identification stage that was not run (§4).
- claim: filtering raises evidence recovery at every k, with every paired sign test at p < 10^-4; but "the rest follow near-tautologically from the design", and the informative results are filtered recall@1 and the unfiltered shortfall (§4).
- evidence: Table 2, n = 100 questions. Mean recall@k, unfiltered against filtered: k=1 0.420 against 0.500; k=3 0.685 against 1.000; k=5 0.765 against 1.000; k=10 0.845 against 1.000. Exact match: k=1 0.000 against 0.000; k=3 0.410 against 1.000; k=5 0.540 against 1.000; k=10 0.690 against 1.000. Sign test p: 3 x 10^-5, 3 x 10^-18, 3 x 10^-14, 9 x 10^-10.
- effect: helps
- reader: E4 because it is a paired comparison on the same 100 questions, but the treated arm is an oracle: its candidate pool is exactly the two gold paragraphs, so recall of 1.0 at k >= 2 is guaranteed. The result bounds the filtering decision and says nothing about a working entity-identification stage, which the authors name as the main threat (§4). The paper adds that its numbers are not comparable to any HotpotQA leaderboard entry (§4). Author evaluates own system design, hence `independent: false`.

### F6 · observation · unfiltered-similarity-retrieval-leaves-gold-evidence-missed · E2
- practice: none applied; the unfiltered arm of F5, top-k nearest paragraphs by cosine over the pooled corpus (§4).
- claim: "topically similar but wrong-entity evidence crowds out correct evidence under pure similarity ranking, and more retrieval budget does not fix it" (§4).
- evidence: unfiltered exact match 0.410 at k=3, 0.540 at k=5, 0.690 at k=10; mean recall@10 0.845 (Table 2). "Unfiltered search recovers all required evidence only 69% of the time even at k = 10" (abstract).
- effect: hurts
- reader: E2, a description of one arm; the contrast is F5. Exact match rises from 0.410 to 0.690 between k=3 and k=10, so more budget does help; the paper's wording is that it does not close the gap to the oracle arm. One embedder, one corpus built by pooling 300 questions; the embedder is not named in the text.

### F7 · observation · structural-fix-by-agent-and-human-caught-emergent-defect · E1
- practice: none applied; the paper compares how the agent handled different defects (§5).
- claim: "In two of five defects, the agent diagnosed the root cause from a single symptom and applied a structural fix rather than a local patch"; in a defect outside the catalogue, a human caught an emergent failure only through interactive testing (§5).
- evidence: structural fixes were centralising configuration-path resolution and generalising the endpoint backfill after recognising the pattern at a second call site. The uncatalogued case: the visualization client re-fetched and re-rendered on every click, "each operation was locally correct and the failure was emergent" (§5). No counts of human corrections are given.
- effect: mixed
- reader: three cases, no tally of how many of the five defects the human reported. The abstract says defects were fixed "either by the agent proactively or in response to a user-reported symptom" without saying how many of each (§1).

## Limits stated by the authors

- Single-session, single-agent case study; no claim that defect frequencies generalise, including to smaller models (§5).
- The retrieval comparison substitutes gold entity labels for query understanding and bounds only the filtering decision in isolation; entity-identification quality is "the main threat to generalizing these numbers" (§4, §5).
- Not a reproduction of HotpotQA's answer or supporting-fact metrics; not comparable with leaderboards (§4).
- Filtering by graph-identified entities is not new (§1).

## Reader's notes

- The only agent-related measurement is a list of five cases. The model, the agent's autonomy level, the session length and the number of human turns are not stated, so the paper cannot show which human interventions were load-bearing.
- The same author wrote the system, ran the session and reports its defects; there is no second rater for the category or the detection method.
- The defects may have been selected for being instructive (§3 discusses "the two most instructive"), so Table 1 need not be every defect of the session.
- The retrieval part tests an embedding retriever and a filter, not a coding agent; it bears on agentic coding only as a property of the specified design.
- The paper has 4 pages of text; arXiv metadata lists 4 pages and the PDF has 5 including references.

## Discrepancies

- §4 calls filtered recall@1 = 0.500 a result "not guaranteed by construction", where "ranking within the 2-paragraph pool still matters". With a pool of exactly the two gold paragraphs and two gold paragraphs per question, the top-1 result is always one gold paragraph, so recall@1 is 0.5 for every question and for any ranking (reader's arithmetic from the §4 description of the filtered pool). The 0.500 and the exact match of 0.000 at k=1 in Table 2 are also guaranteed.
- §4 says more retrieval budget "does not fix" the unfiltered shortfall; Table 2 shows unfiltered exact match rising from 0.410 (k=3) to 0.690 (k=10) and mean recall from 0.685 to 0.845.
- The abstract says filtered recall "reaches 1.0 by k = 3"; §4 says any k >= 2 recovers the gold paragraphs. k = 2 was not measured.
