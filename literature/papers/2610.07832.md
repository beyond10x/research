## Question

Can repository components that each hold a resident LLM, activated on demand and revised from execution
evidence, resolve software engineering tasks better than other harnesses running the same model (§1)?

## Findings

### F1 · practice · per-file-resident-agents · E3
- practice: HERMES gives each activated repository file (source, config, test) its own LLM instance, a Dev-Primitive, that edits only that file and sends directed natural-language messages to the files it depends on; the modified repository is executed and failures are traced back to components (§3, F.5). Compared with other harnesses on the same backbone and reasoning effort (§4.1).
- claim: HERMES "outperforms matched baseline harnesses by 12.4% on average" over four benchmarks (Abstract); "HERMES improves performance by 12.4 percentage points on average" (§1).
- evidence: SWE-bench Verified vs mini-SWE-agent: higher resolved rate for 19 of 20 backbones, tie for Claude Opus 5 at 97.00 (§4.2, Table 1); GPT-5 Mini 60.80 to 80.20 (+19.40), Claude Sonnet 5 79.60 to 85.80 (+6.20), GPT-5.6 Sol 96.20 to 97.00 (+0.80). Against Claude Code on Opus 4.8, 85.80 to 91.00 (+5.20); against Codex on GPT-5.5, 76.40 to 85.60 (+9.20). SWE Refactor Bench (20 tasks), 14 rows, composite gain +7.0 to +24.5, e.g. GPT-5.6 Sol medium 6.5 to 31.0 against Codex (Table 2). Terminal-Bench 4.0, gain +1.2 to +27.6, e.g. Sol medium 33.0 to 51.8 against Codex, Sonnet 5 max 12.4 to 40.0 against Claude Code (Table 3). DevOps-Gym, GPT-5.6 Sol 49.89 to 55.41 against Codex (+5.52), gains also against OpenHands, mini-SWE-agent, SageAgent and Aider (Table 4). Repeating Sol on SWE Refactor Bench three times gives 29.5, 32.0 and 31.5, 31.0 ± 1.3 (G).
- effect: helps
- reader: E3, not E4: the comparison is against other products, not a single-variable ablation, and the baseline rows are a mix of leaderboard numbers and the authors' own runs that the tables do not tell apart (F.8). The authors build and evaluate their own system (independent: false). HERMES spends more per task (F2) and has up to 3 revision rounds with execution feedback; the paper gives no compute-matched run against an external harness. The way the 12.4 average is taken is not stated. HERMES is run once per backbone (§4.1) and the baseline columns carry no variance on SWE Refactor Bench.

### F2 · practice · per-file-resident-agents · E3
- practice: as F1; the measurement is inference cost and latency per task against the baseline harness.
- claim: "These gains generally require higher inference cost due to iterative execution and revision" (§4.2); "HERMES introduces additional inference cost and latency" (I).
- evidence: SWE-bench Verified cost per test, mini-SWE-agent against HERMES: GPT-5.6 Sol $1.15 and $1.80, GPT-5 Mini $0.05 and $0.21, Claude Fable 5 $2.05 and $4.50; Claude Code on Opus 4.8 $0.67 and $2.65 with latency 135.40 s and 482.73 s; Codex on GPT-5.5 $0.65 and $2.45 with latency 108.54 s and 398.74 s (Table 1). Terminal-Bench, Sol medium tokens 3.6B and 6.8B, cost $1.9k and $3.4k (Table 3). SWE Refactor Bench, Sol medium cost $6.0 and $24.8 (Table 2). Exceptions: Claude Sonnet 5 latency 962.37 s to 824.63 s (Table 1), and tokens 15.9B to 13.4B with cost $7.1k to $5.8k at medium effort in Table 3 (§4.2).
- effect: hurts
- reader: cost is higher in every row of Table 1 that was read and in all rows of Table 3 but Sonnet 5, so the direction is clear; the size depends on whether the baseline cost is a leaderboard figure or a matched run, which is not marked. The baselines have no extra budget, so part of F1's gain may be spent compute. F4's control addresses this only inside HERMES.

### F3 · practice · per-file-resident-agents · E4
- practice: replace the per-file Dev-Primitives with one centralized Editor that receives the same activation-selected components and edits them jointly, with the same activation, execution, diagnosis, B = 3 and GPT-5.6 Sol at medium effort (G).
- claim: the Dev-Primitive abstraction helps beyond localization; "the difference cannot be attributed to component localization" (G).
- evidence: single editor against HERMES: SWE-bench Verified 93.4 against 97.0, SWE Refactor Bench 16.8 against 31.0, Terminal-Bench 38.8 against 51.8, DevOps-Gym 44.21 against 55.41 (Table 13). The editor uses 10 to 14% fewer tokens and 11 to 16% lower cost (G). On Terminal-Bench, an editor that generates candidates until tokens and cost match (6.7B and $3.35k against 6.8B and $3.40k) reaches 45.5 against 51.8 (Table 14); matching recovers 6.7 points, 6.3 remain.
- effect: helps
- reader: a real control on equal tasks and equal budget, and the strongest evidence in the paper for the design. One backbone, one run per cell, no variance given for Table 13 or 14. The authors define the control, so a weaker editor prompt would widen the gap; the paper does not say how the editor was prompted beyond the description. The editor also reads all files in one context, which is the failure the authors predict.

### F4 · practice · inter-file-messaging · E4
- practice: let the activated primitives send each other directed messages before the round ends; the ablation keeps local reasoning and editing but removes all messages (F.6).
- claim: communication matters most where changes span files (§4.5).
- evidence: GPT-5.6 Sol without messaging: SWE-bench 94.2 against 97.0 (−2.8), SWE Refactor Bench 23.5 against 31.0 (−7.5), Terminal-Bench 46.1 against 51.8 (−5.7), DevOps-Gym 50.34 against 55.41 (−5.07) (Table 9). Same ordering for Claude Sonnet 5 (−3.0, −5.5, −4.6, −4.37) and Qwen3-8B (−2.8, −4.0, −4.6, −3.74) (Table 11).
- effect: helps
- reader: an ablation, graded E4. Single run per cell; SWE Refactor Bench has only 20 tasks and its repeat spread is ±1.3 (G), so the 7.5 points are well outside it. The same finding is shared by three backbones, which is the main support.

### F5 · practice · execution-feedback-in-revision · E4
- practice: feed the output of actually running the modified repository (exit codes, test failures, runtime errors, logs) into revision; the ablation withholds those observations and has diagnosis inspect the code statically (F.6).
- claim: execution feedback matters for revision, second in size to diagnosis (§4.5).
- evidence: GPT-5.6 Sol without execution feedback: SWE-bench 93.8 (−3.2), SWE Refactor Bench 21.5 (−9.5), Terminal-Bench 43.6 (−8.2), DevOps-Gym 48.17 (−7.24) (Table 9). Sonnet 5 and Qwen3-8B show the same order (Table 11).
- effect: helps
- reader: an ablation, graded E4. The ablated variant keeps the rest of HERMES but is a degraded one, since diagnosis then works without evidence. Task-visible tests and reproduction scripts only; held-out tests are not exposed (F.1).

### F6 · practice · failure-attribution-before-revision · E4
- practice: a separate diagnosis step reads the execution result and returns PASS or FAIL, and on FAIL names the suspected root cause and the components implicated, so that only those are reactivated; the ablation removes this module but keeps execution and raw outputs, so activation interprets the output itself (§3.3, F.6).
- claim: "diagnosis feedback matters most" among the mechanisms ablated (§4.5).
- evidence: GPT-5.6 Sol without diagnosis feedback: SWE-bench 92.6 (−4.4), SWE Refactor Bench 20.0 (−11.0), Terminal-Bench 41.2 (−10.6), DevOps-Gym 46.73 (−8.68) (Table 9). Sonnet 5: −5.2, −9.0, −9.1, −8.01; Qwen3-8B: −5.0, −6.0, −8.5, −7.65 (Table 11). Diagnosis cannot override a failing deterministic check (B.4, F.1).
- effect: helps
- reader: an ablation, graded E4. The module is one LLM call (F.1), so the ablation tests whether a dedicated structured call helps against the activation call reading raw output, not whether attribution as such helps. Single run per cell.

### F7 · practice · on-demand-component-activation · E4
- practice: instantiate only the primitives the current plan needs and change the active set after each failure; the ablation activates everything found in the initial analysis at the start and keeps it active (F.6, G).
- claim: on-demand activation limits unnecessary calls and interference; it costs at most 3.0 points when removed but raises cost 1.61 to 1.88 times (§4.5).
- evidence: GPT-5.6 Sol without on-demand activation: SWE-bench 95.8 (−1.2), SWE Refactor Bench 28.0 (−3.0), Terminal-Bench 49.4 (−2.4), DevOps-Gym 53.26 (−2.15) (Table 9). Average primitive calls per task with and without: 9.6 and 28.7 (SWE-bench), 25.1 and 64.3 (SWE Refactor Bench), 14.2 and 39.6 (Terminal-Bench), 11.7 and 33.2 (DevOps-Gym); relative cost 1.61, 1.88, 1.73 and 1.67 times (Table 15).
- effect: helps
- reader: an ablation, graded E4; the accuracy effect is the smallest in the paper and within what one run can move on 20 tasks, while the cost effect is large and consistent across four benchmarks. The ablation does not activate the whole repository, only the initial candidate set (G), so it understates what naive activation would cost.

### F8 · practice · revision-budget · E4
- practice: allow the activate, edit, execute, diagnose loop up to B revision rounds; sweep B from 0 to 5 with GPT-5.6 Sol (F.3).
- claim: most of the gain comes in the first three rounds (§4.5).
- evidence: Table 12, B = 0, 3 and 5: SWE-bench 92.2, 97.0, 97.2; SWE Refactor Bench 18.5, 31.0, 31.5; Terminal-Bench 39.7, 51.8, 52.7; DevOps-Gym 45.91, 55.41, 55.88. B from 0 to 3 adds 12.5, 12.1, 9.50 and 4.8; from 3 to 5 adds 0.5, 0.9, 0.47 and 0.2 (F.3).
- effect: helps
- reader: a dose sweep on equal tasks, graded E4; the cost at each B is not given. The B = 3 default was picked from this same sweep on the test benchmarks, so the 97.0 and 31.0 in the main tables are not held out from the choice. HERMES at B = 0 on SWE-bench Verified (92.2) is below the mini-SWE-agent baseline on the same Sol backbone (96.20, Table 1), so on that benchmark the gain over the baseline comes from the revision loop (reader's comparison across two tables).

### F9 · practice · strong-model-for-diagnosis-small-model-for-edits · E4
- practice: keep every Dev-Primitive on Qwen3-8B and assign a larger model to activation, to diagnosis, or to both (§4.3).
- claim: with strong activation and diagnosis models, Qwen3-8B primitives "remain within 4.5% of the homogeneous GPT-5.6 Sol configuration" and reduce Terminal-Bench cost by 26.2% (Abstract); diagnosis helps more than activation (§4.3).
- evidence: all-Qwen3-8B 80.6, 10.5, 27.6, 37.48 on the four benchmarks. Only diagnosis on GPT-5.5: 86.4, 16.5, 46.1, 43.25 (Terminal-Bench +18.5); only activation on GPT-5.5: 84.4, 13.5, 36.7, 41.58 (+9.1) (Table 6). Sol for activation and diagnosis, Qwen3-8B primitives: 94.2, 26.5, 50.6, 52.30 against all-Sol 97.0, 31.0, 51.8, 55.41 (Table 6). Terminal-Bench cost: all-Sol $3.40k, 51.8; Sol, Qwen3-8B, Sol $2.51k, 50.6 (26.2% lower, reader's arithmetic); Sol, Qwen3-8B, GPT-5.5 $2.13k, 49.7 (37.4% lower, §4.3, Table 7).
- effect: mixed
- reader: better than all-small on every cell and cheaper but lower than all-Sol on every cell, hence mixed. A comparison on equal tasks with one run per cell. The cost figure is API list cost for hosted models; Qwen3-8B ran locally on A40 GPUs with a 32K context window, and its cost is $0.70k for Terminal-Bench (Table 7), a number the paper does not derive. Whether a cheaper hosted model could replace Sol is not tested.

### F10 · observation · localization-recall-and-task-success · E3
- practice: none applied; selection recall and precision of the activated files against the files of the reference patch (or an oracle's files), split by solved and failed tasks (§4.4, F.4).
- claim: "Solved tasks consistently exhibit higher selection recall than failed tasks", by 16.5 to 24.7 points (§4.4).
- evidence: recall with GPT-5.6 Sol, solved against failed: SWE-bench Verified 96.1 and 71.4, SWE Refactor Bench 94.7 and 78.2, Terminal-Bench 93.5 and 74.8, DevOps-Gym 95.0 and 76.6; overall recall 95.4, 83.3, 84.5, 85.7; precision 72.6, 68.4, 64.9, 70.3; 4.7, 12.6, 6.8 and 5.4 primitives activated on average (Table 8).
- effect: helps
- reader: a correlation inside one system, not a manipulation. A task that is easy may be both selected well and solved. Targets for three of the four benchmarks are not reference patches (F.4); on SWE Refactor Bench "solved" means a non-zero composite score. The case study shows a correct patch with low overlap (H).

### F11 · observation · harness-gain-shrinks-on-strong-models · E3
- practice: none applied; the same HERMES-over-baseline gain compared across backbones of different baseline strength (§4.2, I).
- claim: gains "compress on frontier backbones that already resolve most instances" (§4.2); "gains are also smaller in already saturated settings" (I).
- evidence: SWE-bench Verified: Claude Opus 5 97.00 against 97.00 (0.00), GPT-5.6 Sol 96.20 against 97.00 (+0.80), GPT-5 Mini +19.40 (Table 1). Terminal-Bench 4.0: Opus 5 against Claude Code +1.5 and +1.2 at medium and max effort, against +25.2 and +27.6 for Sonnet 5 (Table 3).
- effect: mixed
- reader: the effect is large on weaker baselines and none on the strongest, hence mixed. The baselines differ by product as well as model (Claude Code, Codex, mini-SWE-agent), and ceiling effects on SWE-bench Verified explain part of it. The Claude Code baseline on Sonnet 5 scores 10.6 and 12.4 on Terminal-Bench against 47.0 and 51.8 on Opus 5, which suggests some baseline rows are configured poorly, but the paper does not say so.

## Limits stated by the authors

- Extra inference cost and latency from multiple primitives, execution and diagnosis (Appendix I).
- Gains are smaller in saturated settings, such as SWE-bench Verified with the strongest backbones (I).
- Results depend on activating the right components and on informative execution feedback; missed dependencies or sparse runtime signals limit recovery (I).
- Files are the only primitive granularity tried, and only four benchmarks (I).
- Qwen3-8B is served locally with Ollama, other models by API, so results may vary with deployment and model updates (I).
- Selection recall and precision measure agreement with the developer patch, not every valid repair path (H).
- SWE Refactor Bench has 20 tasks, so its aggregate is sensitive to run-to-run variation (G).

## Reader's notes

- Every number for HERMES comes from the authors' implementation and each HERMES cell is a single run (§4.1); only Terminal-Bench reports variation across 5 runs and SWE Refactor Bench a 3-run repeat for one cell (G).
- Baseline rows combine "publicly reported results and controlled baseline runs" and the tables do not mark which row is which (F.8). A leaderboard baseline may have a different tool set, budget or prompt.
- HERMES may write its own reproduction tests and run repository tests during solving (F.1); whether the baselines had the same permission is not stated.
- The same HERMES value is reused as the comparison point against several baselines on one backbone, for example 36.07 for Claude Sonnet 4 against Claude Code, OpenHands, mini-SWE-agent and Aider (Table 4), so those four gains (+8.53 to +31.70) differ only by the baseline, and the low Aider and mini-SWE-agent baselines (4.37 and 9.67) inflate them.
- The comparison with MAGIS and CodeTeam (Table 5) uses numbers from those papers "in their original evaluation settings" and GPT-5.6 Luna for HERMES; it is not a matched comparison. Not graded as a finding.
- Model names and benchmark versions (GPT-5.6, Claude Opus 5, Terminal-Bench 4.0) are as given in the paper; I did not check them.
- Time per task and token counts for SWE-bench Verified, DevOps-Gym and SWE Refactor Bench are partly missing (no token column in Tables 1, 2 and 4).

## Discrepancies

- The abstract writes "12.4%" and §1 writes "12.4 percentage points" for the same average; which rows enter the average is not stated.
- §4.1 says "seven backbones" and lists seven; Table 1 has 20 backbones and Table 10 lists more, including Claude Fable 5 and the GPT-5.4 and Gemini models.
- §4.5 calls replacing the primitives with a centralized editor "the most damaging" ablation and cites 14.2 and 13.0 points; on SWE-bench Verified that variant loses 3.6 (Table 13), less than removing diagnosis feedback, 4.4 (Table 9).
- Table 13 gives the single editor on Terminal-Bench 0.86 times the tokens and 0.84 times the cost; Table 14 gives 5.9B against 6.8B and $2.90k against $3.40k, about 0.87 and 0.85 (reader's arithmetic).
- §4.2 says the added coordination "does not always cost latency", citing Claude Sonnet 5 and DeepSeek-V4; against Claude Code on Opus 4.8 latency rises from 135.40 s to 482.73 s and against Codex on GPT-5.5 from 108.54 s to 398.74 s (Table 1).
