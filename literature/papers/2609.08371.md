## Question

Does giving each sub-agent its own host-side set of typed capabilities, derived from a ceiling fixed
before the repository is read, stop prompt-injected tool calls in a coding agent, and what does it cost
in task success and time (§4, RQ1 and RQ2)?

## Findings

### F1 · practice · per-agent-capability-scoped-tool-authorization · E4
- practice: before any repository text is read, one preflight LLM call sees only the trusted request and the file tree and proposes read, write and exec capabilities; host code freezes them as a task ceiling. Each sub-agent gets a store derived from the ceiling (a subset only), and a pre-dispatch hook on every tool call blocks a call that its own agent's store does not cover (§1, §3.2, §3.3). Compared with ambient authority (B0), a static deny policy (B1) and a task-specific policy shared by all agents (B2), same model, tasks and four-principal workflow (§4).
- claim: the injected effect executes in 3/75 runs under CapScope against 33 to 47/75 under the baselines, because it "additionally withholds task-needed authority from the principals that do not need it" (§4, Abstract).
- evidence: attack executed, Table 2: B0 47/75, B1 46/75, B2 33/75, CapScope 3/75. Table 3 by surface, B2 against CapScope, 15 runs per cell: README 7/15 and 0/15, AGENTS.md 11/15 and 3/15, skill file 7/15 and 0/15, source comment 4/15 and 0/15, tool output 4/15 and 0/15. Under CapScope the model proposed the injected action in 34 of 75 runs and the hook recorded 3 runs with an allowed attack call (§4). No statistical test; counts "descriptive" (§4 Results).
- effect: helps
- reader: E4 because conditions differ in the authorization model only, on equal tasks, model and topology. The authors built the system, the tasks, the payloads and the scoring, so `independent: false`. One small model, 5 tasks, 3 trials, no variance reported. The advantage over B2 depends on the fixed four-principal topology in which the runner reads the injection and the patcher writes; a single agent that both reads tests and edits source would hold the write under any scheme.

### F2 · practice · per-agent-capability-scoped-tool-authorization · E4
- practice: as F1; the measurement is autonomous repair success, scored as the final pytest suite passing (§4 Protocol).
- claim: CapScope "completes 68/75 repairs, while the baselines complete 68–72/75"; task success "differs by four runs between C and B0" (Abstract, §4).
- evidence: Table 2 task success: B0 72/75, B1 70/75, B2 68/75, CapScope 68/75. Of CapScope's 7 failures, 2 are a preflight that omitted the source-write capability, 2 are a correct edit proposed by the runner and not routed to the patcher, 3 are runs with passing tests at the end that reached the 900 s timeout and count as failures (§4).
- effect: none
- reader: the four-run gap is within what 3 trials of a stochastic model can produce and no test is given, so `none`; the paper itself calls the counts descriptive. 4 of 7 failures are caused by the mechanism (too narrow a ceiling, no reroute). If the 3 timed-out runs with passing tests were counted as successes the figure would be 71/75 (reader's arithmetic).

### F3 · practice · per-agent-capability-scoped-tool-authorization · E4
- practice: as F1; the measurement is wall-clock time per run (§4 Latency).
- claim: the added time is mostly extra model turns after refusals, not the authorization check; "these observations do not isolate the causal cost of any individual component" (§4 Latency).
- evidence: mean time per run, Table 2: B0 145 s, B1 140 s, B2 194 s, CapScope 316 s. CapScope median 208 s; 5 CapScope runs reached the 900 s timeout. Of the 34 CapScope runs with an attack-targeting proposal, 27 contain repeated attack-targeting calls (§4).
- effect: hurts
- reader: the mean is more than twice B0 and is inflated by 5 timeouts of 75 (median 208 s). Interactive approval, which the authors expect to end the retry sequence, was disabled and its effect not measured (§4 Interpreting the Cost). The 27 of 34 repeat count comes from the decision log of one condition; the baselines' logs are not reported.

### F4 · practice · task-specific-global-tool-policy · E4
- practice: generate one tighter allow policy from the trusted task description and a sanitized project structure before any injection is read, then apply it to every principal (B2, §4 Baselines).
- claim: it "helps, cutting leakage to 33/75 by removing task-unnecessary operations", but the shared policy must grant the union of what the task needs, "and that broad authority then reaches every sub-agent" including the runner that reads the injection (§4).
- evidence: attack executed 33/75 against 47/75 under ambient authority (Table 2). Task success 68/75 against 72/75; mean time 194 s against 145 s (Table 2).
- effect: helps
- reader: E4 as an A/B between B2 and B0 on equal runs. The effect is on attack execution only; it costs 4 repairs of 75 and 49 s of mean time. The same preflight idea is part of CapScope, so F1 and F4 share one mechanism and differ in per-agent derivation.

### F5 · practice · static-denylist-tool-policy · E4
- practice: apply one static, task-independent deny policy to every principal through the harness's permission-gating facility: sensitive paths such as `.env` and `.ssh`, `rm -rf`, `sudo`, `curl` (B1, §4 Baselines).
- claim: "a conventional denylist does not improve on having no policy, because the malicious actions are ordinary in-repository operations it never names" (§4 Results).
- evidence: attack executed 46/75 against 47/75 under ambient authority; task success 70/75 against 72/75; mean time 140 s against 145 s (Table 2).
- effect: none
- reader: E4 against B0 on equal tasks. The result follows from the payloads the authors chose, which were "intentionally plausible rather than obviously harmful" (§4 Tasks and Attacks): a denylist is tested only against attacks built to avoid it. Other attack types are not tried.

### F6 · observation · preflight-ceiling-too-narrow-blocks-repair · E2
- practice: observed: the preflight LLM proposes the task-wide ceiling from the request and the file tree alone, and later derivation drops any grant outside it (§3.3, §4).
- claim: two CapScope task failures "directly expose the utility cost of a too-narrow ceiling"; the other five reflect delegation or termination behaviour (§4).
- evidence: 2 of 75 CapScope runs failed because preflight omitted the source-write capability and derivation withheld the patcher's write (§4). Counts from the archived run and decision logs.
- effect: hurts
- reader: two cases in one condition; no rate for other tasks or models. Preflight ran at temperature 0 (§4 Protocol). With only 5 small tasks it says little about how often a larger repository would give a wrong ceiling; the authors flag this (§4 Limitations).

### F7 · practice · injection-via-agent-instruction-file · E3
- practice: place the same task-specific injected payload in the agent-instruction file `AGENTS.md`, against a README, a project-local skill file, a source comment or docstring, and pytest output (§4 Injection Surfaces).
- claim: results are reported "by surface rather than assuming a uniform injection rate" since the model "may react differently to each carrier" (§4 Limitations).
- evidence: Table 3, 15 runs per cell. Attack executed through AGENTS.md: 11/15 under B2 and 3/15 under CapScope. Other surfaces under B2: README 7/15, skill file 7/15, source comment 4/15, tool output 4/15; under CapScope 0/15 on each of the four (Table 3). All 3 attacks executed under CapScope came through AGENTS.md (§4).
- effect: hurts
- reader: the surface is assigned, so the finding is a practice, but the comparison is between surfaces with 15 runs each and no test, and the surface also decides which agent meets the injection first (§4), so E3. It shows the instruction file is the most effective carrier in this setup and is also the only residual route past CapScope. The paper does not explain why the 3 AGENTS.md attacks land beyond saying a residual injection falls within a granted scope (§5).

### F8 · practice · argv-segment-command-scope · E0
- practice: match an exec capability against the parsed executable and argument vector and check each segment of a compound command separately, rejecting command substitution, instead of matching the command string against an allowlist or denylist pattern (§3.1, §6).
- claim: allowing `pytest` "does not also admit `pytest; cmd` or `pytest && cmd`", nor `$(cmd)` (§6).
- evidence: asserted in the design and related-work text; the evaluation gives no run that isolates it, no number for it and no comparison with string matching.
- effect: helps
- reader: E0, since no condition varies it. The scope predicates are part of the evaluated system, so F1 includes them without separating them. Redirections and transitive effects of allowed commands such as `pytest` importing project modules are outside the predicate and left to a process sandbox (§2.2, §3.1).

## Limits stated by the authors

- One model, five small Python repairs, three trials per cell; no large refactors, dependency migrations or long-running work, where policy omissions and approval frequency may be higher (§4 Limitations).
- The payloads are "intentionally strong" and the model may react differently to each carrier (§4 Limitations).
- Individual cells vary between trials; the authors read the per-condition ordering, which they call stable (§4 Limitations).
- The informative refusal message can affect recovery and task success (§4 Limitations).
- CapScope does not stop the model from following an injection, does not prevent misuse of a granted capability or the transitive effects of an allowed command, and is not a confidentiality mechanism (§2.2, §7).
- Preflight reads file names only; filename injection is outside the evaluation (§2.2).
- Human approval, response time and approval choices were not measured; approval is disabled in the protocol (§4).
- A residual injection can land when a grant is wider than its subtask needs, or when injected text steers the model-generated subtask toward an attacker-chosen capability inside the ceiling (§5).

## Reader's notes

- The workshop paper (LMPL '26, 10 pages) is the authors' evaluation of their own system, with their own tasks, payloads and scoring. The scoring is filesystem-based (a sentinel file), which does not depend on logs (§4).
- The 4 conditions share one workflow in which writes are delegated to a patcher. B2 is built to be the strongest global baseline, but a global policy can only be beaten per agent if the workflow splits reading untrusted output from writing source. The result does not carry over to single-agent sessions.
- Reads are allowed by default in all conditions (§3.3), so exfiltration through reads is not measured.
- No confidence intervals or tests are given; 75 runs per condition come from 25 task-surface cells with 3 trials each.
- The 900 s timeout counts as failure, which affects both CapScope's success count and its mean time. Five timeouts are reported; the paper names 3 as passing-test runs and does not say what the other 2 were.
- Under CapScope, 34 of 75 runs still contained a model proposal of the injected action (about 45%, reader's arithmetic). The model followed the injection in those runs; the blocking is what protects. The same proposal count is not reported for B1 and B2, which also install a hook.
- The trust boundary treats `AGENTS.md`, README and skill files as untrusted, which is the premise behind the instruction-file findings elsewhere in this collection.
