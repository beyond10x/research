## Question

In one agent harness used daily for six weeks, which agent failures occur and come back after a fix
(RQ1), how much stale documentation does an LLM audit find (RQ2), and does a past fix still change
agent behaviour when the original failure is replayed, depending on the model (RQ3) (§1)?

## Findings

### F1 · observation · documentation-drift-as-failure-class · E2
- practice: failures of the harness were logged by category in the author's repository for six weeks and coded in two LLM passes; nothing was assigned (§4.1, Table 1).
- claim: "Drift is the largest failure class and keeps returning after new checks" (§5.1).
- evidence: Table 1: stale documentation is 48 of 118 failures (40.7 %), of which 13 recurred, 0 did not and 35 are unknown. "Wrong fact stated by an agent" is 20 (16.9 %). 35 of the 48 were recorded on 14 October from two full-repository LLM audits that found 38 stale statements (§5.1); without that day drift is 13 of 83 incidents (§7).
- effect: hurts
- reader: counts with nothing to compare against. The author says recorded counts "depend on how hard I looked" (§7). Recurrence is judged "Did not" only after 7 days, so 71 of 118 rows are Unknown and no drift row is "Did not"; recurrence coding has κ = 0.56 (Table 2).

### F2 · practice · precommit-invariant-check · E3
- practice: after each drift failure, add one deterministic pre-commit check (lint.py, 17 checks in total) for that form of staleness, plus a post-edit reminder hook on 14 October (§3, §5.1).
- claim: "Each code check removed the narrow pattern it encoded"; statements that no check covered "kept going out of date" (§5.1).
- evidence: §5.1: a check for coupled files on 24 September, stale skill and script counts on 3 October, retired script names on 9 October; "Within one to nine days, a different form appeared." Weekly failure counts and the checks added per week are in Figure 2, values in the figure only. No recurrence count per check is given.
- effect: mixed
- reader: before and after on one repository, no run without the checks, so E3 at most. The claim that each check removed its pattern is not quantified in the text. The effect is mixed because the pattern went away and the class did not.

### F3 · practice · precommit-invariant-check · E4
- practice: replay the original task for the stale skill-count failure on Claude Sonnet 5.5 in a clone just before the fix (A) and in a clone with only lint Check 12 cherry-picked (B), headless, 3 runs per condition (§4.3).
- claim: the check stopped the failure "in every run" (abstract, §5.3).
- evidence: Table 3: the failure occurred in 3 of 3 runs without the check and 0 of 2 with it (the third run declined the task under the deadline focus rule). In B the linter blocked the first commit and printed the stale lines and the true count; the agent then corrected them (§5.3). One-sided Fisher's exact p = 0.10 (§7).
- effect: helps
- reader: an A/B on equal tasks, so E4, with 3 against 2 runs, p = 0.10 by the author's own calculation and one scenario chosen by the author. It tests a check whose message names the exact lines, not a prose rule. The author's system, so `independent: false`.

### F4 · practice · precommit-invariant-check · E4
- practice: as F3 for the em-dash scenario (lint Check 9 blocks em-dashes in letters; a prose ban is in both conditions), run on Sonnet 4.5, Sonnet 5, Sonnet 5.5 and Gemini 3.8 Flash, 3 runs per cell (§4.3, Table 4).
- claim: "the lint check stopped the one em-dash that reached a commit attempt (Sonnet 5)"; the check rejected the commit and the agent fixed it (§5.3).
- evidence: Table 4, committed cover letters with an em-dash, A against B: Sonnet 4.5 1 of 3 against 0 of 3; Sonnet 5, Sonnet 5.5 and Gemini 3.8 Flash 0 of 3 against 0 of 3. In one B run Sonnet 5 drafted an em-dash and the lint check rejected the commit. The two older Sonnets wrote an em-dash in 2 of 12 drafts (§5.3). On Sonnet 5.5 the scenario "tests only the lint check" (§5.3).
- effect: helps
- reader: E4 by design, but the evidence is one committed em-dash without the check against none with it, and one rejected draft. No test is stated. The prose ban was present in both conditions, so this does not show whether the prose rule is needed.

### F5 · practice · prose-rule-after-failure · E4
- practice: a written prompt rule that 1 to 5 minutes is the normal run-time estimate and that the real time is asked for when an estimate is off by 2× or more, present (B) or absent (A) (§4.3).
- claim: "the prompt rule made no difference" on Sonnet 4.5, the only older model that did the task (§5.3).
- evidence: Table 4, estimates above twice the actual time: Sonnet 4.5 2 of 3 without the rule and 2 of 3 with it. Sonnet 5 and Sonnet 5.5 declined all 6 runs each (deadline focus rule triggered by the host clock); Gemini 3.8 Flash 0 of 2 and 0 of 1 executed runs overestimated, with 1 to 3 minutes estimated against 1.5 to 6 actual (§5.3).
- effect: none
- reader: one model with data, 3 runs per condition, no test. On Sonnet 5.5 the scenario gives "no measurement of the estimation rule" (§5.3).

### F6 · practice · counterfactual-replay-of-lessons · E4
- practice: replay a past failure's original task on the current model in a throwaway git clone without the lesson (A) and with only the lesson (B), same neutral commit message, to see whether the lesson is still needed (§4.3, §6).
- claim: "Lessons may outlive the model failures that motivated them"; "three of the four finished failures did not occur in my replay, with or without their fixes" (§6).
- evidence: Table 3, Sonnet 5.5, failures in A against B: superseded log decision (prose rule) 0 of 3 against 0 of 3, with the latest entry read first in all 6 runs; em-dash 0 of 3 against 0 of 3; destructive git reset (guard hook) 0 of 3 against 0 of 3, no run tried `git reset --hard`. 30 headless sessions across five scenarios took 10 minutes and cost about $3.55 in API-equivalent tokens (§6). The focus-guard skill declined 7 of the 30 runs because the host clock read 19 October 2026 (§7).
- effect: none
- reader: the author states that the em-dash and reset scenarios "do not test whether their lessons are still needed" (prose ban in both conditions; no run reached the destructive command), so only the superseded-decision scenario removed a prose rule and reached its trigger (§6). Absence of failure in 3 runs is not absence of the failure. The original incidents were on Opus models and Antigravity, the replay on Sonnet (§7).

### F7 · practice · monthly-llm-documentation-audit · E3
- practice: a monthly scheduled read-only headless agent with a fixed prompt audits the documentation against the file tree and git history; here run 3 times on each of Haiku 5.5, Sonnet 5.5 and Opus 5.5 on a snapshot of 14 October against 47 real stale statements (11 borderline) and 20 planted errors (§3, §4.2).
- claim: "a single LLM audit pass misses half" of drift; precision is high (§6, §5.2).
- evidence: §5.2, mean recall of the 47 real items: Haiku 5.5 26.2 % (7 to 18 items), Opus 5.5 41.1 % (16 to 21), Sonnet 5.5 49.6 % (22 to 25); the three Sonnet runs together 63.8 % (30 of 47). Planted errors, mean recall: 65.0 %, 80.0 %, 83.3 %. All nine runs together missed 12 of 47. Precision 0.93 to 1.00 per run; 8 false alarms and 9 genuine stale statements outside the key.
- effect: mixed
- reader: models compared with each other; no comparison with no audit or with a human pass, so E3. The key is the set of statements the author corrected on one day, 22 of the 47 had already been found by an earlier LLM audit, which the author says favours detectable drift (§4.2). Opus scored the reports and the author reviewed the scores; only 5 key items and 6 match scores were spot-checked. Opus delegated reading to Haiku subagents, an untested explanation for its score below Sonnet.

### F8 · observation · drift-detection-by-kind · E3
- practice: none applied; the audit results of F7 are split by kind of error (§5.2).
- claim: detection depends strongly on whether a directory listing or paired table contradicts the statement; "semantic and temporal drift" is missed in two-thirds of runs (§5.2).
- evidence: §5.2, pooled over 9 runs (180 item checks) on planted errors: cron schedules 27 of 27, renamed identifiers 25 of 27, dead file paths 43 of 54, modified rule text 7 of 9, item counts 26 of 36, script behaviour 6 of 18, a deadline date 3 of 9. Real drift, all nine runs: 30 of 37 items contradicting another current file, 2 of 5 only visible in git history, 3 of 5 visible from both.
- effect: mixed
- reader: the per-kind groups are small (one planted deadline error, 2 script-behaviour errors; 5 real items for each of two groups) and the author planted the errors. The same planted items are checked 9 times, so the 180 checks are not independent.

### F9 · practice · size-cap-on-always-loaded-rule-file · E3
- practice: a pre-commit lint check capping the word count of AGENTS.md, added on Day 14 (18 September) (§5.1).
- claim: "Capping the main rule file coincided with growth in on-demand skills"; total rule text did not shrink (§5.1).
- evidence: §5.1, Figure 3: AGENTS.md 916 words on Day 0, a peak of 3,543 on Day 14, 1,927 at the end of Day 14 and 1,435 on Day 41. Total rule text (AGENTS.md, nested rules, on-demand skills) 4,921 words on Day 0 and a peak of 17,366 on Day 18, a 3.5-fold growth; rules moved into SKILL.md and nested directory files.
- effect: mixed
- reader: before and after on one repository, no control. The always-loaded file shrank; the paper measures no effect of that on agent behaviour, so "helps" is not claimed.

### F10 · practice · manual-rule-simplification-pass · E3
- practice: the one manual pruning pass of the study, on Day 20 (24 September): merge repeated clauses, cut long explanations (§3, §5.1).
- claim: rule text resumed growth right after; the harness "had no automated mechanism to retire old lessons" (§3, §5.1).
- evidence: §5.1, Figure 3: total rule text fell by 32 % to 11,877 words, then grew by 27 % to 15,122 words by Day 41.
- effect: mixed
- reader: one pass, one repository, no measure of agent behaviour before or after. Consistent with the growth that 2608.11095 reports across repositories, which the paper cites.

### F11 · practice · pretool-command-guard-hook · E2
- practice: a pre-tool hook (guard.py) matches shell commands against regular expressions and blocks destructive operations in all three runtimes (§3).
- claim: the hook blocks real destructive commands but has false positives and regex gaps (§5.1).
- evidence: from 74 Claude Code transcripts, 20 September to 14 October: 13 of 19 recursive deletions (`rm -rf`) blocked and all 4 attempted force-pushes (§5.1). False positive: a harmless documentation edit that quoted a forbidden command in a commit message was blocked, and recurred weeks later. Gap: the `git reset --hard` regex missed `git -C <path> reset --hard` (§5.1).
- effect: mixed
- reader: counts with nothing to compare against, so E2. The text does not say whether the 6 unblocked `rm -rf` commands were harmful or intended. The hook was never exercised in the replay (F6).

### F12 · practice · background-sync-during-agent-session · E2
- practice: a systemd timer ran `git pull --rebase --autostash` every few minutes, added as the fix to stop laptop agents editing out-of-date local copies (§3, §5.1).
- claim: the fix caused a new failure: it interfered with active agent sessions (§5.1).
- evidence: the sync log shows 197 autostash events; "some of them caused file conflicts mid-session" until 14 October, when a lock check was added that pauses background syncs while an agent is active (§5.1). The number of conflicts is not stated.
- effect: hurts
- reader: one case with a count of events and no count of harm, between E1 and E2; graded E2 for the number. It is the author's example of a fix-induced failure, and the paper ties it to harness-level forgetting in 2608.19013.

### F13 · practice · one-instruction-file-across-agent-interfaces · E1
- practice: one AGENTS.md and one set of skills loaded by three runtimes (Claude Code, Antigravity, a headless server agent); in the replay, Gemini 3.8 Flash in Antigravity ran the em-dash and run-time scenarios (§3, §4.3, §6).
- claim: "a markdown harness can govern agents across model providers and client runtimes", which the author says is suggested "but does not establish" (§6).
- evidence: §6 and §5.3: Gemini 3.8 Flash followed the same rules and skills without changes in the two replayed scenarios; the focus-guard skill declined 3 of its 6 estimation runs; it wrote no em-dash in 6 drafts (Table 4).
- effect: helps
- reader: two scenarios in which the failure mostly did not occur; the evidence shows that the skill loaded and fired, not that rule compliance holds in general. The harness was written mainly in Claude Code sessions (§6).

### F14 · practice · lesson-retirement-on-model-upgrade · E0
- practice: record the model version that motivated each rule with a re-test date, and on a model upgrade replay each lesson's trigger task without that lesson, archiving prose rules that no longer change outcomes; add a regression check before a new lesson goes live (§6, §8).
- claim: tools that evolve a harness "add lessons faster than they retire them", so rules should be re-tested and the obsolete ones retired (abstract, §6).
- evidence: no study of retirement itself; the proposal rests on F6 and on the growth in F9 and F10. A retirement test is only run by hand in F6.
- effect: helps
- reader: asserted as a recommendation; the retirement procedure was not applied or evaluated. The replay in F6 is a manual version of the first step.

## Limits stated by the authors

- One repository, one user who designed, maintained and studied it, so selection bias; no statistical generalisation (§7).
- The author designed the logging policy, wrote most fixes, chose the replay scenarios, approved the key and resolved every coding disagreement (§7).
- Recall of the keyword search that seeded the ledger was not measured; minor mistakes corrected in chat and not logged are absent (§7).
- Six weeks of data; incidents fixed in the last week had fewer than 7 days to recur and are Unknown (§7).
- Three runs per cell, with LLMs as coders, scorers and replayed agents; a one-sided Fisher p = 0.10 for 3 of 3 against 0 of 2 is "short of statistical significance" (§7, abstract: "exploratory").
- A replay that does not reproduce a failure may reflect a newer model or a reconstructed prompt that missed the trigger; the original incidents were on Opus models and in Antigravity, the replay on Sonnet and Gemini Flash; the host clock (19 October) made deadlines look imminent and the focus rule declined runs (§7).
- The 47-item answer key under-counts drift by at least 9 statements (§7).

## Reader's notes

- Recurrence is reported by failure category (Table 1). The paper's other split, by fix type, appears only as counts of how failures were fixed: 23 by a prose rule, 38 by executable code, 57 by correcting the document or record directly (§5.1). Whether code fixes recurred less than prose fixes is not given, and 71 of 118 recurrence cells are Unknown.
- Replay scenarios were picked because each had a clear task and a self-contained fix commit (§4.3). The task prompts were reconstructed from the incidents (§7), so a trigger in the original session may be missing.
- Scenario 5 on Sonnet 5.5 and Sonnet 5 produced no measurement (all runs declined), and scenario 1 lost one run in B, so the effective cells are smaller than the nominal 3.
- The study does not compare the harness with a harness-free repository, so no finding here measures whether the harness as a whole raised task success.
- The two ledger coders and the audit scorer are Claude models (Sonnet 5.5, Opus 5.5) that are also in the audited and replayed set; the author resolved every disagreement.
- Model names and dates are as printed (October 2026 models).

## Discrepancies

- §2 says the study differs from prior work by "tracking failure recurrence by fix type". The results give recurrence by category (Table 1) and only the number of failures per fix type (§5.1), not recurrence by fix type.

- 2603.00822: ContextCov, instructions turned into executable checks raise compliance from 67.0 % to 88.3 % (as cited).

- 2608.19013: Kang et al., harness-level forgetting, a harness change degrades earlier behaviour, guarded by a regression check.
- 2604.25850: Lin et al., Agentic Harness Engineering, gains come from tool design, middleware and memory more than system-prompt edits.
- 2607.12227: Wang et al., automated harness evolution overfits training benchmarks and does not beat simple baselines on held-out tasks.
- 2610.14224 and 2608.02276: Harness2 and Harness-R1, systems that add lessons or executable patches from failures.
- 2605.10039: McMillan, factorial study of 1,650 sessions, no significant effect of context-file length, order or conflict on instruction following.
- 2601.20404: Lulla et al., AGENTS.md files and the efficiency of coding agents.
