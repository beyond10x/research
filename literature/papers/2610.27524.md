## Question

Do memory systems built from an agent's earlier work in a repository help a code agent on a later task,
and under which history (related only, noisy, long) do they help or harm (§1)?

## Findings

### F1 · practice · cross-task-memory-system · E4
- practice: let the agent solve a repository's earlier tasks in chronological order, build memory from the trajectories with one of five memory systems (A-Mem, Mem0, MemOS, Supermemory, Claude-Mem), freeze it, then solve the base task with read-only access; compared with no memory (NoMem, 3 fresh runs) on 133 Improvement Tasks, which NoMem fails in at least 2 of 3 earlier runs (§3).
- claim: "memory consistently helps solve tasks that the agent fails without it" (§1); Resolved "rises from 35.3% for NoMem ... up to 42.6% with memory systems" (§4.1).
- evidence: Table 2, Resolved (%) under Relevant, Noisy, Repo history. NoMem 35.3 ±2.7. A-Mem 40.4, 38.1, 41.6. Mem0 40.1, 38.1, 41.1. MemOS 36.8, 37.3, 35.3. Supermemory 40.6, 40.6, 39.3. Claude-Mem 41.6, 40.1, 42.6. Rescue 9.9% to 13.2%, Harm 4.8% to 9.9% (§4.1). Steps 166.4 to 189.5 against 185.1 for NoMem; input tokens 5.82M to 6.68M against 6.45M (Table 2).
- effect: helps
- reader: the NoMem runs are fresh and independent of the runs that chose the subset, so the comparison is not distorted by selection on baseline failure (§3, E.1). Gains are 0 to 7.3 points against a three-run SD of 2.7 for NoMem and SDs of 1.1 to 5.3 for the systems; MemOS in Repo history (35.3) is equal to NoMem. Cost is counted for solving only and excludes the tokens that build memory (H.1). One agent, one model, Python only.

### F2 · practice · cross-task-memory-system · E4
- practice: as F1, on 50 Preservation Tasks sampled from the 211 tasks NoMem solves in at least 2 of 3 runs (§3).
- claim: "Regressions offset gains, especially on already solvable tasks"; "Even modest regressions can thus erase the gains from memory" (§4.1).
- evidence: Table 3. NoMem Resolved 94.0 ±2.0. Averaged over the five systems, Harm exceeds Rescue under Noisy history (3.7 against 3.2) and Repo history (3.2 against 2.6), and Resolved falls to 93.5 and 93.3 (§4.1). Per system Resolved ranges from 91.3 to 96.7 across scenarios (Table 3). On Improvement Tasks every system has Harm of 4.8 to 9.9 (Table 2).
- effect: mixed
- reader: the drop below NoMem is 0.5 to 0.7 points, inside the SD of 2.0, and the high NoMem baseline leaves little room for gain; the paper's own evidence is Harm against Rescue, with 95% bootstrap CIs that overlap (Table 3). Under Relevant history mean Rescue (3.4) is above mean Harm (2.5), so the effect is a gain in one scenario and a loss in two. The 50 tasks are a sample chosen for cost.

### F3 · practice · unrelated-history-in-memory · E4
- practice: add unrelated earlier tasks (7 to 21) to the related ones (3 to 10) that memory is built from (Noisy history), or add up to 35 recent earlier tasks of other base tasks (Repo history), against related-only history (Relevant) (§3).
- claim: "history noise tends to introduce regressions rather than reducing the benefit of useful history" (§4.1).
- evidence: Improvement Tasks, mean over the five systems, Relevant to Noisy: Rescue 11.7 to 11.5, Harm 7.1 to 8.0, Resolved 39.9 to 38.8 (§4.1, Table 2). Preservation Tasks: Rescue 3.4 to 3.2, Harm 2.5 to 3.7, Resolved 94.9 to 93.5 (§4.1, Table 3). FullTraj on Preservation: Harm 0.7 to 4.2, Resolved 97.3 to 92.7 and 90.0 under Repo (Table 3).
- effect: hurts
- reader: the scenarios share the same base tasks, so this is a controlled contrast. The paper hedges with "tends to": a Harm rise of 0.9 and a Resolved fall of 1.1 points are inside the per-system SDs (up to 4.3), and some systems go the other way (Supermemory Resolved 40.6 in both Relevant and Noisy; MemOS 36.8 to 37.3). The pattern is more consistent in Harm than in Resolved. Noisy history also holds more tasks, so quantity and relevance are not separated.

### F4 · practice · cross-task-memory-system · E3
- practice: compare patch alignment with the reference patch, with and without memory, on the 68 Improvement Tasks that also fail in all three fresh NoMem runs (§4.2).
- claim: "Memory mainly improves fine-grained code editing": it "rarely expands gold-file coverage but more consistently improves within-file localization and editing"; F2P gains are "much larger" than patch-alignment gains (§4.2).
- evidence: Table 4. NoMem File Recall 74.22, Line Recall 18.41, Edit Recall 11.02, F2P 18.10, P2P 97.39, Resolved 0.00. Only 2 of 18 non-NoMem settings (FullTraj and the five systems, times 3 history scenarios) exceed NoMem File Recall; 13 exceed Line Recall and 16 exceed Edit Recall, with maximum gains of 4.13 and 3.75 points. F2P 23.15 to 28.57 in all 18 settings; P2P 97.05 to 98.44. Resolved on these tasks 7.84 to 13.73 (Table 4).
- effect: helps
- reader: E3 and not E4 because the 68 tasks are selected for failing the same three NoMem runs that serve as the baseline, so NoMem Resolved is 0.00 by construction and any rerun variation shows as a gain; the paper says this subset allows improvements to be "more reliably attributed" to memory, which this selection does not secure. F2P and the recall metrics are also conditioned on failure. Line and Edit Recall gains are about 4 points or less against SDs of up to 3.6.

### F5 · observation · memory-misapplication-failure-modes · E2
- practice: manual inspection of failed trajectories of the five memory systems on the 76 tasks that NoMem solves in all three fresh runs, counting only failures where "memory visibly shapes the failing decision or edit" (§4.3).
- claim: agents "tend to follow memory as a solution rather than reassess it against the current task context"; four non-exclusive failure modes (§4.3).
- evidence: 115 such cases. Counts under Relevant, Noisy, Repo history and total (Figure 4): misapplied transfer 27, 30, 24 (81); compatibility mismatch 21, 13, 16 (50); scope expansion 15, 13, 16 (44); failure to revise 10, 11, 16 (37). No count of all failed trajectories is given.
- effect: hurts
- reader: a taxonomy from the authors' own reading of trajectories, with no stated coder count, agreement or blinding. The four counts sum to 212 for 115 cases (non-exclusive), and no denominator of memory-run failures or of NoMem failures on the same tasks is given, so the modes are not shown to be specific to memory. The "reuse without reassessing" cause in the abstract is the authors' reading of these cases.

### F6 · practice · raw-trajectory-replay-vs-compressed-memory · E4
- practice: put the raw, unselected trajectories of the earlier tasks into the agent's context in chronological order (FullTraj), against no history and against the five memory systems (§3).
- claim: "FullTraj substantially shortens the solving process" and uses fewer steps than memory systems (§4.4).
- evidence: FullTraj uses about 34% fewer steps and 28% fewer output tokens than NoMem, and 29% to 35% fewer steps and 28% to 34% fewer output tokens than the five memory systems, pooled over 183 instances (§4.4, Figure 5a). Steps on Improvement Tasks 141.7, 114.5, 113.1 against 185.1 for NoMem (Table 2). Input tokens 16.31M, 24.11M, 32.86M against 6.45M for NoMem (Table 2). Resolved 39.1, 37.3, 39.6 against 35.3 (Table 2); on Preservation Tasks 97.3, 92.7, 90.0 against 94.0 (Table 3).
- effect: mixed
- reader: steps and output tokens fall, input tokens rise 2.5 times to 5.1 times (reader's arithmetic from Table 2), and the paper reports no cost in money. Success is not higher than the best memory system, and on Preservation Tasks under Repo history it is 4 points below NoMem. The trajectories are the same agent's own runs on the same repository, a setting where raw replay is cheap to obtain. Every step reduction is shown for one agent and model.

### F7 · practice · raw-trajectory-replay-vs-compressed-memory · E3
- practice: as F6; the measurement is where in the solving process steps and calls fall, by stage and by action type (§4.4).
- claim: agents with raw trajectories "save these steps by reusing process information that compressed memories tend to omit" (abstract, §4.4).
- evidence: Figure 5b: the 46.2 to 60.6 step reduction against NoMem and memory systems is largest in the edit span (24.8 to 31.3 steps), with smaller drops before and after the edit. Figure 5c: 5.9 to 8.1 fewer search and 5.3 to 8.9 fewer read calls per trajectory, smaller reductions in test and edit calls. All trajectories finish within the 200-turn budget (§4.4).
- effect: helps
- reader: a comparison of counts. No run gives FullTraj a version without the process content, so "process information" is an interpretation of the pattern, and the text says "can lose" and "potential benefit". Less searching and reading can also come from seeing the earlier agent's file paths and edits, which is code content and not process.

### F8 · practice · cross-task-memory-system · E3
- practice: run 29 further memory systems, one run each, under Relevant history on a fixed 150-task subset (120 of the 133 Improvement Tasks and 30 of the 50 Preservation Tasks), with NoMem as three runs (Appendix F).
- claim: Appendix F runs these systems "to cover a wider range of memory-system designs"; Table 9 ranks them by Resolved. No separate claim is stated in the parts read.
- evidence: Table 9. NoMem 47.78 ±1.54. Best: causal-memory 52.67, ChronoHybridMem 52.00, Memory Bear 52.00. Worst: Mi-Memory 46.00, then 46.67 twice and 47.33 four times. 22 of 29 systems are above 47.78 and 7 are below it (reader's arithmetic from Table 9). Steps 172.89 to 194.99 against 176.93 for NoMem.
- effect: mixed
- reader: single runs against an SD of 1.54 for the baseline, and one task is 0.67 points on 150 tasks, so most of the ranking is within run-to-run variation; the paper gives no interval. Only a 4 to 5 point gap at the top is clearly above the baseline. Memory-build cost is not reported.

### F9 · practice · block-web-and-code-hosting-in-evals · E3
- practice: instruct the agent not to search for task solutions and block search engines and public code-hosting platforms at tool level, with local tools and dependency installation kept (§3, E.2).
- claim: with web access unrestricted, the agent "often retrieves" the original PRs and fix patches, so "the resolve rate reflect[s] answer retrieval rather than task solving" (§3).
- evidence: no-memory Claude Code with DeepSeek-V4-Flash resolves 93.31% ± 0.87% of the 344 SWE-bench Verified tasks with web access unrestricted and 73.16% ± 0.61% under the isolation protocol (§3).
- effect: hurts
- reader: `hurts` is the direction of the resolve rate, 20.15 points lower (reader's arithmetic); that is the protocol's purpose, and the finding says answer lookup inflates a benchmark score by about a fifth. The unrestricted run is described in one sentence with no setup, number of runs or leak-rate measure in the parts read, so it is E3.
## Limits stated by the authors

- Evaluation is limited to the SWE-bench Verified subset of MemDev-Bench under a single agent-model configuration (§6).
- The construction pipeline is not systematically compared with existing methods (§6).

## Reader's notes

- Every number comes from one agent (Claude Code) and one model (DeepSeek-V4-Flash, also for sub-agents), on Python repositories (§3, Table 6). The paper's three headline findings are stated for "code agents" in general.
- Authors built the benchmark and chose the scenarios; the five memory systems are third-party and all integrate with Claude Code (§3). The 29 systems of Table 9 are GitHub projects, many by single maintainers, and were run once.
- Token cost excludes the cost of building memory from the historical tasks (H.1), which for FullTraj is zero and for LLM-based memory systems is not. Cost is therefore partial for F1 and F8.
- Historical trajectories were produced by the same agent solving the earlier tasks without memory (E.1); the historical tasks are scored by the same pipeline, but the historical results are not reported.
- The Improvement and Preservation subsets are selected on earlier NoMem runs, then 68 and 76 tasks are chosen on fresh NoMem runs for Tables 4 and §4.3, a second selection on the baseline outcome.
- Relevance labels are from DeepSeek-V4-Pro with human verification: 87.82% of LLM labels retained, blind relabeling of 2,270 samples gave Fleiss kappa 0.88 for level and 0.80 for relation type (§2.2). Strong and Weak Related PRs are merged PRs only (§2.2).
- The paper's generative AI statement lists experimental design, analysis and writing among the uses.

## Discrepancies

- §4.1 reports mean Resolved falling from 39.9% to 38.8% as a trend ("tends to fall"), while the per-system changes between Relevant and Noisy are within the SDs in Table 2 and MemOS rises (36.8 to 37.3).
- Table 4's NoMem File Recall is 74.22 and Table 9's is 84.03; the subsets differ (68 tasks and 150 tasks), so this is not a contradiction, but the paper does not say so.
