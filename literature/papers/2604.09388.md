## Question

"What must the codebase encode before the next level of AI effectiveness is possible?" (§2.3). The
answer offered is a 6-level model in which each level adds one feedback mechanism (§3, Table 1):
Assisted, Instructed, Measured, Adaptive, Semi-automated, Fully Autonomous.

## Findings

### F1 · practice · instruction-files · E1
- practice: write the corrections the maintainer keeps repeating into files the agent reads at every session start: `CLAUDE.md`, `.github/copilot-instructions.md`, a card development guide, a PR template checklist (§3 Level 2, Table 2).
- claim: the same mistakes stopped recurring across sessions; the card guide "encoded approximately 90% of the reasons" the author had been rejecting PRs (§3 Level 2, §4.2 weeks 3–4).
- evidence: the author's account. The 90% is the author's estimate; no rejection counts before and after are given.
- effect: helps
- reader: one maintainer's recollection, no measurement of the effect.

### F2 · practice · test-coverage-gate · E2
- practice: 32 nightly test suites (compliance, performance, nil safety, accessibility, i18n, visual regression), an 80% coverage gate on every PR, a full coverage suite in 12 shards hourly on main (§4.2 weeks 5–8, Table 2).
- claim: testing "was the single most important investment in the entire journey"; tests are what make agent output trustworthy enough to automate (§3 Level 3, §8).
- evidence: end state only: 91% coverage, 32 suites (Table 3). Nothing compares agent output with and without the gate.
- effect: helps
- reader: the numbers describe the test estate; the ranking of testing above the other practices is asserted.

### F3 · practice · deterministic-tests · E1
- practice: find flaky tests weekly with a workflow that opens issues, and fix them before test results gate merges (§4.2 weeks 5–8, Table 2).
- claim: a flaky gate blocks good fixes and passes bad ones at random; "you cannot have autonomous AI development without deterministic tests" (§4.2).
- evidence: one case: a Playwright drag-and-drop test passed 85% of the time and took 3 days to fix (§4.2).
- effect: helps
- reader: one test; no count of wrongly blocked or wrongly merged PRs.

### F4 · practice · acceptance-rate-feedback · E2
- practice: record merged against closed agent PRs per issue category in `auto-qa-tuning.json`; weekly, raise the weight of high-acceptance categories and block categories under 20% (§3 Level 4, Table 2).
- claim: the system "learned what the maintainer values and stopped wasting cycles on what doesn't work" (§4.4 Case E).
- evidence: operator category 11 merged against 129 closed (8%), weight set to 0; accessibility at 62%, weight 0.93 (§4.2 weeks 9–12, §4.4 Case E).
- effect: helps
- reader: the inputs of the mechanism are shown; acceptance or cost after the weights changed is not.

### F5 · practice · scheduled-agent-loops · E2
- practice: run agents on timers instead of on request: issue triage every 15 minutes across 4 repositories, Auto-QA 4 times a day with 8 layers of checks, a PR monitor every 60 seconds, hourly production error monitoring that opens issues (§4.2 weeks 9–12, Table 3).
- claim: bug to fix in about 30 minutes and feature to implementation in about 60 minutes, at any hour (Table 3, §1).
- evidence: 654 Auto-QA issues created and resolved; 3,604 issues with the `ai-fix-requested` label; 5,273 of 5,282 issues closed (Table 5). Cases: issue #898 to merged PR #900 in 3 hours; issue #5390 filed 02:03, resolved 02:14 (§4.4 Cases A, D).
- effect: helps
- reader: how the 30 and 60 minute figures were computed is not stated (median, mean or typical). The 3-hour case is slower than the headline figure.

### F6 · practice · staged-feedback-levels · E3
- practice: add the mechanisms in the model's order: instruction files, then measurement, then automated response to the measurements, then unattended proposals, then unattended merges (§3).
- claim: "each maturity level unlocks a step change in throughput"; "you cannot skip levels" (§4.5, §3).
- evidence: Table 4, per day: PRs merged 16, 29, 40, 81; issues closed 4, 8, 32, 150; commits 44, 32, 45, 91, for Jan (16 days, L1–L2), Feb (28, L3), Mar (31, L4), Apr (26, L5–L6). Overall 4,499 PRs merged, 713 closed unmerged, 86.3% acceptance (Table 5).
- effect: helps
- reader: a before-and-after series on one project with no control. Level, calendar time, project size and number of agents all change together. The agents open many of the issues they close (654 Auto-QA issues, Table 5), so issues closed per day measures activity. "Cannot skip levels" has no supporting case: no project that skipped a level is observed.

### F7 · practice · session-concurrency-limit · E0
- practice: a queue processor limits concurrent agent sessions to 2 (§4.2 weeks 9–12).
- claim: it prevents sessions interfering with each other.
- evidence: none.
- effect: helps
- reader: stated in one sentence.

### F8 · practice · external-scheduler · E1
- practice: keep scheduling, restart and health checks outside the agent: systemd services, a systemd timer that decides when to send each agent a work order through `tmux send-keys`, a heartbeat check every 20 minutes that kills and respawns stale agents, a cap on respawns that then pages the human (§5.2).
- claim: it "eliminated the loop-reliability failures" of agent-side loops: sessions stopping on permission prompts, loops silently not firing, full context windows losing the instructions, rate limits ending a session with no restart (§5.1, §5.2, §5.5).
- evidence: the author's account of waking to idle agents (§5.1). No count of stalls before or after.
- effect: helps
- reader: a concrete failure list from one operator, about 1 week of use of the replacement.

### F9 · practice · external-work-ledger · E0
- practice: agents claim a work item under an actor name in a versioned database (Beads on Dolt) before starting, skip items another actor holds, and record completion with notes; a restarted agent reads the ledger first (§5.2 Work Coordination).
- claim: it prevents two agents fixing the same issue, and gives continuity across compaction, restarts, backend switches and rate-limit kills (§5.2, §5.5).
- evidence: none; no count of duplicate PRs or of resumed tasks.
- effect: helps
- reader: a design rationale.

### F10 · practice · policy-file-read-per-run · E0
- practice: each agent reads a markdown policy file at every firing instead of holding instructions in a long session (§5.2, §5.5).
- claim: a behaviour change takes effect at once, with no restart.
- evidence: none.
- effect: helps
- reader: a property of the design, not a measured effect.

### F11 · practice · retry-cap · E0
- practice: count fix attempts per issue in the state database; after 3 failures mark the issue `skip` and notify the operator (§5.5).
- claim: without the counter the loop retries the same unfixable issue every 15 minutes indefinitely.
- evidence: none; no count of skipped issues.
- effect: helps
- reader: plausible from the mechanism; not measured.

### F12 · practice · workload-governor · E0
- practice: every 5 minutes measure the issue and PR backlog and set each agent's cadence by mode: SURGE above 20, BUSY above 10, QUIET above 2, IDLE at 2 or fewer; improvement and outreach agents pause under load (§5.2 governor table).
- claim: fixed cadences waste tokens when quiet and fall behind in a surge; a single session cannot hold a 30-minute issue-to-fix target once the backlog exceeds about 20 items (§5.1, §5.5).
- evidence: none; no token use or time-to-fix per mode.
- effect: helps
- reader: the thresholds are given, their effect is not.

### F13 · practice · role-specialised-agents · E0
- practice: separate agents for scanning, review, architecture and outreach under a supervisor, instead of one agent doing all of it (§5.1, §5.2).
- claim: one agent switching between these tasks produces lower quality on each (§5.1 point 2).
- evidence: none.
- effect: helps
- reader: no comparison of one agent against several on the same work.

### F14 · practice · auto-merge-behind-gates · E2
- practice: verified PRs merge without a human, on top of the tests, coverage gate and acceptance tracking; high-risk paths still require human review; a rollback procedure is documented (§3 Level 6, §5.3).
- claim: the earlier levels' gates are "sufficient guardrails for fully autonomous operation" (§5.4).
- evidence: first week of Hive: 36+ issues closed and 20+ PRs merged autonomously, median fix time about 20 minutes, 6 repositories, 0 production incidents from autonomous fixes (Table 6).
- effect: helps
- reader: about 1 week and about 20 merges. How an incident would have been detected and attributed is not described. The project is a dashboard, not safety-critical (§6.7).

### F15 · practice · root-cause-prompting · E0
- practice: ask the agent "why didn't you catch this?" instead of "fix this bug" (§6.2).
- claim: the question yields a new test or instruction that prevents the class of error; the command yields a patch.
- evidence: none.
- effect: helps
- reader: the author's impression.

### F16 · practice · refactoring-for-agents · E0
- practice: refactor continuously (§6.3).
- claim: "AI agents perform measurably better on clean, well-structured code"; technical debt lowers acceptance rates.
- evidence: none; the measurement the sentence refers to is not shown.
- effect: helps
- reader: the word "measurably" has no number behind it in the paper.

## Limits stated by the authors

- One case, one maintainer, one technology stack (§6.7).
- The project is a dashboard, not safety-critical or algorithmically complex software (§6.7).
- Survivorship bias: no system that failed at an intermediate level is observed (§6.7).
- The model has not been validated independently across organisations (§6.7).
- Hive had been in production for about 1 week at the time of writing (§6.7).
- The paper was written with AI assistance from an interview conducted by Claude Code (transparency note, p. 1).

## Reader's notes

- Every outcome number is a count of activity: PRs merged, issues closed, commits. No measure of defect rate, reverted merges or user-visible quality is reported apart from "0 production incidents" (Table 6).
- The author built the system, ran it, chose the metrics and wrote the paper.
- The paper's central claim, that the infrastructure and not the model drives the result (§6.1), rests on "no change in the underlying AI model" during April (§4.5). The model versions in use per month are not listed.
- Table 4's daily rates are consistent with Table 5's total: 16×16 + 29×28 + 40×31 + 81×26 = 4,414 PRs against 4,499 (reader's arithmetic).

## Discrepancies

- Table 5's caption says 100 days; Table 4's periods sum to 101 days (reader's arithmetic).
- "Time from zero" to Level 5 (about 82 days) and Level 6 (about 93 days) in Table 3 has no defined start. Counted from 2026-01-16 the 93 days end on 2026-04-19, which matches the week Hive was built. Counted from mid-December 2025, the stated start of development (§4.1), they do not (reader's arithmetic).
- Table 4 assigns whole calendar months to levels (Jan L1–L2, Feb L3, Mar L4). The narrative in §4.2 places the levels by weeks from mid-December, which puts Level 3 in mid-January to mid-February.
- §4.1 describes GitHub Copilot as used "for code review"; Table 5 and §4.4 Case C report PRs generated by Copilot (320 of 859 merged).
- The arXiv comment field says 30 pages; the PDF has 28.
