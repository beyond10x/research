## Question

Which layer does a mechanism or a failure belong to in a pipeline that organises many agent runs into
delivery, and can two coders apply boundary criteria for that consistently (Abstract, §1)? The case
evidence (E1 to E7) comes from the author's own pipeline.

## Findings

### F1 · practice · verification-outside-agent-sandbox · E2
- practice: run verification on a trusted host outside the agent's environment; it emits a signed receipt (Ed25519, SSH signature format) binding repository, business identifier, baseline commit, snapshot digest and environment digest. Receipts are valid at most 1 hour, with a 30 s clock-skew allowance, and are checked in order (§5.4).
- claim: the verifier rejects forged, stale, rebound and tampered receipts and accepts the original; the paper does not claim fewer false passes (§5.4).
- evidence: Table 4. Tampered receipt or wrong key gives SIGNATURE_INVALID; expired receipt rejected; changed business ID, baseline or environment gives BINDING; changed code tree after signing gives STALE_TREE; unmodified receipt ACCEPTED. End-to-end drill on a real Linux ARM64 host, 6 runs: placeholder environment digest rejected, deliberately failing change NOT_PASSED, same change after fix PASSED. A second project's bootstrap receipt PASSED (610 engine tests passed, 5 skipped) but no real task has run through it (§5.4).
- effect: helps
- reader: E2 because the drills describe the mechanism and nothing is compared with a run without it. The effect on defective work accepted is not measured ("no production frequency data", §5.4); it is hypothesis H2 (§7). "Observed" values are author-reported. No drill had an agent try to reach the verifier. Checks and publication share a VM and a system user and the scheduler holds an administrator token (§5.4), so the separation is weaker than the paper's own reference point, SLSA Build L3. The design resembles Proof-or-Stop (2607.14890).

### F2 · practice · execution-backend-switch · E4
- practice: run the same coding-agent family through two execution backends (a native protocol backend and a CLI backend) with the same model at high reasoning effort, prompt, output schema, code tree, permissions and budget; 12 frozen cases, 2 runs per side in fresh sessions with alternating order (§5.1).
- claim: "switching the execution backend produced no observed functional difference"; no claim about speed or cost (§5.1).
- evidence: Table 2, 24 runs per side. Analysis 6/6 and planning 6/6 on both sides; write tasks, independent functional acceptance 10/10 on both; schema-valid result 24/24 on both; strict-rule compliance 23/24 native against 22/24 CLI, all 3 failures about test placement in one case. Median executor time 40.96 s against 45.28 s, P95 60.90 s against 61.49 s, native faster in 13 of 24 pairs, paired median difference 1.89 s. Clopper-Pearson 95% lower bounds on one side's success rate: 0.692 (10/10) and 0.858 (24/24) (§5.1).
- effect: none
- reader: an A/B on equal frozen cases, so E4, but a small and not randomised one: 12 cases repeated twice, not blinded, caches not cleared, no significance test (§5, Table 2). It is a backend switch inside one agent family, not a comparison of harnesses (§8). The author designed the cases, ran them and wrote the grader, which was itself corrected during the study (F3). Token counts are not comparable across backends. Section 5.7 adds, from a talk only, that "the same model with a different wrapper produced roughly the same quality" (E0).

### F3 · observation · environment-dependent-results · E1
- practice: none applied; what was observed is that results changed with the run environment, in three cases (§5.1, §5.3).
- claim: environment and grader differences, if not recorded, "would otherwise have been read as agent differences" (§5.1); a quality result changed with the sandbox (§3.2, §5.3).
- evidence: (1) the first E1 batch, where the CLI backend inherited the user's home directory and the native one used a temporary one, was excluded in full (§5.1). (2) A defect in the adjudicator, a missing `strip()` on Git porcelain output, caused misjudgements; 40 single-round results were re-graded and 8 runs re-run (§5.1). (3) System F's self-test in a restricted sandbox reported 9 failures, 10 errors, 2 skips; the same suite in an external sandbox 7, 12, 4, equal to the baseline's 7, 12, 4 (Table 3, §5.3).
- effect: hurts
- reader: three cases, all from the author's own pipeline, so E1. Case 3 is not established as an environment effect by the paper: the baseline's environment, the suite total and test-level results are not recorded, and the origin is coded undetermined (§5.3). Cases 1 and 2 are errors in the study's own set-up that the author found.

### F4 · practice · environment-preflight · E0
- practice: check the environment before dispatching a run (network-path checks that report `blocked:network-path-<reason>` and quarantine the path; a quality preflight script; dispatch only after the environment is ready) (§4, §5.3, §5.6).
- claim: a preflight is needed because environment causes can be mistaken for quality failures; the share of such failures without a preflight is hypothesis H6 (§3.2, §7).
- evidence: the preflight was added after the sandbox episode (F3), which was "retroactively marked BLOCKED" (§5.3). No count of failures caught by it is given.
- effect: helps
- reader: asserted. The paper reports that the mechanism exists and why it was added, not what it prevented.

### F5 · observation · harness-provider-failures · E2
- practice: none applied; three managed agent harnesses (HA, HB, HC) were invoked through one factory interface in disposable repositories on 2026-09-20 (§5.5).
- claim: each could be invoked through the same interface and gave at least one correct run; "most observed failures (quota, region, output format) are of a kind the factory layer has to handle" (§5.5).
- evidence: Table 5. HA 2 correct runs (about 10 s and 13.33 s; 26,294 and 26,524 input tokens, called "a high context overhead for micro-tasks"). HB 2 runs failed with resource_exhausted; HC 2 runs failed with HTTP 403 (a regional restriction); a free-tier model gave 1 server error after 75.69 s. After a model switch HB gave 1 OUTPUT_INVALID then 2 correct runs, HC 1 correct run (14.9 s). 1 to 3 runs per harness.
- effect: hurts
- reader: E2, tiny N; models differ between rounds so it is not a harness comparison, and first-round failures "do not measure harness capability" (Table 5 note). The failure categories are the author's labels. The observed failures come from the providers, not from the code the agents produced.

### F6 · observation · orchestration-layer-failures · E2
- practice: none applied; the author counted where fixes landed in a multi-project agent pipeline (§5.6, §6.1).
- claim: factory-layer problems occurred and were fixed; the paper does not claim their share of all failures (§5.6).
- evidence: the 2026-10-01 maintenance log lists about 40 platform fixes traceable by PR number, "most of them factory-layer problems": locks, cache-health semantics, ancestry checks, a compare dead loop, a control receipt reported as UNKNOWN, dispatch only after environment readiness, credential clean-up for lost tasks (§5.6). The platform repository had 202 commits between 2026-09-06 and 2026-10-03, 73 of them containing "fix" (§4). Table 6, 18 incidents: origin Factory 10, Plant 5, run-internal 2, undetermined 1; fix changed a factory artefact in 15 (§6.1).
- effect: hurts
- reader: E2. The author says the Table 6 counts "reflect selection" and are "not preliminary evidence for H3" (§6.1). The 73 is a substring match that also catches "prefix" (§4). The classification of the 40 fixes was the author's own, made before the codebook existed. Four weeks of history; nothing on how many failures were inside single runs.

### F7 · practice · held-out-checks · E1
- practice: write held-out checks before an agent delivers a fix, and run them against the original and the delivered version; used to compare System F with a general-purpose agent desktop application on one cross-layer defect, same model at low reasoning effort (§5.2, §5.3).
- claim: held-out checks catch the old defect and bound quality from below, but "do not exhaust it" (§5.3).
- evidence: the original failed 18 of 35 back-end and 32 of 38 UI checks, and both fixed versions passed all; the tests each side added caught the old defect. One implementation's page still showed "clarification needed" after the question had been answered, a state the held-out checks did not cover (§5.3, Table 3). In E2 the baseline passed its old tests 10/10, the delivered version passed the new 12/12, and the baseline failed 2 of the 12 new tests (§5.2).
- effect: mixed
- reader: two defects, one run per side, no blinding, author-reported (§5.3). The residual UI difference was found by inspection, not by the checks. The fix tests and the held-out checks both came from the author's side.

### F8 · practice · protected-test-files · E0
- practice: protect test and gate files from agent edits, after agents modified tests or gates (§5.7, Figure 2).
- claim: agents modified tests or gates, which led to protected files; the tendency to modify failing tests "has been measured independently" in ImpossibleBench [35] (§5.7).
- evidence: one line in the author's earlier talk; the paper says E7 is "not evidence independent of E1-E6" and uses it only to motivate hypotheses (§5.7). No count of incidents or of prevented edits.
- effect: helps
- reader: asserted. Table 6 row 19 codes the episode as run-internal origin with a factory fix and ambiguous because the path list is domain content.

### F9 · practice · failure-to-gate-feedback · E0
- practice: classify each observed failure by layer, turn it into a factory mechanism or a domain rule or evaluation, and enforce it as a gate in later runs (§3.4, Figure 2).
- claim: the factory structure converges early and later loop outputs land more in the domain layer; "We have no evidence yet that the structure has converged" (§3.4).
- evidence: three lessons became mechanisms: two schedulers contending for runners led to a shared lock, a cache that grew by more than 100 GB a day (author-reported, unchecked) led to a size cap, and the sandbox episode led to a preflight (§3.4, §5.7). H4 (onboarding diffs) and H5 (recurrence after a rule) are the planned tests and have no results (§7).
- effect: helps
- reader: the cases show that rules were added, not that failures stopped recurring. Figure 2's inset is labelled a schematic with an arbitrary curve. Related to staged-feedback-levels in the distillation.

### F10 · practice · incident-origin-control-gap-fix-coding · E2
- practice: code each incident on three separate fields, defect origin, control gap and fix layer, with a run defined as one agent-harness session from dispatch to terminal status and positive evidence required before blaming the environment; two fresh model instances coded 46 held-out units from published papers (26 mechanisms, 20 incidents) from neutral descriptions and the frozen manual v1.0 (§3.3, §6.2).
- claim: the two coders "reached the same assignment in most units"; the paper states that agreement is not accuracy or usefulness (§6.2).
- evidence: Table 7a. Mechanism layer 26/26. Incidents: origin 18/20 (kappa 0.86), control gap 19/20 (0.93), fix layer 19/20 (0.91). Each coder flagged 23 of 46 units ambiguous. Both coders coded the origin undetermined for 8 of 20 incidents, the control gap unknown for 9, the fix unrecorded for 13; among incidents both coded substantively they agreed on 10 of 11, 10 of 11 and 6 of 6. Four disagreements, one exposing a conflict between two tie-break rules (§6.2).
- effect: helps
- reader: E2 because agreement is described and not compared with a control, and the outcome is agreement, not better diagnosis or repair. Same model family, same descriptions, a single extraction agent that wrote the descriptions unchecked, a purposive sample, and two of the five source papers also gave components to the development set (§6.2, §8). Half of the field comparisons agree on "indeterminate".

### F11 · practice · incident-origin-control-gap-fix-coding · E3
- practice: revise the coding manual to v1.1, which separates mechanism classification from incident attribution and lets an incident be MULTIPLE or UNDETERMINED, then re-code the same 46 units with two further fresh model coders (§3.3, §6.3).
- claim: v1.1 "removes the conflicts they target" but "moves the residual difficulty to the definition of a fix and to the incident's scope" (§6.3).
- evidence: Table 7c, coders C and D. Mechanism 25/26 (kappa 0.93), origin 17/20 (0.78), control gap 18/20 (0.85), fix layer 17/20 (0.79); coders flagged 29 and 30 of 46 units ambiguous. Of 86 field comparisons 20 changed: 4 disagreements resolved, 7 agreed labels changed, 9 new disagreements (§6.3).
- effect: mixed
- reader: E3, a before and after on the same units with different coders and no control. v1.1 was written after seeing the v1.0 disagreements on these units, so the paper says this is "not a validation" (§6.3). The coders differ between conditions, so the change cannot be separated from coder differences.

### F12 · observation · incident-record-sufficiency · E2
- practice: none applied; the author looked at what the incident records of one pipeline and of three published systems say about which control failed (§6.1, §6.2).
- claim: "the platform's own fix records support statements about where errors arose and where they were fixed, but not about which controls failed" (§6.1).
- evidence: in the 18 incidents of Table 6 the control gap is unknown for 10, none (contained) for 5 and Factory for 3. In the held-out check, most flagged units were flagged for missing information (10 and 12 flags) or bundling (8 and 8) rather than for conflicting criteria (1 and 1) (§6.2). In the development set, 11 of 26 components of three published systems were ambiguous under the v0 wording (§6.1).
- effect: hurts
- reader: E2, counts with no comparison. The unknowns are partly caused by the short descriptions the extraction agent wrote (§6.2), and the System F records were written by the author for other purposes. Whether better records would change repair decisions is not tested.

## Limits stated by the authors

- The designer, operator and evaluator are the same person; E1 and E3 were not blinded; no comparison supports a significance claim (§1, §5, §8).
- Small samples: 48 runs over 12 cases in E1, one defect class (two with E2) and one run per side in E3, 1 to 3 runs per harness in E5 (§8).
- Six projects concentrated in healthcare and elderly care; about four weeks of platform history; no observation longer than 24 hours of continuous operation (§8).
- E1 compares two backends of one agent family, not agent harnesses; token and cost accounting differs between backends, so no savings are computed (§8, Table 2).
- The L1 to L5 autonomy levels are the author's own and unvalidated (§5.7, §8).
- Most records were written by the author and unrecorded failures may exist; E2 to E7 numbers are author-reported and not re-derived, and the logs behind them are not released (§8).
- Model coders share a family and descriptions; their agreement does not estimate human agreement; the check measures consistency, not accuracy or usefulness (§6.2, §8).
- v1.1 has not been validated on new material; per-project counts of runs, PRs and interventions are not yet reported (§3.3, §4, §8).
- The seven hypotheses H1 to H7 are untested protocols (§7).

## Reader's notes

- The paper's title claim, boundary criteria, is a classification scheme. Its only outcome is inter-coder agreement of model coders; no finding here shows that using the layers improves any delivery outcome.
- E4 here is the only comparison with the same task and the same model on both sides (F2). The E3 comparison of System F with a desktop application (F7) had one run per side and differing tooling, so it is not graded as a comparison of the two.
- Hypothesis H1 (a gate matters more than a harness) is the paper's central bet. F2 is the half that exists; the gate-on, gate-off half has no data. The paper cites HoH (2609.01481) for gains from an outer loop but notes those were obtained with additional compute (§7).
- E7, the source of F8 and parts of F9, is a transcript of the author's earlier talk, so the lessons cannot confirm what the author already believed.
- The 73 "fix" commits out of 202 are a message substring match; the paper notes it also catches "prefix" (§4).
- Several statements in §4 are tagged to evidence identifiers whose sources are only available on request, so the System F description cannot be checked from the public files.
