## Question

Does alternating harness optimisation and reinforcement learning of the policy, with the policy
proposing its own harness changes, raise a coding agent's resolve rate more than optimising only the
harness or only the policy (§1, §3.2)?

## Findings

### F1 · practice · harness-policy-co-optimisation · E4
- practice: alternate an H-step (the frozen policy reads its failed trajectories on a search set and proposes 6 harness candidates; the best on that set is kept) with a P-step (50 RL updates with GRPO and binary test-pass rewards under the chosen harness); two rounds; the policy is its own proposer (Self-HPO). Compared on the same tasks with policy-only RL on the seed harness (RLVR), harness-only search (Self-Harness) and the unchanged base (§2, §3.1, Appendix A).
- claim: "Self-HPO consistently outperforms policy-only and harness-only optimization", best on all three benchmarks in each setup, with gains that "generalize to out-of-distribution" (§3.2).
- evidence: Table 1, resolve rate, mean of 3 evaluation runs, SWE-Verified, SWE-Multi, SWE-Pro, average. Base 61.0, 54.2, 58.3, 57.8. RLVR 67.5, 56.3, 61.8, 61.9. Self-Harness 65.2, 54.3, 60.7, 60.1. Self-HPO 69.5, 59.7, 65.2, 64.8. Self-HPO beats RLVR by 2.0 points on SWE-Verified and 2.9 on average (§3.2); standard deviations over runs 0.4 to 1.5 for these rows. With Opus 4.8 as proposer: HPO 71.6, 61.4, 66.0, 66.3 against Meta-Harness 69.1, 56.5, 64.8, 63.5 (Table 1). Training and search used Python tasks only; SWE-Multi covers nine other languages (§3.2).
- effect: helps
- reader: baselines are ablations of the method on equal tasks, so E4. The authors built and ran the method and the baselines (`independent: false`); each method was trained once and the ± is over evaluation runs, not training seeds. Several gaps are close to the run deviations, for example 69.5 ± 0.9 against 67.5 ± 0.8. The harness proposer is shown the reference fixes of the search tasks (Appendix D). The paper does not discuss contamination of the benchmarks in the base model's training data.

### F2 · practice · harness-policy-co-optimisation · E4
- practice: evaluate every pairing of the three harnesses (seed H0 and the two evolved ones H1, H2) with the three policies (P0, P1, P2) of one Self-HPO run on SWE-Verified (§3.4, Table 3).
- claim: "each component retains part of the improvement on its own, while combining them gives the largest gain"; the joint gain "exceeds the sum of their individual gains" (§3.4).
- evidence: Table 3, SWE-Verified. H2 with the base policy 64.5 (from 61.0, +3.5); P2 on the seed harness 64.4 (+3.4); H2 with P2 69.5, +8.5 over base, 1.6 points above the sum 3.5 + 3.4 = 6.9 (§3.4). Other cells: H1 with P1 67.8, H2 with P1 68.6, H0 with P1 61.7.
- effect: helps
- reader: a full grid on equal tasks, so E4 for the interaction. The 1.6-point excess is about the size of the standard deviations in the grid (0.5 to 1.6, Table 3). The evolved harnesses were searched with the policy that is then paired with them, so a matched pair may favour its own harness; the grid cells with P0 or H0 are the unmatched ones.

### F3 · practice · harness-self-evolution-single-task-type · E4
- practice: change only the harness, with no weight update: the base policy reads its own failed trajectories on a search set of 300 random training tasks and proposes one new mechanism per candidate, as a Python subclass of the seed agent (§2.2, Appendix A and D).
- claim: harness-only optimisation helps in distribution but does not help consistently; "another harness-only update does not consistently improve performance" (§3.2).
- evidence: Self-Harness against Base, Table 1: SWE-Verified 65.2 against 61.0, SWE-Multi 54.3 against 54.2 ("only 0.1 point"), SWE-Pro 60.7 against 58.3. Second harness-only update dropped SWE-Multi from 55.0 to 54.3 (§3.2). Harness-only search after the shared first H-step: best score 64.3 to 65.2 over six more candidates (Appendix B, Figure 6 text). Cross-evaluation: H2 on the base policy 64.5 against 61.0 (Table 3).
- effect: helps
- reader: the comparison is with the unchanged base on equal tasks. The gain is clear in distribution and absent on SWE-Multi. Harness candidates are chosen on a training search set and then scored once on the benchmarks, so the selection does not touch the benchmark. The seed harness is a minimal loop (mini-SWE-agent), which leaves room that a stronger production harness may not.

### F4 · practice · submission-guards-in-harness · E1
- practice: the evolved harness (HPO, second H-step) adds four runtime checks around the agent loop: a warning near the step or time limit that asks for a best-effort submission; a one-time empty-patch guard that asks the model to include new files with `git add -N`; a hold on the first submission that passes the guard, asking the model to check API names against the repository and tests; a fallback to the sandbox's Git diff when the submitted patch fails the apply check (§3.5, Figure 5).
- claim: "Harness optimization can therefore change execution and termination logic, in addition to prompts"; the checks "target distinct ways in which useful repository edits can fail to become a valid submission" (§3.5).
- evidence: one task, sphinx-doc__sphinx-9658, policy P2. Seed harness: after 131 steps the final summary becomes the submission and no code change is evaluated. Evolved harness H2: the first submission is held, the harness reports that the patch contains no files, the policy writes the diff, checks the fix and submits a valid patch that resolves the task (Appendix E, Figures 10 and 11). A reminder in this run was a false positive (Appendix E). No per-check ablation is given.
- effect: helps
- reader: one run on one task, picked by the authors to illustrate. No count of how often each check fires or changes an outcome, and the overall gain of the harness (F3) is not split by check.
### F5 · observation · premature-completion-report · E1
- practice: observed: under the seed harness the model ends the episode with a prose summary and the harness accepts it as the final submission, so an empty or unusable patch is scored; the seed submit path accepts any output, including an empty patch, a patch built on a guessed API, or one that does not apply (Figure 5, Appendix E).
- claim: the seed harness "lets through" four failure modes: empty result at budget exhaustion, empty patch, patch built on a guessed API or contract, malformed patch (Figure 5, §3.5).
- evidence: one case, sphinx-doc__sphinx-9658 under the seed harness (Appendix E, Figure 10). The proposer prompt names "submission loss" as a diagnostic, defined as a real source edit in the trajectory with an empty or malformed final patch (Figure 7); no rate is given in the parts read.
- effect: hurts
- reader: a single case plus the proposer's diagnostic definition; the size of the problem is not measured. Its use as an observation is limited by that.

### F6 · practice · external-harness-proposer · E4
- practice: let a stronger external model (Opus 4.8) propose the harness changes in the H-step instead of the current policy; same loop otherwise (§2.1, §3.3).
- claim: "an external model is helpful but not required for our method" (§3.3).
- evidence: Table 2, SWE-Verified. HPO with Opus 4.8 proposer 71.6; replacing it with the current policy (Self-HPO) 69.5, 2.1 points lower. Table 1 averages: HPO 66.3, Self-HPO 64.8 (reader's arithmetic: 1.5 points).
- effect: helps
- reader: an ablation on equal tasks, E4. Table 2 gives no deviation; the two numbers equal the Table 1 means over 3 evaluation runs, whose deviations are 0.9 for both. The proposer is one model and one run; the paper does not report what the Opus proposer costs.

### F7 · practice · hard-task-search-set · E4
- practice: choose the harness search set for the next H-step from tasks never resolved in any rollout of the preceding P-step, instead of reusing the initial random set of 300 tasks (§2.2, §3.3).
- claim: "evolving the harness search set with hard tasks ... yields better performance than reusing a fixed set" (§1, §3.3).
- evidence: Table 2, SWE-Verified: HPO 71.6; with a fixed search set in the H-step 70.1 (−1.5).
- effect: helps
- reader: one comparison on one benchmark with no deviation stated; 1.5 points is below the largest deviation in Table 1 (1.9 for Meta-Harness) and above the HPO deviation (0.9). The test is run on the external-proposer configuration only.

### F8 · practice · rl-over-sft-for-policy-update · E4
- practice: in the P-step, update the policy with RL against replacing it by SFT on Opus 4.8 trajectories or rejection-sampling fine-tuning (RFT) on the policy's own successful trajectories (§3.3, Appendix B).
- claim: "RL yields stronger policy updates than SFT/RFT" (§3.3).
- evidence: Table 2, SWE-Verified, HPO reference 71.6: SFT in the P-step 67.2 (−4.4); RFT 70.5 (−1.1).
- effect: helps
- reader: an ablation on equal tasks. The RFT gap of 1.1 is within the run deviations of Table 1. SFT trains for two epochs on resolved teacher trajectories only (Appendix B); the amount of SFT and RL training is not matched in compute and the paper does not compare it.

### F9 · practice · sft-on-teacher-trajectories · E4
- practice: fine-tune the base policy on resolved Opus 4.8 trajectories collected on the RL training tasks (Appendix B), against the untrained base and against using Opus 4.8 only to propose harness changes (Meta-Harness) (§3.2).
- claim: "Learning from Opus 4.8 through harness optimization is more effective than SFT distillation"; SFT falls below base out of domain (§3.2).
- evidence: Table 1, SFT against Base: SWE-Verified 65.0 against 61.0, SWE-Multi 49.6 against 54.2, SWE-Pro 49.1 against 58.3, average 54.6 against 57.8. Meta-Harness over SFT by 4.1 points on SWE-Verified and 8.9 on average (§3.2).
- effect: mixed
- reader: untrained against trained on equal tasks, E4. The two methods spend different effort (SFT data collection with Opus 4.8 against 6 harness candidates per round), and the paper does not match them. One SFT run.

### F10 · practice · rl-on-verifier-rewards · E4
- practice: update the policy with RL (GRPO with balanced adaptive rollout, 8 rollouts per task, groups of 4 with a success fraction between 0.25 and 0.75) under the unchanged seed harness (RLVR), 50 updates per P-step (Appendix A).
- claim: policy-only optimisation helps but is the stronger single-component baseline that Self-HPO still exceeds (§3.2).
- evidence: Table 1, RLVR against Base: SWE-Verified 67.5 against 61.0, SWE-Multi 56.3 against 54.2, SWE-Pro 61.8 against 58.3, average 61.9 against 57.8.
- effect: helps
- reader: untrained against trained on equal tasks. RLVR uses "50 updates per P-step" (Appendix A) and Figure 3 puts it on the same Base, H1, P1, H2, P2 schedule with no update at the H steps; the total number of updates is not stated beside Self-HPO's, which bears on the comparison in F1.

### F11 · practice · hard-task-reward-sparsity · E3
- practice: the P-step of the final Self-HPO round runs under the evolved harness, against RLVR under the seed harness; the measure is the share of rollout groups with no successful rollout (§3.4, Figure 4c).
- claim: "Self-HPO reduces zero-success rollout groups during training", which "alleviates reward sparsity" (§3.4).
- evidence: zero-success groups fall to 6.5% over the final ten updates of Self-HPO's last P-step, against "mostly between 11% and 17%" over the last 50 updates of RLVR (§3.4).
- effect: helps
- reader: E3, a comparison with no control: the two runs differ in harness and in the training stage (Self-HPO's policy has already been trained for one more round). The paper does not link the lower share to the final score.

### F12 · practice · harness-policy-co-optimisation · E3
- practice: sample 8 attempts per task on SWE-Verified with the base agent and the final Self-HPO agent and compute pass@k (§3.4, Appendix B).
- claim: "Self-HPO improves reliability (pass@1) and expands the capability frontier (pass@k)" (§3.4).
- evidence: pass@8 80.0% to 84.8%, +4.8 points, and above base for every k from 1 to 8 (§3.4). Pass@1 by Base success rate p: Medium +17.2, Easy +12.9, Hard (p = 0) +6.1, already-resolved group (p = 1) −2.2 (§3.4, Figure 4b).
- effect: helps
- reader: two systems compared with no control, E3. The groups are defined by the base agent's own success rate on the same 8 attempts, so the Hard group can only gain and the Resolved group can only lose; part of the pattern is regression to the mean. The 95% bootstrap intervals are in the figure only.

## Reader's notes

- Microsoft Research authors evaluate their own method, and the baselines (RLVR, Self-Harness, Meta-Harness, SFT) were re-run by them with "the same search budget" for the harness baselines (Appendix A), so the comparison depends on their implementation.
- Only one model and one seed harness were used. A coding harness other than mini-SWE-agent (one with its own tools, memory and review steps) is not tested; the finding that the harness has room to improve may depend on how minimal the seed is.
- The proposer sees the reference fixes of the search tasks and the proposer prompt forbids injecting them into the agent (Figure 7). A runtime check on this rule is described ("the search then checks that the candidate keeps every parent method and fires on real sandbox tasks"); no check for leaked task-specific facts is described.
- Selection: each H-step keeps the best of 6 candidates on a search set, each task run once (the first set has 300 tasks), so a candidate can be selected on noise; the paper does not give the size of later search sets or the noise level.
- The benchmarks are scored with test-passing verifiers. Whether the harness changes (for example the empty-patch guard) matter outside these verifiers is not measured.
- Appendix A names the hardware (one node, 8 B200 GPUs); no time, token or Opus 4.8 cost total is given in the parts read.
- Table 4 puts the 35B-A3B agent at 69.5 beside leaderboard values for other models on the same harness; the leaderboard runs were not made by the authors.
