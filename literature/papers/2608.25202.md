## Question

How do practitioners practice spec-driven development (SDD), and how does that differ from what
SDD tools and their makers prescribe? Four sub-questions follow the life of a spec: content,
workflow, benefits, challenges (§I).

## Findings

### F1 · practice · implementation-detail-in-spec · E1
- practice: write implementation detail (architecture, task breakdown, code-level detail, library versions, internal APIs, conventions) into the spec next to the "what", mostly when the task is complex or needs knowledge the agent lacks, instead of keeping it in separate design and plan files (§IV-A, Table III).
- claim: "implementation detail may help agents while making specs prone to decay" (Abstract); tool users "added detail as tasks grew more complex or exceeded what they believed the agent could do" (§IV-A).
- evidence: two quotes. P10's team specifies "the how if we believe it's in a place where AI has very low capability of doing it"; P16's design documents include API error codes and OpenAPI definitions "so that it understands better how the integration goes" (§IV-A). Participants coded as including implementation detail 9, selectively 4, keeping it out 8 (Table X, App. J). No agent result with and without the detail is given.
- effect: helps
- reader: E1, the benefit is a belief stated in two quotes. The counts in Table X say who includes detail, not what it did. Nothing in the paper compares agent success with and without the detail.

### F2 · practice · implementation-detail-in-spec · E0
- practice: as F1.
- claim: "a spec that specifies more implementation detail decays sooner"; the authors add that "no participant mentioned" this cost (§V-A).
- evidence: none for decay. The numbers beside it: "75% of the specs with implementation detail include named classes, functions or library versions" (§V-A). §VI-B: "Commit counts therefore cannot show spec decay".
- effect: hurts
- reader: the authors' own inference from the share of specs that name code elements, written with "Thus". Nobody measured decay against detail, so E0.

### F3 · observation · implementation-detail-in-spec · E3
- practice: what 266 repositories' spec files contain, judged by gemini-2.5-pro (temperature zero) on a stratified sample of 1,000 documents, set against what the tools' documentation and the tool makers prescribe (§III-C, §IV-A, Table VII).
- claim: tool makers and tool documentation keep the "how" out of the spec; "most specs in public repositories include implementation detail, under sections their tool supplies" (Finding 1 header, §IV-A).
- evidence: 77.6% of judged specs contain implementation detail, 58.2% in a section or more (§IV-A, App. D). A section or more in at least 94% of files for Spec Kit's .specify/, MoAI-ADK and .specs, against 40% of OpenSpec archived changes and 55% of its open change specs (App. D; Table VII gives 75% for OpenSpec capability specs, 88% Spec Kit, 75% Kiro, 81% Conductor, 95% MoAI-ADK). From Table X, 2 of 8 tool makers and 7 of 13 tool users included detail (reader's arithmetic). For the judge, cited quotes match the source text for 98.3% of content labels (App. B).
- effect: none
- reader: E3, a comparison between tools and between maker and user groups, with no control. The finding states a prevalence and measures no outcome, so `none` records the absence of a result, not a result of zero. OpenSpec is 78.4% of the sample and writes design to a sibling file the judge did not see (App. D). The only judge validation in the parts read is that quotes match the text; no human labels are compared.

### F4 · practice · selective-sdd-by-task-size · E2
- practice: use SDD for large or risky tasks and new features; skip it for small tasks, bugs, one-off scripts and urgent hotfixes (§IV-B).
- claim: "Tool users mostly decide to use SDD by task size and write specs mainly for new features" (Finding 2 header).
- evidence: Table X: 8 participants decide by task size or complexity, 7 by risk or uncertainty. R33: for smaller changes SDD "is too verbose and produces too much overhead and documentation". P4: for a production hotfix "there is no time for spec-driven development". LLM-judged purpose labels of the 1,000 specs, weighted by file count: feat 82.0%, fix 16.5%, refactor 24.3%, perf 11.6% (App. D).
- effect: none
- reader: E2, self-reports and file labels with nothing to compare against; `none` as in F3. The authors write that the labels "do not establish whether task size or urgency explains the pattern" (App. D). A bug fix that got no spec is not in a corpus of spec files.

### F5 · practice · spec-review-partial-or-delegated · E2
- practice: read the agent-drafted spec only in part, or hand its review to other agents (adversarial review by another model, a prompt to find gaps), instead of reading it in full (§IV-B).
- claim: "Practitioners differ in how closely they read specs"; the recorded human participation is limited (Finding 3 header, §IV-B).
- evidence: App. H: review in full 7 participants, partial or skim 7, delegated mainly to agents 5; full review typical where spec review was a team activity. Repositories: 98.3% of 36,888 spec files with a history have one author; in 63% of the 266 repositories one person ever touched a spec; of 1,731 inline comments on specs 68.5% were written by bots, and 210 of the 266 repositories have no such comment (App. D).
- effect: none
- reader: E2, counts with no comparison and no outcome, `none` as in F3. The authors argue in §V-C that delegating spec review "removes the one point where a person decides what the system should do"; that is a risk argument with no data and is not graded here. Review on GitHub is visible only as inline comments, so a one-author spec may have been discussed elsewhere (§VI-B).

### F6 · practice · human-anchored-acceptance-criteria · E2
- practice: a person sets or approves the acceptance criteria or defines behaviour-level tests, and the agent writes the code and the remaining tests (§IV-B, §V-C, App. H).
- claim: "human effort may be better spent on setting acceptance criteria that define correct behavior than on inspecting code line by line" (§V-C).
- evidence: Table X: 11 participants used human-anchored verification (acceptance criteria or human-defined tests); 8 said verification is hard or unsolved. Text: "Most participants who set or checked acceptance criteria, or reviewed the agent's tests, did not raise verification as a challenge" (§V-C), with no counts for that comparison. App. H: 12 participants verify mainly by end-to-end or acceptance tests, 3 mainly by unit tests; behaviour-level tests defined by humans for 5. Nearly all verified through agent-written tests; P14 calls the result "verification debt" (§IV-B).
- effect: helps
- reader: E2, because the comparison behind the claim is stated without a count and rests on what participants chose to raise in an interview. The authors write "We cannot show these practices prevented defects, but the association suggests" the claim. The 11 and the 8 overlap (P1 and P16 are in both lists of Table X).

### F7 · observation · implementation-drift-from-spec · E2
- practice: none applied; agents were observed departing from the spec they were given while implementing it (§IV-D).
- claim: "Agents departed from specs during implementation"; practitioners fixed whichever they blamed, their instructions or their specs (Finding 10 header).
- evidence: Table X: 14 participants coded spec-code drift as a challenge; 8 coded the drift type "agent deviates during implementation" (not all 8 are among the 14, reader's arithmetic). P5: the agent "just goes off the rails and starts doing all kinds of stuff that I didn't ask it to do". Reddit posters who saw drift blamed their instructions or the model and made implicit conventions explicit in instruction files (§IV-D). OpenSpec offers a verify command that checks the implementation against the change (§V-C).
- effect: hurts
- reader: E2, self-reported counts with no rate per task and no comparison. The paper does not measure how often agents depart from a spec.

### F8 · observation · documentation-drift-as-failure-class · E2
- practice: none applied; specs were observed going stale as the code changed (spec decay) (§IV-D).
- claim: "specs went stale as code changed"; checks such as scheduled agent reviews or end-to-end tests in CI "can show that code and spec disagree, but not which is wrong" (Finding 10, §IV-D).
- evidence: Table X: 7 participants coded the drift type "spec goes stale as code evolves"; 7 coded drift detection and checks. R96: "every SDD framework gets the same complaint: spec rot". P2: "the code part will be mutated, and the spec will be left alone". P20: one verify command worked about half the time (§V-C). Decay affects living specs, mainly when a change alters behaviour other specs describe (P10: a small change "might be related to 10 other features").
- effect: hurts
- reader: E2, self-report; no measure of decay in the repositories: "Commit counts therefore cannot show spec decay" (§VI-B). The authors did not establish whether any tool checks spec and code after implementation is complete (§V-C).

### F9 · practice · spec-first-against-direct-prompting · E1
- practice: plan with a spec, plan and task list before the agent implements, compared by one team with prompting the agent directly (§IV-D).
- claim: "SDD shifts token cost, time, and cognitive load from implementation to planning" (Finding 9 header).
- evidence: one Reddit team (R41): "the spec-driven runs typically consume two to three times as many tokens and take about twice as long"; no task count or numbers behind it. Table X: 14 participants raised token and model costs, 4 that planning consumes most tokens (P3: "80% of tokens are being used to make a plan"), 10 time overhead; 7 coded reduced tokens and rework as a benefit and 7 faster delivery. Reported savings "were rework avoided, not a smaller bill" (§IV-D).
- effect: hurts
- reader: the only comparison is one quoted post, so E1; the Table X counts describe what was raised, not a measured cost. The 7 who coded savings point the other way on rework. Tokens, time and cognitive load are three outcomes in one finding.

### F10 · practice · spec-first-against-direct-prompting · E2
- practice: as F9; the outcome is the reliability of the agent's work.
- claim: "Most practitioners found that specs made agent work more reliable, although they could not separate this benefit from improvements in models" (Finding 7 header).
- evidence: Table X: 18 of the 21 participants coded "more reliable agent work" (reader's arithmetic from the 18 names listed). P8: "this has largely to do with models becoming so much better". R41: "We couldn't prove it improved the code". P18: "direct prompting, I think, is way better" than detailed plans (§IV-C).
- effect: helps
- reader: E2, self-reported perception with no run compared; the authors say the benefit coincided with model improvements (§VI-A). Reddit posts were more sceptical than interviews (§IV-C). Interviewees volunteered and use SDD (§VI-C).

### F11 · practice · spec-drafted-in-conversation-with-agent · E2
- practice: draft the spec in conversation with the agent, which asks questions and produces a draft that the person reads and corrects; the agent drafted the specs of nearly all participants (§IV-C, App. H).
- claim: "Drafting a spec with an agent helped some practitioners clarify their intent, which kept developing as they built" (Finding 8 header).
- evidence: Table X: 4 participants coded clarity of thinking and intent as a benefit, 5 that an agent-written spec exposes gaps in their own intent, 5 that intent must be clear before specifying. P9: the "Act of authoring a specification clarifies the objective even to yourself". A few found articulating intent a burden (P10). The authors conjecture the benefit over vibe coding comes from the developer articulating goals before delegation, and "the same benefit should appear with any practice that leads a developer to plan before acting, including plan modes" (§V-D).
- effect: helps
- reader: E2, 4 to 5 self-reports out of 21. The conjecture about articulation against having a spec is untested; §V-D proposes the comparison (spec given, spec withheld, no spec).

### F12 · practice · specs-shared-across-roles · E2
- practice: pass specs between developers and other roles (product owner, architect) as a shared artifact (§IV-C).
- claim: "Some participants reported improved shared understanding when specs passed between developers and other roles" (Finding 6 header); the benefit came from the few organizations where specs reach non-developers.
- evidence: Table X: 3 participants (P6, P10, P16) coded shared understanding across roles, 4 a modest team benefit with the spec as one more review artifact, 3 little or no change in human collaboration, 7 collaboration as a goal and not an observed outcome. P6's product owner: "Now I see what my developers are doing". Repositories: owners and the three most frequent committers account for 90% of 13,640 spec commits, while making up 60% of the people who write them (App. D).
- effect: mixed
- reader: E2, a split of a few participants by setting, with no outcome measured. The commit shares show who writes specs, not who reads them. Tool makers described collaboration as a purpose of specs, not an observed change (§IV-C).

### F13 · observation · individual-champion-adoption · E2
- practice: none applied; participants who introduced SDD to their team as individuals were observed meeting resistance (§IV-D).
- claim: "Participants who introduced SDD to their teams as individuals often met inertia" (Finding 12 header).
- evidence: Table X: 5 participants coded organizational adoption inertia; 7 coded adoption introduced by an individual champion, 4 adoption as an organizational process. "Most participants who reported inertia had introduced SDD to their team themselves"; no solo developer raised it. P21: "you need the whole team to switch". P6 wanted research to convince customers "because people don't believe experience" (§IV-D).
- effect: hurts
- reader: E2, a handful of interviewees. Inertia also appeared in organizations that adopted SDD as a process, "so our data do not show that adopting SDD as a process avoids it". The author-writes, team-benefits explanation in §V-D is an interpretation.

### F14 · practice · sdd-tool-customization · E2
- practice: extend an SDD tool with own skills, steering files or workflow layers, build an own tool, or switch to a lighter tool, instead of using a tool as published (§IV-B, App. H).
- claim: "Almost no participant used an SDD tool as published" (Finding 5 text).
- evidence: Table X: 2 participants used defaults, 8 extended an existing tool, 11 built their own tool or workflow; 6 switched to a lighter or more customizable tool. All 8 tool makers built their own tools or workflows (App. H). "Building one's own SDD tool" was the most frequent code on the Reddit posts.
- effect: none
- reader: E2, a prevalence with no outcome, `none` as in F3. The sample is volunteers; 8 of 21 are tool makers who built tools by definition (§III-B).

## Limits stated by the authors

- Associations, not causal effects: tool makers and users differ in experience, role and organization; reported improvements coincided with model improvements (§VI-A).
- Each source was first coded by one author; no inter-rater agreement was computed (§III, §VI-A).
- Reddit and interviews capture reported experience, not actual practice; the repository sample does not measure benefits, effort or challenges; content and purpose labels come from an LLM and may be wrong (§VI-B).
- Commit counts understate revision (no rename tracking, squashes) and cannot show spec decay; review is visible only as inline GitHub comments (§VI-B).
- Interviewees are likely more engaged with SDD than practitioners generally; Reddit selection favors visible experience; Arctic Shift coverage is incomplete (§VI-C).
- The repository sample is 78.4% OpenSpec; six of 13 document types take at least half their files from one repository, and for OpenCode, Codex and Spec Kit's .specify/ one repository gives more than 95% of the files (§VI-C).
- Early period: repository histories span less than a year; deleted and private specs are absent (§VI-C).

## Reader's notes

- No condition was assigned, so no finding is above E3. The paper compares no run with a spec against a run without one; §V-D lists that comparison as future work. Agent success, defects and time are measured nowhere except in one quoted Reddit post (R41).
- Grades follow the claim. A participant count from Table X (Appendix J) is E2 at best; the text mostly says "most" and "some", and the counts here are read from the table. A participant absent from a code did not raise the topic in a way that was coded; it is not a no.
- Four findings (F3, F4, F5, F14) carry a prevalence and no direction; they are filed as `none`, which the schema cannot tell from a measured zero (schema proposal P9).
- 8 of the 21 interviewees are tool makers and are treated as the prescribed view. The paper compares makers and users only within the interviews (§IV).
- The retention result is not in a finding: participants kept living specs 10, an accumulated change record 6, discarded specs 3 (Table X); 81.5% of spec files have a single recorded commit; OpenSpec archived changes outnumber capability specs 19,067 to 6,644 (§IV-B). The authors say the unit that grows "follows from the lifecycle stage and does not by itself show that repositories favor accumulating records over maintaining living specs" (App. D).
- Specs in the sample exist only where a team committed them; a spec used and deleted is not in SpecMine (§VI-C).
- The Reddit records (R1 to R99) are anonymised quotes; R41, the one comparison of token use, cannot be traced to its post in the text.
- A Google research gift is acknowledged (§IX); none of the tools studied is named as Google's.
- The judge is one model, one pass per document, with the path and tool name hidden from it (App. B); the 13 types include 3 whose files come mostly from the tool vendor's own repository (§VI-C).

## Discrepancies

- Appendix B says the 11 per-tool crawls yield 5,979 distinct spec-modifying PRs from 581 repositories; Table V gives 5,992 pull requests, and Appendix B itself says "five of the 5,992 PRs carry no spec file". Not explained in the parts read; §III-C also says 5,979.
- §IV-A says "Most tool users routinely included implementation-level content"; Table X codes 7 of the 13 tool users as including it, 4 selectively and 2 keeping it out (reader's arithmetic).
- §III-C says OpenSpec and Spec Kit are 85% of the 279 adoptions; the counts 165 and 71 give 84.6% (reader's arithmetic). Spec Kit is 71 in the text and 70 at the end of Figure 8, which the caption explains by the omitted July 2026.
