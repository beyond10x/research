## Question

Can a library be kept as a graph of natural-language design docs, with coding sub-agents regenerating
all of its code from the docs at each version, instead of patching code incrementally (Abstract, §1, §2)?

## Findings

### F1 · practice · design-docs-as-source-of-truth · E1
- practice: the main branch holds almost no code, only a folder of markdown design docs forming a DAG; coding sub-agents regenerate the implementation from the docs alone at each version change; every human change is a natural-language edit to a doc (Abstract, §2, §4).
- claim: "Regenerated implementations reproduce hand-audited reference models—including DeepSeek-V3 serving on a TPU pod slice—to round-off precision" (Abstract).
- evidence: one library, 50 design docs, about 9,000 lines of prose (§4). The reproduction claim is a single sentence in the abstract; the body has no table, number, error value or list of reference models.
- effect: helps
- reader: a single case reported by its builders, so E1. No comparison with hand-written code or with incremental patching, and the reference models and their tolerances are not shown. The agent's model, the number of regenerations and the number of failed attempts are not stated.

### F2 · practice · design-docs-as-source-of-truth · E2
- practice: rebuild the whole library from the docs by Claude Code sub-agent orchestration (§2).
- claim: "continuous, full-library regeneration" is "both practical and economically viable" (§2).
- evidence: a full clean-slate regeneration takes between 1.5 and 3 hours; the API cost of a complete rebuild is "around 100 USD", "roughly 20% of a weekly usage budget" under a high-tier plan such as Claude Max (§2).
- effect: helps
- reader: numbers that describe cost with nothing to compare against, so E2. There is no cost of the incremental alternative, and the direction `helps` is the authors' claim of viability, not a measured difference. Whether the cost includes failed runs and the repair step of Figure 1 is not stated.

### F3 · practice · full-regeneration-instead-of-incremental-patching · E0
- practice: regenerate the whole implementation from the specification on a regular cadence, so the generator never receives the previous implementation as input (§1, Equation 1).
- claim: incremental patching accumulates a debt D(t+1) = G(S(t+1), C(t)) − G(S(t+1)); because C(t) = G(S(t)) is recomputed from scratch, the debt "is driven to zero by construction" (§1) and is paid "down to zero at every regeneration" (§4).
- evidence: none. The paper defines the debt and does not measure it, and does not give a patched system to compare with.
- effect: helps
- reader: asserted by definition, so E0. A regenerated build can differ from the previous one in behaviour that the docs do not pin down, and the paper does not report such differences or how they were caught.

### F4 · practice · worked-examples-in-design-docs · E0
- practice: write each design doc around step-by-step worked examples with intermediate shapes, intermediate values and the exact closed-form result (for example "on a 2×2×2 torus with wraparound, the per-node link count is 3, not 6"), as in-context demonstrations for the generating agent (Abstract, §2).
- claim: worked examples are what "maintains consistency across independent agentic code-generations" and pin down semantics "that prose alone leaves ambiguous"; the authors present them as a bottom-up complement to tests and top-down rules (§2).
- evidence: none. No ablation without the examples, no count of examples, no failure rate.
- effect: helps
- reader: asserted with a citation to in-context learning ([Brown et al., 2020], [Dong et al., 2022]), so E0. The abstract names it one of two ingredients that "make regeneration reliable", with no test of that.

### F5 · practice · reconciliation-anchor-in-design-doc · E0
- practice: end every number-bearing doc with a reconciliation anchor, a small preset whose expected outputs are stated exactly and enforced by generated tests; a doc may also state the exact expected symbolic expression (§2, §3). A regenerated build must pass reconciliation against hand-built reference models, parameter guards and unit tests, with a repair step, before it replaces the previous build (Figure 1).
- claim: the anchor and the reconciliation gate keep the regenerated implementation correct (§2, Figure 1).
- evidence: none beyond the abstract's sentence in F1. No count of failed reconciliations, repairs or caught regressions.
- effect: helps
- reader: described, with no data on what the gate caught, so E0. The same hand-built references that validate the output also exist only because humans wrote them; the paper does not say how many there are.

### F6 · practice · dependency-ordered-subagent-per-document · E0
- practice: read-only agents infer the dependency edges between docs; an orchestrator agent walks the DAG in topological order and assigns one coding sub-agent to each self-contained doc (§2).
- claim: restricting each generation step to one doc bounds the context window and task length, "significantly increasing the probability of correct code generation for each isolated task" (§2).
- evidence: none. No success rate per doc, no comparison with one agent given all docs.
- effect: helps
- reader: asserted, so E0. The context-window argument is also the paper's failure mode 2 in §1; whether the sub-agents in later waves read the code of earlier waves is not stated.

### F7 · practice · orchestrator-struggle-log-for-spec-revision · E0
- practice: the orchestrator keeps a central log of places where sub-agents struggled to interpret the prose and of bugs found in the output of earlier waves; humans read it to decide which doc to rewrite (§2).
- claim: the log shows the "hardness" of each doc, so engineers "know exactly which documents require prose refinement" (§2).
- evidence: none. No log excerpt, count or example of a doc revised from it.
- effect: helps
- reader: asserted, so E0. This is the only point in the paper where an agent's output feeds a human edit of the specification.

### F8 · practice · model-routing-by-document-complexity · E0
- practice: route foundational docs, such as the core DSL design, to a larger model and downstream docs to smaller, cheaper models (§2).
- claim: "many downstream design docs can be successfully translated into working code using smaller, more cost-effective models" (§2).
- evidence: none. Written as an ability of the orchestrator ("can dynamically allocate"); no run is reported with a smaller model.
- effect: helps
- reader: asserted, so E0. It is not stated that the 100 USD cost in F2 used this routing, and the agent model is not named.

## Limits stated by the authors

- None stated in the parts read. The conclusion says the approach "should increasingly be considered" and that its enablers "should generalize wherever specs churn faster than software absorbs them" (§4).

## Reader's notes

- A 5-page paper with no experiment, table, baseline or ablation. Every effect is claimed by its authors for their own library; the only outcome statement is the abstract's reproduction of reference models.
- The domain is narrow: a symbolic cost model whose outputs can be compared exactly with hand-audited references. A repository whose behaviour has no exact reference output would lack the gate that makes F1 and F5 checkable.
- Tests are generated by the agents from the docs (§2, §3); the paper does not say whether any tests are written by humans.
- The IR in §3 (Op, RRT, SymPy cost, fast and slow modes) is a design of the library, not a coding-agent practice; the paper argues that few, orthogonal abstractions are needed for regeneration (§3) and gives no evidence for that either.
- The claimed benefit that an unwritten guess "must be written into a doc to survive" (§4) is an argument; the paper gives no case of a vague intent caught this way.
