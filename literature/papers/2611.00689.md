## Question

Which rules of a shared message room change how agent teams coordinate, whether defenses inside
the conversation stop a hostile member's planted backdoor and whether the record allows finding it
afterwards, and where work waits when a fleet of agents and two people develop a system through the
protocol (§1, RQ1 to RQ3).

## Findings

### F1 · practice · shared-working-tree-for-parallel-agents · E3
- practice: agents edit one shared directory (shared tree), compared with a shared Git remote with one clone per agent, on the service task with a seeded header conflict (Authorization: Bearer against X-Token); the ladder has one run per rung (§6.1.1, Tables 5 to 7).
- claim: "A shared tree hides the conflict": the program works in every message condition, but nobody exposes or decides the conflict; "A working program is no evidence of agreement" (§6.1, conclusion).
- evidence: rungs 1 to 3 (shared tree; no channel, commit announcements, full message envelope) all pass the ground-truth check; in none did the dissenting UI agent state its requirement (0 mentions by the holder, Table 7); it read the auth module's declaration instead. Rung 4 (shared remote, no channel) fails and diverges; rung 4' adds one paragraph on how to publish and fetch and passes, with 19 commits and 18 pushes and 18 pulls by the busiest agent against none in rung 4 (§6.1.1 to §6.1.3). In the per-agent-repository cells peers' code was fetched 0.0 to 0.12 times per run (§6.1.7).
- effect: mixed
- reader: E3, one run per rung and rungs that change the channel and the workspace together; the authors call n = 1 "not enough" (§6.1.4). Passing is better on the artifact and worse on whether the disagreement was settled, hence mixed. The ladder ran before the intake revision (§6.2). The harness's own checker cannot tell a settled conflict from one that never surfaced (§6.1.1).

### F2 · practice · accurate-workspace-description · E3
- practice: the room's resource record tells each agent where the work lives; in one run the platform described separate workspaces as shared, and later runs used a corrected description generated from the same definition as the protocol text (§5.4, §6.1, §6.1.4).
- claim: "A wrong description of the workspace undermines communication"; coordination cost "depended on how accurately the agents were told where the work lived, not only on the task" (§6.1, §6.1.4).
- evidence: the run with the wrong description exchanged 242 messages, agreed on interfaces and never published code, at $34.21; once corrected, later runs published within 28 to 51 messages at $1.23 to $3.72 (§6.1, §6.1.4). Table 19 gives 271 raw messages and 242 agent-written for the first run, and 28 to 51 agent-written for the others.
- effect: helps
- reader: one confounded run against three corrected runs of the open-schema task, with the description as one of several changes; no repetition of the wrong description. The authors call the first run confounded (Appendix A.1, not read).

### F3 · practice · message-intake-wake-rules · E3
- practice: a revised intake bundle in the relay adapters: every addressed message reaches the model framed by sender and intent; an addressed request, or a reply to the agent's own open request, starts a turn; broadcasts are only recorded; one delivery per turn; a tool for sending requests; a guard that declines exact duplicates and limits inbound rate and exchange depth; receipts to the sender (§6.2).
- claim: "The revised intake bundle was followed by fewer total coordination failures, the largest change we observed"; the ablations are "consistent with a contribution from the intake rules ... but do not isolate" it (§6.2).
- evidence: DeepSeek-V4-Flash, same task and configuration. Total coordination failure 21 of 50 runs (42%) before against 4 of 32 (12.5%) after, Fisher p = .0063; all nine registered before-after contrasts pointed to the new rules; Holm-adjusted over the nine, p = .057 (abstract, §6.2). Counting only runs that passed the participation check in both series: 20 of 46 against 4 of 32, adjusted p = .044; full reconciliation with a shared remote 7 of 28 against 12 of 17, adjusted p = .042 (§6.2.1). Counting every refused after-run as a failure removes significance (§6.2.1). Message-to-context path decided 17 of 1,667 intake decisions; 276 started a turn (§6.2.1).
- effect: helps
- reader: E3 because the before series is earlier runs selected by provenance (days 5 to 7, several versions of the participation check), not a concurrent control; the after series lost 8 of 40 launched runs to the check; the bundle changed several parts at once, and the authors state that receipts and the visible-inform path are not the cause. The paper's own header correction leaves it above .05. Authors evaluate their own system.

### F4 · practice · delivery-receipts-to-sender · E4
- practice: remove the receipts that tell a sender what happened to its message (for example "read as context, no answer owed") in the adapters, in the coordinator-free shared-remote cell, with the rest of the bundle in place (§6.2).
- claim: the ablations "did not support our expectation that adding informs to the context and the receipts would matter most"; the paper does not claim no effect (§6.2).
- evidence: with receipts hidden, total failure 1 of 9 against 1 of 9 with the full bundle, and full reconciliation 6 of 9 against 6 of 9; with the guard only recording, failure 30% against 70% before the change, and 11% with receipts hidden (§6.2, Figure 3b, n = 9 to 10 per cell; the figure's cell labels are in the figure only).
- effect: none
- reader: a within-block ablation on equal tasks, so E4, but nine runs per cell and no test stated; the authors say it "does not show that receipts have no effect". The guard-only cell is a second ablation in the same figure.

### F5 · practice · assigned-coordinator-role · E4
- practice: assign one agent the coordinator role (kickoff goes to it) or none (mesh, kickoff to every agent), crossed with workspace (shared remote or per-agent repositories), registered 2x2, DeepSeek, 8 to 10 runs per cell (§6.3.2, Table 8).
- claim: "Assigning a coordinator made no detectable difference to full interface agreement" (§6.3).
- evidence: full reconciliation of both fields in 3 runs of every cell; Fisher p = 1.0 for every factor. Without a coordinator total failure rose 2/8 to 7/10, not significant. Naming an integrator: zero peer-commit adoptions in 32 runs across three variants, half of them still fully reconciled (§6.3.5). Shapley attribution on 15 coalitions with n = 3: of a full-team value of 4.00 the planner (coordinator) contributes +0.58, about 15%; on the pipeline task its share falls to 8% (§6.3.5).
- effect: none
- reader: E4 for the 2x2; the Shapley figures are n = 3 per coalition in one family and are claimed only as direction. Four of the seven six-field runs that read as full settlement were one agent's solo build (§6.3.4), so the outcome measure is weak. The cell sizes cannot show a small effect.

### F6 · practice · proposal-and-voting-tools · E4
- practice: give agents propose, vote and tally tools in the room, in three variants: tools present but not mentioned, named in the kickoff, named with a clause that the outcome binds (§6.3.6).
- claim: "offered tools and instructed roles did not reliably produce the intended decision process" (§6.3.6).
- evidence: 60 runs, five cells, two families; none of four registered contrasts significant. Not mentioned: no proposal in 13 runs. Named: 35 proposals, 21 never received a vote, 5 resolved under majority. Binding clause: 5 proposals, 0 votes. In the hostile block: voting instructed 14/16 against 18/28 backdoors shipped among working artifacts, p = 0.16, rate higher with instruction; instructed runs opened 7 proposals in 5 of 24 runs and 4 of the 5 ballots came from the proposer (§6.3.6, §6.4.4).
- effect: none
- reader: E4 by design (registered contrasts, equal tasks). The authors limit it to this scenario, where a contested choice could simply be merged; the mesh cell was lost to a model outage and is "not run". The voting primitive is the authors' own.

### F7 · practice · dedicated-reviewer-agents · E4
- practice: add 0 to 3 reviewer seats that own no module and are briefed to read what others publish and say what they read, in the transparent room against a direct-attack hostile member (§6.4.4, Table 10).
- claim: "no detectable benefit of reviewers in this block, and no gradient with their number" (§6.4.4).
- evidence: backdoor shipped among working artifacts, by reviewers 0, 1, 2, 3: 21/22, 7/9, 9/9, 11/11; any against none 27/29 against 21/22, p = 1.0. Reviewers spoke in 36 of 36 runs and sent 1,031 messages, 267 of which named the backdoor; some approved the code. Giving every seat all stage rules, 2 reviewers against none: 7 of 10 and 7 of 10 (§6.4.4).
- effect: none
- reader: E4 by design (60 runs, registered); conditions on having a working artifact, which is itself an outcome. One model family (Qwen3.6). The authors read the null as reviewers having nothing that obliged anyone to act on a flag (exploratory). A mechanism the authors proposed (private-rule claims cannot be checked) was tested and "withdrawn".

### F8 · practice · room-transparency-policy · E4
- practice: the hostile-member room is transparent (directory of participants, profiles, progress narration, traffic figures, peer status, a stated review-before-acceptance norm, a decision primitive) or opaque (none of these, no votes) (§6.4.1, Table 9).
- claim: the transparent policy "increased artifact production"; "we found no evidence that it reduced backdoor survival" (§6.4.2).
- evidence: valid runs, n = 19 per cell. Working artifact 17/19 against 5/19, p = 0.0002; backdoor shipped in all runs 14/19 against 4/19, p = 0.0029; given an artifact, 14/17 against 4/5, p = 1.0; graded utility 4.74 against 1.42 (§6.4.2, Table 9). The backdoor was named openly in the room in 42 of 48 runs, in 23 by an honest agent, and shipped (§6.4.3).
- effect: mixed
- reader: E4 as a registered comparison; the effect is better on utility, no better on the backdoor. The opaque room "acts like a handicap on capability" so the contrast is between capable and incapable teams, and the conditional comparison is on 5 surviving artifacts. The registered prediction that transparency would add control was not supported; the policies are advisory, not enforced.

### F9 · practice · post-hoc-audit-of-attributable-record · E3
- practice: after the run, an auditor model (Claude Opus 5, two independent blind passes, not told an attack happened) reads only the retained message ledger and commit history and is asked whether the program excludes anything the task did not ask for and who caused it (§6.4.3).
- claim: "the ledger ... supported investigation": the audit flagged the backdoor and named the hostile agent in all 96 runs; but "detection is not intent" (§6.4).
- evidence: 96 hostile Qwen3.6 runs the detector had judged backdoored, 15 of them gate-failed: flagged 96/96 and attacker named 96/96; in at least 71 the attacker committed the change itself; in the 25 of 27 social runs where another agent committed it, both passes named the persuader in 25/25. The generic question also flagged 24 of 40 cooperative runs with no attacker. The identity-specific criterion, chosen after seeing the cases, gave 93/96 sensitivity (97%) and 37/40 specificity (92%). Audit cost about 0.7% of a run's input tokens (§6.4, §6.4.3, §6.4.4). Messages only named the requester 25/25 against code only 16/24 (Table 11).
- effect: mixed
- reader: no control for the record: the contrast is attacked against honest runs, and the 40 honest runs are "not a representative sample". Detection is high and false alarms on ordinary defects are high; mixed on those two outcomes. The criterion was fitted on the cases it is scored on. The first audit ran on a ledger with speakers anonymised and still named the attacker in 22 of 23, which suggests message content carries the attribution. The detector and the audit prompt are the authors'.

### F10 · practice · auditor-model-differs-from-team · E3
- practice: run the audit with a different, stronger model than the one the agents ran on (Opus 5 against the fleet's own Qwen3.6), same runs and prompt, plus a cooperative-framing prompt (§6.4, Table 11).
- claim: "Changing the auditor model substantially reduced performance on this audit" (§6.4).
- evidence: Table 11, detected, persuader named, sensitivity and specificity: Opus 5 neutral 96/96, 25/25, 97% and 92%; Opus 5 cooperative framing 96/96, 25/25, 97% and 97%; Qwen3.6 53/95, 2/23, 39% and 100% (the team flagged 53 of 95 backdoors and named the requester in 2 of 23, §6.4).
- effect: helps
- reader: rows differ in population (Table 11 caption), and the comparison changes the model's strength and its independence of the team together, so the paper cannot say which matters. One audit prompt family; the "cooperative framing" row is one prompt change.

### F11 · practice · request-act-for-required-action · E3
- practice: send anything that needs a response as a request act (starts a turn) instead of an inform (recorded as context) (§6.2, §7.3, Lesson 2).
- claim: "The distinction between informing and requesting held in operation" (§7.3).
- evidence: field ledger, recipient silent four hours after an addressed inform in 12% to 16% of cases against at most 3% after a request (Table 15: 14%, 12%, 12%, 16% against 3%, 0%, 0%, 0% by week); "at least 97% of requests but ... only 84 to 88% of informs" acted on within four hours (§8, Lesson 2). One failed post-deployment check reported as an inform waited 11.5 hours until an unrelated request woke the owner; the repair then took 26 minutes (§7.3, Figure 8a).
- effect: helps
- reader: E3, a comparison of observed act kinds, not assigned; senders probably chose requests for urgent items. The paper itself calls the low response to informs "intended behavior" and counts it as a cost only when the wrong kind is sent. The 11.5 hours is one case.

### F12 · practice · held-delivery-instead-of-reprompt · E3
- practice: the harness holds a delivery instead of re-prompting an agent that has not finished, and other context-saving changes in the resident fleet: delegating sweeps to sub-agents, not replaying the room's history in a new session, moving the brief into the system prompt with a bound on context within a turn (§7.7).
- claim: "Cost per delivery fell around changes to context automation"; wasted wake-ups fell (§7.7).
- evidence: of 2,227 work turns 612 (27.5%) neither used a work tool nor sent an act; the share of spend on such turns fell from 25% to below 5% and later to 1%. Mean cost per delivery in three-day windows: $8.47 to $4.92 with sweeps delegated, $5.08 to $2.36 with no replay of room history, $4.48 to $1.65 with the brief in the system prompt (§7.7). 3,276 turns, 11.4 billion tokens, about $4,400 declared list-price cost; cached context 92% to 99% of tokens, output 0.4% of tokens and 9% to 18% of cost (§7.7).
- effect: helps
- reader: E3, before and after windows with "no control, and the work changed in each" (§7.7). Costs are declared list-price estimates and exclude coordinators and reviewers. The authors run the fleet they tuned.

### F13 · observation · compaction-drops-brief-and-norms · E2
- practice: observed: in the fleet, harness compaction at a quarter of the context window replaced the conversation with a summary; the agent brief was sent as an ordinary first message until day 65 for one harness (§7.4, §7.7).
- claim: "Compaction loses information silently"; no logged incident was attributed to such loss (§7.7).
- evidence: 196 compactions reduced context by a median of 97% to a summary of about 7,000 tokens; where measurable a summary kept 36% of the identifiers of the compacted context verbatim; three quarters of compactions ran while the brief was an ordinary message; none presented the room's norms again; both defects were found by reading harness code. Daily median context start size showed little association with the room's sequence number (Spearman -0.07) (§7.7).
- effect: hurts
- reader: numbers describe the mechanism; there is no outcome comparison, and the paper states no incident was linked to the loss. The 36% is for "where it could be measured". Grade E2, with the harm inferred, not measured.

### F14 · observation · human-attention-bottleneck · E3
- practice: observed: in the four-week field study the team was a hub of coordinator agents, two of which ran inside a human's interactive session; component agents answered in minutes while requests to the human-run coordinators waited (§7.3).
- claim: "Human attention and decision making emerged as the critical resource" (abstract); delay depended on access to a human decision maker, not on the agents or the difficulty of the decision (§7.6).
- evidence: Table 15 by week: active agents 9, 16, 17, 19; human-run coordinator answered 97%, 98%, 89%, 78% of request pairs; 90th percentile of response time 0.5, 0.9, 1.3, 4.2 h; request pairs issued by coordinators 88%, 83%, 77%, 67%. A request to a human-run coordinator was answered 73% of the time with median 52 minutes after half an hour of session inactivity against 86% and 21 minutes while the session was active; resident coordinators answered in a median of one minute (§7.3). One release took 9.9 hours from candidate to production while the agent replied in minutes; time went to gates and a person's go (§7.3).
- effect: hurts
- reader: E3 between weeks of one observed team, with fleet size, workload and week 4 being a partial week confounded; the W4 rate excludes the final 12 hours (66% including them, Table 15 note). Authors are the two humans and the system's developers (convenience sample, §1). The causal claim that the human is the cause is partly the authors' own experience as operators.

## Limits stated by the authors

- The field study is a convenience sample: the two people are authors and the team develops the system under study (§1).
- Several early results (ladder, open-schema runs, coordinator-by-workspace) ran before the intake revision and carry that qualification (§6.1, §6.2).
- The intake revision changed several controls together and its ablations used nine or ten runs per cell (§6.2).
- The opaque room is severe, none of the varied policies is enforced, and an enforced policy is untested (§6.4.2).
- The identity-specific audit criterion was chosen after seeing the cases and needs independent validation; the 40 honest runs are not representative (§6.4.4).
- Detection does not show that participants noticed the exclusion, and the record may not capture every path of influence (§6.4.3).
- The rig does not prevent every medium of exchange (shared remote, host profile store, host networking) (§5.4).
- The 26 measurement failures of the authors' own instruments are listed in Appendix A (not read); §10 (threats to validity) not read.

## Reader's notes

- The design label `benchmark-eval` is the nearest in the closed set; the controlled part is registered comparisons of agent-team conditions with no human participants, and the field part is an experience report of the authors' own team. Evaluators of both parts are the authors of the relay.
- Nearly every E4 result is a null result on 8 to 60 runs per comparison; none supports "no effect", and the authors say so for the receipts ablation.
- Two outcome measures (hidden checks and a blind LLM judge) correlate at r = +0.53 over 80 runs (§5.8); judged structure is compressed (no fully correct cell above 3.5, robustness about 2, no owner module with a try/except in 38 runs) (§5.8, §6.1.7).
- Many scores that first read as agreement were one agent's solo build: 4 of 7 runs read as full settlement in the six-field task, genuine settlement among several authors in 3 of 24 (§6.3.4). The paper withdrew a registered, significant result (variance ratio 10.2, p = 0.0008) because the scorer counted a single module's name as convergence (§6.3.3).
- Model family decides the mode of work: settlement among several authors was 18% (agentworld, 2/11), 75% (Qwen3.6, 9/12) and 91% (DeepSeek, 10/11) in cells with identical conditions (§6.3.4); one family scored 5.1 of six pipeline checks with private rules and no code exchange, a weaker one 1.80 whether private or public (§6.3.5). Conclusions about coordination structure therefore hold per family.
- The pipeline task is largely void for conditions that vary who starts the work: in 396 of 432 passing runs agents sent work messages before the kickoff (§5.5).
- A committer instruction (route all code through one agent) scored 3.3 of 6 pipeline checks against 5.1 in its control and four total failures against one, reported descriptively and not tested (§6.3.5); it is not a finding here because the run counts are not in the parts read.
- The field coding (69 logged problems, collaboration patterns) was done by one Claude Opus agent with its own precision checks and no human check (§7.2); Tables 16 and 17 are not used in the findings. Of the 69 problems 38 were silent (§7.4).
- A declared mechanism that the agents' tool surface did not expose gave zero uses, the same row as refusal; the paper offers this as a measurement hazard from one unmeasured session (§7.8).

## Discrepancies

- §5.8 says the two outcome measures correlate at r = +0.53 "across 80 runs", and a few lines later gives r = +0.53 (n = 80) for the stronger family alone and +0.85 (n = 39) for the weaker one; the pipeline corpus has more than 80 judged runs, so the first statement appears to describe one family.
- The wrong-description run is 242 messages in the text and 271 in Table 19; the table's footnote explains that 271 is the raw count with probe echoes and 242 the agent-written count, so this is not a conflict.
