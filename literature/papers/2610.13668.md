## Question

Can review agents detect human-verified bugs in the PR that introduced them, how does that depend on
the change and the repository, and which agent design choices improve it? The framing question is when
an agent-written, agent-reviewed repository can run without human review (§1, §5.1).

## Findings

### F1 · observation · model-generation-progress · E3
- practice: observed, not applied: the same review task set run with successive model releases through one pinned harness (copilot-cli 1.0.74, the official `/review` prompt, xhigh or max reasoning) (§4.1).
- claim: review capability "has steadily increased"; the best agent still "misses 20%+ bugs human found" (§1).
- evidence: average recall@5 over both tracks 47.7% for opus-4.6 and 71.9% for opus-5, February to July 2026 (§1, §4.3); opus-5 Table 1 recall@5 79.6% (pre-merge track) and 64.2% (post-merge track), opus-4.6 59.1% and 36.4%, so both averages check (reader's arithmetic). opus-5 costs $2.55 and $3.38 per task, 8.6 and 11.1 minutes (Table 1); opus-4.6 $0.99 and $1.44.
- effect: helps
- reader: E3, models compared on equal tasks but with no control on what else changed between releases. The newer model costs about 2.3 to 2.6 times as much per task (reader's arithmetic from Table 1). Public repositories may be in the training data of newer models; the authors argue only the proprietary portion is certainly not (§1).

### F2 · practice · human-plus-agent-review · E3
- practice: combine a human review and an agent review of the same PR (§4.3, Figure 5b).
- claim: "a clear opportunity for human-agent collaborative code review"; humans alone 50%, best agent alone 71.9%, together 82.1% of the bugs (§4.3).
- evidence: those three numbers in the text. Footnote 3: 49.7% of the benchmark bugs are pre-merge and 50.3% post-merge, so the human figure follows the construction (§4.3).
- effect: helps
- reader: the human figure is set by construction: pre-merge bugs were found by a human reviewer and post-merge bugs escaped one, so 50% is not a measured human recall (and the paper says "by the nature of our benchmark construction"). The 82.1% is partly built in the same way. The comparison shows the agent finds bugs humans missed; it does not measure what a joint human and agent review would catch.

### F3 · observation · agent-in-large-mature-repository · E3
- practice: observed, not applied: the same agents on two proprietary industry monorepos, with more than 100k source files on average against 3k in the open-source repositories (§3.5), against the open-source tasks.
- claim: "agents fall short at large industry repositories", a drop of up to 25.5%, partly explained by a different bug distribution (§1, §4.3, §4.4).
- evidence: drop of "up to 25.5%" (§1, §4.3; per-model values are in Figure 2a only). Diff-visible bugs are 22.8% of industry tasks against 46.1% of GitHub tasks; adjusting for bug visibility alone explains 20% of the gap (§4.4).
- effect: hurts
- reader: a comparison between two task sets that differ in repository, company, bug mix and time, with no control. Four models only (§4.1). The authors say what remains unexplained is "domain knowledge that is not part of models' training data", which the paper does not test.

### F4 · observation · pr-complexity-and-agent-review · E3
- practice: observed, not applied: which task features go with a review catching the bug, in one multivariable logistic regression over all review runs, standard errors clustered by task, adjusted for model, track and calendar time (§4.1, §4.4).
- claim: agents are less effective on larger, more heterogeneous and bug-fixing PRs, and on non-functional or less severe bugs (§4.4).
- evidence: odds ratios of detection: diff size +1 SD 0.591 (p < 0.001); heterogeneity (subchange types) 0.795 (p < 0.05); bug-fixing PR against feature 0.521 (p < 0.001); usability bug 0.454 (p < 0.001); portability 0.523 (p = 0.07, not significant); high or critical severity 1.906 (p < 0.01). No significant effect of language or of repository size once diff size is adjusted (§4.4, Figure 6). Only 104 of the tasks have a high or critical bug against 891 low or medium (Figure 7).
- effect: hurts
- reader: observational; the authors say these are "adjusted associations, not causal effects" (§4.2). Features other than the counts are LLM annotations with human-LLM kappa 0.64 and 0.68 for severity and visibility (§3.4). The practical reading (split PRs, spend more review on large ones) is advice (§5.2), not tested.

### F5 · observation · context-outside-the-diff · E3
- practice: observed, not applied: whether the bug can be seen in the diff or needs project knowledge, cross-file checks or runtime checks (§4.4).
- claim: agents "struggle with bugs that are not directly visible" (§4.4); many failing tasks need knowledge absent from the diff (§4.5).
- evidence: odds ratio of detection for a bug visible in the diff 2.621 (p < 0.001) (§4.4). 459 tasks are visible in the diff and 536 need extra context, 995 in all (Figure 7; sum is reader's arithmetic). Across all executions, 95.6% inspect the file holding the defect, 80.2% produce a finding for it and 56.2% hit the bug; for opus-5 91.9% produce a finding for it and 75% a correct diagnosis (§4.5).
- effect: hurts
- reader: the visibility label is an LLM annotation; the regression is observational. The funnel numbers show the loss is in diagnosis, not in finding the file, but they come from matching file paths to the ground truth and no test is stated. The paper's remedy (repository-specific instructions and knowledge bases, §5.2) is not tested.

### F6 · observation · agent-overtrust-of-pr-claims · E1
- practice: observed, not applied: qualitative reading of 20 sampled tasks where agents' outcomes diverged (§4.1, §4.5).
- claim: agents "accept author claims or existing code as evidence of correctness without independently verifying behavior, even when those descriptions are wrong" (§4.5).
- evidence: two cases. A Selenium task where all models endorsed the buggy condition because an in-code comment and the PR description stated the intended behaviour the code failed to implement. An Elasticsearch task where opus-5 cited the defective line as its gold standard of correctness (§4.5). The PR title and description are given to the agent in every task (§3.3).
- effect: hurts
- reader: two cases; the number of tasks showing this is not given. The PR description is part of the task input by design, so every run is exposed to it. The paper links this to prompt-injection risk in automated review [18] without measuring it.

### F7 · observation · code-execution-in-review · E1
- practice: observed, not applied: how review agents spend tool calls, classified into Read, Probe, Write, Execute, Git and Other by tool name and shell verb over all executions (§4.1, §4.5).
- claim: review agents run the same read-and-search loop and rarely execute the code (8%); the model that executes more finds a few bugs others miss (§4.5).
- evidence: runs open with git operations (64%), then reading and searching are 75% of turn mass (39% Read, 36% Probe), running code 8%. opus-5 executes in 9.7% of turns, gpt-5.6-sol in 6.9% (§4.5). Two cases of discovery by execution: opus-5 fetched about 25 archived pages and ran the yt-dlp extractor; opus-5 installed the .NET SDK and built an MSBuild probe on a GitExtensions task (§4.5).
- effect: helps
- reader: E1 for the effect: two anecdotes; the 8% and 9.7% describe the behaviour and have nothing to compare against for outcome. The two models also differ in run length (§4.5), so execution is not isolated.

### F8 · practice · comprehensive-then-rank-review-prompt · E4
- practice: replace the default copilot-cli review prompt, which optimises signal-to-noise and asks for important findings only, with one that asks for comprehensive findings; the agent still ranks its findings by severity and recall is read at the top 5 (§4.1, §4.6).
- claim: "prompting agents to output more comprehensive findings is fairly effective", with similar cost, and it dominates multi-agent setups on the cost-performance frontier; for claude-opus-5 the gain is "much smaller or even non-existent" (§4.6). The abstract names these prompts "exploration-nudging" and reports "up to 5.8%" at 10% higher cost (abstract).
- evidence: Table 2, recall@5 pre-merge and post-merge track, change from default: opus-4.8 +5.5 and +6.0 (cost $1.54 to $1.67, $1.98 to $2.21); gpt-5.6-sol +5.6 and +5.0 (cost $1.50 to $1.36, $2.03 to $1.81); gpt-5.5 +4.2 and +5.2; opus-5 +0.3 and −1.8 (cost $2.55 to $2.76, $3.38 to $3.60). Findings per review rise, for example 5.76 to 9.26 for opus-5 on the first track (Table 2). 89% of the findings ever found are in the top 3 items (§4.3, Figure 5a), the reason the authors give for asking for more findings.
- effect: mixed
- reader: an ablation on identical tasks, so E4. The effect differs by model, and the strongest model gains nothing. The table gives no variance or repeat count; with 500 tasks per track, differences of one or two points cannot be told from noise. The comprehensive prompt is the authors' own design, evaluated by the authors. More findings per review costs reader attention, which recall@5 does not count.

### F9 · practice · multi-agent-review-ensemble · E4
- practice: scale a single review agent (gpt-5.6-sol) with a second agent that refines the review (self-refine), an orchestrator that merges 3 or 5 independent reviews (same model, or opus-4.8, gpt-5.5 and gpt-5.6-sol mixed), or an orchestrator that spawns sub-agents on sub-directions (§4.1, Table 3).
- claim: "multi-agent setups provide smaller improvements (+2.8% on average ...) with a much higher cost (3.68x)" (§4.6); in the introduction "multi-agents improve 4.7% performance (5.55x cost)" (§1).
- evidence: Table 3, recall@5 change and cost, pre-merge and post-merge track. Base $1.50 and $2.03. Self-refine +1.4 and +3.0 ($3.10, $4.14). Ensemble@3 +2.4 and +4.6 ($5.14, $7.48). Ensemble@5 +4.7 and +4.6 ($8.07, $11.47). Ensemble@3 with mixed models +1.2 and +3.8 ($5.57, $6.91). Sub-agents −3.7 and +6.0 ($5.24, $7.63).
- effect: mixed
- reader: ablation on identical tasks (E4), one model only. Gains are small and cost is 2 to 6 times the base (reader's arithmetic from Table 3); sub-agents lose on one track and win on the other. The 4.7 appears to be Ensemble@5 and the 2.8 an average over configurations; the paper does not say which (see Discrepancies). Mixing models did not beat the same-model ensemble.

### F10 · practice · reasoning-effort-scaling · E4
- practice: raise the model's reasoning effort setting (gpt-5.6-luna at low, medium and max) (§4.1, §4.6).
- claim: "adjusting effort levels is the simplest yet effective strategy to scale up test-time compute" (§4.6).
- evidence: detection from around 36% at low to 57% at max, at 23.22 times the cost (§4.6, §1). The medium value is in Figure 2b only. At the default max setting gpt-5.6-luna costs $0.51 and $0.72 per task (Table 1).
- effect: helps
- reader: an ablation of one setting on one model. The 36% and 57% are approximate reads of a figure and the metric (recall@5 averaged over tracks) is not named in the sentence. Cost rises much faster than detection.

### F11 · practice · model-cost-tiering · E3
- practice: choose a cheaper or smaller model for review when cost matters, and dispatch models by PR characteristics (§4.3, §5.2).
- claim: "gpt-5.6-luna matched 78% claude-opus-5 performance at 21% cost"; the Pareto front is held by small OpenAI models at the cheap end and large Anthropic models at the top (§4.3, Figure 2b).
- evidence: Table 1 recall@5 and cost per task, pre-merge and post-merge track. gpt-5.6-luna 63.9 and 47.8 at $0.51 and $0.72; opus-5 79.6 and 64.2 at $2.55 and $3.38; haiku-4.5 43.0 and 23.0 at $0.21 and $0.26; gpt-5-mini 54.7 and 33.4 at $0.12 and $0.14. From these the 78% and 21% check (reader's arithmetic). Half of gpt-5.6-sol runs end by turn 17 and half of opus-5 runs by turn 35 (§4.5).
- effect: helps
- reader: models are compared without control; cost is list-price estimate per task. The recommendation to dispatch by PR size or type (§5.2) rests on F4 and is not tested: no experiment routes tasks by characteristic.

### F12 · practice · review-harness-choice · E4
- practice: run the review through claude-code's `/review` command instead of copilot-cli's, for opus-4.8 and opus-5 (§4.1, §4.6).
- claim: "copilot-cli outperforms claude-code"; opus-5 in claude-code uses 9.0 sub-agents per run against 0 in copilot-cli and 0.1 for opus-4.8 in claude-code, with "a sharp increase in cost" (§4.6).
- evidence: sub-agent counts in the text; the recall and cost values are in Figure 2b only. The authors tie the sub-agent use to the vendor's note that opus-5 "delegates to sub-agents more readily than prior models" (§4.6).
- effect: hurts
- reader: the harness is the only change on equal tasks (E4), but the numbers are not in the text. The authors are at Microsoft and copilot-cli is a GitHub product; the review prompt of each harness also differs, so this is a comparison of harness-plus-prompt. Also supports the paper's advice to re-check harness and cost on each model change (§5.2, E0).

### F13 · observation · human-agent-complementary-strengths · E3
- practice: observed, not applied: interaction of reviewer identity (human comments against agent reviews) with bug impact and severity in the same regression (§4.1, §4.4).
- claim: humans are better at maintainability, agents at severe and reliability bugs (§4.4).
- evidence: humans against agents, odds ratios: maintainability 2.702 (p < 0.05), high or critical severity 0.450 (p < 0.05), reliability 0.591 (p < 0.05) (§4.4).
- effect: mixed
- reader: same construction problem as F2: the human observations are the benchmark's own source bugs, caught by a human or missed by one by definition. The odds ratios are on a few categories (60 maintainability bugs, 104 high or critical, Figure 7) and are significant only at p < 0.05 under the false discovery rate procedure the authors name.

## Limits stated by the authors

- The benchmark measures recovery of known bugs, not overall review usefulness; LLM judges may be unreliable, mitigated by a three-model panel (§4.2).
- Ground truths can be wrong and some tasks unsolvable; a sample of 40 bugs had 37 valid, 92.5% (95% Wilson interval 80.1 to 97.4%) (§3.2, §4.2).
- Agent behaviour is stochastic; the primary harness is pinned and the prompt and environment held fixed (§4.2).
- Regressions give adjusted associations, not causal effects (§4.2).
- Popular, active, mature projects and textually well-evidenced changes only; smaller or younger projects, rare languages, generated or configuration-heavy code may differ (§4.2).
- The full replication package is not public (Data Availability).

## Reader's notes

- Every judge model of the panel (gpt-5.5, claude-opus-4.8) is also a model under test, and opus-4.8 filtered the post-merge bug pairs (§3.2, §3.3). The agreement check is 40 reviews (kappa 0.89 and 0.95).
- A "hit" is a finding matched to one ground-truth bug. Extra valid findings are not credited and false positives are not counted; recall@5 never penalises noise. The paper measures cost in dollars and findings count but not precision, and no result here says how much human time the findings cost.
- The number of runs per task and model is not stated in the parts read; the regression allows "multiple review executions" per task (§4.1). Tables 1 to 3 carry no intervals.
- The post-merge track is built from SZZ blame; the authors drop 1,168 pairs to 736 and 689 with an LLM, which selects bugs that an LLM judges clearly blamed on the PR (§3.2). This may favour visible bugs.
- The section 5.1 conclusion that lights-off operation is supported "only for narrowly scoped, low-consequence PRs" has no experiment behind it: no result is split by consequence of the change beyond bug severity (F4).
- The paper reviews PRs written by humans. Agent-written PRs, the case the title asks about, are not studied.
- Recommendations in §5.2 (scale review effort by complexity, steer with priorities, supply repository knowledge, monitor and re-benchmark) are derived from F4, F5, F8 and F12 and are not tested as treatments.

## Discrepancies

- Task counts: the abstract and §3.4 give 1,000 tasks from 98 repositories; §3.1 and Figure 3 give 106 repositories; §3.2 gives 865 pre-merge bugs across 99 repositories. The step from 106 to 98 is not explained in the parts read.
- The introduction and the abstract call the improvement prompt "exploration-nudging"; §4.1 and §4.6 describe it as asking for comprehensive findings and ranking by severity.
- Multi-agent gain: "4.7% performance (5.55x cost)" in §1 against "+2.8% on average" at 3.68 times the cost in §4.6. Table 3 values match Ensemble@5 for the first (+4.7, +4.6 points; cost 5.4 and 5.7 times, reader's arithmetic) and an average for the second.
- "Five months of model evolution" (abstract, February to July in §1) against "six months in 2026" (Figure 2 caption).
- The abstract says the best agent is "claude-opus-5 with copilot-cli" at 71.9%; §1 says "claude-opus-5-xhigh" catches 79.6% and 64.2%. Both are the same runs; 71.9% is the mean of the two tracks.
- §4.6 says comprehensive prompting costs "similar" and the abstract "10% higher", while Table 2 shows cost falling for gpt-5.6-sol and gpt-5.5 and rising 7 to 12% for opus-4.8 and opus-5 (reader's arithmetic).
