## Question

How much time does GitHub Copilot save across software development tasks in real projects on large
proprietary code bases, where does it fall short, and how does that vary by language and task
complexity (§1)?

## Findings

### F1 · practice · ai-tools-allowed · E3
- practice: 26 engineers used Copilot for their everyday tasks and logged efficiency changes; the study "established a baseline for coding efficiency by comparing it to work on similar tasks but without Copilot" (§3). Copilot was not fine-tuned on the code bases (§3).
- claim: Copilot reduced coding time by about 35% against the baseline; across a feature's task mix the reduction would be 26% to 35% (§4.1, §4.4).
- evidence: "reduce coding time by around 35% compared to the baseline" (§4.1). "an efficiency gain of between 26% and 35%" from a model of the share of time spent per task type (§4.4). The Abstract gives a projected 33-36% for coding-related tasks in a cloud-first lifecycle. No n per task, no variance, no test, no description of how the baseline was formed.
- effect: helps
- reader: E3 because a baseline exists but the paper does not say how the without-Copilot work was matched, measured or whether it was the same engineers; there is no assignment. The time saved is most likely the participants' own log entries (§3); the paper does not say. The 26% to 35% figure is a projection from averages and excludes requirements, design, coordination and test execution (§4.4).

### F2 · observation · task-family-difficulty · E3
- practice: time saved and acceptance rate reported per development task type (§4.1, Figure 1).
- claim: gains vary "significantly based on the type of task": largest for documentation and CI/CD, smaller for generated tests and monitors, and Copilot is least useful for code that follows no existing pattern (§4.1).
- evidence: comment and Doxygen generation and CI/CD "just over 50%" time saved; unit test and monitor generation "around the 30-35% mark" (§4.1). Autocompletion, compiler and linter error fixing and code explanation are called good, with no number in the text (§4.1). Other per-task values are in Figure 1 only.
- effect: mixed
- reader: the comparison is between task types with no control for who did them or for task size. The Abstract's "up to 50% ... in code documentation and autocompletion" does not match §4.1, which gives no autocompletion number. Task types were partly chosen by participants, who self-selected towards the tasks where Copilot helped as the study went on (§4.4).

### F3 · observation · task-complexity-and-time-saved · E3
- practice: time saved grouped by task complexity: repetitive, boilerplate, small function or context, complex multi-file (§3, §4.3, Figures 5 and 7).
- claim: Copilot saves most on repetitive and boilerplate work and does not do well on complex tasks that need a large local context or changes across many files (§4.3).
- evidence: repetitive tasks "as much as 60%" time saved (§4.3). For complex tasks that need a large context or multi-file edits the saving is "around 26%" (§4.3, Figure 7). Participants did not see a "notable efficiency gain" there (§4.3). Other category values are in the figures only.
- effect: mixed
- reader: grouping is by the authors' category, assigned after the fact, and n per category is not given. A 26% saving is a gain by the paper's own numbers, so "does not do well" is relative to the other categories.

### F4 · observation · uneven-language-and-file-support · E3
- practice: time saved and acceptance rate reported per programming language and per file type (§4.2, Figures 3, 4 and 6).
- claim: effectiveness varies widely by language; C and C++ are the weakest (§4.2, Abstract).
- evidence: JavaScript close to 50% time saved, Java around 45%, Golang, Python, scripting and config files "between 37% and 33%" (§4.2). For C and C++ the text gives no figure and says Copilot "often failed to generate useful code", including basic null checking (§4.2). The C and C++ components in the study are data plane components with high performance and low latency requirements (§4.2).
- effect: mixed
- reader: language is confounded with component type, since the C and C++ code was performance-critical data plane code; the paper does not separate the two. No counts of tasks per language.

### F5 · observation · plausible-wrong-output · E1
- practice: cases where generated or rewritten code was functionally correct and still not acceptable, or was wrong in a way that needed expert review (§4.1, §5.2).
- claim: the generated code can be correct and un-optimized, missing error checks or insecure; these need careful review (§4.1, §5.2).
- evidence: in a back-end case an expensive method was called three times instead of once (Figure 2, §4.1). Asked to optimize a function, Copilot moved conditionally called expensive methods to run unconditionally, and "multiple prompts and attempts did not lead to optimized code" (§4.1). Golang low-level Linux networking code got incorrect suggestions and explanations with all relevant files open (§4.2). §5.2 names missing error checks, unoptimized code and insecure code as subtle errors, and says hallucination "is less of an issue since that is a problem easily caught by the compiler".
- effect: hurts
- reader: a handful of cases told in prose, with no count of how often each occurred. The security claim in §5.2 is asserted; the study measured no vulnerabilities.

### F6 · observation · unit-test-generation-gaps · E1
- practice: using Copilot to generate unit tests and monitors (§4.1).
- claim: generated unit tests are good for simple cases and often find extra cases, but need manual work when mocking is required, and vary between runs (§4.1).
- evidence: Copilot "generated comments indicating which objects and interfaces needed to be mocked but was not able to generate the relevant code"; "different sets of tests would be generated over multiple iterations of unit test generation, some with better coverage than others" (§4.1). §5.1 says Copilot "can contribute to improved code coverage and quality by generating useful unit tests"; no coverage number is given.
- effect: mixed
- reader: cases and statements only. The coverage claim in §5.1 has no data.

### F7 · practice · reference-code-in-prompt · E0
- practice: first write some code or tests in the wanted pattern, then prompt for more, using that code as the reference (few-shot prompting) (§4.1).
- claim: "the quality of generated code improved with few-shot prompting" for code, unit tests and monitors (§4.1).
- evidence: the statement only; no data, no case (§4.1).
- effect: helps
- reader: asserted from the participants' experience. The first week of the study included swapping learnings on prompts and context (§3), so this may be shared folk practice, not a tested result.

### F8 · practice · relevant-files-open-as-context · E0
- practice: open the relevant files in the IDE, and give detailed prompts, so Copilot has more context (§4.1, §5.2).
- claim: "code generation was better if more context was provided by opening relevant files"; quality "improves significantly when context is provided through relevant files with similar patterns" (§4.1, §5.1).
- evidence: the statements only; no data (§4.1, §5.1). A counter case in §4.2: Golang networking code was still misunderstood with all relevant files open.
- effect: helps
- reader: asserted. "Significantly" in §5.1 has no test behind it.

### F9 · practice · restart-with-better-prompt · E0
- practice: clear the prompt window and start over with a better prompt when the output is poor (§4.1).
- claim: this was "found to be useful in generating better code" (§4.1).
- evidence: the statement only (§4.1).
- effect: helps
- reader: asserted. Against it, repeated prompts and attempts did not fix the optimization case in F5.

### F10 · observation · existing-code-quality-shapes-output · E0
- practice: none applied; the quality and naming of the code around the edit were observed to track the quality of the output (§4.1, §5.2).
- claim: "Code quality was better if the code provided as context was of good quality, and especially if function and variable names used in the existing code were descriptive" (§4.1). The authors recommend keeping existing code high quality and names descriptive (§5.2).
- evidence: the statements only; no data (§4.1, §5.2).
- effect: helps
- reader: asserted from the log entries. The recommendation is the authors' own and is not tested.

### F11 · practice · code-explanation-for-unfamiliar-code · E0
- practice: ask Copilot to explain unfamiliar code, functions and syntax in the IDE instead of searching outside (§3, §4.1, §5.1).
- claim: it speeds understanding of unfamiliar repositories and onboarding, with "accurate code explanations", and reduces context switching to browser searches (§4.1, §5.1).
- evidence: statements only; no time number for this task in the text (§4.1, §5.1). For C and C++ code the explanations were "very basic" (§4.2).
- effect: helps
- reader: asserted. The accuracy of explanations was not checked against a reference.

### F12 · practice · review-of-ai-output · E0
- practice: review generated code thoroughly before accepting it, and add static analysis and vulnerability analysis tools (§4.1, §5.2).
- claim: "a thorough review was always needed before accepting generated code"; careful review and complementary tools are recommended for quality (§4.1, §5.2).
- evidence: the statements only; no measure of review time or of defects caught (§4.1, §5.2).
- effect: helps
- reader: a recommendation with no data. The paper does not count what the review cost, so the time saved in F1 is not net of review unless the participants counted it, which is not stated.

## Limits stated by the authors

- The model ran without fine-tuning on the internal code bases; fine-tuning could raise relevance (§6).
- The time-efficiency model covers only the areas where Copilot is used and shows a gain; requirements analysis, design, dependency alignment, coordination and test execution are outside it (§4.4).
- The model is based on averages and varies by language and complexity (§4.4).
- Participants self-selected towards tasks where Copilot was likely to help as the study progressed (§4.4).
- Copilot is one part of the tool stack; agentic workflows and other tools are left for later work (§6).

## Reader's notes

- Not stated: how time saved was measured, how many tasks or hours each average covers, which tasks had a without-Copilot baseline and who did them, the study dates, the Copilot version or model, and what "acceptance rate" counts. The acceptance rate series in Figures 1, 3 and 5 is not discussed in the text.
- The authors are engineers of the organisation whose staff were the participants, and the participants kept their own logs (§3); the paper does not say whether authors took part. A study aim of showing benefits for the company's own SDLC is a possible bias.
- Self-selection of tasks (§4.4) makes the per-task savings upper bounds for the tasks where Copilot is used, not averages of all work.
- The tool is an IDE completion and chat assistant, not an autonomous agent. The paper's findings on context and prompting concern that mode of use.
- Copilot was used by developers working on tasks they chose. No task was assigned to the with and without conditions, so no finding here is E4.

## Discrepancies

- The Abstract says 15 software development tasks; Table 1 lists 14 rows, including "Other".
- The Abstract projects a 33-36% time reduction for coding-related tasks; §4.4 gives "between 26% and 35%" and §4.1 gives about 35%.
- The Abstract says up to 50% saved in "code documentation and autocompletion"; §4.1 gives just over 50% for documentation and CI/CD, and no autocompletion number.
- The Abstract gives 30-40% for repetitive coding tasks; §4.3 says repetitive tasks save "as much as 60%".
- §4.3 says Copilot "does not do well" on complex tasks and gave no notable gain, while §4.3 also reports about 26% time saved for that category.
- §5.1 lists "Java, Golang, and Python benefiting more substantially than C and C++"; §4.2 puts JavaScript first at about 50%.
- Figure 4 carries the caption "Efficiency by Development Task Type", the same as Figure 1, while it shows task type by language.
