## Question

Can a code review agent that fixes file selection, tool set and comment filtering in advance find
more of the real review issues, with fewer tokens, than the review commands built into Claude Code
and Codex (§1, §4)?

## Findings

### F1 · practice · review-harness-choice · E3
- practice: run the authors' own review agent (rule-driven file dispatch, six bounded review tools, one sub-agent per file, a diff-only reflector) against Claude Code's `/code-review` and Codex's `/review`, on the same 200 pull requests and with the same model per row (§4.1.2).
- claim: OpenCodeReview "consistently outperforms" both across all model backends, "up to 2.17× higher SEM-F1"; the gain "stems from precision, not recall inflation" (Abstract, §4.2).
- evidence: SEM-F1, OpenCodeReview against Claude Code, Table 3: Claude-4.6-Opus 25.10% against 11.57%, Qwen3.7-Max 21.20% against 12.17%, Claude-4.8-Opus 17.90% against 14.13%, Deepseek-V4-Pro 17.90% against 10.93%, GLM-5.1 20.40% against 11.93%; GPT-5.5 against Codex 21.00% against 8.36%. Precision 25.20% to 37.80% against 7.23% to 15.93% for Claude Code (§4.2). Recall is lower than Claude Code's in all five pairs, e.g. 20.00% against 28.90% (Table 3; reader's arithmetic on the comparison). Comments generated: 465 to 1,096 against 1,200 to 5,980 for Claude Code (Table 3).
- effect: helps
- reader: E3. The systems differ in every component at once (dispatch, tools, parallelism, reflector, prompts), so the table compares whole systems and isolates none of the three designs. The authors built the system and share authors with AACR-Bench (ref. 30 lists Lei Zhang, Zhengqi Zhuang, Guoping Rong, Zhengfeng Li, Boge Wang). Each configuration is one run; the judge is repeated 5 times, the agent is not (§6). The precision gain comes with lower recall in 5 of 5 pairs, which the abstract's "preserving recall" does not show.

### F2 · practice · review-harness-choice · E3
- practice: as F1; the measurement is tokens and wall-clock time per pull request.
- claim: OpenCodeReview "consumes 5–15× fewer tokens than Claude Code while achieving 1.3–2.2× higher SEM-F1"; against Codex "2.5× higher SEM-F1 at comparable token cost" (§4.3).
- evidence: average tokens per sample, OpenCodeReview against Claude Code, Table 3: 385K against 5,664K, 625K against 5,153K, 352K against 2,062K, 394K against 5,450K, 743K against 4,038K; GPT-5.5 422K against Codex 525K. Average time: 1m23s against 13m06s, 4m41s against 8m06s, 1m06s against 5m38s, 6m28s against 14m24s, 4m11s against 14m10s; GPT-5.5 2m51s against Codex 2m58s.
- effect: helps
- reader: E3 for the same reason as F1. The paper credits the saving to three decisions, "rule-guided dispatch", "bounded-output curated tools" and "file-level parallelism" (§4.3), but runs no ablation of any of them. How tokens are counted for Claude Code, including any sub-agents it starts, is not stated.

### F3 · practice · rule-driven-file-and-criteria-dispatch · E0
- practice: a four-tier chain of natural-language rule documents (ad-hoc, project-level, user-global, built-in) with glob path patterns decides which changed files are reviewed and by which checklist; first match wins; a project rule replaces or is merged with the built-in one. Files are also filtered by extension, include and exclude patterns, default exclusions (fixtures, generated code) and size: a diff over 80% of the context window is dropped (§3.2, Table 1).
- claim: file selection and criteria "are fully determined by rules rather than agent discretion, eliminating a major source of run-to-run variability" (§3.2.3).
- evidence: none for this component; no run-to-run variance and no with-and-without comparison is reported. Its share in the token saving is asserted in §4.3.
- effect: helps
- reader: E0, a design argument. The paper reports no repeated runs of any agent, so the stability claim is not measured.

### F4 · practice · curated-bounded-tool-set-instead-of-bash · E0
- practice: give the review sub-agent six tools (`file_read` max 500 lines, `file_find` max 100 results, `code_search` max 100 matches and a 10 s timeout, `file_read_diff`, `code_comment`, `task_done`) and no general shell; cap the loop at 30 iterations (§3.3.1, §3.3.2, Table 2).
- claim: a general bash tool "inflates the context and token budget" and adds non-determinism; bounded tools keep behaviour "predictable and cost-bounded without sacrificing the ability to trace cross-file dependencies" (§1, §3.3.2).
- evidence: none for this component; the support cited is other work (refs 4, 23, 24, 25). No comparison with a bash-equipped variant of the same agent.
- effect: helps
- reader: E0. The 5 to 15 times token difference in F2 is between whole systems and cannot be assigned to the tool set. The claim that the tools match what human reviewers need is said to rest on "a data-driven analysis" of expert reviewers' retrieval patterns (§1); that analysis is not in the parts read.

### F5 · practice · file-level-parallel-subagents · E0
- practice: dispatch one independent sub-agent per changed file, each with only its own diff, its rule and the list of other changed files; a `file_read_diff` tool lets it read another file's diff, and a prompt rule forbids comments about other files (§3.2.3, §3.3.2).
- claim: file-level partitioning balances "context coherence against execution efficiency" and avoids "the monolithic context window that centralized agents accumulate" (Abstract, §4.3).
- evidence: none for this component; no run with a single agent or another granularity.
- effect: helps
- reader: E0. The time results in Table 3 (F2) mix this with every other difference between the systems.

### F6 · practice · context-compression-module · E0
- practice: monitor token use in the agent loop; at 60% of the context window start an asynchronous compression, at 80% a synchronous one that summarises the middle of the history and keeps the system prompt and the latest turns (§3.3.1).
- claim: this "three-region strategy (frozen–compress–active) mitigates the token snowball effect" (§3.3.1).
- evidence: none; no run without it.
- effect: helps
- reader: E0, a design statement. The thresholds are not justified in the parts read.

### F7 · practice · diff-only-falsification-filter · E0
- practice: after a sub-agent finishes, a second LLM call receives only the file's diff and the sub-agent's comments and deletes a comment only when the diff directly contradicts its claim; it cannot add comments; a parse failure keeps all comments (§3.4).
- claim: it removes hallucinated comments "without the self-reinforcing bias of intrinsic self-critique", raising precision while "preserving recall"; "the information boundary may matter more than the model identity" (Abstract, §3.4, §5).
- evidence: none that isolates the reflector. The only numbers are the final precision of the whole system, 25.20% to 37.80% over six backends (§4.2, §5), against 7.23% to 15.93% for Claude Code; no run without the reflector, no count of comments removed.
- effect: helps
- reader: E0. The precision numbers are F1 and cannot be assigned to this component. The paper says the reflector "uses the same LLM" as the agent (§3.4.1), so the difference lies in what it sees; nothing compares that with a reflector that sees the exploration.

### F8 · observation · review-comment-volume-and-precision · E3
- practice: none applied; the comment counts and precision of the five Claude Code configurations and of the six OpenCodeReview ones are compared (§4.2, §4.4).
- claim: agents "compensate for shallow analysis by emitting many low-confidence comments", the low signal-to-noise problem; OpenCodeReview "maintains precision above 25% even when generating 700–1,100 comments", Claude Code's falls to 7% to 8% at similar or higher volumes (§4.2, §4.4).
- evidence: Table 3, Claude Code comments generated and precision: 5,980 and 7.23%, 4,260 and 8.23%, 3,742 and 8.37%, 2,945 and 8.27%, 1,200 and 15.93%. OpenCodeReview: 728 and 32.10%, 820 and 28.90%, 889 and 33.90%, 1,096 and 25.20%.
- effect: hurts
- reader: E3, a comparison between systems, not an assigned condition. Precision counts a valid comment that is not in the 1,505 ground-truth comments as a false positive (§6), so a high-volume agent is penalised for correct findings the benchmark lacks; the paper cannot separate the two.

### F9 · observation · model-ranking-changes-with-review-harness · E3
- practice: none applied; the ranking of the same models is compared across the two systems (§4.2).
- claim: "a 2.17× improvement attributable solely to system design"; "system design contributes more to review quality than model choice" (§4.2, §7).
- evidence: Claude-4.6-Opus ranks first under OpenCodeReview (25.10%) and 4th of 5 under Claude Code (11.57%); Claude-4.8-Opus is best under Claude Code (14.13%) and ties for last under OpenCodeReview (17.90%) (Table 3). Spread across models: 17.90% to 25.10% under OpenCodeReview, 10.93% to 14.13% under Claude Code (§4.2).
- effect: mixed
- reader: the direction is not clean: the best model differs by system, and the gap between systems exceeds the gap between models in every row. The claim "attributable solely to system design" holds only if the two systems differ in nothing but design; prompts and sampling for Claude Code are not described. Rank positions are the reader's reading of Table 3.

## Limits stated by the authors

- Agent systems are non-deterministic; the semantic judge is non-deterministic, so it ran five times per configuration and the mean is reported (§6).
- AACR-Bench cannot cover all industrial code, domain-specific languages or unusual repository structures (§6).
- Only two baselines were compared (§6).
- SEM-F1 does not measure actionability, clarity or severity; a useful comment missing from the ground truth counts as a false positive (§6).

## Reader's notes

- No ablation of any of the three modules, no repeated runs of the agents, no human rating of comments and no cost in currency; so the paper's central premise, that determinism makes outcomes more stable, is not tested. Only the evaluator is repeated.
- The ground-truth comments come from a benchmark whose authors overlap with this paper's authors, and the judge is another model (Qwen3-235B-A22B-Instruct) that is not one of the compared backends.
- The Claude Code and Codex runs use the vendors' review commands with the version numbers given; the prompts, settings and the method of turning their output into scored comments are not stated in the parts read.
- A cited study of 3,109 pull requests reports a 45.2% merge rate for agent-only review against 68.4% for human-only review, and 60% of rejected agent-only pull requests with a signal-to-noise ratio below 30% (§2.1, ref. 2). That is another paper's result and is not a finding here.
- The `file_read_diff` tool and the focus rule are the only multi-file mechanism; whether cross-file issues are found more often is not measured separately.

## Discrepancies

- §4.2 says Claude Code generated "4,580" comments across 200 pull requests; Table 3 gives 5980 for the same row (Claude-4.6-Opus, 28.90% recall).
- §4.1.2 says Claude Code is evaluated "with six models, excluding GPT-5.5"; that is five models, and Table 3 has five Claude Code rows.
- The abstract and §3.4 say the reflector improves precision "while preserving recall"; recall under OpenCodeReview is below Claude Code's in all five paired rows of Table 3 (reader's arithmetic).
- §4.2 says Claude-4.6-Opus "ranks near the bottom under Claude Code (11.57%)"; it is 4th of 5 (second lowest, reader's arithmetic).
- §4.2 names Deepseek-V4-Pro as the "weakest" OpenCodeReview configuration at 17.90%; Claude-4.8-Opus has the same SEM-F1.
