## Question

Does the number of agents in a self-organised team with no central orchestrator, where workers claim their own sub-tasks and merge through a shared Git workspace, raise the test-pass rate and shorten the time to a given rate on long software-reproduction tasks (§1, §3)?

## Findings

### F1 · practice · agent-count-scaling-without-orchestrator · E4
- practice: run the same worker prompt on 1, 8, 32 or 128 concurrent agents with no orchestrator, on the same five tasks, same model, same harness and the same 6 h budget; workers claim sub-tasks themselves and merge into one Git repository (§2.1, §3.1, App. C).
- claim: "agent count is a scaling dimension for multi-agent organizations"; more workers "consistently and substantially improve" the quality of the reproduction (§3.1).
- evidence: mean final test-pass rate over the five tasks 19.31% (1 agent), 20.68% (8), 26.52% (32), 28.78% (128); +9.47 percentage points, "approximately 49% relative improvement" (§3.1, Figure 5). Per-task scores are in the figure only; the text says only that they show "a generally increasing trend" (§3.1).
- effect: helps
- reader: a contrast on equal tasks with the team size as the only treatment, so E4. The paper states no number of runs per configuration, no variance and no seed, so every gap may be one run; the gap from 1 to 8 agents is 1.37 points (reader's arithmetic), small against the spread one would expect between runs. The authors built and evaluate their own system. Token cost per configuration is not reported, so the gain is not set against what 128 agents spend. The 1-agent baseline receives a stop hook that keeps it working (see F8).

### F2 · practice · agent-count-scaling-without-orchestrator · E4
- practice: as F1; the measurement is the time at which the test-pass rate first crosses a threshold (§3.1).
- claim: "more concurrent agents can also reduce the latency to achieve the same score" (§3.1).
- evidence: on pandoc, 128 agents exceed 30% at the 30-minute checkpoint, 32 agents at 60 minutes, 8 agents at 90 minutes; the single agent stays below 30% for the first 2 hours (§3.1, Figure 6). The claim for the other four tasks is "larger organizations generally achieve higher test-pass rates earlier" (Figure 6 caption), shown in the figure only.
- effect: helps
- reader: the numbers in the text are for one task of five and read off checkpoint curves; the other four tasks are not quantified in the text. Same single-run and own-system limits as F1.

### F3 · practice · agent-count-scaling-without-orchestrator · E4
- practice: as F1, extended to 1,024 agents on pandoc only, spread over 16 nodes with 64 agents each (§3.1, App. C).
- claim: "Agensh continuously scales self-organized cooperation among more than a thousand agents" (§3.1).
- evidence: pandoc final test-pass rate 33.89% (1 agent), 50.94% (128), 55.06% (1,024); +4.12 points over 128 agents and +21.17 over 1 agent (§3.1, Figure 1).
- effect: helps
- reader: one task, one reported number per size. Going from 128 to 1,024 agents (8 times the agents) adds 4.12 points, against 17.05 points from 1 to 128 (reader's arithmetic from 50.94 and 33.89), so the return per agent falls steeply; the paper does not comment on this and gives no cost. pandoc is the smallest of the five repositories (104,336 lines, Table 1), so it may not transfer to the large ones.

### F4 · practice · typed-shared-context-board · E0
- practice: workers write short typed entries to an append-only shared board: `OBSERVED`, `FACT`, `FAIL` for a falsified hypothesis, `CLAIM` for work in progress, `PATCH_SUMMARY` as files, idea and evidence. Entries are capped at 100 characters (300 for a patch summary), new entries reach peers inside their current turn, and a grep tool searches the full history (§2.2, App. A).
- claim: `FAIL` is "the highest-value entry: it stops peers spending budget on it"; `CLAIM` lets "peers pick a different angle" (App. A).
- evidence: none. The board is not ablated, and no count of entries, duplicated work or reads of the board is given. The prompt text is the only source.
- effect: helps
- reader: E0, since the claim sits in the worker prompt and no result bears on it. The board follows an earlier system (DeLM, [14]); the paper does not say which part of the F1 gain, if any, comes from it.

### F5 · practice · shared-git-workspace-with-peer-merge · E0
- practice: the shared workspace is a Gitea instance; workers push branches, open issues and pull requests, and merge into `main` themselves after syncing with the latest `main`; a refused merge means merge `main` into the branch, recheck against the reference and push again. Direct messages through Mattermost settle two workers about to edit the same thing (§2.2, App. A).
- claim: Git "records the provenance of changes and detects textual merge conflicts", and the message interface lets workers "resolve overlapping claims, negotiate dependencies, and request assistance" (§2.2).
- evidence: none beyond the trajectory cases of F6; no merge-conflict rate, PR count or rejected-merge count is given.
- effect: helps
- reader: E0, the infrastructure is described and not ablated. Compare 2611.00314 and 2609.40303, where adding a message channel between parallel agents did not help.

### F6 · observation · emergent-peer-roles-at-scale · E1
- practice: observed in the recorded trajectories, with no treatment applied: cooperation forms that no prompt assigns appear as the team grows. 8 agents: workers agree on a module interface in gromacs and one worker changes scope after an overlap talk in FFmpeg. 32: in PHP-src an approval of a contribution is withdrawn after a peer finds a counterexample, the author fixes it, peers review again and one merges. 128: workers choose reviewers by prior experience and reuse them; in pandoc two workers set up an integration protocol (branch, commit hash, peer validates and merges) that others reuse and revise after failures. 1,024: in pandoc several workers act as integrators, a worker contacts several and takes the first valid responder, and workers in the same area take over after a failed attempt (§3.2).
- claim: forms of cooperation different forms of self-organized cooperation "gradually emerges and standardizes as the organization grows" (abstract), "entirely self-organized" (§3.2).
- evidence: single named cases per scale in prose, one to two per scale, with no counts, no frequency, no transcript excerpts and no comparison of the same task at a smaller scale (§3.2).
- effect: none
- reader: E1, picked cases. The paper claims no effect of these behaviours on the score; "none" is the nearest closed value for a finding with no measured effect and is not a result of zero (P9 in SCHEMA.md). Every worker has the same prompt, which already names claims, direct messages and PRs (App. A), so the cases are behaviour the prompt invites; "emerge" is the authors' word and there is no run without the board or messages to compare.

### F7 · practice · idle-detector-and-deadline-reminders · E0
- practice: an idle detector prompts a worker that has been idle for 10 minutes to continue with new work; a follow-up prompt reminds a worker whose turn produced no board entry to publish findings; two fixed-time reminders go to all workers, at 45 minutes before the end (stop new features, merge, land open PRs) and 5 minutes before (merge, confirm `bash compile.sh && ./executable` works on the default branch) (App. B.1, App. C).
- claim: not stated as an effect; the reminders and the idle prompt are listed as part of the setup.
- evidence: none; no count of idle prompts sent or of runs that failed to build at the end.
- effect: helps
- reader: E0, kept because the task scores only a build that `compile.sh` produces from a fresh clone (App. A), so a final-state reminder bears directly on the score. The effect direction is the reader's reading of the purpose, since the paper reports no result for it. Compare 2609.40303 F9, where elapsed-time nudges hurt.

### F8 · observation · single-agent-run-stops-early · E0
- practice: the single-agent baseline is given a stop hook with the prompt "There is always new work ... Let's make the 6h fulfilled", because "a single-agent run can rarely sustain the full 6-hour runtime" (App. C).
- claim: without a hook, one agent stops long before the 6 h budget (App. C).
- evidence: the sentence only; no stop times, no run counts.
- effect: hurts
- reader: E0. It is a stated reason for a design choice. It bears on F1: a baseline that stops early would have made the comparison with a 128-agent team unfair, so the authors added the hook, and the paper does not report the baseline without it.

### F9 · practice · staggered-agent-activation · E0
- practice: start agents one every 30 seconds during the first hour and one every 3 seconds afterwards instead of all at once (App. C).
- claim: done "to reduce scope contention" (App. C).
- evidence: none; no run without staggering.
- effect: helps
- reader: E0. At these rates 120 agents start in the first hour and the remaining 904 take 2,712 s more, so the 1,024th agent starts about 1 h 45 min after the first (reader's arithmetic). The large teams therefore have fewer effective agent-hours than their count suggests, and the stagger is part of what F3 measures.

## Limits stated by the authors

- None stated as a limitation. The conclusion states the results hold "with the same agent model GPT-5.6-sol (high) and 6h budget" (§5).

## Reader's notes

- Authors evaluate their own system, in a technical report from the lab that built it; no outside replication (p. 1).
- Number of runs per configuration, variance, seeds and confidence intervals are not stated anywhere in the paper. The 1-to-8 step (+1.37 points) cannot be told from run-to-run spread with this information.
- No cost is reported: tokens, dollars or agent-hours per configuration. A 128-agent team uses far more compute than one agent in the same 6 h, so the result shows latency and final score, not efficiency.
- The score is the "canonical-kept pass rate" on ProgramBench's hidden tests (App. C); the paper does not define it further. Code quality, size and maintainability of the rebuilt code are not scored.
- Only 5 of 200 tasks, picked as the hardest by other models' pass rates (§3). Floor effects may apply: all scores are under 56%.
- 1,024 agents ran on one task only. The abstract's "1,024 agents" gain is a pandoc result.
- The single-agent baseline gets a stop hook where teams get an idle detector (App. C). Whether the 1-agent run uses the team worker prompt, with its board, claims and PR workflow, is not stated.
- The worker prompt tells workers to reach for coordination tools "only when your information can greatly impact others' work" (App. A), which restrains messaging; the message volume per scale is not given.
- The paper does not say when the runs took place.

## Discrepancies

- §3.1 says the per-task final scores show "a generally increasing trend", and in the next clause says the increase is "consistent" and "substantial"; per-task values are in Figure 5 only, so the text cannot be checked against them.
