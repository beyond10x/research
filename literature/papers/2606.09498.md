## Question

Can a fixed LLM agent improve the harness that governs its own behaviour, by mining its own
failed traces, proposing minimal edits and promoting only edits that pass regression tests
(abstract, §1)?

## Findings

### F1 · practice · harness-self-evolution-single-task-type · E3
- practice: run the loop of weakness mining, harness proposal and proposal validation on a minimal DeepAgent harness, with the model that is evaluated also acting as the proposer, separately per benchmark and model; final harness against initial harness on the same tasks (§3, §4.1).
- claim: "every final harness improves both held-in and held-out pass rates, with overall relative gains of up to 132%" (abstract); no stronger external agent or human engineer is needed (§1).
- evidence: Table 1 overall Pass, initial to final. Terminal-Bench-2.0: MiniMax 42.2 to 53.9, Qwen 18.0 to 36.7, GLM-5 46.1 to 57.0. SWE-bench Verified: 46.0 to 52.5, 19.5 to 41.5, 52.0 to 55.5. AppWorld: 48.6 to 58.9, 22.5 to 52.2, 44.4 to 85.0. Largest absolute gain 40.6 points (GLM-5, AppWorld), largest relative gain 132% (Qwen, AppWorld) (§4.2). Two attempts per task and harness; no variance, confidence interval or seed spread is given.
- effect: helps
- reader: E3, before and after on the same tasks, with no control: no human-written harness, no random edits, no run of the loop with another proposer. The authors evaluate their own method (`independent: false`). The final harness was selected on the same tasks it is scored on, held-out ones included (F2), which inflates the gain. Cost, tokens, number of rounds T and proposal width K are not stated in the parts read.

### F2 · practice · deterministic-gate-over-llm-proposed-edits · E2
- practice: accept a candidate harness edit only if its pass count on the held-in split and on the held-out split are both at least those of the current harness and at least one is higher; merge all accepted candidates of a round; log rejected ones (§3.4, Algorithm 1). The held-out split is hidden from the proposer and used only by this gate (§4.1).
- claim: the gate stops proposals that "only trade off one split against the other" and "no promoted harness degrades either split" (§3.4, §4.2).
- evidence: every final harness is at or above its initial harness on held-in and held-out in all 9 runs (Table 1), so no final harness regressed on either split. Rejected candidates are shown as grey crosses in Figure 4, 10, 11 (counts in the figures only). No run without the gate is reported.
- effect: helps
- reader: E2: the outcome is described, with no comparison to ungated promotion. Because the gate selects on the held-out pass counts, non-degradation on them follows from the rule, up to run-to-run noise from two attempts. The authors say that higher-stakes changes need "stronger acceptance gates than pass-rate non-regression alone" (§5).
### F3 · practice · failure-attribution-before-revision · E0
- practice: before proposing edits, cluster the failed traces by exact agreement of a signature (terminal verifier cause, causal status of the agent behaviour, abstract agent mechanism) and hand the proposer ordered failure patterns with representative cases, not raw logs; non-addressable patterns are dropped (§3.2, §3.3).
- claim: the attribution step "prevents the clustering procedure from conflating superficial symptoms with reusable failure mechanisms", for example two runs with the same timeout that need different harness changes (§3.2).
- evidence: none given. No comparison with raw-log input or with another clustering is reported; Figure 4 labels the failure patterns the retained edits address (for example "Missing files", "Untested patch").
- effect: helps
- reader: E0: the claim is argued from the design. The accepted edits do name failure patterns, but nothing shows that the clustering, rather than the model's own reading of traces, produced the gain.

### F4 · observation · harness-edits-differ-by-model · E1
- practice: the retained edits of the nine runs were compared by model and benchmark (§4.3, Appendix B).
- claim: "the retained edits are model- and task-environment-specific and align with the dominant failure mechanisms observed under each initial harness" (§4.3).
- evidence: on Terminal-Bench-2.0 MiniMax retained early creation of the required output file, a cap on total tool messages and a fix for schema-invalid tool content; Qwen retained dependency prechecks, a loop breaker, retry discipline and a tool-error-triggered prompt; GLM-5 retained persistence of environment changes across shell sessions and a shift from exploration to implementation (§4.3, Figures 5, 6, 10). On SWE-bench Verified MiniMax added two verifier subagents, Qwen a patch-verifier subagent, GLM-5 a dependency-aware repair step in its verification instruction (B.2).
- effect: helps
- reader: E1: descriptions of the retained edits and a few single traces (Figures 7 to 9, 12, 14, 16, 18). No edit of one model was run on another, so "model-specific" is a reading of the edit lists, not a measured transfer gap.

### F5 · practice · pre-submission-test-run-in-harness · E2
- practice: on SWE-bench Verified, the loop's retained edits make the agent inspect its diff and run the most relevant failing or targeted tests before it submits: a diff-detector and test-verifier subagent pair (MiniMax), a patch-verifier subagent plus a pre-submission instruction (Qwen), a FAIL-TO-PASS cycle with dependency repair (GLM-5) (B.2).
- claim: on SWE-bench Verified the retained mechanisms "target patch validation and executable verification" and are associated with the gains (§4.3, B.2).
- evidence: overall Pass 46.0 to 52.5 (MiniMax), 19.5 to 41.5 (Qwen), 52.0 to 55.5 (GLM-5) (Table 1). MiniMax steps in Figure 11, values in the figure only: 46.0, 50.0 after the diff detector, 51.0, 52.5 after local-test enforcement. One Django trace: the initial harness submits without running the suite, the retained one runs the 49-test `expressions_window` suite and passes 1 FAIL-TO-PASS and 46 PASS-TO-PASS tests (B.2).
- effect: helps
- reader: E2: the gain belongs to the whole set of retained edits of a run, and the edits of one run are not isolated. 100 tasks, 33 of them held-out. The per-step values sit in a figure with ambiguous labels. Evaluating on the benchmark's tests is the same signal the gate selects on.

### F6 · practice · exhaustive-retrieval-and-completion-rule-in-harness · E2
- practice: on AppWorld, the retained edits make the agent exhaust paginated record lists and apply time boundaries before it changes state, and separate action-only tasks from information requests when it completes (MiniMax: state-auditor subagent; Qwen: completion-contract guard and pagination guard; GLM-5: completion rule and exhaustive pagination before state mutation) (B.3).
- claim: across AppWorld "the runs converge on complete state retrieval and correct completion semantics" (B.3).
- evidence: overall Pass 48.6 to 58.9 (MiniMax), 22.5 to 52.2 (Qwen), 44.4 to 85.0 (GLM-5) (Table 1). Venmo trace, GLM-5: the initial harness reads only the first transaction page and adds an unnecessary answer; the retained one reads all pages, changes all 12 records and answers null (B.3). Held-in is the official AppWorld training split.
- effect: helps
- reader: E2: before and after for the whole edit set of a run, with no isolation of the pagination or completion rule. The three AppWorld gains are the largest in the paper (+10.3 to +40.6 points); the starting harness lacks both rules by design (a minimal prompt, Figure 3), so a single obvious rule may carry most of the gain.

### F7 · practice · early-required-output-in-harness · E2
- practice: on Terminal-Bench-2.0, change the bootstrap instruction from "identify the smallest relevant edit surface" to identifying the required output artifact and creating a first version as early as possible; Qwen's harness adds a tool-error-triggered prompt that sends the agent back to a missing artifact (§4.3, Figures 5, 6, 8).
- claim: these edits address "late deliverables", "missing files" and artifacts deleted after tool errors, which the verifier rejects (§4.3, Figure 4).
- evidence: overall Pass on Terminal-Bench-2.0 42.2 to 53.9 (MiniMax) and 18.0 to 36.7 (Qwen) (Table 1). Qwen trace on `extract-elf`: the initial run deletes `/app/extract.js` and stops, the edited run recreates it and writes the output (§4.3). MiniMax trace on `count-dataset-tokens`: the initial run ends without `/app/answer.txt`, the edited one writes and reads it back (§4.3). Per-edit steps in Figure 4 only.
- effect: helps
- reader: E2 with two single traces. The edit sits among others in the same final harness; whether this one edit carries the gain is not shown. The task set is a 64-case subset chosen by the authors for stable evaluation (§4.1).

### F8 · practice · tool-call-cap-redirect-in-harness · E2
- practice: enable the runtime control policy so that the agent is redirected after a limit of total tool messages, or recent tool errors; MiniMax's retained edit redirects after 50 tool calls, and Qwen's adds a loop breaker (§4.3, Figure 4).
- claim: it stops "unproductive tool-use loops before they become too long" (§1) and "exploration loops" and "stalled tool loops" (Figure 4).
- evidence: overall Terminal-Bench-2.0 Pass 42.2 to 53.9 (MiniMax) and 18.0 to 36.7 (Qwen) for the full edit sets (Table 1). The tool-message cap is part of the three MiniMax edits in Figure 5; no run isolates it. Step values in Figure 4 only.
- effect: helps
- reader: E2: description with a before and after of the whole edit set. The initial harness has the control policy disabled (Figure 3), so the comparison is no cap against a cap. Related to `timeout-budget-reminders-in-harness`, where the reminder is tied to repeated timeouts.

### F9 · observation · held-out-gain-after-selection-on-held-out · E3
- practice: the held-out split, hidden from the proposer, was scored for the initial and final harness of each run (§4.1, §4.2).
- claim: the gains "are not confined to the held-in failures used to construct proposal evidence" and Self-Harness "can discover broadly useful harness modifications that transfer to tasks whose traces are hidden from the proposer" (§4.2, §1).
- evidence: held-out Pass, initial to final: Terminal-Bench-2.0 40.5 to 61.9, 23.8 to 38.1, 42.9 to 57.1; SWE-bench Verified 34.8 to 40.9, 18.2 to 39.4, 48.5 to 50.0; AppWorld 45.6 to 55.0, 20.0 to 44.4, 41.1 to 77.8 (Table 1). In 4 of 9 runs the relative held-out gain is larger than the held-in gain (§4.2).
- effect: helps
- reader: E3 as numbers before and after, but the split is not held out in the usual sense: the held-out pass counts decide which edits are accepted (F2). The unselected evidence would be a third split that is scored once. Held-out sizes: 33 tasks (SWE-bench Verified) and 90 (AppWorld); the Terminal-Bench-2.0 split sizes are not stated in the parts read.

## Limits stated by the authors

- It "studies bounded harness edits under fixed benchmarks, not open-ended self-improvement" (§5).
- "Accepted edits may still reflect benchmark-specific failure patterns" (§5).
- "The protocol depends on the quality of verifier outcomes and trace records" (§5).
- "Higher-stakes harness changes would require stronger acceptance gates than pass-rate non-regression alone" (§5).
- Terminal-Bench-2.0 is evaluated on 64 of 89 tasks, excluding tasks with unstable web resources or multimodal input (§4.1).

## Reader's notes

- The relative gain falls with the baseline score: Qwen, which starts at 15.1 to 25.0 on held-in, gains +104%, +113% and +132% overall; GLM-5 and MiniMax on SWE-bench Verified, which start at 46.0 and 52.0, gain +14% and +7% (Table 1). The paper does not claim this and does not test it.
- No ablation of the loop's parts: no run without clustering, without the held-out gate, with K = 1, or with a stronger or weaker proposer. The claim of "no stronger external agent" has no comparison run against one (Meta-Harness is cited, not run).
- Run-to-run noise is not reported. Each harness is scored on 2 attempts per task, and the accept rule compares pass counts, so a candidate can pass on noise; the paper says repeats reduce this, with no numbers.
- Qwen's baseline is low (15.1 held-in on Terminal-Bench-2.0), and the minimal baseline prompt has no verification-before-submission or pagination rule (Figure 3); part of the gain may be a general instruction that a human would write at once.
- The harness edits are applied through one definition file of the DeepAgent SDK; all three models share it (§4.1). Results on another harness SDK are not given.
- The baseline harness has `/AGENTS.md` as a memory source (Figure 3). The paper does not say whether the loop edited that file or whether it exists in the tasks.
- MiniMax M2.5 and GLM-5 are served by hosted APIs and Qwen locally (A.1); hosted model versions can change between rounds, and the paper does not say how this was controlled.

## Discrepancies

- §4.3 says "Red nodes and grey slots denote rejected branches and failing trials"; the Figure 4 caption says gray crosses are rejected candidates and red crosses are explored branch endpoints.
- §1 calls held-out tasks ones "whose execution traces are never used as inputs to the evaluation system"; §3.4 and §4.1 use the held-out pass counts in the acceptance rule. Traces are hidden, outcomes are not.

## Leads

- Meta-Harness, where a stronger external agent improves a weaker agent's harness (§1, §2, cited as Lee et al., 2026 and Lin et al., 2026): the approach this paper positions against; no arXiv id in the text read.
- Agentic context engineering (Zhang et al., 2026), Reflexion (Shinn et al., 2023) and STOP (Zelikman et al., 2024): adaptation of contexts, memory and generated programs (§2); no arXiv ids in the text read.
- Automated Design of Agentic Systems (§2): search over agent designs; no arXiv id in the text read.
