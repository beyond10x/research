## Question

Can a coding agent be given a repository-specific skill library that is built from the repository's
pull-request history and kept current as new PRs arrive, and does that raise the share of
benchmark tasks it resolves (abstract, §1)?

## Findings

### F1 · practice · repository-skill-library-from-prs · E4
- practice: build a skill library from a repository's historical PRs (PR records are retrieved, repaired or synthesised, verified by tests, then distilled by an LLM writer into skills that say when they apply, how to implement and how to validate); retrieve at most B_s skills per task by dense similarity and inject them into a fixed-weight agent. Base is the same mini-swe-agent without skills (§4, §5.1, Table 3).
- claim: skills "improve the official resolved rate from 79% with the base agent to 88%" on SWE-bench Pro (§1).
- evidence: Table 3, official harness. SWE-bench Pro, Claude Opus 5: 0.79 to 0.88. SWE-bench Verified, Opus 5: 0.83 to 0.92; Sonnet 4.6: 0.77 to 0.79. The table labels the gains +9.0%, +9.0% and +2.0%; they are percentage points. Sonnet 4.6 is left out of SWE-bench Pro "due to its weak baseline performance" (§6.1).
- effect: helps
- reader: a with and without comparison on equal tasks, so E4, but no run count, variance or task count is given. The treated arm is more than a skill file: it also runs PR-record construction and "bounded repair and re-verification" (§4.4), which the base arm does not; Table 8 shows best-of-K sampling reaches the same score (F8). Authors evaluate their own system. The gain on the weaker model is 2 points.

### F2 · practice · repository-skill-library-from-prs · E4
- practice: as F1, on 6 repositories; each repository's historical PRs are split into a skill-construction set and an evaluation set, and the skill pool starts empty (§6.2).
- claim: skills improve "task success across all six repositories, with gains ranging from 0.07 to 0.20" and improve Maintenance Surface F1 (§6.2).
- evidence: Table 5, Opus 5, task success base to ours: Click 0.72 to 0.83, Black 0.53 to 0.60, Rich 0.90 to 1.00, HTTPX 0.80 to 0.93, Arrow 0.58 to 0.75, Agents 0.50 to 0.70. Surface F1: Click 0.70 to 0.72, Black 0.48 to 0.67, Rich 0.78 to 0.90, HTTPX 0.72 to 0.80, Arrow 0.71 to 0.74, Agents 0.85 to 0.88.
- effect: helps
- reader: E4 by the no-skill arm. The table gives no task count per repository; the values (for example 0.90 and 1.00 for Rich, 0.80 and 0.93 for HTTPX) fit small denominators such as 10 or 15 (reader's arithmetic), so a gain of 0.07 may be one task. The six are small-to-mid Python libraries, not the large mature repositories of the main benchmarks. Surface F1 counts file categories touched (code, tests, docs, config, examples, changelogs) and "does not verify the correctness of individual changes" (§5.2).

### F3 · practice · append-only-skill-accumulation · E4
- practice: add each newly distilled skill to the library without revising or retiring existing ones (Table 4, Table 11).
- claim: the paper compares it as a weaker baseline to full alignment: Skill Dreaming "outperform[s] all baselines, including append-only skill accumulation" (§6.1).
- evidence: Table 4, Opus 5, SWE-bench Verified, base agent to append-only to Skill Dreaming: resolved 0.83, 0.88, 0.92; safe rate 0.83, 0.94, 1.00; surface F1 0.62, 0.72, 0.74. Table 11 task success: append-only 0.89, full 0.93. Of the 9-point gain over base in Table 3, append-only provides 5 and alignment the other 4 (reader's arithmetic).
- effect: helps
- reader: E4 against the no-skill base. The finding is that simply accumulating skills yields most of the gain; the supersede, conflict and specialise operations add the rest. No variance is given, so 0.88 against 0.92 cannot be called a difference.

### F4 · practice · skill-supersession-and-stale-filtering · E4
- practice: keep a relation graph between skills and supporting PRs, mark old skills superseded when a later PR changes the convention, and exclude superseded and stale skills from retrieval; ablate each filter and both (§4.3, §4.4, §6.4).
- claim: the results "demonstrate the importance of jointly maintaining supersession and stale-skill filtering" (§6.4).
- evidence: Table 10, task success (TS), Skill Filtering setting: no supersession 0.67, no stale filtering 0.72, neither 0.78, append-only 0.89, full 0.93. Hybrid Retrieval setting: 0.83, 0.78, 0.89, 0.89, 0.94. Surface F1 full 0.75 and 0.77. Table 11: no conflict/supersede 0.78 against full 0.93.
- effect: helps
- reader: an ablation on equal tasks, so E4. The pattern is not monotone: removing both filters (0.78) scores above removing either one alone (0.67, 0.72), which the paper does not explain; the "full" arm beats append-only by 4 and 5 points on TS. Table 10 precision in Hybrid Retrieval is lowest for the full method (0.90 against 0.97). Authors ablate their own system; no variance.

### F5 · practice · rewrite-all-skill-update · E4
- practice: when a new PR arrives, rewrite every relevant existing skill, or only the directly related parent skill, instead of appending or applying the typed operations (Table 11, §6.4).
- claim: the full method "outperform[s] all skill updating variants" (§6.4).
- evidence: Table 11, task success: rewrite-all 0.82, parent-only 0.87, append-only 0.89, SkillLens-style selective 0.83, Learning to Commit-style 0.78, Skill Dreaming 0.93.
- effect: hurts
- reader: rewrite-all and parent-only score below simply appending (0.89), so more editing of skills did not help in this setup. The two baseline variants are the authors' re-implementations, and they overlap in authorship with the SkillLens paper they compare to. No variance.

### F6 · practice · review-and-failure-records-in-skill-learning · E4
- practice: distill skills from several PR information sources together (merged code, review corrections, failed implementations as negative constraints), rather than from positive PRs only or from review and reply text only (§4.2, Table 9).
- claim: skills from multiple sources reach "the highest Task Success of 0.89" (§6.3).
- evidence: Table 9, TS, reuse precision, recall: positive PRs only 0.84, 0.67, 0.78; review/reply only 0.83, 0.48, 0.56; Trace2Skill 0.72, 0.61, 0.76; Socratic 0.83, 0.67, 0.77; Skill Dreaming 0.89, 0.72, 0.82.
- effect: helps
- reader: an ablation on information source, so E4; the gain over positive-only is 5 points on a task set of unstated size. Full-method TS is 0.89 here and 0.93 in Tables 10 to 12 with no explanation (see Discrepancies).

### F7 · practice · learned-skill-library-baselines · E3
- practice: run other published skill-learning methods in the same agent harness against the same base agent (Table 4).
- claim: Skill Dreaming has "the highest resolved rate of 92%, outperforming all baselines" (§6.1).
- evidence: Table 4, SWE-bench Verified, Opus 5, resolved rate against base 0.83: Trace2Skill 0.76, Learning to Commit 0.72, CODESKILL 0.79, SkillLens 0.90, Socratic-SWE 0.91. Safe rate of those five: 0.78, 0.67, 0.56, 0.61, 0.72, below the base 0.83; only Append-only (0.94) and Skill Dreaming (1.00) exceed it.
- effect: mixed
- reader: E3, methods against methods with no control on the baselines' own settings. Three of five published methods resolve fewer tasks than no skills, and all five lower the safe rate; this is the paper's most informative number for practice and also the one most exposed to a weak re-implementation, because the authors built the comparison. The SkillLens and SkillOps authors overlap with this paper's authors ([20], [29]).

### F8 · practice · best-of-k-sampling · E3
- practice: generate K candidate patches and select one, against a single sample, against skill-based methods on shared candidate outputs (Table 8, §6.3).
- claim: Skill Dreaming achieves "a Task Success of 1.000 and a Maintenance Surface F1 of 0.871, outperforming Single Sample and both skill-based baselines while matching Best-of-K" (§6.3).
- evidence: Table 8, TS and surface F1: single sample 0.94 and 0.80; best-of-K 1.00 and 0.87; Trace2Skill 0.78 and 0.60; SkillLens-inspired composition 0.61 and 0.71; Skill Dreaming 1.00 and 0.87. K is not stated.
- effect: helps
- reader: E3. In this table best-of-K sampling gets the same scores as the skill system, and a single sample already scores 0.94, so the room for skills here is 6 points on a task set of unstated size. Table 8 has a different base (single sample 0.94) from Table 4 (base 0.83); the setting is not described.

### F9 · practice · repository-skill-library-from-prs · E3
- practice: as F1; the measurement is tokens and wall time per task, against SkillLens (§6.6, Table 12).
- claim: "higher token consumption but only a modest increase in execution time" (§6.6).
- evidence: Table 12: Skill Dreaming 26,894 tokens and 36.00 s per task, TS 0.93, surface F1 0.80; SkillLens 14,300 tokens and 32.90 s, TS 0.61, F1 0.71. Tokens are 1.9 times (reader's arithmetic).
- effect: hurts
- reader: a comparison with one baseline only; cost against the no-skill base is not given in the parts read, and offline skill construction cost is "reported separately when excluded" (§5.2) with no number found. The conclusion calls the cost "modest" for a 1.9-fold token count.

### F10 · observation · skill-library-growth-with-pr-history · E2
- practice: none applied as a treatment; the skill set starts from 500 historical PRs and is updated with 50 more at each stage up to 1,000, with Opus 5 on SWE-bench Pro (§6.5, Figure 2).
- claim: "all three metrics exhibit an overall upward trend despite occasional fluctuations" (§6.5).
- evidence: Figure 2; the text gives no per-stage values. Axis labels at the right end of the figure read 0.93, 0.88 and 0.77 (in the figure only; which line each belongs to is not in the text).
- effect: helps
- reader: described numbers with nothing to compare against: the start values are not in the text, there is no no-update arm run on the same stream, and "overall upward" over 10 points with fluctuation is not a test. It does not separate growth of the library from accumulated PR count.

### F11 · practice · pr-quality-classification-for-skill-input · E2
- practice: label each historical PR as usable, repairable, outdated, irrelevant or unsafe from compatibility with the current repository, API changes and review or CI feedback, before it is used for skill learning (§4.1, Table 7).
- claim: "All categories achieve F1 scores above 0.86" on 1,000 SWE-bench Pro Ansible PRs (§6.3).
- evidence: Table 7, F1 and support: usable 0.94 (260), repairable 0.88 (50), outdated 0.90 (190), irrelevant 0.94 (450), unsafe 0.86 (50).
- effect: helps
- reader: the source of the reference labels is not stated in the parts read, and no run without this filter is given, so the table does not show that the classification changes skill quality. The two smallest classes, repairable and unsafe, have 50 PRs each.

### F12 · observation · function-level-localization · E2
- practice: none applied; code localization from the PR-record step is scored at module, file and function level (§6.3, Table 6).
- claim: "function-level localization remains more challenging" (§6.3).
- evidence: Table 6, Top-1: module 1.00, file 0.64, function 0.25; function-level Top-3 0.39, R@5 0.33, R@10 0.33, MRR 0.33.
- effect: hurts
- reader: describes the localiser inside this system, with no other localiser to compare; whether localisation accuracy changes resolved rate is not tested.

## Limits stated by the authors

- Probabilities in the constraints of Eq. (6) represent "desired reliability rather than guarantees from available tests" (§3).
- The staged process approximates the objective "without updating model weights or guaranteeing global optimality" (§3).
- Safe rate "does not guarantee feature completion"; Maintenance Surface F1 "does not verify the correctness of individual changes"; logging and compatibility "are not evaluated separately" (§5.2).
- In historical evaluation each request uses its recorded base repository, and generated changes are not chained (§3).
- No limitations section in the text.

## Reader's notes

- No table or text gives the number of tasks, the number of runs per task, a seed, a confidence interval or a significance test. Several tables have values that fit small denominators (Table 8: 0.61, 0.78, 0.94 are 11, 14, 17 of 18; reader's arithmetic, a guess, not stated). All differences of 2 to 5 points are unreadable without n.
- SWE-bench tasks are historical PRs of public repositories, and the skills are built from the same repositories' earlier PRs. The paper says "only previously available PR information and skills are used to prevent future information leakage" (§5.1) but does not say how the cut-off date relates to the model's training data, and Claude Opus 5 may have seen the task PRs.
- The 0.92 and 0.88 resolved rates come with a Safe rate of 1.00; Safe equals Existing in every row of Table 4 (Safe rate counts "valid, nonempty test execution", §5.2), so the two columns carry no separate information.
- Base resolved rates of 0.79 and 0.83 are high for a mini-agent with no skills, so the ceiling is near; Sonnet 4.6 on SWE-bench Pro is excluded for a weak baseline, a choice made after seeing results (§6.1).
- The treated arm differs from the base in several ways at once (PR retrieval, candidate synthesis, bounded repair, skill injection); only the skill-handling variants (F3 to F6) isolate skill management.
- Authors evaluate their own system and re-implemented the baselines. Authors overlap with the SkillLens and SkillOps papers ([20], [29]).
- Nothing in the paper concerns human turns, instruction files written by developers, or review load; the skills are LLM-written from PRs, which makes this a relative of generated instruction files (see 2602.11988 F1) but with a benchmark gain reported.

## Discrepancies

- Table 3 labels the gains "+9.0%" and "+2.0%"; the differences are percentage points (0.88 minus 0.79, 0.79 minus 0.77), and §6.1 says "by 9%".
- The full method's task success is 0.89 in Table 9, 1.00 in Table 8, 0.93 in Tables 10 to 12, and its resolved rate is 0.92 in Table 4. Its surface F1 is 0.74 (Table 4), 0.87 (Table 8), 0.75 (Table 10), 0.80 (Table 12) and 0.867 (§6.4 text). The settings behind each are not distinguished.
- §6.4 says disabling filtering lowers Surface F1 "from 0.867 to 0.756, a decrease of 0.111"; Table 10 gives 0.75 for full and 0.69 for neither filter, a difference of 0.06 (reader's arithmetic).
- §6.4 says "existing PR retrieval achieves 1.00" next to Table 11; no such row is in Table 11.
- Table 11 has two rows named SkillLens-style: "selective" 0.83 and "SkillLens-style" 0.89.
- Table 10: removing both filters (TS 0.78) scores above removing either one (0.67, 0.72).
- §6.3 text gives irrelevant-class F1 as 0.945; Table 7 shows 0.94. §6.3 gives 0.871 for Surface F1; Table 8 shows 0.87.
- The conclusion says "modest additional computational costs"; Table 12 shows 26,894 tokens against 14,300.
