## Question

Which design choices a multifaceted, contextualized agentic code review needs (RQ1), how accurate
its reported issues are (RQ2), and how many of the correct issues developers rate as important
(RQ3), in one industrial setting (§1).

## Findings

### F1 · practice · contextual-multi-agent-review · E2
- practice: run an orchestrator agent that builds a context from the repository and a code knowledge graph, delegates to four dimension agents (readability, maintainability, reliability, performance) and merges their findings into one report for a commit; prototype in Kiro CLI (§4, §4.2, Figure 1).
- claim: "combining specialized agent skills with context-specific knowledge yields accurate, practically useful code reviews" (Abstract, §6).
- evidence: 197 of 206 issues labelled correct, 96%, 9 (4%) incorrect (Table 7). Of the 197 correct, 65 (33%) rated high, 70 (36%) medium, 62 (31%) minor (Table 8). Two quoted developer comments, one saying the review found "more" than the developers had (§5.3). Data: 7 commits, 4 projects, 5 labellers.
- effect: helps
- reader: E2, numbers with no comparison: no human review, no single-agent run, no diff-only run, no other model. "Accuracy" is the share of reported issues judged correct (precision); missed defects were not counted. The labellers wrote the commits, which the authors name as a bias in either direction (§7). The authors built the system and two of them work at the company (Ericsson address, §1).

### F2 · practice · role-specialised-agents · E2
- practice: split the review into four sub-agents, each with its own prompt, antipattern catalog and review instructions, run in parallel, each given only the path to the shared context document and the source files (§3.2, §4.2).
- claim: each agent "contributed findings that the other agents did not, and a review targeting a single dimension would have covered at most about a third of what was reported" (§5.1).
- evidence: issues per dimension, Table 6: reliability 64 (31.1%), readability 58 (28.2%), maintainability 50 (24.3%), performance 34 (16.5%), total 206. The authors state that "neither an ablation nor a comparison with alternative designs was performed" (§5.1).
- effect: helps
- reader: E2. The counts describe how the issues divide; they do not show that a single agent with the four catalogs would have found fewer. Whether the findings of different agents overlap or repeat the same defect is not reported. The "about a third" is the largest share, 31.1% (§5.1, Table 6).

### F3 · practice · code-graph-context-for-review · E2
- practice: give each review agent the diff, changed files and repository metadata from GitLab, plus a code knowledge graph (file imports, symbol definitions, external library usage, fan-in and fan-out per file, folder summaries, semantic search, Cypher queries), through two MCP servers (§4.2).
- claim: the low share of incorrect issues is attributed to the context; the context "appears to reduce hallucinated comments" and constrains reasoning "to what actually holds in the surrounding system" (§5.1, §6).
- evidence: 9 of 206 issues (4%) incorrect (Table 7). No run without the graph or without repository context. The paper cites another study, in which supplementary descriptions raised accuracy from 59.62% to 68.50% for GPT-4o and from 55.56% to 63.89% for Gemini (§6, citing [8]).
- effect: helps
- reader: the claim is causal and the paper's own data has no contrast; the 4% rate may come from the model, the antipattern catalogs, the checklist format or the commits chosen. The authors say the observations "provide feasibility evidence rather than controlled comparative proof" (§5.1). Graded E2 for the numbers that exist, not for the causal claim.

### F4 · practice · dimension-specific-context-view · E0
- practice: the context builder produces a different context view per agent: the readability agent gets local code structure and formatting, the maintainability agent also gets dependencies and structural relationships (§4.2).
- claim: "also reduced prompt complexity" compared with "a single undifferentiated context" (§5.1); "reduces prompt complexity and keeps the solution extensible" (§6).
- evidence: no data. No prompt sizes, no comparison with a shared context.
- effect: helps
- reader: asserted only. Prompt complexity is not measured.

### F5 · practice · antipattern-catalog-in-review-skill · E0
- practice: put a published antipattern catalog for the dimension into each agent's skill document as its checklist: 12 readability items (Table 2), maintainability items (Table 3), 18 reliability items (Table 4), 13 performance items (Table 5); agents report only antipattern name, location, problem description and fix suggestion (§3.1, §4.1, §4.2).
- claim: grounding the assessment of each dimension in an established antipattern catalog is part of what addresses the narrow-review gap (§3.1, §5.1).
- evidence: no data on the catalogs' effect. The catalogs come from earlier work and are listed in Tables 2 to 5.
- effect: helps
- reader: asserted. No run without the catalogs, and no count of how many issues map to a catalog entry or fall outside it.

### F6 · practice · strict-output-format-with-examples · E0
- practice: constrain every finding to a four-field format and give the agents positive and negative examples (§4.2, §5.1).
- claim: "providing agents with positive and negative examples was an effective way to constrain their output"; the format "made a systematic assessment of 206 issues feasible" (§5.1, §6).
- evidence: no data; no run without the examples or the format.
- effect: helps
- reader: asserted. The labelling template (Table 1) mirrors the output format, so the format also served the study's own data collection.

### F7 · observation · orchestrator-error-propagation · E0
- practice: observed while validating the prototype: an error in agent selection, context construction or aggregation "propagates to the final review, even when the individual agents reason correctly"; the orchestration is "a single point of failure" (§5.1, §6).
- claim: orchestration accuracy "matters as much as agent design" (§6).
- evidence: no failure case, count or rate is given. The text says all seven commits ran through the complete workflow (§5.1).
- effect: hurts
- reader: a design lesson stated without an example. "As much as" is not measured.

## Limits stated by the authors

- Single company, 7 commits from 4 projects, Python only; may not generalise (§7).
- Single LLM, Kiro CLI's default model; accuracy and importance may vary with other models or frameworks (§7).
- Only four code quality dimensions; security, technical debt and testability left out (§7).
- Developers who wrote the commits validated the findings, a bias in either direction (§7).
- LLM non-determinism: repeated runs on one commit may differ; commits and reviews are proprietary, which limits replication (§7).
- No ablation and no comparison with alternative designs; the RQ1 observations are feasibility evidence (§5.1).
- Further validation across projects and languages is needed (§5.2).

## Reader's notes

- Five labellers: four labelled one commit each (36, 36, 27, 11 issues) and one labelled three commits (96 issues) (§3.3). That one person labelled 96 of 206 issues, 47% (reader's arithmetic).
- Each issue got one label for correctness and one for importance; no second labeller and no agreement figure (§3.3).
- Importance was rated only for the 197 correct issues (Table 8). Recall against the defects that human review or later bugs would find is not measured, so the 96% says nothing about missed issues.
- The model is not named, and its version, the run dates and the number of runs per commit are not stated, so the result cannot be placed against other models.
- The prototype's token cost and run time per commit are not reported.
- The qualitative evidence is two quoted comments (§5.3); how many developers commented is not stated.
- The problem was discussed with three practitioners, one manager and two senior developers, before the design (§3.1).
