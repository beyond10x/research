## Question

Can a skill document for a frozen agent be trained like a model, with bounded edits, a held-out
acceptance gate, a rejected-edit buffer and an epoch-wise update, so that it reliably beats no
skill, human skills, one-shot LLM skills and other skill-learning methods, and does the learned
skill transfer (Abstract, §1)?

## Findings

### F1 · practice · validation-gated-skill-optimization · E4
- practice: SkillOpt. A separate optimizer model reads scored rollouts of the frozen target model, proposes add/delete/replace edits to one skill document, and an edit is accepted only if the held-out selection score strictly improves; the exported `best_skill.md` is run on a disjoint test split and compared with the same model and tasks with no skill (§3, §4, Table 1).
- claim: SkillOpt lifts GPT-5.5 by +23.5 points on average in direct chat, +24.8 in Codex and +19.1 in Claude Code, and is positive over no skill on every cell (Abstract, §4.1, Table 1 caption).
- evidence: Table 1, GPT-5.5 direct chat, no skill against SkillOpt: SearchQA 77.7 to 87.3, SpreadsheetBench 41.8 to 80.7, OfficeQA 33.1 to 72.1, DocVQA 78.8 to 91.2, LiveMathematicianBench 37.6 to 66.9, ALFWorld 83.6 to 95.5; six-benchmark average 58.8 to 82.3 (§4.1). Average gain over no skill per other direct-chat model: GPT-5.4 +12.7, GPT-5.4-mini +15.4, GPT-5.4-nano +26.7, GPT-5.2 +16.6, Qwen3.5-4B +19.2, Qwen3.6-35B-A3B +9.1; about +17.6 per model (§4.1). Codex, GPT-5.5, SpreadsheetBench 27.5 to 85.0; Claude Code, GPT-5.5, SpreadsheetBench 22.1 to 80.4 (Table 1). Smallest gain in a cell: Qwen3.6-35B-A3B OfficeQA 45.9 to 47.1, +1.2 (Table 1).
- effect: helps
- reader: no-skill against optimized skill on identical test splits is an A/B on equal tasks, so E4. One run per cell and no variance or test-set sizes in the parts read, so the small cells (+1.2) cannot be told from noise. The 52 cells are 7 models by 6 benchmarks in direct chat plus 5 and 5 harness cells, and the harness cells are GPT-5.5 only. None of the benchmarks is a repository software task; SpreadsheetBench is the nearest (code against a real openpyxl/pandas runtime, §4). The authors built and evaluated their own method.

### F2 · practice · validation-gated-skill-optimization · E4
- practice: as F1; the comparison is against the best of the other adaptation methods on the same target model, test split and scorer: human skill, one-shot LLM skill, Trace2Skill, TextGrad, GEPA, and EvoSkill in the harness rows (§4, Baselines).
- claim: "SkillOpt wins or matches the best measured result on 52 of 52 evaluated cells"; +5.4 points over an oracle that picks the best baseline per cell (§4.1).
- evidence: GPT-5.5 direct chat six-benchmark average 82.3 against 76.9 for the per-cell best baseline (+5.4). Codex: +14.0 over EvoSkill, the next-best baseline; Claude Code: +3.2 over EvoSkill, whose five-benchmark average is 57.8 to 73.7 against no skill (§4.1). Codex SpreadsheetBench, GPT-5.5: EvoSkill 67.5, SkillOpt 85.0 (+17.5) (§4.1). One tie: GPT-5.4-mini LiveMathematicianBench, SkillOpt 32.8 and Trace2Skill 32.8 (Table 1).
- effect: helps
- reader: E4 as an A/B on equal tasks, but the methods differ in more than the gate and budget (a gate-less Trace2Skill, prompt-only TextGrad and GEPA), so the contrast does not isolate one component. The authors ran all baselines themselves. EvoSkill scores 61.4 on Codex SearchQA, 20.4 points below no skill (Table 1), which may point to a weak baseline run. EvoSkill is only reported where a matched run existed (Appendix C). Some wins are narrow (GPT-5.2 DocVQA 89.6 against GEPA 89.5), within what one run per cell can move.

### F3 · practice · human-written-skill · E4
- practice: run the target model with an expert-written skill document curated per benchmark, against no skill (§4, Baselines).
- claim: human skills "can help when prior instructions happen to match the benchmark, but they cannot correct failures after observing rollouts" (§4.1).
- evidence: Table 1, change over no skill. Large gains: GPT-5.5 SpreadsheetBench +31.1, OfficeQA +33.8; GPT-5.4-nano DocVQA +42.7. Losses: GPT-5.4-mini ALFWorld 56.7 (-16.4), Qwen3.6-35B-A3B ALFWorld 44.8 (-14.9), GPT-5.2 ALFWorld 56.7 (-12.0), GPT-5.4-nano LiveMathematicianBench 16.8 (-6.4), Qwen3.5-4B SearchQA 66.3 (-1.8). Human skills are 145 to 516 tokens long (§4.1).
- effect: mixed
- reader: the same expert-written skill helps one model and hurts another on the same benchmark (ALFWorld: GPT-5.5 +8.2, GPT-5.4-mini -16.4), so the sign depends on the model; one run per cell. The paper does not say who wrote the skills or how much effort that took. Table 6 gives initial skill lengths of 16 to 516 tokens (see Discrepancies).

### F4 · practice · one-shot-generated-skill · E4
- practice: have GPT-5.5 write one skill from a high-level task description and never update it, against no skill (§4, Baselines).
- claim: one-shot skills are brittle; the gains "come from feedback-driven skill editing rather than from a better one-shot prompt" (§1, §4.1).
- evidence: Table 1, change over no skill. GPT-5.5 direct chat: +1.4 on SpreadsheetBench, +18.6 on OfficeQA, +9.7 on ALFWorld. Losses: GPT-5.4 OfficeQA 20.4 (-29.6), GPT-5.2 OfficeQA 14.0 (-20.9), GPT-5.4-nano OfficeQA 12.8 (-3.5), GPT-5.4-mini ALFWorld 65.7 (-7.4), Qwen3.6-35B-A3B LiveMathematicianBench 24.8 (-6.4). Codex, GPT-5.5: SpreadsheetBench 25.0 (-2.5), OfficeQA 34.3 (-4.0) (Table 1).
- effect: mixed
- reader: matches the pattern of 2602.11988 F1 for generated instruction files, with larger swings, and sits in a different slug because this is a skill and the benchmarks are not repository tasks. The same OfficeQA generator output costs 29.6 points on GPT-5.4 and gains 18.6 on GPT-5.5, one run each.

### F5 · practice · held-out-selection-gate-on-skill-edits · E2
- practice: accept a candidate skill only if its score on a held-out selection split is strictly above the current score; ties are rejected; every step writes an `edit_apply_report.json` with the accept or skip status of each edit (§3.5, §4.2).
- claim: the gate "turns reflection into propose-and-test optimization rather than unconditional self-editing, which is crucial because plausible textual diagnoses can still hurt the actual target model"; the optimizer proposes many more edits than survive (§3.5, §4.4).
- evidence: accepted edits per benchmark are 1 to 4, median 2.5; LiveMathematicianBench +29.3 over no skill from one accepted edit and OfficeQA +39.0 from one (§4.4, Table 6). No count of proposed or rejected edits is given. Figure 3 shows validation checkpoints tracking test scores across epochs (figure only, §4.2). The gate is not removed in any ablation row (Table 3).
- effect: helps
- reader: E2 because the gate has no ablation: Table 3 removes the learning-rate form, the rejected buffer and the slow/meta update, not the gate, and Trace2Skill, the gate-less baseline, differs in other ways. The authors call the edit counts "direct evidence that the validation gate is doing real work"; the numbers show few edits were accepted, not that the rejected ones would have hurt.
### F6 · practice · bounded-edit-budget-per-skill-update · E4
- practice: cap the number of edits applied per step at a textual learning rate Lt (default 4, cosine decay to 2); the optimizer ranks the merged edit pool and keeps the top Lt; compare with a dynamic budget and with no budget (§3.4, §4.2, Table 3).
- claim: "any moderate, bounded edit budget already beats baselines that rewrite the skill without a budget" (§4.2).
- evidence: Table 3, SearchQA / SpreadsheetBench / LiveMathematicianBench: lr=4 default 87.1 / 77.5 / 61.3; dynamic lr 85.8 / 71.8 / 54.0; without lr 84.6 / 75.7 / 57.3. Table 2(d), Lt from 1 to 16: SearchQA 85.5 to 87.0, SpreadsheetBench 73.6 to 78.2, LiveMathematicianBench 56.5 to 66.9. Table 2(e), schedule: constant 87.3 / 80.7 / 62.1, cosine 87.1 / 77.5 / 61.3, linear 87.2 / 72.9 / 62.9.
- effect: helps
- reader: an ablation on equal tasks with GPT-5.5 as target and optimizer, one run per row. Differences between budgets are as large as the difference to "without lr": LiveMathematicianBench is 56.5 at Lt=4 and 66.9 at Lt=8 in Table 2(d). The default row also differs between Table 2(d) and Table 3 (see Discrepancies), so run-to-run noise may be about the size of the effect.

### F7 · practice · rejected-edit-buffer-in-skill-optimization · E4
- practice: keep an epoch-local buffer of failure patterns and of rejected edits with the score drop each caused, and give it to later reflection calls in the same epoch (§3.5).
- claim: it converts failed edits into negative feedback with no deployment-time cost; "a stabilizer for the default loop" (§3.5, §4.2).
- evidence: Table 3, SearchQA / SpreadsheetBench / LiveMathematicianBench: with buffer 87.1 / 77.5 / 61.3, without 85.5 / 72.9 / 58.9; drops of 1.6, 4.6 and 2.4 points (§4.2).
- effect: helps
- reader: ablation on equal tasks, three benchmarks, one run each, GPT-5.5 only. The "matched no-buffer ablation setting" (Table 3 caption) is not described further.

### F8 · practice · epoch-wise-cross-epoch-skill-update · E4
- practice: at the end of each epoch, run the same 20 training items under the previous and the current skill, sort them into improvements, regressions, persistent failures and stable successes, write guidance into a protected slow-update field of the skill, and keep an optimizer-side meta skill that is not shipped (§3.6, §4).
- claim: the slow/meta update "improves long-horizon refinement without bloating the deployed skill" (§1); removing both parts is "the largest degradation in the ablation suite" (§4.2).
- evidence: Table 3, SearchQA / SpreadsheetBench / LiveMathematicianBench: both parts 87.1 / 77.5 / 61.3; without meta skill 85.1 / 75.7 / 58.1; without meta skill and slow update 86.3 / 55.0 / 59.7 (SpreadsheetBench -22.5). Table 2(f), sample count 5, 10, 20, 40: LiveMathematicianBench 64.5, 65.3, 61.3, 54.8.
- effect: helps
- reader: E4 as an ablation, but the pattern is not monotone: on SearchQA and LiveMathematicianBench the variant with neither part (86.3, 59.7) scores above the variant with only the slow update (85.1, 58.1), and the -22.5 on SpreadsheetBench is one run. The text's "within +-2.7 points" for the sample count does not hold for 40 on LiveMathematicianBench (see Discrepancies).

### F9 · practice · training-tasks-exposed-to-skill-optimizer · E4
- practice: vary how much of the training split the optimizer sees, from 1 example to 100%, and vary rollout batch size, reflection minibatch size and learning-rate settings (§4.2, Table 2).
- claim: "procedural benchmarks reward more training evidence"; the gains are "not the product of a fragile prompt-search batch size" (§4.2).
- evidence: Table 2(a), 1 example, 20%, 40%, 80%, 100% of train: SpreadsheetBench 47.5, 69.0, 73.5, 77.6, 78.0; LiveMathematicianBench 59.1, 65.9, 64.8, 67.0, 70.5; SearchQA 81.0, 84.1, 86.1, 86.1, 84.1. Reflection minibatch 1 to 32: SearchQA 85.9 to 87.1, SpreadsheetBench 75.4 to 77.9 (Table 2(b), §4.2). Rollout batch 8 to a full epoch: SearchQA 85.1 to 87.2, SpreadsheetBench 75.0 to 77.5; LiveMathematicianBench 62.9 at 24 and 53.2 at a full epoch (Table 2(c)).
- effect: helps
- reader: the training-size rows are a treatment, so a practice. The "1 example" skill at 47.5 on SpreadsheetBench is already +5.7 over the 41.8 no-skill score (reader's arithmetic from Table 1). The split ratio for panel (a) is 4:1:5 in the Table 2 caption and 2:1:7 in Appendix C (see Discrepancies), so what "100%" means is unclear. LiveMathematicianBench has 35 training items per epoch (§4), so its percentages are small counts.

### F10 · practice · skill-transfer-across-harness · E4
- practice: train the skill inside one harness (Codex CLI or Claude Code CLI) and run it unchanged in the other, with the same GPT-5.5 target model, against no skill in the target harness (§4.3, Table 4b).
- claim: "the learned rules are not only harness-specific command recipes"; the optimization cost "can be amortized across related deployment environments" (§4.3).
- evidence: Table 4(b), target baseline, in-domain SkillOpt, transferred. SpreadsheetBench Codex to Claude Code 22.1, 80.4, 81.8 (+59.7); Claude Code to Codex 27.5, 85.0, 71.1 (+43.6). LiveMathematicianBench Codex to Claude Code 40.8, 56.5, 42.4 (+1.6); Claude Code to Codex 35.2, 78.4, 48.0 (+12.8).
- effect: helps
- reader: against no skill on the same tasks, E4; one model, two benchmarks, four directions, one run each. A skill that says "write evaluated static values" (§4.5) is a benchmark-level rule that either harness can follow, so the transfer may be benchmark knowledge more than harness portability. The LiveMathematicianBench Claude Code to Codex skill reaches 48.0 against 78.4 for the in-domain skill.

### F11 · practice · skill-transfer-across-model-scale · E4
- practice: train the skill on GPT-5.4 and deploy it unchanged on GPT-5.4-mini and GPT-5.4-nano (§4.3, Table 4a).
- claim: "All four cross-model rows are positive"; on one the transferred skill beats the in-domain one (§4.3).
- evidence: Table 4(a), target baseline, in-domain, transferred. SpreadsheetBench, mini 36.1, 47.5, 45.5 (+9.4, 82% of the in-domain gain); nano 23.5, 42.5, 26.5 (+3.0). LiveMathematicianBench, mini 14.7, 32.8, 19.2 (+4.5); nano 23.2, 27.2, 28.8 (+5.6).
- effect: helps
- reader: four rows, one run each, small gains on 3 of 4 (+3.0 to +5.6). Transfer from a larger to a smaller model of one family; no transfer to another model family was run in the parts read.

### F12 · practice · skill-transfer-across-benchmark · E4
- practice: train the skill on OlympiadBench and run it unchanged on Omni-MATH, against no skill on Omni-MATH (§4.3, Table 4c).
- claim: "the optimized skill encodes reusable mathematical procedure rather than memorized benchmark-specific formatting" (§4.3).
- evidence: Table 4(c), baseline to transferred: GPT-5.4 56.6 to 60.3 (+3.7), GPT-5.4-mini 34.8 to 36.6 (+1.8), GPT-5.4-nano 38.8 to 40.1 (+1.3).
- effect: helps
- reader: positive in all three rows, with gains of 1.3 to 3.7 points from one run each and no test size given, so the sign is the only firm part. OlympiadBench itself is not a row of Table 1.

### F13 · practice · strong-optimizer-model-for-skill-edits · E4
- practice: run the optimization loop with a frontier optimizer (GPT-5.5) or with an optimizer that is the same model as the target, everything else fixed (§4.3, Table 5).
- claim: the stronger optimizer gives larger gains in every cell tested; the target-matched optimizer "recovers 56-74% of the strong-optimizer gain", so SkillOpt "is not a distillation pipeline" from a stronger teacher (§4.3).
- evidence: Table 5, gain over baseline, strong against target-matched: SpreadsheetBench GPT-5.4-mini +11.4 against +7.1, nano +19.0 against +11.9; SearchQA mini +4.3 against +2.4, nano +19.0 against +14.1.
- effect: helps
- reader: four cells, one run each, only GPT-5.4-mini and -nano as targets and GPT-5.5 as the strong optimizer. The "56-74%" range is the paper's; the ratios from Table 5 are 62%, 63%, 56% and 74% (reader's arithmetic).

### F14 · practice · validation-gated-skill-optimization · E2
- practice: the training cost and size of the artifact for the GPT-5.5 (student) and GPT-5.5 (teacher) runs (§4.4, Table 6).
- claim: the deployed skill is compact and the cost is "paid once during skill training"; no optimizer calls, no weight updates at deployment (§4.4).
- evidence: Table 6, final `best_skill.md` length 379 tokens (LiveMathematicianBench) to 1,995 (SpreadsheetBench), median about 920; training tokens 20.8M (OfficeQA), 21.4M (SpreadsheetBench), 23.2M (LiveMathematicianBench), 59.3M (ALFWorld), 188.2M (DocVQA), 213.8M (SearchQA); training tokens per absolute test-point gain 0.6M (SpreadsheetBench) to 46.4M (DocVQA).
- effect: mixed
- reader: describes a cost next to the gains of F1, with nothing to compare against: no run of a baseline method is costed, and no inference-time saving is measured. `mixed` here means better success at a one-time training cost. The cost-per-point column does not follow from the Table 1 gains for five of six rows (see Discrepancies).

## Limits stated by the authors

- The loop needs scored trajectories and a held-out selection split, so it fits tasks with automatic verifiers, exact-match metrics or executable checks; subjective or costly-to-judge tasks need a stronger gate (Appendix B).
- Training needs extra rollouts and optimizer calls, which pays off only when the skill is reused (Appendix B).
- It optimizes one skill, not a library, which may not suit domains with many disjoint procedures (Appendix B).
- Learned skills can encode training-distribution heuristics; transfer to different models, harnesses or tasks needs a held-out check (Appendix B).

## Reader's notes

- Every number in Tables 1 to 6 is one run; the paper reports no seeds, intervals or tests in the parts read. Gains of a few points on the smaller test sets (ALFWorld 134 environments, §4) are within what resampling can move.
- The authors implement SkillOpt and all baselines. Skills for the human baseline are "expert-written", with no author, effort or source given.
- The "52 of 52" count includes ties and counts the 10 harness cells that cover one model.
- No benchmark is a repository coding task. The harness rows run Codex and Claude Code CLIs with GPT-5.5 on QA, spreadsheet and math tasks, so the paper says little about the SWE-style tasks the repository's research question is about. The practice of promoting an edit only when a held-out score rises needs a scorer; Appendix B says as much.
- The best skill is chosen on the selection split, so the 1 to 4 accepted edits are chosen with that split's noise; the test split is separate (§4).
- The ablations (Tables 2 and 3) use GPT-5.5 as target and optimizer on three of the six benchmarks (SearchQA, SpreadsheetBench, LiveMathematicianBench); the weak-model and harness behaviour of the components is not tested.
- Appendix C lists SealQA among the benchmarks; it does not appear in the main text tables.

## Discrepancies

- Table 2(d) gives the lr=4 row as 86.5 / 78.2 / 56.5 and §4.2 repeats those numbers, while Table 3 and Table 2(a) to (c) give the default (lr=4) as 87.1 / 77.5 / 61.3.
- §4.2 says the slow-update sample counts 5, 10 and 40 are "each within +-2.7 points" of the default 87.1 / 77.5 / 61.3; Table 2(f) has 74.3 for 10 on SpreadsheetBench (-3.2) and 54.8 for 40 on LiveMathematicianBench (-6.5) (reader's arithmetic).
- The Table 2 caption says panel (a) fixes the split to 4:1:5; Appendix C says the train-size ablation fixes the split to 2:1:7.
- §4.1 says human skills are "145-516 tokens long"; the initial skill lengths in Table 6 run from 16 (SearchQA) to 516 (ALFWorld), with 81 for DocVQA and 154 for LiveMathematicianBench. Table 6 does not say its initial skills are the human skills.
- Table 6 cost per point against Table 1 gains: 21.4M / 38.9 = 0.55M matches the 0.6M for SpreadsheetBench; the other rows do not (reader's arithmetic): SearchQA 213.8M / 9.6 = 22.3M against 37.9M, OfficeQA 20.8M / 39.0 = 0.53M against 1.1M, DocVQA 188.2M / 12.4 = 15.2M against 46.4M, LiveMathematicianBench 23.2M / 29.3 = 0.79M against 3.6M, ALFWorld 59.3M / 11.9 = 5.0M against 15.9M. §4.4 states "+39.0 points on OfficeQA at 1.1M tokens / point, total 20.8M tokens". Table 6 may come from different runs than Table 1; the paper does not say.
- §4.5 reports ALFWorld GPT-5.4-nano 49.3 to 74.6 and SpreadsheetBench GPT-5.5 40.4 to 78.9 for "representative runs"; Table 1 has 34.3 to 69.4 and 41.8 to 80.7 for the same model-benchmark cells. Different runs are implied and not stated.
- §4.1 and the abstract say "52 of 52 best or tied"; the Table 1 caption says "positive gains over the no-skill baseline throughout" and the text (§4.1) "wins or matches"; GPT-5.4-mini LiveMathematicianBench is a tie with Trace2Skill at 32.8. Not a contradiction, but the tie is the only one.
