## Question

Coding agents often fail a requirement after having considered a way to meet it. Can a prompt that
makes the agent report such choices before it writes code, and then re-check them against the task
description, raise the pass rate more than generic self-correction does (§1)?

## Findings

### F1 · practice · pre-implementation-choice-elicitation · E4
- practice: SatisFix, two messages sent once, just before the agent writes code. Step 1 asks the agent to report where it concluded a requirement could be handled differently from the task text: the requirement, its choice and its reason. The message says it comes from the task maintainers, who may revise the description, and casts the agent as their advisor; it does not ask the agent to judge its choices. Step 2 says the maintainers will not revise the task, asks the agent to list alternatives to each reported choice and a plan to check each against the task description and the repository, then to carry the plan out, settle each choice and finish the task (§3.1, §3.2).
- claim: SatisFix "improves the pass@1 of the base agent by an average of 5.09% on DeepSWE and 7.06% on the hard subset of SWE-bench Pro" (Abstract).
- evidence: DeepSWE, four runs, pass@1 base against SatisFix: GPT-5.6-Luna 44.25 against 50.22, DeepSeek V4 Flash 53.32 against 57.08, Qwen3.8-27B 42.26 against 47.79 (Table 3). Standard deviations over runs are 1.69 to 3.64 (Table 3). Gemma 4 26B A4B and Muse Glimmer 30B "hit a capability floor" on DeepSWE and are not reported (§4.3). SWE-bench Pro hard subset, 51 tasks: Luna 78.43 against 84.31, DeepSeek 78.43 against 82.35, Qwen 76.47 against 84.31, Gemma 9.80 against 21.57, Muse 37.25 against 43.14 (Table 3). The averages 5.09 and 7.06 are the means of these per-model differences in percentage points (reader's arithmetic). SWE-bench Pro full set, 642 tasks: Luna 91.12 against 92.37, DeepSeek 92.21 against 92.37, Qwen 91.28 against 92.21, Gemma 52.65 against 55.92, Muse 80.37 against 83.02 (Table 3). The three strong models solve more than 92% of the tasks outside the hard subset with either method (§4.3).
- effect: helps
- reader: E4: the same tasks with and without the method, four runs on DeepSWE. No significance test is given. The DeepSWE gains for DeepSeek (3.76 points) are about the size of the base standard deviation (3.64). SWE-bench Pro has one run per cell and no spread, so a one-task change on the 51-task subset is 1.96 points. The authors built and tuned the method and ran the comparison. On the full Pro set the gains for the three strong models are 0.16 to 1.25 points, near the ceiling.

### F2 · practice · pre-implementation-choice-elicitation · E4
- practice: as F1, run in a second agent framework, OpenHands, in place of mini-swe-agent, GPT-5.6-Luna on DeepSWE (§4.4).
- claim: the gain also holds on OpenHands, "close to" the gain on mini-swe-agent (§4.4).
- evidence: pass@1 46.90 (sd 4.02) against 51.33 (sd 2.40), a gain of 4.43 against 5.97 on mini-swe-agent; four runs each (Table 4, §4.4).
- effect: helps
- reader: the gain is smaller than the base sd of 4.02. One model, one benchmark. Same authors.

### F3 · practice · pre-implementation-choice-elicitation · E4
- practice: as F1; the measurement is steps and cost per task (Tables 2, 4, §4.3).
- claim: on DeepSeek V4 Flash it "saves 14.0% of the token cost per task, as the coding agent takes fewer steps (131.6 vs. 152.9)" (§4.3).
- evidence: with GPT-5.6-Luna on mini-swe-agent, steps 58.6 against 49.0 and cost $0.897 against $0.644 (Table 2); on OpenHands, steps 127.4 against 118.8 and cost $1.714 against $1.404 (Table 4). Cost ratios 1.39 and 1.22 (reader's arithmetic). The DeepSeek figures are stated in the text only; no table row (§4.3).
- effect: mixed
- reader: cost goes up for the model that is the paper's main subject and down for DeepSeek; the paper does not explain the difference. Costs are as the authors computed them; the price table is not in the parts read.

### F4 · practice · self-review-prompts · E4
- practice: three published self-correction methods run as baselines on the same tasks: Self-Refine (the model gives feedback on its own output and revises over several rounds), DeCRIM (split the task description into requirements, check the output against each, revise), ProgCo (the model writes a verification program for the task, runs it, revises on failure) (§4.1).
- claim: the baselines "improve pass@1 over the base agent by at most 1.99%", consistent with the view that "an agent that has accepted [a choice] can accept it again when it reviews its own work" (§4.2).
- evidence: DeepSWE, GPT-5.6-Luna, four runs, pass@1: Base 44.25 (sd 2.98), Self-Refine 46.24 (3.98), DeCRIM 44.25 (2.61), ProgCo 46.24 (1.82), SatisFix 50.22 (2.64). Self-Refine takes 70.2 steps against 49.0, 10.14M input tokens against 3.37M, and costs $2.022 against $0.644, about 3.1 times (reader's arithmetic). DeCRIM costs $0.645 and ProgCo $0.809 (Table 2, §4.2).
- effect: none
- reader: the 1.99-point gains are inside one standard deviation (Self-Refine sd 3.98), so "none" is the reading at this sample size; the paper words it as a small gain. One model, one benchmark. The authors chose the baselines and their prompts; the baseline prompts are not in the parts read. Self-Refine's extra cost buys no gain here.

### F5 · practice · advisor-role-elicitation · E4
- practice: ablation of step 1's framing. "w/o objective-aligned elicitation" removes the advisor role and asks the agent directly whether it concluded that a requirement could be handled differently from what the task states; the reconsideration step is kept (§4.5).
- claim: "Objective-aligned elicitation accounts for most of the gain"; without the advisor role "the agent does not have anything to report about a choice it has accepted" (§4.5).
- evidence: DeepSWE, GPT-5.6-Luna, first run only: SatisFix 49.6, without the advisor-role elicitation 43.4, base 43.4 (Table 5). The drop is 6.2 points (§1, §4.5).
- effect: helps
- reader: each cell is one run on 113 tasks; the base standard deviation over four runs is 2.98 (Table 2) and the paper does not repeat the ablation. 6.2 points is about two of those. The ablation changes the wording and the role in one step, so it does not separate the role from the wording of the question. Same authors.

### F6 · practice · recheck-reported-choices · E4
- practice: ablation of step 2. "w/o reconsideration" keeps the elicitation, then only puts the agent back in the developer role and asks it to finish; no alternatives list, no check against the task description (§4.5).
- claim: "Without reconsideration, part of the gain remains. The report alone can bring the choices back to the agent's attention" (§4.5).
- evidence: first run on DeepSWE with GPT-5.6-Luna: 47.8 without reconsideration against 49.6 with it and 43.4 for base (Table 5). A variant that replaces both steps with one generic "review your plan and check whether you made a mistake" message, repeating the task description, scores 44.2 (Table 5, §4.5).
- effect: helps
- reader: the difference between 47.8 and 49.6 is 1.8 points on one run, below the base run-to-run sd of 2.98, so the second step's own contribution is not resolved. The generic-review variant at 44.2 against base 43.4 is the paper's direct control that rereading the task alone does not give the gain. The paper does not test reconsideration alone, without elicitation.

### F7 · observation · satisficing-reports-per-task · E3
- practice: none applied; the first SatisFix run on all 113 DeepSWE tasks with GPT-5.6-Luna and DeepSeek V4 Flash is split by whether the elicitation report held at least one item that two LLM annotators judged to be specification satisficing (§5).
- claim: elicitation brings out such items in most tasks, and the gain is on those tasks (§5.1, §5.2).
- evidence: items and tasks with a report, Luna 90 items in 61 of 113 tasks, DeepSeek 227 items in 105 tasks (Table 6, §5.1). The agent reconsiders all 90 and 226 of the 227 (§5.2). Pass rate of SatisFix first run against base pass@1 over four runs, on tasks with a reported item: Luna 55.7 against 47.1 on 61 tasks, 42.3 against 40.9 on the other 52; DeepSeek 59.6 against 52.2 on 104 tasks, 9 others too few to compare (§5.2, Figure 2). By reason type with Luna the SatisFix run is higher for each type; with DeepSeek the gain per type is at most 2.5 points against 7.4 on all such tasks (Table 7, §5.2).
- effect: helps
- reader: a post hoc split of one run per task. The tasks with reports are chosen by the treatment arm's output, and the base agent has no report, so "tasks with a reported item" are not a matched group. One SatisFix run is compared with a four-run base mean. The paper measures that the agent reports items; it does not measure whether the reported item was the cause of a failure, since the annotation "judges what the reports say, not whether the final code meets each requirement" (Limitations).

### F8 · observation · satisficing-reports-per-task · E3
- practice: none applied; the DeepSeek V4 Flash tasks of F7 split by the number of reported items per task (§5.2, Table 7).
- claim: with many reported items, reconsidering them all at once "can then help less" (§5.2).
- evidence: DeepSeek V4 Flash, SatisFix first run against base pass@1: 1 item, 39 tasks, 69.2 against 53.8; 2 items, 29 tasks, 65.5 against 47.4; 3 or more, 36 tasks, 44.4 against 54.2 (Table 7). 67.6 against 51.1 on the 68 tasks with one or two items (§5.2). With Luna only 2 tasks have three or more items (Table 7).
- effect: hurts
- reader: the strongest per-subgroup differences in the paper are in subgroups of 29 to 39 tasks, single run against four-run mean, and the grouping depends on the treatment's own output. The explanation offered, that the plan is built on many such choices, is the authors' guess ("A possible reason"). The effect is for the condition "three or more items reported" relative to base.

## Limits stated by the authors

- The elicitation message claims to come from the task maintainers. The authors "do not measure whether this changes how the coding agent treats later messages" (Limitations). The follow-up message withdraws the claim, apologises and states that the task has not changed (Ethical Considerations).
- SatisFix relies on the agent's own answer to decide when to step in, and steps in once per task, so it does not elicit choices committed to later (Limitations).
- Two LLM agents annotated the reports in §5 and an author checked only the items on which they disagreed; the annotation judges what the reports say, not whether the final code meets each requirement (Limitations).

## Reader's notes

- Authors evaluate their own method, so `independent: false`. The method was designed after the authors saw the failure pattern in agent transcripts (§1); whether prompts were tuned on the evaluated tasks is not stated.
- No significance test appears anywhere in the parts read. Every DeepSWE gain is within about two standard deviations of the base run-to-run spread (Tables 2, 3).
- The paper writes differences of pass rates as percentages ("5.97%", "3.98%", "6.2%", "11.77%"); the values are percentage points (§1, §4.2, §4.3).
- The ablation (Table 5) and the §5 analysis use the first run only; the base comparison in §5 uses the four-run mean. Table 5's base is the base's first run (43.4) and differs from its four-run mean (44.25).
- Pass@1 is the benchmark's tests passing. The paper's example failure is two of 69 tests (§2); no other outcome (review, requirement coverage judged by a human) is scored.
- The method elicits choices the agent already considers. It cannot help where the agent never considered the alternative (Definition 1, condition i).
- The elicitation framing is an untrue statement made to the agent about who is writing; the paper states that it does not test whether this alone is what works, and the retraction message is part of the protocol.
