## Question

When an agent's tool call reaches its program over several hops (serialization, host wrapper, shell,
process interface, target parser), how often does a hop change the call, how much does that cost,
and can the harness deliver the call so that it executes as emitted or refuse it (abstract, §1)?

## Findings

### F1 · practice · tool-call-rendering-through-unparsed-channel · E4
- practice: IntAct renders each shell call for the hop the IEC protocol named: the command is delivered as a sourced file, an `-EncodedCommand` argument or a natively quoted argument vector, so the named hop has nothing to parse. Agent in the loop, same items with and without the rendering, 3 LLMs on IEC-Bench (§2.4, §4.4).
- claim: "IntAct raises pass@1 for every LLM on every launch" (§4.4).
- evidence: Table 7, items passed by the 3 LLMs, none against IntAct, 1 trial. One-argument launch: pairs 104 against 129 of 201, chains 35 against 74 of 405. Appended launch: pairs 26 against 127, chains 9 against 74. Claude Code Bash: pairs 109 against 125 of 201. Typed Bash on Linux: pairs 74 against 86 of 90. Pooled over the 2 Qwen2.5 LLMs, exact McNemar: 20 more pairs and 1 lost on the one-argument launch, 81 and 5 on the appended launch, chains 30 against 1 and 46 against 1, each p < .001; Claude Code Bash 13 against 2, p = .007 (§4.4).
- effect: helps
- reader: same items and launch with and without the repair, so E4. The hazards were written from changes the authors observed (§3.3), and IntAct was built for those changes, so the gain is on the cases it was made for. Temperature 0, pass@1. Authors evaluate their own system.

### F2 · practice · tool-call-rendering-through-unparsed-channel · E4
- practice: as F1; the measurement is the tokens per passed item, original launch over IntAct (§3.5, §4.2).
- claim: after a changed call "a passed task costs 2.4 times the tokens, and up to 12.3 times for the chains of the appended launch" (§4.2, RQ-2 findings).
- evidence: over all rows of Table 7 the ratio is 2.4; 12.3 for the chains and 7.9 for the pairs on the appended launch, 4.0 on Claude Code's Bash launch (§4.2).
- effect: helps
- reader: the ratio is computed over a benchmark where most items are hazard variants, so it is an upper-range figure for tasks with such literals. Costs here are tokens, not money.

### F3 · practice · tool-call-rendering-through-unparsed-channel · E4
- practice: as F1, with every recorded action of a lost pair held fixed and replayed through the transport with the named hop repaired (§4.4).
- claim: "the repair acts on the path alone" (§4.4).
- evidence: 137 of the 173 lost pairs with a changed call pass after the repair, 79.2%; from 68.6% on the one-argument launch to 90.9% on Claude Code's Bash launch. None of the 187 lost pairs without a changed call pass, Fisher's exact p < .001. Of the 36 unrecovered, 22 fail at an action no hop changed, 12 were abandoned after the misleading feedback, 2 use a construct outside the rendering's domain (§4.4).
- effect: helps
- reader: the 187 pairs without a changed call are a real control, and the 79.2% in the abstract is this replay result, not a deployment result (the abstract says "deployed in a commercial product"). A replay of recorded actions does not let the agent adapt.

### F4 · practice · repair-at-named-hop · E4
- practice: pick the rendering by the hop that the first-divergence check names, and on a path with two changing hops repair both in path order; against repairs that apply one uniform form or only one hop (§2.4, §4.4).
- claim: "the hop selects the repair"; "The agent cannot repair the path from inside" (§2.4, §4.4).
- evidence: on 168 injected faults, 30 change what the target receives; IntAct restores or refuses all 30 (17 restored and 13 refused), requoting every argument restores 3, uniform `-EncodedCommand` 7 (Figure 5b, §2.4). On the appended launch's 81 lost pairs: process interface alone recovers 0 of 69, host wrapper alone 31, both 69 (Figure 5a, RQ-4 findings; 38 of the 69 path-caused failures appear only after the first hop is repaired, §1). Native rendering alone recovers nothing and `-EncodedCommand` alone 38.9% to 87.5% of what both gain (§4.4).
- effect: helps
- reader: an ablation inside the authors' own system on faults the authors injected. The first-hop-hides-later-hops result is specific to the PowerShell 5.1 appended launch.

### F5 · practice · shell-command-via-sourced-file · E2
- practice: a Claude Code Bash tool mod replaces a command longer than 200 characters, or one with a heredoc or a backslash pair, with a statement that sources a file holding the command (§5, Table 1).
- claim: the wrapper-level repair removes the changed calls in production at low cost (Table 1, Table 8).
- evidence: Table 1, Claude Code's Bash launch: all 227 calls rerouted, 20 of 22 lost pairs recovered, changed calls 143 to 0. Table 8: of the 3,577 rerouted production calls, all 227 that would have changed were rerouted and none of the 3,540 that ran changed; 4 ms added per call. Release forms (SWE-ReX, OpenHands): 9 of 11 solutions, 34 of 34 commands (Table 1).
- effect: helps
- reader: counts from a replay of recorded calls, with no group left on the original launch. 227 plus 3,540 is 3,767, not 3,577 (reader's arithmetic; see Discrepancies). No measure of whether the sessions' tasks then succeeded more often.

### F6 · practice · refuse-call-that-cannot-be-delivered · E2
- practice: when no rendering carries a call (multi-line text under `cmd.exe`, Git Bash CRLF, a fault at the target parser), return a tool result that names the hop and execute nothing (§2.4, Algorithm 1).
- claim: "the refusal is the only outcome that keeps the correspondence" (§2.4).
- evidence: Qwen Code's `cmd.exe` launch: changed calls 41 to 0 with 54 calls refused (Table 1); 13 of the 30 injected faults are at the target parser and all 13 are refused (§4.4). On all 47,119 recorded calls of the 3 launches with a rendering, none is refused (§5).
- effect: helps
- reader: "helps" is on the number of changed calls; a refused call does not run, and the paper does not measure how often agents then complete the task another way. In Qwen Code on Windows, 30 of 31 multi-line commands ran as an empty program before (§4.1).

### F7 · practice · task-instruction-delivered-as-file · E4
- practice: hand the task instruction to the agent as a file instead of a command-line argument, in Qwen Code on Windows (§4.2).
- claim: "The delivery of the instruction to the agent also determines a score" (§4.2).
- evidence: delivered as an argument, 33 of 46 Terminal-Bench 2 instructions are cut at the first line break, 3 lose all double quotes and 5 exceed the `cmd.exe` limit; as a file all 46 arrive as written, with no LLM. On the 10 pairs with agent runs every run with the argument scores 0; with the file Qwen Code passes 6 of 30 runs on Windows against 7 of 30 on Linux (§4.2).
- effect: helps
- reader: the delivery test of 46 instructions is deterministic; the agent comparison is 10 pairs and 30 runs per cell, with no test stated. It concerns one harness and one OS.

### F8 · practice · evidence-of-change-in-tool-result · E4
- practice: return the call as sent and as received, with the named hop, in the tool result; and, as a second condition, return structured execution feedback (command, status, exit code, output, error) after Gupta et al. (§3.4, §4.4).
- claim: "Evidence about the change does not help the agent, and retries recover part of the loss at many times the cost" (§4.4).
- evidence: with the evidence ablation the Qwen2.5 chains stay at 7 and 12 on the one-argument launch and 0 and 3 on the appended launch, none significantly different from the original launch, p >= .500 exact McNemar. Table 7, structured feedback against none: one-argument pairs 101 against 104, chains 45 against 35; appended pairs 23 against 26, chains 8 against 9; Claude Code Bash pairs 104 against 109 (Table 7).
- effect: none
- reader: single trials at temperature 0 on the 3 LLMs; the feedback is read by small open LLMs (Qwen2.5, Hermes-3), so a stronger agent might use it. The paper's own point stands that the agent in a loop cannot fix what it cannot see.

### F9 · practice · disclose-transport-boundary-in-prompt · E4
- practice: replace the tool description's sentence that names the shell with a description of the transport's path (QuoteBench's disclosed-boundary contract) (§3.4).
- claim: "The agent cannot repair the path from inside" (§4.4, RQ-4 findings).
- evidence: Table 7, boundary against none: one-argument pairs 85 against 104, chains 35 against 35; appended pairs 25 against 26, chains 5 against 9; Claude Code Bash pairs 112 against 109. With the boundary disclosed Qwen2.5-Coder-32B chains commands with `&&`, which PowerShell 5.1 rejects, in each of the 15 pairs with a regular expression, loses each, and reports completion without running its program; one LLM falls from 50 pairs to 36 (§4.4, RQ-4 findings).
- effect: hurts
- reader: one cell rises (+3 on Claude Code Bash) and the rest are equal or lower, so "hurts" rests mainly on the one-argument pairs and the 50 to 36 case. Whether the paper tested the difference is not stated for this column.

### F10 · practice · reflection-retries-on-failed-tool-call · E3
- practice: Reflexion, 10 trials, with the task oracle as evaluator, on the original launch (§3.4, §3.5).
- claim: "At the same 10 trials, IntAct passes significantly more items than Reflexion" (RQ-4 findings).
- evidence: Table 7, 10 trials, Reflexion against IntAct: one-argument pairs 148 against 172, chains 81 against 155; appended pairs 50 against 181, chains 36 against 150; Claude Code Bash pairs 131 against 162; typed Bash pairs 86 against 88. Reflexion gains 11.4% to 55.0% of what IntAct gains with 1 trial on the appended launch, at 463 to 1,180 retries per cell; IntAct with 10 trials needs 22 to 913 (§4.4). On typed Bash, Qwen2.5-Coder-32B needs no retries with IntAct, Reflexion reaches 29 pairs with 20 retries (§4.4).
- effect: mixed
- reader: Reflexion does recover part of the loss, so it helps, at many times the retries; E3 because the Reflexion column has 10 trials and the 1-trial None column is not an equal comparison. The head-to-head with IntAct at equal trials is the comparison the paper stresses.

### F11 · practice · receiver-parser-comparison-of-tool-call · E4
- practice: decide whether a hop changed a call by the receiver's own parser (Bash words and operators, PowerShell parse tree, argument vector) instead of string comparison or an LLM judge (§2.3, §4.3).
- claim: texts that differ can denote the same action; the receiver parse is needed (§2.3).
- evidence: on 115 labelled pairs the IEC protocol agrees on all 115, kappa 1.00; string comparison and the qwen3-coder-plus judge reach kappa 0.65 and classify 15 of the 35 unchanged pairs as changed (§4.3). Mutation test: of 297 mutants, Bash executes 262 differently and the comparison detects all 262 (§4.4). Failure attribution, Table 5 (102 failures): without the receiver parse 13 correct and 5 incorrect, kappa 0.09; IEC protocol 54 and 1, kappa 0.77 (Table 5).
- effect: helps
- reader: ablation on the authors' own protocol against a human reference. Labels are agreement of 2 annotators (kappa 0.79 and 0.89) and execution evidence in 13 items (§3.4). The 115 pairs are a sample stratified by the protocol's own verdict.

### F12 · practice · llm-judge-failure-attribution · E3
- practice: attribute a failed run to the LLM or the path with a trajectory judge, the three Who&When judges on Qwen2.5-72B, and with an LLM judge in place of the witness (§3.4).
- claim: "Trajectory-based analyses read the call and its result but not what a hop received, so a changed call is incorrectly attributed to the LLM" (§7.1).
- evidence: Table 5, 102 failures of which 56 path-caused: Who&When all-at-once 0 correct, kappa 0.00, and 97 of 102 attributed to the LLM; step-by-step 29 correct and 20 incorrect, kappa 0.04; binary search 25 and 20, kappa 0.01; LLM judge qwen3-coder-plus 8 and 0, kappa 0.10. Using the error message alone, 56 and 46, kappa 0.00. IEC protocol 54 and 1, kappa 0.77 (Table 5). Resampling a step (Causal Agent Replay) gives a passing rollout in 12 of 67 shell-only lost pairs with a changed call and in 29 of 53 without (§4.3).
- effect: hurts
- reader: judges compared with a human reference on one 102-failure sample, no control. The judges ran on one smaller LLM (Qwen2.5-72B) with the released prompts, without ground truth. The abstract's 95.1% is 97 of 102 (reader's arithmetic) from this sample, not from all production failures.

### F13 · practice · same-models-across-execution-paths · E3
- practice: run the same 4 LLMs and the same 135 chains under 6 execution paths, so the launch is the only change (§3.3, §4.2).
- claim: "The path removes an LLM's lead" and "A score should reflect the LLM, not the launch" (RQ-2 findings).
- evidence: Qwen2.5-72B is 29 chains ahead of Hermes-3 with direct JSON calls, 2 and 3 chains behind on the PowerShell launches, and 5 and 4 ahead once IntAct repairs them. On the control transport, which changes no calls, the 3 Qwen LLMs answer 6 to 26 fewer chains than with direct JSON and Hermes-3 loses none (§4.2).
- effect: hurts
- reader: the transport was assigned by the authors, so this is a practice; the comparison is between transports on the same items, one trial. 4 LLMs, 3 of them from one family.

### F14 · observation · harness-launch-alters-tool-calls · E2
- practice: observed, no treatment: recorded shell calls of production sessions, public runs and MCP servers replayed through the witness of each hop (§4.1).
- claim: "All 10 measured harnesses change a call"; "A changed call comes from the launch, not from the platform or the LLM" (abstract, §4.1).
- evidence: Windows corpus: 1,199 of 11,982 exposed calls change, 10.0%; Claude Code's Bash tool changes 12.0% of 7,491 exposed Bash calls, 67.0% of calls with a backslash pair (846 of 1,263), 100% of calls of 8,000 characters or more (64 of 64), and 0 of 24,768 calls with none of these features (Figure 3a). A changed call occurs in 65 of 199 sessions with an exposed call, 32.7%. 6 of the 16 MCP servers tested change a payload (§4.1, Table 4; Table 4's cells give 5 on Windows, see Discrepancies). On Linux 4 harnesses change none in 80 runs (§4.1). Held-out sessions of 2 external developers: 5 of 605 and 2 of 52 exposed calls change (§4.1).
- effect: hurts
- reader: rates are over "exposed" calls the authors selected by text feature, from one company's 6 developers on Windows, so the headline rate is not the share of all calls. Counts are by replay of the shortest wrapper, which the authors call a lower bound.

### F15 · observation · silent-tool-call-change · E2
- practice: observed, no treatment: what the agent's tool result says after a changed call (§4.1).
- claim: "For 80.7% of the calls whose backslashes are changed, the wrong action runs without any reported error" (abstract); "Every payload that a harness changes is reported as a success" on the PowerShell paths (§4.1).
- evidence: the wrong action ran without a reported error for 535 of the 663 backslash-merged Bash calls that ran, 80.7% (Figure 3b). All 11 cut calls that ran fail with an error. Of 426 parse errors, 306 are attributed to the path (253 cut commands, 46 merged backslash pairs, 7 quotes left open), 84 to generation and 36 to a nested hop; each of the 306 was reported to the agent as an error in its own text (Figure 3c, §4.1). Under Qwen Code's `cmd.exe` launch 30 of the 31 multi-line commands ran as an empty program (§4.1).
- effect: hurts
- reader: attribution of the 426 errors is by the authors' protocol, validated on a human sample (F11), and 231 of the 306 were changed only by the session's longer wrapper than the one replayed (§4.1).

### F16 · observation · interactive-shell-typing-alters-commands · E3
- practice: observed, no treatment: commands handled before Bash parses them are compared with commands passed to the shell as an argument (§4.1, Table 3).
- claim: "a call changes only where the harness handles the command before Bash parses it" on Linux (§4.1).
- evidence: arriving as written for an argument to `bash -c` in all 1,779 calls of 4 harnesses, 4,012 calls of 9 developers and 161,214 held-out Codex calls. Terminus-2 typing into an interactive Bash: 1,113 of the 1,118 Toolathlon programs with an expandable `!` change, against 2 of 12,030 without a tab or such a `!`; 186 of 245 leaderboard keystroke batches change (81 at a tab, 105 by history expansion), in 137 of 4,356 scored trials. `event not found` occurs 2,546 times in 1,532 of 113,674 trajectories of harnesses that type, and never in 90,036 of the harnesses that pass the command to a non-interactive Bash (§4.1). dash stops 5 reference solutions, zsh changes 5 (§4.1).
- effect: hurts
- reader: a comparison between groups that nobody assigned; the 203,710 public trajectories are grouped by harness, which differ in other ways. The cause (history expansion) is shown directly by the witness.

### F17 · observation · retry-after-path-caused-failure · E2
- practice: observed, no treatment: what agents do after a failure the path caused, in the 306 production failures (§4.2).
- claim: "In production, 144 of the 306 path-caused failures are not recovered by a retry" (RQ-2 findings).
- evidence: the agent recovered 162 of the 306 by retrying, in 2 to 8 steps, abandoned 30 after retries and did not retry 114; each call that finally succeeded cost 3.9 times the tokens of one clean request (§4.2, Figure 3c). In the fix task all 13 API LLMs get a first command that fails, in all 45 runs, and the run takes 2 to 7 steps; under PowerShell 5.1 an LLM uses a median 1.8 times the tokens of its Linux run (§4.2).
- effect: hurts
- reader: the fix-task runs are on a task built around one literal that triggers the change, so the 45 of 45 shows the hazard is real, not how often it occurs. The 3.9 times has no stated comparison group beyond "one clean request".

### F18 · observation · premature-completion-report · E2
- practice: observed, no treatment: the final report of runs that failed under a changed call (§4.2).
- claim: "Agents report 665 of 949 failed runs as completed" (RQ-2 findings).
- evidence: 665 of the 949 failed runs of hazard variants and multi-line programs are reported as completed, a false-confirmation rate of 70.1%. In the commit task, the commit carries the intended message in 1 of 39 runs and 19 runs end in a false confirmation (§4.2). On typed Bash without IntAct 4 and 1 of the affected Qwen2.5 episodes end in a false confirmation, none with IntAct (§4.4).
- effect: hurts
- reader: the failed runs are those of hazard variants made to fail on a changed launch, so the 70.1% is a rate under the benchmark's own hazard mix and on small open LLMs and qwen3-coder-plus.

## Limits stated by the authors

- Agent runs vary between executions; IEC-Bench fixes the temperature at 0 and compares on the same items with an exact McNemar test (§6).
- A witness could change the call itself; the Bash witness confirms by its exit code that it ran in place of the command (§6).
- Changes on Linux happen before Bash parses the command, so the Linux corpora go through the released command handling of 5 harnesses and 2 further shells (§6).
- Scores cover 4 LLMs on IEC-Bench and 15 LLMs from 4 vendors on the fix and commit tasks; results on few LLMs could reflect those LLMs (§6).
- Planned: extend the measurement to harnesses that type into a terminal and to later launches; a repair that rewrites a call must leave the harness's permission rules judging the original call (§8).

## Reader's notes

- The Windows corpus is 6 developers of one company over 11 weeks (§3.2); the abstract's "production sessions" and "9 developers" combine this with the Linux corpus.
- IEC-Bench pairs are written from the changes the authors saw, and IntAct is built against the same changes, so its gains are at the best case (F1, F3). Only the commit and fix tasks and the production calls (F5) are outside that loop, and F5 has no outcome measure.
- Three of the 4 LLMs on IEC-Bench are Qwen models (qwen3-coder-plus, Qwen2.5-Coder-32B, Qwen2.5-72B) and the open ones run on vLLM; no frontier coding agent is run on IEC-Bench with a model's own harness, except in the production corpus where Claude Code and Codex are observed.
- Most findings are about Windows launches (PowerShell 5.1, `cmd.exe`, Git Bash). On Linux the paper finds changes only where the harness handles the command before Bash (F16).
- No cost in money is reported; "cost" is tokens (F2) and added milliseconds (F5).
- Several pass counts are of the form "items passed by 3 LLMs"; the denominators are 3 times the item counts (201, 405, 90).
- Tests in Table 7 are reported pooled over the 2 Qwen2.5 LLMs; which other cells were tested is not stated in the parts read.

## Discrepancies

- Table 8 says the mod ran on 3,577 rerouted production calls, "all 227 that would have changed rerouted and none of the 3,540 that ran changed"; 227 plus 3,540 is 3,767 (reader's arithmetic).
- §4.1 says "6 of the 16 and 4 of the 6 change a payload"; Table 4's Windows cells sum to 5 (4, 0, 0, 1) and its Linux cells to 2 (reader's arithmetic). RQ-1 findings say "10 of the 22 MCP servers changed a call", which Table 4 (16 servers) does not show.
- The abstract says IntAct "deployed in a commercial product, recovers 79.2% of the failures with a changed call"; §4.4 gives 79.2% (137 of 173) as a replay of recorded actions in a sandbox, and the commercial-product number in Table 8 is 197 of 9,032 native invocations changed before and none after.
- The abstract says trajectory-based judgment "attributes 95.1% of the production failures to the LLM"; §4.3 gives 97 of 102 for one judge on a labelled sample, 95.1% (reader's arithmetic), where 56 of the 102 are path-caused.
