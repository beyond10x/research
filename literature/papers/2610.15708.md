## Question

Can a coding agent with frozen model weights improve its own natural-language behavioural
specifications of a codebase by generating code from them, running tests and revising from the
failures, and how must the loop be structured so that fixing one entity does not break others
(Abstract, §1)?

## Findings

### F1 · practice · execution-grounded-specification-refinement · E3
- practice: SpecForge, a loop that generates code for every entity from its specification alone, runs LLM-generated tests that were validated on the reference implementation, and rewrites one entity's specification at a time from its failing tests, with tree search over specification states, callee-before-caller order and W = 3 children per step; budget B = 50 rollouts (§3, §4.1, Table 1, App. C.3).
- claim: it "achieves the best performance across five backbone models", a "94.9% solve rate with Claude-4.5-Sonnet", and 5.7 points on average over the strongest baseline (Abstract, §4.2).
- evidence: solve rate on DevEval+ (hidden ground-truth tests), Table 1, SpecForge against the closest prior method DocSearch: Qwen3 88.9 against 81.5, Gemini-2.5-Flash 89.6 against 82.2, GPT-4o 90.9 against 85.5, Gemini-3.1-Pro 91.0 against 87.2, Claude-4.5-Sonnet 94.9 against 90.4. Against static documentation: RepoAgent 19.2 to 35.3 and DocAgent 14.5 to 28.9 across the same five backbones. Against Cursor with Topo and Test, Claude-4.5-Sonnet 52.1, and Claude Code with Topo and Test, 61.9. 50 rollouts (§4.2).
- effect: helps
- reader: E3. The baselines are different systems with different loops, budgets and inputs, not ablations of this one, so the comparison has no control. The authors built the benchmark, wrote the method, and re-ran the closest baseline on a benchmark release that they say was made harder "to stress-test SpecForge", where it scores 5.6 points lower than in its own paper (§4.1 footnote, App. G). The task is to reconstruct code that the loop's tests were validated against, so the loop needs a reference implementation (App. N). Number of seeds, intervals and cost per run are not stated.

### F2 · practice · callee-before-caller-refinement-order · E4
- practice: restrict refinement to entities whose callees are already resolved (call-graph order, strongly connected components refined jointly); the ablation removes this constraint (§3.2, §4.4).
- claim: reverse topological order "is the structural foundation"; without it "the search refines callers before their callees are stabilized" (§4.4).
- evidence: ablation, GPT-4o, 10-module subset, full model solve rate 90.9: removing the order costs 18.6, the largest of the four components (§4.4, Figure 3c). Case study of one module of 6 entities: solving the callee PnF.get ohlc data (0% to 100%) lifted its caller from 33% to 100% with no edit to the caller's specification (App. D.3).
- effect: helps
- reader: an ablation on equal tasks, so E4. The unit of the −18.6 is not defined in the text and the figure gives a second value per row (17.6), so the metric of each number is inferred. One backbone, one subset of 10 modules, no repetition stated. The full-model values of the subset equal the full 20-module Table 1 values (see Discrepancies).

### F3 · practice · dependency-order-context-for-agent · E4
- practice: give a commercial coding agent the dependency graph or reverse topological order as extra context when it writes the specifications (the +Topo variant), against the same agent with default settings (§4.1).
- claim: "topological ordering and test feedback are valuable signals" (§4.2).
- evidence: Table 1 solve rate, base against +Topo: Cursor on Claude-4.5-Sonnet 30.6 against 37.7, Cursor on Gemini-3.1-Pro 27.5 against 37.6, on Gemini-2.5-Flash 15.8 against 21.2; Claude Code 40.1 against 45.1. In the iterative baseline: random order against reverse topological order, 41.0 against 43.5 (Qwen3), 37.8 against 40.5, 49.7 against 54.3, 57.5 against 67.5, 59.5 against 64.4.
- effect: helps
- reader: same agent, same tasks, one prompt change, so E4. Single runs; no variance given. Specification writing from reference code is not the usual task of these products.

### F4 · practice · agent-written-tests-for-self-verification · E4
- practice: prompt the commercial agent to write tests from its own specifications and refine until they pass, budget 50 manual action approvals (the +Test variant), against the default agent (§4.1, App. G).
- claim: test feedback is a valuable signal, yet commercial agents "still trail SpecForge by 33.0–42.8" points (§4.2).
- evidence: Table 1 solve rate, base against +Test: Claude Code 40.1 against 55.3; Cursor on Claude-4.5-Sonnet 30.6 against 47.8, on Gemini-3.1-Pro 27.5 against 44.9, on Gemini-2.5-Flash 15.8 against 31.0. With both additions (+Topo+Test): Claude Code 61.9, Cursor 52.1 (Claude-4.5-Sonnet).
- effect: helps
- reader: E4 as a prompt contrast on the same agent and tasks. The agent's tests come from its own text and are not validated on the reference implementation, unlike the tests of SpecForge, so this is not the same signal; the gap to SpecForge mixes the signal, the search and the budget.

### F5 · practice · adaptive-budget-bandit-for-entity-selection · E4
- practice: choose among eligible entities with a discounted-UCB bandit over the rate at which refining an entity closes its remaining gap (γ = 0.95), against the ablation without it (§3.2, §4.4, App. C.2).
- claim: "adaptive budget allocation is critical" (§4.4).
- evidence: removing the bandit costs 10.4 on the 10-module GPT-4o subset (§4.4, Figure 3c; second figure value 10.2).
- effect: helps
- reader: E4 by ablation, but one backbone, no repetition stated, and the replacement policy used in the ablation is not described in the parts read.

### F6 · practice · error-diversified-expansion · E4
- practice: for each refinement, sample W = 3 different halves of the failing tests and write one candidate specification per half, instead of conditioning all candidates on the full failure set (§3.3, App. C.3).
- claim: noisy failures "actively corrupt" the refinement; a diversified batch raises the chance that one candidate sees a cleaner signal (§3.3).
- evidence: removing error diversity costs 9.5 on the 10-module GPT-4o subset (§4.4, Figure 3c; second figure value 9.9). The supporting proof (Appendix B) was not read.
- effect: helps
- reader: E4 by ablation. The ablation changes the batch construction and may change the number or the cost of calls; the text does not say. The signal-corruption argument is a derivation under assumptions that the authors call mild; no measurement of failure noise is given in the parts read.

### F7 · practice · pareto-archive-of-states · E4
- practice: keep an archive of non-dominated specification states (per-entity pass-rate vectors) and expand a state sampled by how many entities it is best on, rather than a single best state (§3.1, §4.4).
- claim: it "preserves frontier diversity, enabling recovery from suboptimal early refinements; its value increases on harder modules" (§4.4).
- evidence: removing the archive costs 5.2 on the 10-module GPT-4o subset, the smallest of the four components (§4.4, Figure 3c; second figure value 4.9). The "harder modules" statement has no number in the text.
- effect: helps
- reader: E4 by ablation; the smallest effect of the four and no repetition or interval is given, so it is the most likely of them to be within run-to-run variation.

### F8 · practice · execution-signal-over-llm-judge · E4
- practice: drive the loop with execution results (tests run on generated code), against a variant in which the model scores its own generated code against the specification without running anything (§E, Table 2).
- claim: "the execution signal cannot be substituted by model judgment" (App. E).
- evidence: Table 2, GPT-4o, module pass rate: LLM-generated tests 93.2, LLM-as-a-judge 73.6, a drop of 19.6 points. The judge variant is still below the weakest coverage setting, 87.5, by 13.9 (App. E).
- effect: helps
- reader: signal ablation on equal tasks and budget, so E4. Judge prompt and judge model are not described in the parts read. One backbone, no repetition stated.

### F9 · practice · self-generated-tests-validated-on-reference · E4
- practice: use tests that the model wrote and that were kept only if they pass on the reference implementation as the feedback signal, against the hidden ground-truth tests as the signal (App. E, App. J).
- claim: the self-generated signal is "near-equivalent to the ground truth"; the gains "reflect genuinely better behavioral specifications rather than reward hacking" (App. E).
- evidence: Table 2, GPT-4o, module pass rate: ground-truth tests 94.8 against LLM tests 93.2, a gain of 1.6 points.
- effect: none
- reader: E4 as a signal swap. A 1.6-point gap with no interval cannot show equivalence. The tests' expected outputs come from running the reference implementation, so they are correct by construction only for code whose reference exists; the claim does not carry to tasks with no reference. The reward-hacking argument also rests on the same hidden tests used for the main score.

### F10 · practice · test-coverage-threshold-of-feedback · E4
- practice: lower the branch-coverage target used when generating the feedback tests from 0.9 to 0.7, 0.5 and 0.3, so that fewer tests drive the search (App. E, App. J.4).
- claim: "Degradation is graceful rather than brittle: the loop does not depend on a complete test suite, only on an execution-grounded one" (App. E).
- evidence: Table 2, GPT-4o, module pass rate against 93.2 at 0.9: 93.4 at 0.7, 92.6 at 0.5, 87.5 at 0.3 (a drop of 5.7).
- effect: mixed
- reader: E4 as a dose series on equal tasks. No change down to 0.5 and a loss at 0.3, so the direction depends on the dose. One backbone, no repetition stated.

### F11 · practice · specifications-added-to-source-for-translation · E4
- practice: when translating Python code to Java with GPT-4o, give the model the optimized behavioural specifications together with the source, against the source alone (§4.5.1).
- claim: specifications and source "provide complementary 'what' and 'how' signals" (§4.5.1).
- evidence: DevEval+-Java, 208 entities and 680 tests, solve rate and pass rate: source only 39.7 and 50.5, specifications plus source 76.2 and 80.4. Specifications alone 65.7 and 71.3; RepoAgent specifications 33.5 and 44.6; ACE 49.7 and 56.0 (§4.5.1, Figure 4).
- effect: helps
- reader: E4 for the plus-specifications against source-only contrast, on equal entities. The specifications were generated and tuned with the Python reference code and its tests in view, so the translation task gets information about behaviour that the source-only arm does not. The comparison of Claude Code with the other methods mixes backbones: it is the +Topo+Test setup on Claude-4.5-Sonnet, the others on GPT-4o (§4.5 footnote 3).

### F12 · practice · specifications-of-existing-code-for-new-features · E3
- practice: generate specifications of the existing package with each method, remove those of the target functions, and give the model the existing-code specifications plus only each target's signature and original docstring, against the benchmark's product requirements document (PRD) (§4.5.2, App. I).
- claim: SpecForge specifications "surpass the default PRD provided by the SWE-Dev benchmark" "despite never accessing the PRD or target tests" (Figure 4 caption).
- evidence: SWE-Dev, 27 instances, GPT-4o, Pass@1, easy and hard: SpecForge 74.5 and 51.7, PRD 55.7 and 44.6 (+18.8 and +7.1 points), ACE 50.0 and 38.0, Claude Code 38.0 and 27.0, RepoAgent 22.0 and 14.0 (§4.5.2).
- effect: helps
- reader: E3: the arms differ in what text they carry, not in one switched part. The authors call the comparison conservative because the PRD holds more target-specific information (App. I). The specifications were made on the complete package, with the reference implementation of the targets present and executable before the targets' specifications were removed, which may leak target behaviour through the callers' specifications. The percentages are not whole counts of 15 or 12 (reader's arithmetic), so the scoring or the number of samples is not as described; there are only 12 hard instances and no interval.

### F13 · practice · monolithic-specification-bundle-rewrite · E3
- practice: optimize the whole specification bundle as one prompt, rewritten in each iteration (MIPROv2, GEPA, ACE), against entity-wise refinement (§4.1, App. G).
- claim: monolithic optimizers "suffer from attribution failure ... and coupling amplification (a single rewrite alters all entities simultaneously)" (§4.2).
- evidence: Table 1 solve rate: MIPROv2 28.5 to 50.0, GEPA 34.8 to 50.4, ACE 58.9 to 74.9, against random-order entity-wise iterative refinement 37.8 to 59.5 and SpecForge 88.9 to 94.9 across five backbones. Trajectories on GPT-4o (§4.3, Figure 3b): GEPA peaks at 37% at B = 20 then falls to 24%; ACE falls from 38% to 30% between B = 10 and 20; random-order iterative refinement oscillates between 45% and 54%.
- effect: mixed
- reader: E3. ACE beats the random-order entity-wise baseline on all five backbones and trails the structured entity-wise searches, so the direction depends on the comparator. The three optimizers were adapted by the authors to a task they were not built for, with a budget matched by metric calls, and the authors do not report tuning them. The trajectory numbers are read from a figure and text, not from a table.

## Limits stated by the authors

- The recursion is over the specifications, not over the improver: the search procedure is fixed (App. N).
- The loop "requires a reference implementation against which self-generated tests are validated" (App. N).
- The loop is evaluated on 20 Python modules; other languages appear only as a downstream target (App. N).
- It "does not remove the need for verification or human oversight" (App. O).

## Reader's notes

- Every number is a single reported value; the parts read give no seeds, no confidence intervals, no tests of significance and no per-run cost or token count. "50 rollouts" is the search budget B = 50, not 50 repeats (§4.2, App. G).
- The paper is a method paper whose authors also built the benchmark and ran every baseline. The closest baseline, DocSearch, is by the same authors (reference 24, ICML 2026). `independent` is false for that reason.
- The task is to rewrite documentation for code that already exists, with the code present, and then to reconstruct that code from the documentation. It is not the task of an agent changing code in a repository; the transfer to translation and feature work (F11, F12) is the paper's own evidence for that step, on 16 modules and 27 instances.
- Final scores use ground-truth tests that the search never sees, and the feedback tests are model-written; this is the paper's guard against fitting to the tests (§4.1).
- The commercial agents did not run the same loop: they wrote documentation in one session, with their own tests and 50 approvals (App. G, F.6). The table compares products with a research loop and no cost is reported for either.
- The ablation in Figure 3c is on a 10-module subset of GPT-4o runs and its second value per row is not named in the text.
- Appendices A, B and C.1 (definitions, proofs, cyclic graphs) were not read, so the theory behind F6 was not checked.

## Discrepancies

- Figure 3c's caption gives the full model as 90.9 solve rate and 93.2 pass rate on a 10-module subset; these are identical to the GPT-4o values of Table 1 on all 20 modules (§4.2, Table 1).
- §4.2 states the gaps of the commercial agents to SpecForge as "33.0–42.8%"; the values are differences in solve rate of 94.9 against 61.9 and 52.1, so points (reader's arithmetic).
- Figure 4's SWE-Dev percentages (74.5, 51.7, 55.7, 44.6) are not whole counts of 15 easy and 12 hard instances (reader's arithmetic); the text says Pass@1 and does not say how it is averaged.
- The DocSearch scores differ from its own paper by 5.6 points on average because of the "revised" benchmark; the main text says "modestly", App. G says the new release has 12.4 entities per module against 11.4 (§4.2 footnote, App. G).
