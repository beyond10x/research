## Question

Does turning every accepted human review comment into a persistent rule in a version-controlled
instruction file, plus a self-review checklist, stop a coding agent from repeating corrected
mistakes and move review effort to design (Abstract, §I)?

## Findings

### F1 · practice · accepted-review-comments-as-instruction-rules · E2
- practice: when a human reviewer accepts a comment that names a generalisable class of mistake, the engineer adds a rule for it to the shared instruction file, which every later session loads (§I, §II-C, §II-D).
- claim: "accumulated rules suppress the recurrence of previously-corrected error classes within the observation window"; "0% recurrence rate for ruled-against error classes" (Abstract, §V-A).
- evidence: Table IV, 9 tracked error classes, 74 cumulative post-rule session-exposures, 0 recurrences; post-rule sessions per class 6 to 10 (reader's arithmetic: the nine values sum to 74). Rule set grew from 5 to 18 behavioral rules in 4 weeks (Table III). The authors call it "an observational result inside a single deployment, not a controlled experiment" (§IV-C).
- effect: helps
- reader: E2, numbers with no comparison: there is no run without the rules, and §VIII says so. A session counts as an exposure whether or not its task could trigger the error class, so zero recurrences may reflect tasks that never touched the class; how the 9 classes were chosen is not stated. The authors built and run the system.

### F2 · practice · self-review-checklist-from-review-rules · E0
- practice: keep a numbered self-review checklist, 15 items at the end, that the agent runs before presenting code; each rule maps to a checklist item (§II-A, §II-B, Table I).
- claim: the checklist is "a verifiable bridge between the instruction file and the pre-submission check" and expands "the set of error classes the agent can self-detect" (§II-B, Abstract).
- evidence: none for the checklist's effect. The count of items per week is in Table III (0, 9, 13, 15, 15). Recurrence is reported for rules, not for the checklist alone.
- effect: helps
- reader: E0, asserted. The checklist and the rules are never separated, so no result can be credited to the checklist.

### F3 · practice · one-instruction-file-across-agent-interfaces · E2
- practice: two different agent interfaces, one IDE-integrated and one terminal-based, load the same instruction file (§III-A, §IV-F).
- claim: "Rules added through one agent interface immediately benefited sessions conducted through a different interface"; both "benefited equally" (§III-D, §IV-F).
- evidence: of 15 documented review learnings, 3 were cross-tool, 4 cross-repository, 2 cross-task-type and 6 same-repository; 9 of 15 (60%) crossed a repository, tool or task-type boundary (Table VI, §IV-E). "Benefited equally" has no numbers.
- effect: helps
- reader: E2. Table VI counts how a learning was reused, not whether the second interface stopped making the error. The 60% is a share of 15 learnings, with 3 cross-tool cases.

### F4 · observation · review-comment-mix-with-rules-loaded · E2
- practice: observed: the category of review comments in 36 PR reviews across 6 repositories after the rule set existed (§IV-D).
- claim: "accumulated rules shift review effort from low-level correctness toward design-level validation"; reviewers "reported spending less time on mechanical issues" (Abstract, §III-D).
- evidence: Table V: architecture and design 12 (33%), API design 7 (19%), performance 5 (14%), auth and security 4 (11%), query correctness 3 (8%), mechanical correctness 3 (8%), style 2 (6%). Mechanical and style are 14%, architecture, API and performance 66% (§IV-D). Reviewer statement is reported, with no count.
- effect: helps
- reader: E2. The paper gives no distribution before the rules, so a shift is not shown, only a current mix. The counts in Table V sum to 36, the number of PRs, so it seems to give one category per PR; §IV-D says "comments".

### F5 · practice · explicit-actionable-instruction-wording · E0
- practice: write rules as specific, actionable constraints; early rules were broad, later ones precise (§III-D, §VII principle 2).
- claim: "Specific, actionable rules were more reliably followed than general guidance"; "Concrete, actionable constraints outperform abstract guidance" (§III-D, §VII).
- evidence: Table VII counts rules by specificity: general 4, 4, 4 and specific 6, 12, 14 for week 1, week 2, weeks 3 and 4; ratio 0.60, 0.75, 0.78. The table shows how the mix changed; it has no compliance rate by specificity.
- effect: helps
- reader: E0 for the claim, since no outcome is split by specificity. The ratio rose partly because specific rules were added while the 4 general ones stayed (reader's arithmetic from Table VII).

### F6 · practice · append-mostly-rule-file-growth · E2
- practice: let the rule file only grow ("Monotonic growth"): rules are added and refined in place, rarely removed; duplicates are merged by hand in periodic review (§II-A, §II-D, §VII principle 1).
- claim: the rule set can grow safely and stays small relative to the context window (§II-F, §IV-B).
- evidence: combined file about 4,809 words (about 6,250 tokens), under 5% of a 128K-token window (§IV-B, Table VIII). Growth is "logarithmic", tapering from week 1 to week 4 (Table III).
- effect: helps
- reader: E2 at 4 weeks. The 4,809 words include 1,628 words of one developer's personal rules (Table VIII), which other agents do not load. The authors say behaviour at context saturation "has not yet been observed" (§VIII). No test of whether more rules lower compliance with each.

### F7 · observation · contradicting-rules-in-instruction-file · E1
- practice: observed: two rules in the accumulated file contradicted each other (§III-E).
- claim: rule conflicts happen as the set grows and need governance; this one was resolved "as a factual question" (§III-E, §VIII).
- evidence: one case. Rule 1 "All IDisposable types MUST use using declarations" against Rule 8 "HttpClient from IHttpClientFactory must NOT be disposed by the caller"; fixed by a scope qualifier on Rule 1. Found in a code review, not by a tool.
- effect: hurts
- reader: E1, one case in an 18-rule set. Detection was manual and the authors call automated detection future work; undetected conflicts would not appear in this count.

### F8 · practice · instruction-file-schema-validation-at-session-start · E0
- practice: run an automated check at session start that agent definitions have valid frontmatter, skill directories are well formed, knowledge documents carry freshness dates, and the instruction file has all required sections (§II-F).
- claim: "the rule set can grow safely because every addition is validated against a known-good schema" (§II-F).
- evidence: none. No count of malformed additions caught is given.
- effect: helps
- reader: E0. The check is structural, so it cannot catch a wrong or conflicting rule, which is the failure the paper names in §VIII (F7).

### F9 · practice · human-gated-rule-promotion · E0
- practice: a rule is added only by the engineer who received an accepted review comment, who judges "Would this mistake plausibly recur in a different context?"; each rule records its origin and the PR that added it (§II-B, §II-D, §V-B).
- claim: human validation is needed because the file is loaded as authoritative context and "an incorrect rule would amplify rather than correct errors"; it gives provenance that autonomous insight extraction (ExpeL) lacks (§VI-C).
- evidence: none. No wrong rule or rejected candidate is reported.
- effect: helps
- reader: E0, an argument about a risk with no measurement of it. §IV-A says the instruction file had 2 committed revisions with "continuous local growth", which does not match PR-by-PR provenance (see Discrepancies).

### F10 · observation · sources-of-accumulated-rules · E2
- practice: observed: where the first 18 behavioral rules came from (§III-C).
- claim: "The dominance of human reviewer feedback (39%) validates the core premise: human review is the highest-quality signal for rule generation" (§III-C).
- evidence: Table II: human PR reviewers 7 (39%), automated review bots 4 (22%), self-discovered through proactive analysis 4 (22%), production errors 3 (17%). By session type, PR review and incident investigation sessions gave 4 and 3 of 18 rules, 39% together (Table IX, §IV-H).
- effect: mixed
- reader: E2. 39% is a plurality; 11 of 18 rules (61%, reader's arithmetic) came from other sources. No measure of rule quality is given, so "highest-quality" is not supported by the table. `mixed` because the rules from non-human sources also fed the same rule set.

### F11 · practice · shared-rule-file-as-onboarding-artifact · E0
- practice: new team members start with the whole accumulated rule file instead of learning each rule from their own reviews (§III-D, §V-B).
- claim: they inherit the rules "immediately, bypassing the learning curve that originally produced those rules" (§III-D).
- evidence: none. No onboarding data is given.
- effect: helps
- reader: E0. Here the rules are for agents and for people alike; whether a new person reads and follows them is not observed.

## Limits stated by the authors

- No parallel control group and no ablation against static prompt engineering or a no-rule baseline; results are "initial empirical evidence, not ... a causal proof" (§VIII).
- Counts are small (74 exposures, 9 classes, 36 PRs, 11 sessions); no p-values reported (§VIII).
- One organisation, one team, one typed language, four weeks (§VIII).
- Rule quality depends on review quality; "a noisy review culture can poison the rule set faster than the validation step can catch" (§VIII).
- Context saturation was not reached; conflict detection is manual; multi-team governance is "an open problem" (§VIII).
- Preconditions: a review culture that yields written accepted comments, engineers willing to codify them, and agents that load a project instruction file (§VIII).

## Reader's notes

- The tool or model names are not given, so the agents cannot be matched to other studies.
- The recurrence count has no denominator of opportunities and no comparison period before the rule was added, so it cannot show whether the error would have recurred.
- Table X puts "0% (74 exp.)" beside "N/M" (not measured) for other systems; the rows measure different things and the comparison is not like for like.
- Which 9 of the 18 behavioral rules were tracked, and why, is not stated; five are the examples of §II-E.
- The same two authors build the system, run the deployment, choose the metrics and classify the review comments. Table V's classification criteria are "adapted from prior code review studies" with no inter-rater check.
- The paper's "self-improving" is the humans improving the file; the agent proposes no rule, and automated rule proposal is left as future work (§Future Research 4).

## Discrepancies

- §I-A says the memory content is "derived exclusively from accepted review outcomes" and the Abstract says the rules are "all derived from real review feedback"; Table II says 4 of 18 rules came from automated review bots, 4 were self-discovered and 3 came from production errors, 7 from human PR reviewers.
- §III-C says the 39% share of human reviewers "validates the core premise"; 39% is below half.
- §V-B says each rule has "a change record (the pull request that added the rule)" and §II-D that changes "require pull requests"; §IV-A says the file had 2 committed revisions with "continuous local growth" over 4 weeks and 18 rules.
- §IV-B calls the 4,809 words "the combined instruction file"; Table VIII splits it into 3,181 shared words and 1,628 words of one developer's personal rules, which only one developer's agents load, while §III-A says all interfaces read "the same instruction file".
- §IV-D says 66% for architecture, API and performance; Table V gives 24 of 36, which is 66.7% (reader's arithmetic). The 66% is the sum of the rounded 33, 19 and 14.
- §IV-D reports "36 PR reviews" and calls Table V a distribution of review comments; the counts in Table V sum to 36.
