## Question

Are the explicit, actionable instructions written in agent context files reflected in the commits that
coding agents produce in real repositories, and which instruction categories and agents follow them
least (§1, §3.1)?

## Findings

### F1 · observation · instruction-compliance-split · E2
- practice: for each instruction that could be turned into an LLM-generated check script and that had at least one applicable commit, the share of its applicable commits that satisfy the script. 2,053 instructions, 18,594 instruction-commit pairs (§4.3.1).
- claim: compliance is "strongly bimodal": instructions are mostly either followed in every applicable commit or in none; context-file governance "behaves less like a dial ... and more like a switch" (§4.3.2, §5.2).
- evidence: mean per-instruction compliance 59.8%, median 100.0% (Table 8). 1,116 instructions (54.4%) followed in every applicable commit, 766 (37.3%) in none, 171 (8.3%) in between (§4.3.2). The median instruction has 3 applicable commits and 540 (26.3%) have exactly 1. Instructions at 0% or 100%: 91.7% in the full sample, 87.3% with at least 3 applicable commits (n = 1,144), 86.2% with at least 5 (n = 819) (§4.3.3).
- effect: mixed
- reader: E2 because nothing in the paper shows what the same agents do without the instruction (§6 states "we never observe what an agent would produce in the absence of a given instruction"), so a 100% rate may be a model default. The authors say reported non-compliance is "a floor" because the scripts are permissive (F6) and also say 3 in 10 scripts are wrong in a way that biases the other direction (F5); the net is not quantified (§6).

### F2 · observation · instruction-category-compliance · E3
- practice: compare per-instruction compliance rates across the 19 context-file categories of an earlier study (§3.3).
- claim: "ACF-based governance works best for code-level conventions, and less well for testing and process-oriented guidance" (§5.2).
- evidence: Kruskal-Wallis over 18 categories H = 59.13, p < .001 (§4.3.2). Of 153 Bonferroni-corrected pairs, 4 are significant. Implementation Details (mean 63.6%, median 100.0%, 1,022 instructions) above Testing (mean 49.2%, median 37.5%, 270 instructions): p Bonf = .002, Cliff's delta 0.15, and it stays significant at the at-least-3 and at-least-5 thresholds (§4.3.3, Table 8). Development Process (mean 34.0%, median 0.0%, 50 instructions) below Build and Run (p = .013, delta -0.39), Documentation (p = .037, delta -0.29), Implementation Details (p = .002, delta -0.32); none of these three survive at the at-least-3 or at-least-5 thresholds, where its evaluated n falls to 14 and 7 (§4.3.3). Architecture mean 38.2% (n = 40) and Debugging 21.9% (n = 4) are descriptive only (§4.3.2).
- effect: mixed
- reader: E3, a comparison between groups with no control. The only robust difference is a small one (delta 0.15). The Development Process gap is the authors' own "suggestive" reading, lost under the sensitivity check. Categories were labelled by a 9-billion-parameter local model with 96.6% category accuracy on a validation sample (Table 5).

### F3 · observation · instruction-compliance-by-agent · E3
- practice: compare per-instruction compliance by the agent whose context file the instruction came from.
- claim: "Copilot-authored commits comply significantly more often than Claude Code's"; Claude Code and Codex are indistinguishable (§4.3.2, §4 answer to RQ3).
- evidence: Table 9, mean (median) compliance: Copilot 66.0% (100.0%, 1,137 instructions), Claude Code 52.2% (66.7%, 799), OpenAI Codex 51.2% (100.0%, 117). Kruskal-Wallis H = 41.58, p < .001. Copilot against Claude Code p Bonf < .001, delta 0.15, and stable at the at-least-3 and at-least-5 thresholds (p Bonf .002 and .004). Copilot against Codex p Bonf = .018, delta 0.13; not significant at at-least-3 (.165) or at-least-5 (.102). Claude Code against Codex p Bonf = 1.0 (§4.3.2, §4.3.3).
- effect: mixed
- reader: the authors call it "an association, not an established cause" and say the comparison does not control for category mix, repositories or languages (§5.2, §6). Agent attribution rests on different signals per agent (bot account, co-author line, branch name), and only the strict subset is used, which they say is likely imbalanced across agents (§3.2.2, §6). No model versions are given, so it is a tool-level comparison. It does not show that Claude Code is worse at following instructions.

### F4 · observation · observable-instructions · E3
- practice: apply three criteria in sequence to the candidate instructions in context files: explicit, actionable, observable in the files a commit leaves behind (§3.3.1).
- claim: process and execution guidance is "often explicit and actionable, but rarely verifiable from the artifacts it leaves behind", for example "run the linter" (§4.1.1); a large share of context-file text reads "more like documentation for human readers than instruction for an agent" (§5.1).
- evidence: of 14,902 candidates, 10,324 (69.3%) explicit, 8,726 (58.6%) also actionable, 6,552 (44.0%) also observable (Table 2). Build and Run falls from 8.8% of the explicit-and-actionable set (767) to 2.9% of the final set (189); Implementation Details, Testing and Documentation make 76.6% of the final set and 83.2% when weighted by commits reusing the snapshot (§4.1.1, Table 3). Security is 99 instructions (1.5%) and Performance 25 (0.4%) of the final set (Table 3). In the 84-snapshot hand-validated sample the observable share is 27.7% (Table 2). Annotator accuracy on observability is 85.0%, with more than 90% of its disagreements turning a yes into a no, so 6,552 is an upper bound (§4.1.2, Table 5).
- effect: hurts
- reader: E3 for the claim about process guidance, from category shares before and after one filter. The labelling is by a local 9-billion-parameter model checked by one author on a sample (§3.3.3). "Observable" here means checkable from file contents only; a process instruction is not shown to be ignored, only to be unverifiable by this method.

### F5 · practice · generated-compliance-checks · E2
- practice: turn each instruction into an executable check. A code model (Qwen2.5-Coder-14B-Instruct, temperature 0.8) writes 10 candidate scripts and 10 test fixtures (a compliant and a non-compliant synthetic commit) per instruction; a script is accepted if it passes at least 2 fixtures and at least one other script has at least 60% overlap with the best script's set of passed fixtures (§3.4.2, §3.4.3).
- claim: "automated, per-instruction compliance checking is practical at scale for a large share of ACF content today", but "generated checks still need human review before they are trusted as enforcement" (§5.4).
- evidence: 4,123 of 6,552 observable instructions (62.9%) reach an accepted script; 2,429 (37.1%) do not (§4.2.1, Table 6). By category: Configuration and Environment 269 of 356 (75.6%), Testing 626 of 927 (67.5%), Security 48 of 99 (48.5%), Management 31 of 65 (47.7%). By agent 62.1% to 63.5% (§4.2.1). Exclusions: no script passed any fixture 1,006, no corroborating script 997, best script passed only one fixture 386, fewer than two valid candidates 40 (Table 7). Manual spot-check of 94 accepted scripts by one author: 67 (71.3%) correctly implement the instruction; the commonest error is hardcoding an example from the file as a literal requirement (§4.2.2). The thresholds were set on a pilot in which exact-match agreement "essentially never happened" (§3.4.3).
- effect: mixed
- reader: E2, the numbers describe the pipeline with no comparison pipeline. The authors evaluate their own pipeline, and the 71.3% check is one rater on 94 scripts. Whether a check that passes this gate would catch a real violation is not tested.

### F6 · observation · vacuous-compliance-in-generated-checks · E2
- practice: observed property of LLM-generated check scripts: they look for evidence of a violation and report compliance when they find none, so run against a commit that touches nothing relevant they pass (§3.5.1).
- claim: without an applicability filter "every adherence figure" would be inflated by "empty compliance"; the filter used here (file extensions and basenames taken from the script's own fixtures) is "a methodological necessity" (§3.5.1).
- evidence: 2,569 of the 4,123 accepted scripts (62.3%) return True on a commit that touches no relevant files (§4.2.2). The filter matches by extension or basename, so any file of the right type counts as applicable even if unrelated to the instruction (§6). The unfiltered inflation is not measured.
- effect: hurts
- reader: E2, a count of one property of the scripts with no comparison of filtered against unfiltered rates. It matters for anyone who builds an instruction checker with a model: a check that returns True on irrelevant input is a hidden source of false assurance. The filter's residual leakage is acknowledged but not sized.

### F7 · practice · continuous-compliance-checks · E0
- practice: pair the context file with automated checks that run on every change and aim them at the categories and agents found least reliable, instead of spot-checking a few rules; calibrate the checks per agent (§5.4).
- claim: spot-checking "is a poor substitute for systematic verification" because non-compliance sits in instructions that are essentially never followed; "reliability of ACF adherence may be better understood as a property of the ACF and agent together" (§5.4).
- evidence: no test of the recommendation. The argument rests on the 37.3% of never-followed instructions (F1) and the agent gap (F3), both of which the authors qualify.
- effect: helps
- reader: E0, an implication drawn by the authors; no intervention was run. The bimodal shape it relies on rests on a median of 3 commits per instruction.

### F8 · practice · enforce-conventions-in-tooling · E0
- practice: encode workflow conventions such as commit message format and branching discipline in commit hooks, branch-protection rules or CI configuration, instead of context-file prose (§5.3).
- claim: Development Process guidance is "plausibly the kind of guidance that natural-language phrasing in an ACF is least suited to carry reliably"; "a direction worth checking further, not a settled recommendation" (§5.3).
- evidence: rests on the Development Process compliance mean of 34.0% (median 0.0%, 50 instructions), a gap that does not survive the sensitivity check (F2, §4.3.3). No tooling was tested.
- effect: helps
- reader: E0 and the authors say it is tentative. Listed because it matches an operator-side practice (enforcement outside the prompt) and the paper gives no evidence for or against that practice.

### F9 · practice · explicit-actionable-instruction-wording · E0
- practice: write one concrete, imperative, artifact-checkable behaviour per rule; avoid qualifiers such as "when appropriate" or "if needed" and process-only directives whose execution leaves no trace; vendors flag non-observable instructions when the file is authored (§5.3).
- claim: this closes the gap between documentation-like and agent-directed text (§5.3).
- evidence: no test of the wording rules. The motivation is the funnel in F4: 30.7% of candidates not explicit and 15.5% of explicit ones not actionable (§4.1.1; the 15.5% is the paper's, matching 10,324 to 8,726).
- effect: helps
- reader: E0. The paper never compares compliance for instructions that differ in wording; its explicit, actionable and observable labels are inputs to which instructions are checked, not variables tested against compliance.

## Limits stated by the authors

- No counterfactual: agents are never observed without the instruction, so compliance may reflect ecosystem or model defaults; a full ablation is out of scope (§6).
- Scripts see full before and after file contents but no line-level diff, so pre-existing violations may be charged to the agent and pre-existing compliant content may hide a violation (§3.5.2, §6).
- Compliance is binary; partial adherence is not captured (§6).
- 71.3% of accepted scripts were judged correct; hardcoded examples bias compliance down and permissive defaults bias it up, net effect "cannot quantify" (§4.2.2, §6).
- Annotation and script generation used local open-weight models (Qwen 3.5 9B, Qwen2.5-Coder-14B) and validation was by one annotator; cross-model agreement on the observable label was 76.1% (§6).
- Agent attribution comes from heuristic signals; the strict subset is likely imbalanced across agents; the agent comparison does not control for category mix (§6).
- Three agents only, public GitHub repositories only, a snapshot in time (§6).
- The RQ3 results describe only the operationalizable subset: 2,053 of 6,552 observable instructions (31.3%) were ever checked (§4.2 answer, §4.3.1).

## Reader's notes

- "Compliance" is agreement with a script a 14-billion-parameter model wrote from a 9-billion-parameter model's paraphrase of the instruction. Both steps were checked on small samples by one author (84 snapshots, 94 scripts). A 100% rate means the script saw no violation in file contents, not that the agent read the instruction.
- The "agent" in F3 is the kind of context file an instruction came from; the paper moves between "Copilot instructions" and "Copilot-authored commits" for the same grouping. Whether the commit-author tool matches the context-file tool in every case is not stated in the parts read.
- The commit corpus is AIDev's, so commits are often pull-request work opened by agent products; no model versions, no dates and no task descriptions are given, so the data window is `not stated`.
- Unit of analysis is the instruction with its own compliance rate. Instructions from one file share repository and agent, and the authors aggregate to avoid counting commits twice but do not model repository clustering.
- The paper never compares a repository's compliance before and after an instruction was added, which would be the cheapest quasi-control with this data.
- Its relation to 2602.11988: that paper measures task success and tool use with and without a file; this one measures per-instruction presence in artifacts with no without-file arm. They do not test the same outcome.
- The result sections are not independent of each other for a reader: F1 to F3 depend on F5's 71.3% correct scripts and on F6's filter.

## Discrepancies

- §4.2.2 says 997 exclusions (41.1%) had no corroborating script; Table 7 gives 41.0% for the same row. 997 of 2,429 is 41.05% (reader's arithmetic); trivial rounding.
- §3.2.1 gives 676 unique snapshots over 10,763 commits and 307 repositories; §1 and §3.3 use 621 snapshots, and 6,541 commits in 268 repositories. §3.3 and §3.2.3 explain the steps (empty and malformed snapshots removed; commits without context or file data removed), so this is a change of population between stages, not a contradiction. Noted because the 10,763 commits reappear in the weighting of Table 3.
- Otherwise none found in the parts read.
