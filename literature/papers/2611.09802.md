## Question

When a line in an agent instruction file goes stale (a path or command that a later code change
made wrong), what leads the agent to act on it, what does it cost in tool calls and tokens, and how
does the agent recover (§I, RQ1 to RQ3)?

## Findings

### F1 · practice · stale-instruction-line · E4
- practice: leave a real stale line in the instruction file (stale) against the same line corrected to the new path (corrected); code, task, model and harness fixed; the agent gets the bug report only and loads the file through Claude Code itself (§III-D).
- claim: agents take the stale path when the task leads through what the line names and offers no other starting point: "always for the test command, mostly for the procedure ... and never for the code location" (§IV, answer to RQ1).
- evidence: runs that ran, read or wrote the stale path, stale condition, both models: Command case 78 of 80, Procedure case 55 of 80, Location case 0 of 84; corrected condition 0 in every case (Table II). Holm-corrected p = 2 × 10^-28 (Haiku) and 2 × 10^-33 (Sonnet), stale against corrected over all three cases (§IV, Table II caption).
- effect: hurts
- reader: E4 as an equal-task contrast with one factor changed. The outcome is use of the stale path, which the authors' own detector measures; the detector missed relative paths after a change of directory and was fixed after the protocol, changing 19 Sonnet runs in the Procedure case (§VI). Only three cases, so line kind, repository and tasks vary together (§VI).

### F2 · practice · stale-instruction-line · E4
- practice: as F1; the outcome is whether the bug is fixed, graded by restoring the original tests and running the target tests and the suite offline (§III-D).
- claim: "Agents fixed the bug in nearly every run under every condition"; "task success did not change, so an evaluation that checks only the outcome does not see the cost" (§IV, RQ2).
- evidence: fixed runs, stale against corrected against removed, both models: Command 79 of 80 in each; Location 84 of 84 in each; Procedure 79, 77 and 79 of 80 (Table II). p = 1.0 for both models (§IV). In four Command tasks all 15 Sonnet runs across the three conditions produced the same patch byte for byte (§IV, §V).
- effect: none
- reader: the tasks are small seeded bugs that the repository's own tests catch (§VI), so a ceiling near 100% leaves no room for a difference in success. The grader is the repository's tests; quality outside them is not scored.

### F3 · practice · stale-instruction-line · E4
- practice: as F1; the outcome is tool calls and tokens per task, as per-task medians averaged over the case's tasks, with bootstrap intervals (§III-D, Table II).
- claim: the stale line cost "a few tool calls each time an agent met it, measurably only for Sonnet on the test command (about two calls per run, a third more than with the corrected line; exploratory)" (§IV, answer to RQ2).
- evidence: Sonnet, Command case, stale against corrected: 7.8 against 5.8 tool calls, stale median higher in 7 of 8 tasks; tokens 195k against 152k, not significant (§IV, Table II). The 95% interval excludes zero but not after correction for the number of estimates (§IV). Haiku, Command case: 16.0 stale against 18.2 corrected calls, from 18 fewer to 9 more calls per task, no difference resolved (Table II, §IV). Procedure case with a broad report: about 2 calls per task (2.25 Haiku, 2.0 Sonnet), with a named function 0.0 and 0.25 (§IV). Location case: 6.1 stale against 6.3 corrected calls, both models (Table II). Single example in Fig. 1: 6 calls and 120k tokens stale against 4 calls and 78k corrected, Sonnet.
- effect: hurts
- reader: the one resolved difference is a single model on a single case and is labelled exploratory by the authors; the cost is "none detected" elsewhere, and "none detected" is not "none". Fig. 1 is the task whose runs varied least, chosen by the authors, so it illustrates and does not estimate. The cost measured is one encounter; how often tasks reach a line is not measured (§V).

### F4 · practice · empty-test-run-reported-as-success · E4
- practice: the stale test command points to a folder that no longer exists; the agent runs it and the check of its fix runs no tests (§IV, RQ2).
- claim: the stale test command "failed quietly": the call reads as a success, so the fix is checked by nothing (§IV, RQ2).
- evidence: in 64 of the 80 stale Command runs at least one call on the stale path ran no tests; Claude Code flagged none as an error, because every run piped output through tail or head. In 19 of Sonnet's 40 stale runs the first check of the fix ran no tests, against none of its 40 corrected runs. Haiku hid the message with 2>/dev/null in 16 of its 38 runs on the stale path (§IV).
- effect: hurts
- reader: the 19 of 40 against 0 of 40 is a controlled contrast; the piping and redirection are the agents' own choices under the stale line, not an assigned condition. The agents recovered and the bug was fixed in 79 of 80 stale runs (Table II), so the measured harm is a check that tested nothing, with no harm to the final patch in these tasks.

### F5 · practice · correct-stale-instruction-line · E4
- practice: repair the line by changing the path to the location the code moved to, in every instruction file that mentions it (§III-D).
- claim: "correct the line rather than delete it": "only correcting it removed all of it" (§V, maintainers).
- evidence: stale path in 0 of 80 runs in the Command case, 0 of 80 in the Procedure case, 0 of 84 in the Location case with the corrected line (Table II), against 78 and 55 with the stale line and 1 and 20 with the line removed (§V). Sonnet Command: 5.8 calls corrected, 7.8 stale and 7.8 removed (Table II); Fig. 5 medians for the same runs 5 corrected, 6 stale, 5 removed calls.
- effect: helps
- reader: the contrast is controlled, but the corrected line is also the condition with the most information given to the agent; the paper does not measure the maintainer's effort of either repair (§V). The Command-case effort figure is one model (see F3).

### F6 · practice · delete-stale-instruction-line · E4
- practice: delete the stale line and keep the rest of the file (§III-D).
- claim: "Deleting a stale line removed most of its effect, but only correcting it removed all of it"; deleting also "kept the effort cost where the line was needed" (§V).
- evidence: with the line removed, stale path used in 1 of 80 Command runs and 20 of 80 Procedure runs, all 20 with a broad report (guessed an agents folder inside the core crate from the code's structure; Haiku 13, Sonnet 7 of 40), against 78 and 55 stale (§IV, §V, Table II). Sonnet Command: 7.8 calls removed, same as stale, against 5.8 corrected (Table II, §V). Fig. 1 example: removed 5 calls and 100k tokens against stale 6 and 120k.
- effect: mixed
- reader: better than stale on stale-path use, no better than stale on effort in the one case where effort was resolved; the effort side is one model and one case. A removed line also removes true guidance the other conditions keep, which is the point of the contrast.

### F7 · observation · task-reach-of-stale-line · E3
- practice: nobody assigned this: the same stale lines are met or not depending on the task and the kind of bug report; the Location case was chosen as a contrast whose tasks never need the file the line names (§III-C).
- claim: "Whether agents used a stale line thus depended on the task more than on the line itself" (§I, §IV).
- evidence: Procedure case, broad report: stale folder used in 20 of 20 Haiku and 19 of 20 Sonnet runs; report that names the function: 4 of 20 Haiku and 12 of 20 Sonnet runs (§IV). Location case 0 of 84 (Table II). Sonnet searched the stale folder in 12 of 20 runs although the report named the function's correct module (§IV, §V).
- effect: mixed
- reader: report type is tied to the task and not randomised, as the authors say (§IV); line kind, repository and task also vary together, so the comparison between cases is confounded (§VI). The authors expect the interest to be largest on steps most tasks share, such as the test command; this is a hypothesis (§V).

### F8 · observation · unattributed-stale-path-use · E2
- practice: nobody assigned this: how the agents reached the stale path and whether they said where it came from (§IV).
- claim: "They took the path silently from the loaded file"; a reader of the trajectory cannot tell that the instruction file misled the agent (§IV, §V).
- evidence: before the first stale call agents cited the instruction file in 2 of 133 runs that used the stale path and opened it in none. Sonnet copied the documented test command whole in 35 of its 40 Command runs (§IV).
- effect: hurts
- reader: counts from the authors' coding of transcripts with fixed rules; the coding is not checked by a second coder in the text read. The file is loaded by Claude Code at session start, so not opening it is expected; the finding is about attribution, not about reading.

### F9 · observation · stale-line-not-surfaced-or-repaired · E2
- practice: nobody assigned this: what the agent did after it operated on the stale path, in the stale condition only (§IV, RQ3, Table III).
- claim: "Operational recovery therefore removed the immediate blockage without repaying the documentation debt" (§IV, RQ3).
- evidence: 133 encounters (Command: Haiku 38, Sonnet 40; Procedure: Haiku 24, Sonnet 31). Reached the current target in 130 of 133, 98 of them through search, median 2 calls after the first stale operation. Final response identified the studied mismatch in 21 of 133 (Sonnet Command 17 of 40, Haiku Command 3 of 38, Haiku Procedure 1 of 24, Sonnet Procedure 0 of 31). Suggested repair 0 of 133. No instruction file edited in any of the 732 runs (Table III, §IV).
- effect: mixed
- reader: recovery on the task is good and the maintenance signal is absent. The tasks asked for a code fix, not documentation upkeep, so the authors state this is what agents do by default, not what they would do if asked (§V). The sequences include only runs that took the stale path and are not causal estimates of net cost (§IV).

### F10 · observation · model-differences-in-stale-line-cost · E3
- practice: nobody assigned this: the same stale lines run under Haiku 5.5 and Sonnet 5.5 (§III-D).
- claim: "A cost measured with one model therefore says little about another" (§V).
- evidence: both followed the stale lines at similar rates (Command: Haiku 38 of 40, Sonnet 40 of 40 stale runs; Table II). Sonnet's runs were short and consistent, so its extra calls on the test command could be measured; Haiku's runs varied from 18 fewer to 9 more calls per task, with no difference resolved (§IV, §V). Sonnet named the stale test folder in 17 of its 20 runs with a named-function report and in none of 20 with a broad report; Haiku in 3 of 38 Command runs (§IV).
- effect: mixed
- reader: two models of one vendor in one harness; model differences are confounded with run-length variance, which is what limited the Haiku comparison. The two models differ in size, and the paper does not separate size from model family.

### F11 · practice · stale-path-check-in-harness · E0
- practice: four safeguards, none evaluated: a harness flags paths in a loaded instruction file that do not exist; the shell sets pipefail; the agent treats "no tests ran" as a failure; an agent that works around a missing path says so in its summary and proposes the one-line fix (§V, agent and tool builders).
- claim: "Unlike a stale convention, a stale path can be detected without deciding whether the file or the code is right" (§V).
- evidence: no data; the authors write "none of which we evaluated" and did not measure the effort of either repair (§V).
- effect: helps
- reader: asserted as a design direction. The first safeguard is cheap to build, and pipefail does not help when the agent hides the error itself (Haiku, F4).

## Limits stated by the authors

- Three cases: line kind, repository and tasks vary together, so their separate effects cannot be told apart; the kind of instruction "remains a hypothesis for larger studies" (§V, §VI).
- Most tasks are small seeded defects; harder maintenance work may show different costs (§VI).
- The 732 runs repeat three cases and are not independent samples of debt; per-task estimates are imprecise; the tool-call and token differences are exploratory (§VI, §IV).
- Two models from one vendor, one harness, three cases of stale context, 22 tasks; the findings are about these cases, not general rates (§VI).
- The measured interest is the cost of one encounter, not how often tasks reach a line; the effort of repairing the file is not measured (§V).
- The tasks asked for a code fix, so not editing the file is the default, not a refusal (§V).
- The case search found cases and does not count them; it covers a small sample of repositories (§III-A).
- Stale-path detector bug found after the protocol was fixed, corrected, and both results are in the package (§VI).

## Reader's notes

- The authors chose and built the cases, the tasks and the coding rules, and the trajectory coding is theirs. Two coding agents (Claude and Codex) confirmed which lines presented the path as current (§III-A). The text read gives no second human coder and no agreement figure for the coding of transcripts.
- The Claude models run the agents and the authors use Claude agents to review candidate lines. The study evaluates a product the authors neither sell nor built.
- §III-D says failed runs "were repeated from scratch", while Table II lists runs not fixed (for example 39 of 40 Haiku Command runs). The text does not say how a failed run differs from an unfixed one.
- The stale lines are one-line path changes. Stale conventions, the kind studied by 2610.30571 and 2608.16630, are not covered; they produce worse code, and stale paths produce wasted work (§I).
- Table II calls and tokens are medians per task averaged over tasks, so the "both models" columns are not sums of the model columns. The 10.2 against 9.6 calls for the Command case (stale against corrected, both models) is below the difference in the Sonnet column, because Haiku shows the opposite sign (Table II).
- No cost in dollars is given; tokens include cached input.

## Discrepancies

- §I says that "as Fig. 1 shows, Sonnet needed as many tool calls without the test command as with the stale one". Fig. 1 shows 5 calls (removed) against 6 (stale). Table II gives 7.8 against 7.8 over the Sonnet Command tasks; the Fig. 5 medians are 5 against 6.
- §IV states fixed in "nearly every run" and §III-D that failed runs were repeated; Table II still has unfixed runs (see Reader's notes).
