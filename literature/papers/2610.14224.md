## Question

Can recursive self-improvement of an agent's harness work without ground-truth verifiers on tasks
unseen at design time, improving both the harness for the current task and the way later harnesses
are improved (§1)?

## Findings

### F1 · practice · per-task-harness-refinement-by-contrast · E4
- practice: for each task, run the stock harness once as a reference, let an editor model (Claude Opus 4.8) propose two edited harnesses (an invariant one for planning, tool use, context and delegation, and a domain one), run both on the same task, compare their trajectories and deliverables with the reference, and compose a successor harness from the supported edits. The 8 editable components are files: system prompt, guardrails, memory, skills, tool guidance, scripts, subagents, middleware plugin. No ground-truth answer or score is shown to any model; the improvement library starts empty per benchmark (§2.2, §3.1, D.1, D.2). One step, k=1.
- claim: "a single step consistently improves GLM-5 and Gemini 3.5 Flash over their base harnesses" on all three benchmarks in all four configurations (abstract, §3.2).
- evidence: Table 1, WorkBuddy-Bench average, base harness against one step: Gemini 3.5 Flash/OpenCode 72.4 to 77.5, Gemini/Codex 74.5 to 77.5, GLM-5/OpenCode 64.2 to 75.7, GLM-5/Codex 64.4 to 75.3. Table 2, JobBench: 31.5 to 36.0, 33.9 to 35.3, 20.6 to 24.2, 23.6 to 24.8. LAB Partial: 79.9 to 81.9, 71.6 to 75.6, 59.6 to 71.4, 58.1 to 65.9. Standard deviations over 3 runs of the Harness2 WorkBuddy average: 2.5, 2.0, 2.2, 1.3 (Table 1). A GLM-5 harness after one step (75.7 and 75.3) exceeds the base Gemini scores (72.4 and 74.5) (§3.2).
- effect: helps
- reader: E4 as a base-harness against refined-harness comparison on the same test tasks, 3 runs. Confounds: the refined arm uses far more compute than the base (a reference run, 2 candidate runs, a composed run and editor sessions; the token totals are in Figure 6, figure only); the editor Claude Opus 4.8 is a stronger model than either executor and is also the JobBench judge (B), so the editor and the judge share a model; the 12 cells are all measured on authors' own system, `independent: false`. Several gains lie inside one standard deviation: JobBench Gemini/Codex +1.4 against SDs of 2.6 and 3.5, LAB Gemini/OpenCode +2.0. The ablation row "w/o library" (74.4, Table 3) is still above the base 72.4, so the per-task part alone carries about 2 points on that configuration (reader's arithmetic).

### F2 · practice · per-task-harness-refinement-by-contrast · E3
- practice: as F1; the measurement is the tool-call error rate and number of tool calls per task, Gemini 3.5 Flash under OpenCode at k=1 (E.4).
- claim: "Harness2 lowers the tool-error rate on every benchmark"; "refinement can improve performance without shortening execution" (Table 7 caption, E.4).
- evidence: Table 7, error rate base against refined: WorkBuddy-Bench 0.8% to 0.5%, JobBench 14.4% to 9.1%, LAB 2.0% to 1.6%. Tool calls per task: 20.0 to 17.8, 27.4 to 32.8 (up 19.7%), 20.8 to 25.2 (up 21.2%). Steps per task on the WorkBuddy-Bench average fall in 3 of 4 configurations, for example 25.4 to 21.9 for Gemini/OpenCode and rise from 13.5 to 13.7 for GLM-5/OpenCode (Table 1; the count of 3 of 4 is reader's arithmetic).
- effect: helps
- reader: the outcome here is tool reliability, not score; one configuration, no spread reported in Table 7. Same authors-own-system confound as F1.

### F3 · practice · harness-refinement-budget-scaling · E4
- practice: spend a larger exploration budget k on the same task: parallel (k reference runs, k invariant and k domain candidates, k independent composition sessions, then an agentic selector over anonymised deliverables) or sequential (k chained contrastive steps). Compared with best-of-k of the base harness, ReasoningBank and Harness Scaling at the same k (§2.2.2, §4, Appendix C).
- claim: both forms "improve monotonically as k increases from 1 to 5"; "increasing test-time exploration alone therefore does not ensure better performance"; Harness2 at k=2 beats every plotted baseline at k=5 (§4).
- evidence: parallel at k=5 adds 2.9 to 3.9 points on WorkBuddy-Bench, 3.0 to 4.2 on JobBench and 2.6 to 6.7 points on LAB Partial over one step (§3.2, Tables 1 and 2). Gemini 3.5 Flash/OpenCode: Code 76.5 to 80.8 and Office 79.5 to 83.4 as k goes from 1 to 5 (§4, Figure 5); gain over base from 4.5 to 7.5 on JobBench and 5.1 to 8.4 on WorkBuddy-Bench (§4, Figure 6). Harness Scaling falls from k=2 to k=3 on both plotted domains; ReasoningBank fluctuates. Parallel ends above sequential at k=5, sequential is higher on Code at k=2 (§4).
- effect: helps
- reader: the curves are in Figure 5 and the best-of-k values are in the figure only; the text gives the end points. Cost rises with k (stated in F, Limitations) and the compute axis is in Figure 6 only. Two domains plotted for the budget study.

### F4 · practice · improvement-library-of-adopted-harnesses · E4
- practice: after each task, keep the adopted harness and an EXPERIENCE.md (situation, lessons, evidence) in a library that later tasks' proposals can read and adapt; ablation "w/o library" improves each task as before but neither reads nor writes the library (§2.3, §4, D.2).
- claim: "All three components contribute to performance" (§4); the library lowers the score when removed.
- evidence: Table 3, Gemini 3.5 Flash/OpenCode, k=1: WorkBuddy-Bench average 77.5 with the library against 74.4 without (minus 3.1), JobBench 36.0 against 34.2 (minus 1.8).
- effect: helps
- reader: E4 as an ablation on equal tasks. One configuration, 3 runs; the JobBench loss of 1.8 is smaller than the SD of the full system on JobBench Gemini/OpenCode (2.3, Table 2). Library entries are full executable harness trees, not prose (D.2), so this does not test a prose-only memory.

### F5 · practice · invariant-and-domain-scoped-harness-candidates · E4
- practice: draft one candidate edit about general agent deficiencies (planning, tool use, context management, delegation) and one about the domain's knowledge and constraints, each by its own editor role; ablation "w/o scoping" uses two generic editors drafting the same number of candidates from the same evidence (§2.2.1, §4).
- claim: scoped editor roles contribute to performance (§4).
- evidence: Table 3, Gemini 3.5 Flash/OpenCode, k=1: WorkBuddy-Bench 74.6 against 77.5 (minus 2.9), JobBench 32.3 against 36.0 (minus 3.7).
- effect: helps
- reader: E4 by ablation. Single configuration. The generic editors may differ from the scoped ones in prompt length and wording as well as in scope; the prompts are in Appendix H, not read.

### F6 · practice · composition-of-probed-harness-candidates · E4
- practice: merge, revise or choose among the probed candidate harnesses in a composition step, each decision tied to an observed contrast; ablation "w/o composition" probes both candidates and returns whichever the evidence favours (§2.2.1, §4).
- claim: composition contributes to performance (§4).
- evidence: Table 3, Gemini 3.5 Flash/OpenCode, k=1: WorkBuddy-Bench 75.9 against 77.5 (minus 1.6), JobBench 34.1 against 36.0 (minus 1.9).
- effect: helps
- reader: E4 by ablation; the smallest of the three ablation losses and inside one SD of the full system on JobBench (2.3). Single configuration.

### F7 · practice · harness-edit-without-execution-evidence · E4
- practice: let the editor refine the base harness directly, with no reference executions, no candidate probes and no improvement library (§4, Figure 7 left).
- claim: "directly refining the base execution harness without access to reference executions, candidate probes, or the improvement library degrades performance on Code and Web" (§4).
- evidence: Code 73.4 to 63.2, Web 69.9 to 65.0 (§4, Figure 7). A library accumulated at k=1 "restores base performance".
- effect: hurts
- reader: E4 as a with-and-without comparison against the base. The base values equal the Gemini 3.5 Flash/OpenCode row of Table 1, so that is the configuration, though the text does not name it. The Office value is in the figure only. This shows that edits not checked by running them can be harmful; it does not separate the effect of the probe from the effect of the reference run.

### F8 · practice · library-from-larger-budget-and-other-benchmark · E3
- practice: reuse a library accumulated under a larger recursion budget (k=5), or one built on JobBench, to refine one step on WorkBuddy-Bench without further probing; also re-run each task with its own library entry removed from the completed library (§4, E.2).
- claim: "Greater task-level exploration thus benefits subsequent harnessing without further probing" and a library "transferred from JobBench improves performance on WorkBuddy-Bench" (§1, §4).
- evidence: k=5 library gains over the base of 0.9 (Code), 4.4 (Web), 5.1 (Office) (§4, Figure 7 left). JobBench library, one-step WorkBuddy-Bench: +0.6, +0.5, +2.9 (Figure 7 right). Leave-one-out re-run: WorkBuddy-Bench 77.5 to 79.4, JobBench 36.0 to 37.7 (E.2, Figure 11). Library provenance in 22% of modified files on LAB and WB-office and 47% on JobBench; 2% to 10% of modified files keep at least half their lines from an entry (E.2, Figure 10).
- effect: helps
- reader: E3, no randomised control. The transfer gains of 0.6 and 0.5 and the Code gain of 0.9 are below the per-domain SDs of 1.3 to 4.5 in Table 1. The authors say the leave-one-out run uses later tasks' experience, is "offline" and that repeated execution may contribute to the difference (E.2).

### F9 · practice · skills-and-scripts-in-evolved-harness · E4
- practice: remove the prompt-related components, the skills or the scripts from the already improved harness (full k=5) and re-evaluate without rerunning improvement (E.1).
- claim: "the full harness outperforms every ablation in all three domains"; skills contribute most on Code and Web, scripts most on Office (E.1).
- evidence: Table 6, WorkBuddy-Bench, Gemini 3.5 Flash/OpenCode: full 80.8 average; without prompt group 79.3, without skills 75.5, without scripts 77.1; base 72.4. Losses by domain: skills 3.6 (Code) and 6.9 (Web), scripts 7.4 (Office). "Every ablated harness still exceeds the base"; the authors say additive effects are not established.
- effect: helps
- reader: E4 by component removal on equal tasks. The middleware plugin, subagents, guardrails and memory components were not ablated, so nothing here says whether enforcement hooks matter. Skills and scripts account for roughly half the edits on every benchmark (E.2), so the large loss partly reflects how many edits land there.

### F10 · practice · harness-transfer-across-executor-models · E3
- practice: take the harness refined for Gemini 3.5 Flash under OpenCode and run it unchanged on other executors (E.3).
- claim: "adopted harnesses can transfer across models, although the benefit varies substantially with the executor and domain" (E.3).
- evidence: Figure 12, against each executor's own base harness, WorkBuddy-Bench: GLM-5 +17.3 on Code (58.5 to 75.8); Gemini 3.7 Flash +0.3 on Code and +6.4 on Office; Claude Opus 4.8 +2.6 and +1.1.
- effect: helps
- reader: E3; the number of runs and the spread are not given in the text for Figure 12. The weakest executor gains most; the strongest gains least, which matches the gain pattern in §3.2. Only Code and Office reported.

### F11 · practice · same-model-as-harness-editor · E3
- practice: use the same model as executor and as harness editor, OpenCode, k=2 (§4, Figure 8).
- claim: "harness refinement need not rely on a stronger editor"; "All five models, from GLM-5 to Claude Opus 5, improve on every benchmark" (§4).
- evidence: Opus 5 gains 3.3 on WorkBuddy-Bench, 5.5 on JobBench and 3.0 on LAB; GLM-5 gains 13.7 on LAB (§4). The other gains are in Figure 8 only.
- effect: helps
- reader: E3. The comparison is base harness against refined harness for each model, not same-model editor against stronger editor on equal tasks, so what is shown is that gains persist, not how large they are against a stronger editor. Spread and run count not given in the text.

### F12 · practice · offline-harness-search-on-training-split · E4
- practice: search harness code offline on a training split (10 iterations, 2 candidates per iteration, 3 replicates, margin 0.01) and deploy the best harness unchanged on the test stream (baseline Meta-Harness, §3.1, Appendix C).
- claim: Meta-Harness is the strongest baseline; Harness2 exceeds it on WorkBuddy-Bench average and JobBench in all four configurations, while on LAB Partial Meta-Harness leads for Gemini 3.5 Flash under Codex (§3.2).
- evidence: base harness against Meta-Harness, WorkBuddy-Bench average: 72.4 to 76.4, 74.5 to 73.3, 64.2 to 69.7, 64.4 to 74.2 (Table 1). JobBench: 31.5 to 35.8, 33.9 to 34.8, 20.6 to 20.9, 23.6 to 23.9. LAB Partial: 79.9 to 81.6, 71.6 to 76.5, 59.6 to 60.0, 58.1 to 59.0 (Table 2). Higher than the base in 11 of 12 pairs (reader's arithmetic).
- effect: helps
- reader: E4 on the same test tasks, 3 runs. The authors ran the baseline themselves with their own editor model and a search set of the training half (24 dev tasks for LAB), so its tuning is theirs. The gain over the base is under 1 point in 5 of the 8 JobBench and LAB pairs (reader's arithmetic).

### F13 · practice · retrieved-strategy-memory-in-context · E4
- practice: keep the harness fixed and prepend up to three distilled strategy items from the most similar past task in the same domain to the task prompt; the items come from an answer-free self-judge of earlier rollouts (baseline ReasoningBank, Appendix C).
- claim: "ReasoningBank falls as much as 6.6 points below the base harness on coding tasks" (§3.2).
- evidence: base harness against ReasoningBank, WorkBuddy-Bench average: 72.4 to 73.4, 74.5 to 72.5, 64.2 to 65.6, 64.4 to 64.1; GLM-5/Codex Code 56.8 to 50.2 (Table 1). JobBench: 31.5 to 30.8, 33.9 to 30.2, 20.6 to 20.7, 23.6 to 22.8. LAB: 79.9 to 77.3, 71.6 to 74.8, 59.6 to 71.3, 58.1 to 63.8 (Table 2). Higher than base in 6 of 12 pairs and lower in 6 of 12 (reader's arithmetic).
- effect: mixed
- reader: E4 as an A/B on equal tasks. The authors implemented this baseline with their own retrieval embedding and judge, so the result may not match the original system's. The large LAB gain for GLM-5/OpenCode (+11.7, reader's arithmetic) and the coding losses sit in the same method.

### F14 · practice · per-task-harness-revision-without-state · E4
- practice: revise the harness for each task in isolation from one base rollout and the revision session's own later rollouts, with no scope split, no aggregation, no library and no score seen (baseline Harness Scaling, Appendix C).
- claim: "Harness Scaling underperforms the base in seven of the twelve benchmark-configuration pairs" (§3.2).
- evidence: base harness against Harness Scaling, WorkBuddy-Bench average: 72.4 to 75.3, 74.5 to 73.8, 64.2 to 67.8, 64.4 to 62.9 (Table 1). JobBench: 31.5 to 32.9, 33.9 to 33.6, 20.6 to 19.3, 23.6 to 17.5. LAB: 79.9 to 78.9, 71.6 to 67.9, 59.6 to 67.8, 58.1 to 63.7 (Table 2). Lower in 7 of 12 pairs (reader's arithmetic, matches §3.2). Falls from k=2 to k=3 on both plotted domains (§4).
- effect: mixed
- reader: E4 as an A/B on equal tasks; a port by the authors of a reference implementation to their component set (Appendix C). F1 to F6 are the same pipeline with the missing parts added, but that gap is not a clean ablation, because the baseline also differs in loop structure.

### F15 · observation · blind-selection-takes-weaker-candidate · E1
- practice: the final selector chooses one deliverable from a pool of candidates without seeing scores; across 9 regressions below the reference, it chose a weaker candidate in 3 (E.6).
- claim: "selection can prefer a weaker candidate" (E.6).
- evidence: Figure 14, retrospective scores: WB-code, output scoring 55 chosen over one scoring 95 (96 to 55 against reference); LAB tax, 54 to 26, the selector ranked precision over coverage; WB-web, 100 to 70 on one static check. The scores are not available to the pipeline.
- effect: hurts
- reader: E1, three cases picked by the authors from a larger run, with no rate of selector error given. It marks where the pipeline loses the gain that F3 shows.

### F16 · observation · editor-written-check-shares-editor-assumption · E1
- practice: the editor writes both a rule or skill and the script that checks it; an incorrect premise in the edit is inherited by all candidates and the check passes it (E.6).
- claim: "an incorrect premise can propagate across candidates"; "A checker written by the editor cannot catch the editor's assumption" (E.6, Figure 14).
- evidence: Figure 14: WB-code header injection, an edit saying to keep key = name storage, all four candidates inherit it and score 42 (50 to 42), while one stock run scoring 83 had lowercased the keys; WB-code validator cache, the skill's own checker reported PASS 3 times, 75 to 64, 4 of 11 tests need an equivalent dict to hit the cache; LAB tax, a prior distilled from stock trajectories became a rule, 83 to 81. Losses of 2 to 11 points (E.6).
- effect: hurts
- reader: E1, three cases of nine. This is the self-verification problem in a small form: the same model proposes the edit and writes the check. It is described, with no rate.

### F17 · practice · process-guardrail-and-verification-script-from-failure-trace · E1
- practice: after reading a base trajectory that showed procedural failures (figures never reconciled across source files, outputs never reopened after writing), the editor added a guardrail file (inventory all inputs with a script, trace every figure to its source, reopen every produced file with a verification script before finishing), a skill for reconciliation and tool guidance for number formats (§4, Figure 9).
- claim: the failures were "procedural failures rather than knowledge gaps"; the composed harness "successfully cross-referenced the figures and restored the memo's missing sections" (§4).
- evidence: one JobBench task, Gemini 3.5 Flash/OpenCode: score 43.1 to 77.8. Component sizes: guardrails 1,464 B, verification script 3,881 B, skill 4,942 B, tool guidance 645 B (Figure 9). The composer kept all four edits.
- effect: helps
- reader: E1, one task chosen for the paper. The case is the paper's illustration of what the pipeline writes; the same figure family shows other cases (E.7, not read).

## Limits stated by the authors

- Recursive refinement needs additional executions and editor sessions; a larger budget adds inference cost; parallel sessions lower latency but not total computation; the trade-off is characterised over a bounded range of budgets (F, Limitations).
- Refinement relies on behavioural contrasts and model judgment, which are sensitive to execution variability and shared model biases; they do not guarantee correctness or that a change will transfer to another task (§2.2.1, F).
- The leave-one-out result is an offline reuse analysis, not an estimate of online gains (E.2).
- The component ablations do not establish additive effects (E.1).
- Future work: consolidate the library as it grows, revise outdated experience, choose the recursion form and budget per task (G).

## Reader's notes

- WorkBuddy-Bench is a Tencent benchmark and JobBench and LAB are third-party benchmarks, but the harness results and the baseline runs are the authors' own (App. C, "our"/"we port"). The Code domain of WorkBuddy-Bench is the only coding-agent task set here (80 tasks, 40 in the test half); the other domains are web, office and legal work.
- Editor, selector and baseline revisions all use Claude Opus 4.8, a model stronger than the executors; the JobBench rubric judge is also Opus 4.8, and the WorkBuddy-Bench judge items use Gemini 3.5 Flash, one of the two executors (B). A rubric or verdict never reaches the editor (D.2), but a shared model family between editor and judge is not ruled out as a source of gains.
- Test sets are small: 34 JobBench tasks, 100 LAB tasks, 25 to 40 WorkBuddy-Bench tasks per domain; reported SDs over 3 runs are 0.2 to 4.5, so many per-domain and per-benchmark differences under 2 points are within one SD.
- Gains are larger for the weaker executor (GLM-5) and the stock harness is nearly empty (always-on files empty, placeholders only, D.1), so the base is a low reference. In Figure 13 no fixed production harness leads on all domains; Claude Code is best on Code and Office, Codex on Web, and Harness2 from OpenCode at k=5 exceeds the best fixed harness by 4.6, 5.8 and 4.9 points (E.5, Figure 13). The authors note this uses extra test-time compute.
- The always-on files (AGENTS.md under Codex) start empty apart from the benchmark's instructions (D.1); the edits the pipeline writes are roughly half skills and scripts (E.2), so this is evidence about generated skills and scripts and not about a hand-written instruction file.
- The score is the benchmark's: hidden tests plus LLM or VLM judge items (WorkBuddy-Bench), a weighted rubric (JobBench), an LLM judge against criteria with no executable check (LAB). Judge crashes count as failures (Figure 14, WB-web 44 to 10).
- The pipeline runs the executor several times per task (reference, candidates, composed successor), while the base harness is scored from its own runs in the 3 streams. A best-of-k base harness is the only compute-matched comparison in the text, and its values are in Figure 5 only.
