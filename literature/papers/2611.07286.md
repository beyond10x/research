## Question

Which repository views, exposed to a coding agent as on-demand map tools, change retrieval behaviour,
task success, token use and latency, and on which kinds of task (abstract, §I)?

## Findings

### F1 · practice · repository-graph-exploration · E4
- practice: mount a repository-map MCP server (AST, call graph, dependencies, documentation, or all four merged) next to Claude Code's built-in Read, Edit, Write, Bash, Grep and Glob tools, and run fault localization on LinuxFLBench against the same agent with no map server (§III.B, §IV.B, §IV.C).
- claim: on fault localization "the code representations provide the clearest benefit": all five raise recall@10 and cut tokens (§V.A.a).
- evidence: Table III, 152 tasks, file recall@10 baseline 0.717 against AST 0.757, Callgraph 0.770, Deps 0.757, Docs 0.770, Hybrid 0.829. Average tokens baseline 1,008,163 against 610,910 (Hybrid) to 754,768 (AST), a reduction of 25% to 39% (§V.A.a). Baseline 8.4 reads, 6.0 greps and 9.5 shell calls per task against 0.3 to 1.1 reads, 0.0 greps and 0.3 to 1.7 shell calls with a map, plus 8.5 to 13.1 map calls (Table III). Recall@1 baseline 0.572; AST and Hybrid 0.526, Docs 0.586, others 0.572 (Table III; the text calls the differences "smaller and mixed").
- effect: helps
- reader: A/B on equal tasks, so E4. One run per task, no significance test, and a difference of 0.040 in recall@10 is 6 tasks of 152 (reader's arithmetic; Table VII shows the same net +6). The treatment arm also carries a usage steer toward the map tools that the baseline lacks (§IV.C, §VI), so the gain is not from the data structure alone. The authors built and evaluate these servers, so `independent: false`.

### F2 · practice · repository-graph-exploration · E4
- practice: as F1, on SWE-bench Pro program repair, where the measured outcomes are resolution rate and tokens (§V.A.b). On repair the arms also have a pre-tool-use hook that forces one map query before native reads (§VI).
- claim: "the efficiency win persists, but the accuracy effect largely vanishes"; every map cuts tokens by 17% to 26% and resolution "stays close to the baseline" (§V.A.b).
- evidence: Table IV, 253 tasks, resolved: baseline 49.0%, AST 50.6%, Callgraph 46.2%, Deps 49.4%, Docs 44.3%, Hybrid 50.6%. Tokens baseline 3,116,193; Callgraph 2,310,653 (-26%), Hybrid 2,590,046 (-17%). Native Read 12.7 per task against 7.6 to 8.7. Wall time 268.8 s against 193.7 to 209.1 s (Table IV, §V.A.b). The authors call the gains of AST, Hybrid and Deps "within noise".
- effect: helps
- reader: E4 by design (same tasks, no-map baseline), one run each, no test. The effect is on cost: resolution is 2.8 and 4.7 points below baseline for Callgraph and Docs (reader's arithmetic from Table IV), which the authors do not test. The forced first map query is a second difference between arms.

### F3 · practice · repository-graph-exploration · E4
- practice: as F1, on SecBench security patching, where the measured outcomes are patch-resolution rate and tokens (§V.A.d).
- claim: "Callgraph has the highest controlled patch-resolution rate in this sample"; the efficiency picture "is mixed" (§V.A.d).
- evidence: Table VI, 166 tasks, resolved: baseline 28.9%, Callgraph 34.3%, Deps 31.9%, Docs 31.3%, Hybrid 29.5%, AST 25.3%. Tokens baseline 683,774; Callgraph 614,360, Docs 697,763 (above baseline). Table VII: Callgraph 18 wins and 9 losses (net +9); AST 9 wins and 15 losses (net -6); for every map more instances use more tokens than fewer (for example Callgraph 79 fewer against 87 more).
- effect: mixed
- reader: E4 by design, one run per task. Callgraph's +5.4 points is 9 tasks of 166 (reader's arithmetic; Table VII net +9). The authors' own caveat is that small SecBench and SWT-bench differences "may reflect one-shot patch- or test-generation variance" (§VI). Better for one map, worse for another, so mixed.

### F4 · practice · repository-graph-exploration · E4
- practice: as F1, on SWT-bench test generation, where the measured outcomes are reproducing-test rate and tokens (§V.A.c).
- claim: "the success differences are small"; every map costs more tokens and time; the decisive step "is often writing the right assertion rather than finding the right code" (§V.A.c).
- evidence: Table V, 161 tasks, reproducing-test rate: baseline 44.7%, Hybrid 47.8%, Docs 47.2%, AST 45.3%, Deps 42.9%, Callgraph 37.9%. Tokens baseline 1,671,772 against 1,687,094 to 1,871,848. Table VII: net -11 (Callgraph) to +5 (Hybrid); fewer tokens than baseline on a majority of instances only for Callgraph (85 fewer, 76 more).
- effect: mixed
- reader: E4 by design, one run per task, no test. Two maps score higher, two lower; all cost more. The most likely reading is that the maps do not touch the limiting step, which is the authors' own interpretation, not a tested one.

### F5 · practice · repository-graph-exploration · E4
- practice: as F1; the measurement is end-to-end wall-clock time per task on each benchmark.
- claim: representation workflows "increase wall time" on fault localization, security patching and test generation; on program repair wall time falls (abstract, §V.A).
- evidence: average wall seconds, baseline against maps: LinuxFLBench 66.7 against 82.2 to 105.6 (Table III); SecBench 66.4 against 136.4 (Hybrid) to 290.4 (Docs) (Table VI); SWT-bench 161.4 against 170.1 to 201.1 (Table V); SWE-bench Pro 268.8 against 193.7 to 209.1 (Table IV).
- effect: mixed
- reader: E4 by design. Time is end-to-end including model latency and map-query round trips; the paper does not break it down. The index build before each run is not in these numbers (§VI lists map construction among omitted one-time costs). Higher in 3 of 4 benchmarks, lower in 1, so mixed.

### F6 · practice · hybrid-multi-relation-map · E4
- practice: merge the call, dependency and containment relations and the documentation into one map (Hybrid), against single-relation maps and the baseline (§III.A.e).
- claim: "hybrid is the safe default" for localization because it "combines all relation types", but it is not the best choice for security patching (§V.B.3).
- evidence: LinuxFLBench recall@10 0.829 against 0.757 to 0.770 for single-relation maps, 17 wins and 0 losses (Table III, Table VII). SecBench resolved 29.5% against Callgraph 34.3%; among 18 instances Callgraph resolved and Hybrid did not, Hybrid edited the same file in 14 and still failed (§V.B.3c). Hybrid had the largest token cost of the five on SWE-bench Pro (2,590,046) and SWT-bench (1,871,848), and its main more-token cause is "verbatim-source explosion" (27/35 on LinuxFLBench, 94/94 on SWT-bench; Table VIII).
- effect: mixed
- reader: the contrast is on equal tasks, so E4, but the 14 of 18 comes from authors reading trajectories and the explanation (more context made the execution flow less prominent) is a hypothesis ("This suggests"). One run per task.

### F7 · practice · relation-matched-code-view · E3
- practice: choose the map's relation to match the relation the task needs: containment for a fault the report names in a file, call edges for a fault in a caller or callee, import edges for a fault in a module cluster, documentation search for term-rich faults (§V.B, RQ2 takeaway).
- claim: "representations help when their relation matches the task bottleneck"; each single-relation map "fails when that relation is missing" (§V.B).
- evidence: Table VIII, wins and losses per map on LinuxFLBench from two authors' coding of paired trajectories: AST wins are report-named in-file faults 17/17 and its main loss is symptom not equal to root-cause file 7/11; Callgraph wins are call-reachable cross-file faults 17/17 and its main loss is neighbour drift 5/9; Deps wins 13/17 report names function or API, losses 9/11 architecture file outside the import cluster; Docs wins 17/17 terms in comments, losses 7/9 symptom-only crash. SecBench: Callgraph win category "flow localization" 9/18, loss "wrong/over-local sink" 4/9.
- effect: mixed
- reader: E3. The categories are the authors' judgement after reading the instances, derived separately per benchmark, and "describe common trajectory patterns, not causal proof" (§V.B.2). Only the instances that diverged from baseline were coded, and the counts per map are small (9 to 28 instances). No run was repeated, so some wins and losses are run variance.

### F8 · observation · map-read-displacement · E2
- practice: observed which trajectories used fewer tokens than the baseline when a map was available, and what the agent did instead of reading (§V.B.4).
- claim: fewer-token runs "are dominated by one mechanism": the map returns code bodies inline, the agent "treats them as already read" and skips source reads (§V.B.4).
- evidence: category "read displacement" in the fewer-token runs, Table VIII: LinuxFLBench AST 79/111, Callgraph 109/109, Deps 72/115, Docs 93/115, Hybrid 85/117; SWE-bench Pro AST 184/190, Callgraph 188/197, Deps 186/190, Docs 115/181, Hybrid 174/181; SWT-bench 100% for every map. One case: Docs on LinuxFLBench 16043 used 0.15 times the baseline tokens at equal accuracy (Figure 7).
- effect: helps
- reader: E2, a category count with no comparison; the category is assigned by two authors. It explains the F1 and F2 savings; it is not independent evidence of them. On SecBench the dominant fewer-token category is "abstention-cheapness" (54/75 for AST), a different mechanism.

### F9 · observation · map-query-overhead · E2
- practice: observed which trajectories used more tokens than the baseline when a map was available (§V.B.4).
- claim: the overspend comes "from unavoidable map overhead on easy cases or from too many, too large, or too noisy map calls" (§V.B.4).
- evidence: Table VIII, more-token categories: LinuxFLBench map overhead AST 30/41, Callgraph 34/43, Deps 32/37, Docs over-exploration 27/37, Hybrid verbatim-source explosion 27/35; SWE-bench Pro Deps "generic/popular symbol name" 51/63, Docs over-exploration 53/72, Hybrid verbatim-source explosion 44/72; SWT-bench Docs over-exploration 102/102, Hybrid 94/94. One case: Docs on LinuxFLBench 11391, a report that names the file, used 27.7 times the baseline tokens (Figure 7).
- effect: hurts
- reader: E2, category counts assigned by the authors. The cost is at the level of single instances; averages in Tables III to VI are net of savings and overhead.

### F10 · observation · correct-localization-wrong-patch · E2
- practice: observed why maps lose against the baseline on repair and test generation (§V.B.3).
- claim: on SWE-bench Pro "failures are often not navigation failures"; the dominant failure for every map is "correct localization, wrong patch"; on SWT-bench the decisive step "is authoring a discriminating assertion, not finding the repository neighborhood" (§V.B.3).
- evidence: Table VIII, dominant loss category: SWE-bench Pro AST 16/24, Callgraph 22/27, Deps 19/20, Docs 23/33, Hybrid 20/20; SWT-bench AST 24/26, Callgraph 27/29, Deps 27/28, Docs 19/21, Hybrid 22/23. Further failures no map handles: tree-wide find-and-replace, new-file creation, non-Python fix sites such as YAML or docker-compose (§V.B.3b).
- effect: none
- reader: E2, authors' coding of the instances that lost. It says maps leave the patch or assertion step untouched; the paper has no condition that changes that step, so it is an interpretation of why F2 and F4 show little success gain. Schema proposal P9 applies, because the finding has no direction.

### F11 · observation · single-run-outcome-variance · E2
- practice: observed how many task outcomes flip between the baseline and a map when each is run once (§V.B.3, §VI).
- claim: many wins and losses "reflect one-shot patch variance rather than a stable representation effect"; on SWT-bench the dominant win and loss category is the same for every map, a generated test that happens to reproduce or not (§V.B.3b, §V.B.3d).
- evidence: Table VII, SWE-bench Pro: AST 28 wins and 24 losses for a net of +4 on 253 tasks; Docs 21 wins and 33 losses. SWT-bench Table VIII: win category "test-variance win" AST 25/27, Callgraph 15/18, Deps 22/25, Docs 23/25, Hybrid 24/28. Each instance was run once per workflow (k=1) (§VI).
- effect: none
- reader: E2. The inference from win and loss counts to variance is the authors', made without repeat runs, so the share that is noise is not measured. It does show that net differences of a few points rest on 40 to 60 flipped instances. Schema proposal P9 applies.

## Limits stated by the authors

- Agent runs are not fully deterministic; each instance is run once per workflow (k=1), not pass@k; small success differences on SWT-bench and SecBench may be variance; close resolution rates are "descriptive" (§VI).
- The arms differ by more than the data structure: representation workflows add usage steering and, on repair, a pre-tool-use hook that forces one map query before native reads, so "behavior changes such as reduced native reads are not effects of the data structure alone" (§VI).
- One agent stack (Claude Code, Haiku 4.5) and four benchmarks; other models, agents, languages and repositories may differ (§VI).
- Benchmark success does not capture patch quality or developer usefulness; token and tool counts omit map construction, local compute, clone and Docker setup, grading and human costs; qualitative attribution needs judgement (§VI).

## Reader's notes

- No significance test, confidence interval or repeat run appears anywhere in the parts read; "within noise" in §V.A.b is a judgement. The sampling at 95% confidence and 5% margin sets the task count, not the precision of a difference between two workflows.
- The baseline lacks the steer toward map tools and, on repair, the forced first map query. A baseline with an equivalent prompt but no map, or a steer without the forced query, is not in the grid, so F1 to F5 measure "a map plus a map-first workflow" and not the map alone. The paper says this in §VI and still words the abstract and contributions as a controlled comparison of representations.
- The model runs at effort=low and is Haiku 4.5; a stronger model might search with raw tools more efficiently, or use the map better. Nothing in the paper tests this.
- The benchmarks differ in language (Python repositories use jedi and griffe; C and C++ repositories, such as the Linux kernel, get call names matched to definitions by name, §III.B), so call-graph quality differs between benchmarks and is not measured.
- The result tables carry no cost in dollars; the paper does not say whether cached input tokens are counted in "total token usage" (§IV.D).
- SecBench prompts often expose crash stack frames, which favours the call graph by construction (§V.B.3c states this).

## Discrepancies

- §III.B says the representation tools are "available alongside built-ins" and that only the representation-use steer differs from the baseline (§IV.C); §VI adds a pre-tool-use hook on repair that forces one map query before native reads. The hook is not described in the method.
- §V.A.a says representation agents use "9–13 map calls" on LinuxFLBench; Table III gives 8.5 for Deps and 13.1 for AST.
- The abstract and introduction say all five workflows "improve" fault localization; recall@1 in Table III is lower than baseline for AST and Hybrid (0.526 against 0.572), including Hybrid, the best on recall@10. The text notes the recall@1 differences as "smaller and mixed".
- §V.B.3c says Callgraph's SecBench advantage "is not just more information"; the same section reports Hybrid, which holds the call edges, edited the same file as Callgraph in 14 of 18 cases and failed, which the authors read as dilution. The reading is untested, and one-run variance (§VI) would produce the same counts.

## Leads

- ARISE, a repository-level graph and slicing toolset for agentic fault localization and repair (arXiv:2605.03117, cited §II.A).
- RepoRepair, hierarchical documentation for repository-level program repair (arXiv:2603.01048, §II.B).
- SWE-bench Pro, the repair benchmark used (arXiv:2509.16941).
- LocAgent, RepoGraph, OrcaLoca, AutoCodeRover and Agentless are cited as localization or graph-guided systems (§II); the text gives no arXiv id for them.
