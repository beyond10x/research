## Question

When a coding agent chooses the program structure, how many end-to-end behavioral specifications
(tests, examples) must a developer supply, and does supplying the structure itself as a code-like
"skeleton" (types, signatures, contracts, invariants) make the agent produce the intended program with
fewer of them (Abstract, §1)?

## Findings

### F1 · practice · code-like-skeleton-specification · E4
- practice: give the implementation agent a structural specification derived from the reference program (function stubs, then local contracts, then global invariants) in place of a behavioral one (task only, EARS behaviors, behavioral tests); the agent rebuilds the program without the reference (§4, App. A).
- claim: "no matter the format, behavioral specifications underperform compared to structural specifications"; the best skeleton cuts mean test error by 48.4% relative to the best end-to-end behavioral specification (§4.1, Abstract).
- evidence: SCBench mean pass rate 71.7% to 89.2%, SDDBench 29% to 74.2%; behavioral specifications gain at most 9.4 percentage points (§4.1, Figure 2). Function stubs alone raise SDDBench from 53% to 66.4% (§4.1). Pooled with ProgramBench, error 40.7% to 21.0% across 4 models (§4.1). 35 SCBench problems, 13 SDDBench libraries, 4 models (App. D).
- effect: helps
- reader: an assigned comparison of specification types on the same tasks and models, so E4. The skeleton is generated from the reference program, so it carries the names and signatures the hidden tests call; a behavioral specification does not. The gain partly measures interface agreement. No repeat runs, variance or test are stated.

### F2 · practice · code-like-skeleton-specification · E4
- practice: add a skeleton to an agent that can already query the oracle executable (a full behavioral specification) on ProgramBench; compared with the same setup without a skeleton (§4.1, Figure 10).
- claim: structure helps "even with perfect behavioral specifications"; the agent does not reach the skeleton's result by querying more (§4.1).
- evidence: mean pass rate 64.0% task only, 70.9% with local contracts (+10.9% relative), 73.7% with global invariants (error 36.0% to 26.3%, 27.0% relative) (§4.1, Figure 10). Oracle with no skeleton: the text says 61.5% of hidden tests pass (§4.1). 20 ProgramBench tasks, 4 models (App. D).
- effect: helps
- reader: E4 on equal tasks. In Figure 10, the prose Design (EARS) condition reaches 73.6%, about the same as global invariants and above signatures (71.7%) and local contracts (70.9%), so on this benchmark the gain is not specific to code-like form. Original code comments reach 63.3%, below task only.

### F3 · practice · behavioral-test-supply-without-structure · E4
- practice: give the agent a larger share of the tests (0, 33.3, 66.7, 100% of the available pool) or more curated observations (20, 40, 80, 160) with oracle access, and no skeleton (§4.1, App. D).
- claim: more tests help, but "on average no number of tests provided is enough to let the agent identify the correct program" (§4.1).
- evidence: no share of tests gives a program that passes the full hidden suite on average (§4.1, Figure 1 left; values in the figure only). For any number of curated observations up to 160, pass rate is lower than a skeleton with 20 observations (§4.1, Figure 6 right; values in the figure only). About 25% of the reference-passing tests were held out for scoring (App. D).
- effect: helps
- reader: effect is on pass rate, which rises with test supply; the finding is that it saturates below the skeleton. Test values are in figures only. The held-out tests are the same style as the supplied ones, so this does not show how a developer would write tests.

### F4 · practice · prose-architecture-document · E4
- practice: add progressively more architecture detail to a prose markdown specification (components, state, collaborations, repository layout, per-file sketches), compared with task only and with code-like skeletons (§4.1, App. A (ix)).
- claim: more architecture detail raises pass rate but "every architecture specification still remains below the best code-like specification" while expanding the input by roughly 4 to 7 times (§4.1).
- evidence: pass rate 61% to 71% on SCBench and 40.1% to 52.8% on SDDBench across the five nested versions (§4.1, Figure 6 left). 5 SCBench and 4 SDDBench repositories, 4 models (App. D).
- effect: helps
- reader: E4 within the nested versions; the comparison to the skeleton is across conditions on the same repositories. The prose versions and the skeletons carry different information as well as a different form, so form and content are not separated. Small repository sample.

### F5 · practice · small-model-with-detailed-skeleton · E3
- practice: give the smaller model GPT-5.6 Luna the "detailed global invariants" skeleton and compare its pass rate and implementation cost with GPT-5.6 Sol (§4.1, Figure 5).
- claim: skeletons "narrow the average gap between small and large models by about 52.4% while lowering implementation cost by 15-26x" (Abstract).
- evidence: Luna pass rate 67% to 90% on SCBench and 21.1% to 79.5% on SDDBench; within 5.0 to 8.2 percentage points of the best Sol results at about 15 times and 26 times lower implementation cost (§4.1). The 52.4% is not derived in the text read.
- effect: helps
- reader: the gain of Luna over its own task-only run is controlled, but the cross-model cost comparison is between models and not an ablation, so E3. Cost excludes specification generation and evaluation compute (App. D); who writes the detailed skeleton, and at what cost, is not counted.

### F6 · practice · overly-detailed-contracts · E4
- practice: add extra local and global contracts, correct but very detailed, to the best skeleton (§4.1, Figure 2).
- claim: "this reduces performance, especially on smaller models"; prompting a model with more specifications "need not approximate the Bayesian posterior" (§4.1).
- evidence: shown in Figure 2 only; no number in the text.
- effect: hurts
- reader: E4 by design (the same skeleton with and without the extra detail), but the size of the drop is not in the text. It sits next to F5, where the detailed global invariants give the best small-model result; the text does not say what "detailed" changes between the two.

### F7 · practice · skeleton-code-erosion · E4
- practice: give a structural specification and measure the erosion of the code the agent produces (share of cyclomatic-complexity mass in functions of complexity above 10), against task only (§4, §4.1, Figure 7).
- claim: structural specifications reduce erosion by up to 24.7%; behavioral specifications increase it; verbosity changes little (§4.1, Figure 7 caption).
- evidence: signature specifications lower erosion from 0.66 to 0.56 on SCBench and from 0.41 to 0.24 on SDDBench; behavioral specifications raise it to as much as 0.73 and 0.43 (§4.1). Verbosity is lowest under structural specifications on SDDBench only (§4.1).
- effect: helps
- reader: E4 on the same reconstructions. Erosion is one cyclomatic-complexity metric from SCBench; no review or maintainer rating of the code is given. The skeleton fixes function boundaries, which bounds complexity per function by construction.

### F8 · practice · agent-maintained-skeleton-in-repair · E4
- practice: in 8 rounds of iterative repair, ask the agent to maintain a skeleton alongside the code, carry code and skeleton into a fresh conversation each round, and disclose new failing tests between rounds; compared with a code-only workflow (§4.1, App. D).
- claim: "by round 8, the skeleton workflow reaches similar error rates with 32% fewer reference-binary calls", lower erosion and higher maintainability (§4.1).
- evidence: cumulative reference calls 2,341 without and 1,587 with skeletons (Figure 8; 32.2% fewer, reader's arithmetic). Model cost at least $823.19 without and $661.71 with (Figure 8). Erosion 0.890 and 0.840 (Figure 8). 20 ProgramBench task pairs, one model (Sol) (App. D).
- effect: helps
- reader: E4 on paired tasks, one model, no variance. Reference-binary calls stand in for a developer's clarification effort ("a proxy"); no human was involved. The error-rate curve is in the figure only.

### F9 · practice · partial-skeleton-coverage · E4
- practice: write contracts for only the 25, 50 or 75% most complex callables, and add per-folder descriptions to a directory sketch, against task only and the full skeleton (App. D, Figure 9).
- claim: "Providing additional coverage increases pass-rate"; per-folder descriptions on a directory sketch improve pass rates (Figure 9 caption).
- evidence: Figure 9 only, values in the figure only; full-skeleton means 94.62% on SCBench and 92.09% on SDDBench (Figure 9). Sol and Luna, 5 repositories per benchmark (App. D).
- effect: helps
- reader: E4 by design with nested coverage; the numbers are not in the text, so a reader cannot see how much of the gain the first 25% gives. The 94.62% and 92.09% differ from the Figure 2 means (89.2% and 74.2%) because the repository subset and models differ.

### F10 · practice · skeleton-reduces-required-tests · E0
- practice: fix the program structure (hypothesis class) in the specification so that behavioral tests select within it (§2).
- claim: skeletons "can reduce exponentially the number of tests developers must supply" (Abstract): two skeletons for one function need 2^d - 1 against d tests (Theorem 2.1); local tests at component interfaces need 4n against 2^n end-to-end (Theorem 2.2); behavioral tests cannot select among programs with the same behavior (Proposition 2.3).
- evidence: proofs on constructed examples (parity target, a chain of n one-bit stages), App. E. No measurement of how many tests a developer needs; the empirical sections do not vary test count against a developer's effort except Figure 1 left and Figure 6 right (F3).
- effect: helps
- reader: a formal argument on toy classes, with an assumed prior over programs. The paper says the exponential result "concerns exact behavioral identification and a specified prior" and is not a bound for every prior (App. E.2). Graded E0 because no data tests the exponential claim.

### F11 · practice · contract-bounded-parallel-implementation · E0
- practice: write complete pre- and post-conditions for each component so components can be implemented by independent agents in parallel (§2.4).
- claim: complete Hoare-style contracts make no compatibility tests needed, "independent agents can implement them in parallel with no risk of conflict", and each agent's task is simpler for a smaller model (§2.4).
- evidence: none given; the argument rests on Theorem 2.4. No experiment runs parallel agents on a skeleton.
- effect: helps
- reader: asserted. The experiments use informal docstring contracts that are not machine-checked (§5), so the condition of the argument (contracts that fully imply global correctness) is not met in the study.

## Limits stated by the authors

- The skeletons evaluated "are not machine-checked"; the formal checks and the rejection-sampling loop of §3 "remain a direction for future experiments" (§5).
- Test pass rate "measures agreement on the tested cases; passing a finite suite does not by itself establish membership in G" (§4).
- SDDBench anonymises the library names, which "does not completely rule out training-data contamination" (App. B).
- The exponential separation concerns exact identification under a specified prior, not every prior or prediction at fixed nonzero error (App. E.2).
- Pass rate "reflects both the information each specification carries and the agent's ability to use that information" (§4).

## Reader's notes

- All specifications are generated from the reference program by the authors' pipeline, then the agent rebuilds it. A real developer writes the skeleton before the code exists. The effort of writing a skeleton, and whether a developer can write one that matches what the hidden tests call, is not measured; the effort claims are about test counts (theory) and reference-binary calls (F8).
- The agents are four models run in the AI Functions framework on greenfield reconstruction, not a product coding agent on a repository with history. The tasks rebuild known open-source programs and libraries, so contamination applies to every condition.
- No repeat runs, confidence intervals or significance tests are stated in the parts read; differences of a few points (F2) cannot be judged.
- The authors propose the method and evaluate it on benchmark setups they configured (specification types, subsets, metrics); `independent` is false.
- On ProgramBench the prose Design (EARS) condition matches the code-like conditions (Figure 10: 73.6% against 71.7%, 70.9%, 73.7%), while the text's claim that code-like beats prose rests on Figure 2 and Figure 6 for SCBench and SDDBench.
- Code quality is measured by a complexity metric and a duplication metric; no human reads the code.
- Behavioral and structural conditions differ in information content as well as in kind: a signature fixes names and types the hidden tests use.

## Discrepancies

- §4.1 says that with the oracle executable the models "only pass 61.5% of the hidden tests"; the task-only baseline with oracle access in Figure 1 (middle) and Figure 10 is 64.0%. Not explained.
- The Abstract says erosion falls "by 24.7% on average"; the Figure 7 caption says "up to 24.7%". The §4.1 numbers give 0.66 to 0.56 (15%) and 0.41 to 0.24 (41%) (reader's arithmetic).
- SDDBench baselines differ without explanation: 29% (task only, §4.1), "from 53% to 66.4%" for function stubs (§4.1), 40.1% at the start of the architecture series (§4.1, Figure 6).
- Figure 2 and §4.1 say overly detailed contracts lower pass rate, especially on smaller models; §4.1 reports the best small-model result (Luna, 67% to 90% and 21.1% to 79.5%) with "detailed global invariants".
- The 52.4% gap narrowing in the Abstract is not derived anywhere in the text read.
