## Question

How often do AI coding agents change code in a pull request without updating any documentation
file, and is that associated with merge time, later same-file fixes and later documentation (§I)?

## Findings

### F1 · observation · agent-pr-documentation-co-change · E2
- practice: count agent PRs that change at least one code file and no documentation file ("drifted") against those that change both ("co-changed"); documentation means Markdown and text files, `docs/` files, README, LICENSE and CHANGELOG (§III-B).
- claim: "63.2% of AI-generated PRs change code without co-updating documentation" (Abstract, §IV-A).
- evidence: 18,751 of 29,669 PRs drifted (63.2%) and 10,918 co-changed (36.8%) (§IV-A). No human baseline: the authors "do not claim this rate is specific to agents" (§IV-A).
- effect: hurts
- reader: a share with nothing to compare against, so E2. The paper reports a prevalence and no outcome; `hurts` is the nearest closed value (the schema has no value for a distribution). The label counts any documentation file, so an unrelated CHANGELOG edit is co-change and an internal refactor that needs no documentation is drift (§V-A). Documentation outside the repository and inline comments count as drift (§V-A).

### F2 · observation · documentation-co-change-by-task-type · E3
- practice: compare the co-change share between PR task types labelled in the dataset (§III-B, Figure 1).
- claim: "co-change rates vary by task type"; agents "document additive work more than corrective or restructuring work" (§IV-A).
- evidence: co-change rate by task type, merged PRs with n >= 100: feature 44.8%, chore 43.9%, docs 43.2%, fix 23.2%, refactor 22.5% (§IV-A, Figure 1). Drift feature 55.2% against refactor 77.5% (Abstract). Within every agent, feature PRs co-change documentation 1.6 to 2.1 times as often as fix PRs (§IV-A).
- effect: mixed
- reader: a comparison between groups with no control for PR size or repository. The authors note that fixes and refactorings "may also less often need a documentation change" (§IV-A), so the lower rate is not shown to be a lapse. Bars are in the figure; the text gives the five rates.

### F3 · observation · documentation-co-change-by-agent · E3
- practice: compare the drift share between the five agents (§IV-A, Figure 2).
- claim: "Drift is widespread across agents rather than concentrated in one" (§IV-A).
- evidence: drift from 48.1% (Claude Code) to 72.8% (Devin), 65.3% without Codex (§IV-A). Codex is 65.8% of the PRs and Claude Code 1.4% (§V-A). Per-agent n other than these two shares is not in the text.
- effect: mixed
- reader: a comparison between groups, with agents working on different repositories and task mixes; no control for either. The agent range is wide and the sample per agent is very uneven. Model versions behind each agent are not stated.

### F4 · observation · documentation-co-change-and-later-fixes · E3
- practice: for each changed code file in a merged PR, record whether the PR also changed documentation, then whether a later merged bug-fix PR touched the same file within 30, 60 and 90 days; unit is the file, which holds exposure to PR size fixed (§III-C).
- claim: "undocumented files are followed by a same-file fix 8.6–11.7% more often than documented ones" (Abstract, §IV-B).
- evidence: probability of a later same-file fix, documented against drifted, Table III: 14.1% and 15.3% at 30 days (+8.6%), 14.8% and 16.5% at 60 (+11.3%), 14.9% and 16.6% at 90 (+11.7%), over 177,743 file-changes in 1,513 repositories. Drifted files have more later fixes in every per-file line-change bin below 50 lines, for example 15.6% against 11.9% for 1 to 5 lines (§IV-B). At PR level the sign reverses: 3.78 against 2.11 mean fixes within 30 days for co-changed against drifted PRs (+79%, p < 0.001), while co-changed PRs are 3.9 times larger, 24.83 against 6.43 files (Table II).
- effect: helps
- reader: E3, no control for task type, agent, repository workflow or prior churn (§V-A). Fix attribution is by file path and time, not by cause, and one fix is credited to every earlier PR that touched the file (§III-C). The file-level rates are descriptive with no test (§III-C). The gap is 1.2 to 1.7 points on a base of about 15%, and the PR-level result shows the sign depends on how size is handled. Windows near the data cutoff are censored (§III-C). `helps` is for documented against undocumented change.

### F5 · observation · documentation-co-change-and-merge-time · E3
- practice: compare time from PR creation to merge for co-changed against drifted merged PRs (§III-C, Table I).
- claim: "Documented changes merge faster despite being larger" (§IV-B).
- evidence: Table I, co-changed against drifted: median 40 s against 184 s, share merged within 5 minutes 67.3% against 55.9%, mean 17.8 h against 10.0 h, mean comments 0.98 against 1.03, mean review touches 1.94 against 1.76.
- effect: mixed
- reader: median and the 5-minute share favour co-changed PRs, the mean favours drifted ones, so `mixed`. The authors say most merges are automated, so time to merge is "a noisy proxy for the human effort" and its direction is "suggestive rather than conclusive" (§IV-B). No control for task type, agent or automation policy; their explanation (documentation clarifies intent) is untested (§IV-B).

### F6 · observation · undocumented-file-re-documentation · E3
- practice: follow each changed code file for 90 days and record whether a later PR touching it co-changes documentation, split by whether the original PR did (§III-C).
- claim: "Drift persists": a file changed without documentation is re-documented "at half the rate" of one changed with it (Abstract, §IV-C).
- evidence: 24.0% against 48.2% within 90 days (§IV-C, Figure 5). Odds ratio 3.2 (95% CI 2.20 to 4.69, p < 10^-9) with lines changed and agent controlled and errors clustered by repository. Within repositories (fixed effects, 487 repositories with both behaviours) documenting a file raises the probability of later documentation by 18.9 percentage points (95% CI 3.0 to 34.8, p = 0.02) (§IV-C).
- effect: helps
- reader: E3, with statistical control for size, agent and repository but not task type and no randomisation (§V-A). A later documentation change may concern other code, so it is not shown that the original gap was repaid (§III-C). The authors read both rates as lower bounds because of censoring (§IV-C). `helps` is for documenting at the time of the change.

### F7 · practice · prompt-agent-to-document-revisited-files · E0
- practice: prompt agents to document previously undocumented files that they revisit, not only the files they create (§V, Recommendations).
- claim: this would "repay accumulated debt" (§V).
- evidence: none; a recommendation. Not tested in the paper.
- effect: helps
- reader: E0, asserted from the F6 association. No agent was prompted in the study.

### F8 · practice · review-trigger-on-change-size · E0
- practice: trigger human review on change size (the example is more than 5 files), not on the presence of documentation, and treat drift as a risk signal (§V, Recommendations).
- claim: PR-level fix counts are confounded by size, and undocumented changes are more often followed by fixes (§V).
- evidence: none for the policy. The supporting numbers are the 3.9 times size gap and the sign reversal in F4 (Table II); the 5-file threshold has no data behind it in the text.
- effect: helps
- reader: E0 for the policy itself. No review rule was applied or compared in the study.

## Limits stated by the authors

- The label is the presence of any documentation file, not whether an update was needed, related or correct; inline comments, docstrings and out-of-repository documentation are invisible (§V-A).
- RQ2 does not control for task type, agent, repository workflow, automation policy, prior churn or change complexity; RQ3 does not control for task type (§V-A).
- Fix attribution is by file and time, not cause; defects may be older or from intervening PRs (§V-A).
- Right-censored follow-up near 4 August 2025 may bias comparisons (§V-A).
- AIDev is from December 2024 to August 2025, imbalanced (Codex 65.8%, Claude Code 1.4%), and RQ2 and RQ3 pool agents (§V-A).
- The human PR data has no file-level detail, so there is no human baseline (§V-A).

## Reader's notes

- The AIDev dataset spans agents run by many users on public repositories; whether a human or a bot merged each PR is not separated except through the 5-minute share (§III-C).
- All numbers on later fixes use only merged bug-fix PRs labelled `fix` by the dataset's task taxonomy (§III-B, §III-C), so unlabelled fixes are missed.
- No finding shows that an agent given a documentation instruction would document more or have fewer defects; the practice findings F7 and F8 are advice.
- The paper mixes populations: prevalence uses all 29,669 PRs, while Figure 1 and all later analyses use merged PRs only (§III-A, Figure 1 caption).
- Whether documentation presence is a cause of fewer fixes or a marker of a careful PR, agent or repository is open; the authors say so in §V.

## Discrepancies

- Table II gives fixes per file of 0.85 (co-changed) and 1.06 (drifted), but mean fixes divided by code files is 3.78 / 16.34 = 0.23 and 2.11 / 4.17 = 0.51 (reader's arithmetic); the paper does not define the column.
- Table III's 90-day excess is stated as +11.7%, while 16.6 / 14.9 is +11.4% (reader's arithmetic); the shown percentages are rounded.
- The abstract and §IV-A call the 63.2% rate over "AI PRs" and give task-type rates "(merged PRs)" in Figure 1, so the 63.2% and the task-type rates come from different PR sets (§III-A).
