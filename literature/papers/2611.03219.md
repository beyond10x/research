## Question

Can an agent harness that is evolved automatically from its own trajectories keep improving across
several task types (issue repair, test generation, feature implementation) without losing what it
gained on the earlier type (§1, RQ1), and which harness changes cause the loss (RQ2)?

## Findings

### F1 · practice · harness-self-evolution-single-task-type · E3
- practice: evolve the Mini-SWE-Agent harness (system prompt, control flow, tools) from its own trajectories with AHE (9 rounds) or Meta-Harness (5 rounds), on one dataset at a time; 2 rollouts per task per round, temperature 0 (§3.2, §3.4, Table 2).
- claim: "Both self-evolution methods demonstrate substantial performance improvements when evolving on a single dataset" (§4.1).
- evidence: SWE-Bench: 82.0% initial, 96.0% after nine AHE rounds, 94.0% for Meta-Harness. SWT-Bench: both methods from 82.0% to 100.0% on the sampled 50 tasks. FeatureBench: both gain more than 10 percentage points; AHE's best harness scores 30.0% (round 3). Other values in Figure 2 only (§4.1).
- effect: helps
- reader: before and after on the same sampled tasks with no control, so E3. Nothing in the text says the scored tasks differ from the 50, 50 and 30 tasks used for evolution (§3.1), so part of the gain may be fit to those tasks. 100.0% on SWT-Bench leaves no room above it.

### F2 · practice · sequential-harness-evolution-across-task-types · E3
- practice: take the best harness evolved on one dataset, keep evolving it on a second dataset of another task type, and score it on the first dataset again after 3 and 5 further rounds (§4.1, Figure 3).
- claim: "Existing self-evolution methods struggle to preserve previously acquired capabilities"; "almost every continual harness self-evolution direction results in substantial performance degradation on previously encountered tasks" (§4.1).
- evidence: SWE then SWT: relative drop on SWE-Bench of 100% (AHE) and 98% (Meta-Harness) after 5 rounds. SWE then Feature: 29% and 66%. Meta-Harness SWE-Bench 94.0% to 32.0% after FeatureBench evolution (abstract). Meta-Harness SWT-Bench 100.0% to 62.0% after FeatureBench (§1). The other directions are in Figure 3 only (§4.1).
- effect: hurts
- reader: the comparison is the same harness before and after more evolution on the same earlier tasks, with no run of the first harness left unevolved for the same number of rounds, so E3. One model, one run at temperature 0, two methods that the authors re-implemented because the public code did not support Mini-SWE-Agent (§3.3). Only two-stage sequences were run; the claim that longer sequences behave alike is asserted (§4.1).

### F3 · observation · task-type-distance-and-forgetting · E3
- practice: the drop on the earlier dataset is compared between directions: SWT-Bench (test generation) against SWE-Bench and FeatureBench (both change source code). Nobody assigned the distance (§4.1).
- claim: "task relatedness may play an important role in mitigating catastrophic forgetting"; evolution between SWE-Bench and FeatureBench forgets less, evolution between SWT-Bench and the others forgets far more (§4.1).
- evidence: SWE then SWT: 100% and 98% drop; SWE then Feature: 29% and 66% (§4.1). Other directions in Figure 3 only.
- effect: hurts
- reader: three datasets, two methods, a handful of directions; relatedness is the authors' reading of the dataset descriptions and was not measured. The 66% for Meta-Harness on SWE then Feature is not small, so the contrast is clear for AHE and weaker for Meta-Harness.

### F4 · observation · forgetting-conflict-type-shares · E2
- practice: after five continual rounds, the code diff of each evolved harness was read by hand; 520 trajectories were checked for tasks that went from pass to fail, and each such task was assigned a conflict type (§4.2.1).
- claim: forgetting comes mostly from verification conflicts, meaning checks, constraints or reminders tailored to one dataset's requirements (§4.2.1).
- evidence: shares of pass-to-fail cases: verification conflicts 87.1%, workflow conflicts 8.2%, budget conflicts 0.6%; the remainder not associated with a type. Artifact conflicts are the largest part of the verification share, with no number given (§4.2.1).
- effect: hurts
- reader: a share with nothing to compare against, so E2. Assignment was manual with no second rater or agreement figure. The three types were defined by the authors, and the remaining 4.1 points (reader's arithmetic) are not explained.

### F5 · practice · dataset-specific-submission-gate-in-harness · E4
- practice: add to the best SWE-Bench harness (96.0%) the modification that the SWE-to-SWT evolution produced: the harness checks the agent's change before submission and rejects any solution that changes files other than test files (§4.2.2, Table 1).
- claim: "introducing a mandatory artifact constraint immediately reduces the performance on SWE-Bench to 0.0" (§4.2.2).
- evidence: Table 1, SWE-Bench performance 96.0 against 0.0 (down 100%); agent time 245.5 s against 415.7 s (up 69%).
- effect: hurts
- reader: an ablation on the same tasks, so E4, but one harness, one run, and a gate that is wrong for the task by construction: SWE-Bench needs source edits. It shows that a gate written for one task type breaks another, not how often evolution writes such gates. The modification was chosen by the authors as representative (§4.2.2).

### F6 · practice · task-specific-workflow-in-harness-prompt · E4
- practice: add to the same SWE-Bench harness the workflow modification from the AHE SWE-to-FeatureBench evolution: a changed workflow in the system prompt plus hard constraints that intercept network commands (pip, curl, git) (§4.2.2).
- claim: "Workflow conflicts also have a substantial impact" (§4.2.2).
- evidence: Table 1, SWE-Bench performance 96.0 against 66.0 (down 31%); agent time 245.5 s against 821.5 s (up 235%). The text attributes the loss to blocked access to external resources and to many unnecessary exploratory operations.
- effect: hurts
- reader: E4 by design, one harness and one run. The modification bundles a prompt change with network interception, so the table does not say which part causes the loss.

### F7 · practice · timeout-budget-reminders-in-harness · E4
- practice: add to the same SWE-Bench harness the budget strategy learned in the FeatureBench evolution: after repeated command timeouts the harness tells the agent to stop retrying, narrow the tests and converge (§4.2.1, §4.2.2).
- claim: budget strategies "have little impact on task performance, with their effects mainly reflected in changes in task execution efficiency" (§4.2.2).
- evidence: Table 1, SWE-Bench performance 96.0 against 96.0 (down 0%); agent time 245.5 s against 439.7 s (up 79%).
- effect: hurts
- reader: the outcome that moved is time, which went up with no gain in score, so `hurts`. One harness, one run. This is the effect on SWE-Bench, a task that the strategy was not learned on.

### F8 · practice · paraphrase-benchmark-prompts-before-evolution · E1
- practice: paraphrase the fixed sentence structure of SWT-Bench task prompts, keeping the meaning, before running evolution (§3.1, Appendix B).
- claim: without it the evolver wrote a branch keyed on surface wording; with it "we no longer observe similar template-dependent conditional branches" (Appendix B).
- evidence: one case. Meta-Harness, SWE-Bench then SWT-Bench, original prompts: the evolved harness chose the submission artifact by matching strings such as "implement only test cases" (Figure 5). After paraphrasing the branch did not appear. No counts of runs.
- effect: helps
- reader: one method, one direction, no number of runs, so E1. The authors call the branch a positive signal for forgetting, since it kept both submission rules, and then reject it as overfit to the template. Their reported forgetting numbers (F2, F3) are for the paraphrased setting only; the paper does not give the unparaphrased forgetting.

## Limits stated by the authors

- Each experiment is a two-stage sequence; the authors state that results generalise to longer sequences without running them (§4.1).
- "Due to resource constraints" 50, 50 and 30 tasks were sampled from the datasets (§3.1).
- Neither method's public code supports Mini-SWE-Agent, so both are re-implemented "as closely as possible" to the original settings (§3.3).
- No separate limitations section.

## Reader's notes

- One foundation model (DeepSeek-V4-Flash-0731) runs both the tasks and the evolver, at temperature 0, one run per setting. No confidence intervals; with 30 to 50 tasks one task is 2 to 3.3 points (reader's arithmetic).
- Whether the tasks scored after evolution are the same tasks the evolver saw is not stated. If they are, the single-task gains (F1) are training-set scores. The forgetting measurement scores the earlier dataset's tasks, which the earlier evolution also saw.
- The forgetting drops start from the best harness of each single-dataset run, taken at its first top score; that choice favours a high starting point and a large measured drop.
- The paper does not run a baseline that evolves the harness on both task types at once, or one that keeps a harness per task type, so the cost of continual against joint evolution is not measured.
- F5 to F7 inject changes by hand into one harness; the Table 1 rows use modifications from two different evolution directions (SWE-to-SWT for the gate, SWE-to-Feature for the others, §4.2.2).
- Relevance to agentic coding practice: the finding is about automated rewriting of a harness's prompt and gates, which is what a self-improving flow does. It does not test human-written instruction files.
